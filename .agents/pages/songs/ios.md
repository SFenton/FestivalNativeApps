# Songs — iPhone notes

> **What:** what the iPhone Songs page implements, native decisions that differ from the web, gotchas and open gaps. **Read when:** changing Songs on iPhone. Behavior: [spec.md](spec.md). Wave 1 task list: [PROGRESS.md](../../../PROGRESS.md) (Lane S).

## Implemented (partial)

- Live public Songs by default (728 songs decoded on 2026-09-25); fixtures via loopback override.
- List search: the inline `.searchable` list filter, prompt "Filter Songs", pinned above the list on iPhone (`.navigationBarDrawer(displayMode: .always)`, issue #92, see below). It is separate from [global search](../../controls/global-search/ios.md), the trailing Search tab; the A–Z rail is centred in a region with a fixed top (it does not move when the large title collapses) and ends above the tab bar; section titles are pinned on an opaque `appBackground` backing with a hairline; rows arriving from a load fade in (`festivalFadeIn`, first screen only); no visible "Item Shop: New" chip (the gold row outline marks it; VoiceOver keeps the label); title-ordered list by default, scene-owned instrument filter (now applied via [Filter](../../controls/songs-filter/ios.md), not its own toolbar Menu), Detail/Solo navigation, accessible notice when a publication change or hidden instrument clears a route/filter.
- `.festivalRootChrome(session:)` owns the top-right profile button and (drawer, Lane A) — Songs no longer keeps its own profile button/sheet or an Item Shop toolbar button; Shop is reached from the drawer. The in-page "Choose Profile" empty state uses `@Environment(\.openProfile)`.
- Sort + Filter are a `ToolbarItemGroup(.festivalPageAction)` (`.topBarTrailing` on iOS, `.primaryAction` elsewhere); both tint gold when their applied choice is non-default. Per the [toolbar order rule](../../controls/app-navigation/ios.md#toolbar-order-rule-tab-roots), Songs ends its own `.toolbar` with `FestivalRootTrailingItems(session:)` and applies `.festivalProvidesRootTrailingItems()` so the shared bell+avatar capsule (which owns its own `ToolbarSpacer`) stays the rightmost item: `[drawer] … [sort] [filter] [quick links] [bell] [avatar]`.
- Duration and Item Shop sorts show a **Quick Links** toolbar menu ([quick-links/ios.md](../../controls/quick-links/ios.md)); Title/Artist/Year hide it because the section-index scrubber already owns jump navigation there.
- Sort: Title/Artist/Year/Duration + conditional Item Shop with Leaving/In/Not sections, plus Score/Percentile/Stars for a selected player on one instrument, grouped into the web's quick-link buckets ([songs-sort/ios.md](../../controls/songs-sort/ios.md)).
- Filter (always offered; General only without a selected player, issue #77): General Year, Duration, Item Shop (when visible) and Double Bass; with a player, score/FC checks, the single-chart Instrument picker and, with an instrument, Percentile and Stars buckets; every change applies at once ([songs-filter/ios.md](../../controls/songs-filter/ios.md)).
- **Profile presets (Lane A3):** `PlayerStatNavigator.showSongs` (root) saves a `SongsFilterPreset` through `SongsPresetStore`; Songs reads it as its normal saved state. Presets match the web updaters: instrument Songs Played/FCs → that chart's check + Score ascending; `.stars(_, starKey:)` → only that star bucket + Stars ascending; `.percentile(_, scoredOnly:)` → Percentile ascending (+ Has Scores); `.percentileBucket` → only that bucket, saved sort kept, ascending. Each first clears the chart's checks and both bucket filters (web `cleanFilters`). Links: `PlayerStatLinks.instrumentStars`, `.instrumentPercentile`, `.percentileBucket` (Profile tiles still to be wired by the Profile owner).
- Right-edge Contacts-style section-index scrubber for Title/Artist/Year sorts; animates in/out when the sort mode does or doesn't have a meaningful key ([songs-section-index/ios.md](../../controls/songs-section-index/ios.md)).
- Rows are `festivalRowCard()` material cards ([liquid-glass.md § Material card](../../design/apple/liquid-glass.md#material-card)) with tightened List row insets (2pt vertical) to match the web list's 2pt virtual row gap; cards drop the trailing disclosure chevron per Apple HIG (see Native decisions).
- Selected-player card: status chips ([chips](../../controls/songs-instrument-status-chips/ios.md)) or typed metadata pills ([metadata](../../controls/song-score-metadata/ios.md)); duration (e.g. 6:06) shown, including at accessibility sizes. The pill order is `MetadataField.songRowOrder(independent:saved:)`: Settings' `fst.settings.songRowVisualOrder` only while `fst.settings.enableVisualOrder` is on, else the web default (#372; `SongProfileCardPolicy.reordered`), applied after visibility filtering so the reorder never adds, drops or invents a field.
- `#if DEBUG` env `FST_DEBUG_SONG=<title-or-songId>` auto-pushes that song's Detail once the catalogue loads (local `.navigationDestination(item:)`, independent of the shared route stack) so `tools/ios_sim.py shot`/`drive` can reach Song Detail without manual navigation. Adding `FST_DEBUG_SONG_BAND=<bandType>` pushes that song's full band leaderboard instead (issue #306).
- Row title and artist·year·duration use `Design/MarqueeText.swift` (2026-09-28), a native port of web's `MarqueeText.tsx`/`MarqueeText.module.css`: auto-scrolls a two-copy track only once measured wider than its row, dwell-pauses at each end like the web keyframe, falls back to static `.truncationMode(.tail)` under Reduce Motion, and stops (no timer) once its row leaves the List or the scene backgrounds. This replaced a `.fixedSize(horizontal: false, vertical: true)` that let long combinations (e.g. "6 Foot 7 Foot"'s artist/year/duration on folded Duo) wrap to a second line instead of staying on one. Pure cycle math lives in `MarqueeTiming` (unit-tested, `MarqueeTimingTests`); should also be adopted by `Features/SongDetail/SongDetailScreen.swift`'s title header (web's `SongInfoHeader.tsx`) and `Features/Suggestions/SuggestionCategoryCardView.swift` (web reuses the same `SongInfo.tsx` there) — both outside this lane's ownership.
- Shop/Duration sort groupings are now real `List` `Section`s (matching the Title/Artist/Year section-index groups) instead of a plain row styled to look like a header; see [quick-links/ios.md](../../controls/quick-links/ios.md) for why they still register as Quick Links rather than a scrubber section.
- First reveal waits for the catalogue **and** the first ~12 visible rows' artwork to decode (bounded to 900ms so slow/unreachable art can never block it), then cross-fades in — a native-only addition (the web has no equivalent first-paint gate; it reveals rows immediately and fades each `<img>` in independently). See `SongsScreen.primeFirstArtwork(for:)`.

## Native decisions (deliberate deviations)

| Web | iPhone | Why |
|---|---|---|
| Lower Search/Sort dock, bottom sheets | iPhone, iPad, Mac: pinned `.searchable` "Filter Songs" field above the list; iPhone Duo: the field at the bottom of the page, trailing page in book pose only (owner, #333, #334); iPhone: Sort, Filter and Quick Links in the system tab-bar accessory before the bell, avatar in the header (issue #92 follow-up, #300; folded into one Sort and Filter control, expanded and inline alike, only on windows too narrow for the inline accessory and at accessibility text sizes); Duo/iPad: trailing navigation-bar items. Global search is the Search tab. Full-height system sheets that apply immediately with Done | HIG Search fields: an inline field above its list filters one view. The accessory placement is the owner's supported deviation from HIG Tab bars (accessory for persistent items such as the MiniPlayer); the field stays in the header because a `TextField` in the accessory does not focus |
| Row is a link with a trailing chevron in most lists | Card-style row **is** the tap target, no chevron | Apple HIG: card rows drop the disclosure indicator. | Last Played hidden under Title | Toggle-controlled date under Title | Until Last Played sort ships |

| Instrument selector always visible in Filter | Instrument section only when a player is selected | Matches web: without a profile Filter shows only General filters (issue #77) |

## Gotchas

- `TabView` retains a failed Songs view: its catalogue `.task` is keyed by the prepared publication revision **and visibility** and must retry when the tab returns, even if Settings already fetched a valid catalogue at the same generation. A cancelled older request must not overwrite the replacement with a late error.
- Service errors use `ServiceUnavailableView` (scrolls at large text; scroll the error view itself). `.refreshable` only on the loaded List.
- No-results view uses a wrapping title and bright semantic text; an instrument-only empty result says no songs **match the filters**.
- Grouped (Shop-sort) and section-indexed (Title/Artist/Year) Lists share one `songRowInsets` (2pt vertical, 16pt horizontal) so cards stay tight and clear the floating tab.
- At AX sizes, only the chip-visible row mode stacks title/artist full-width above art and chips.
- Real Liquid Glass (`glassEffect`, iOS/macOS 26+) does not reproduce through `NSHostingView.cacheDisplay`: hosted pixel tests that render a `festivalGlass` surface must force the deterministic fallback (`fst.accessibility.moreContrast = true` in the test's `UserDefaults`/`@AppStorage`), or every state renders byte-identical. See `deterministicGlassDefaults()` in `SongScreenStatesTests.swift`/`SelectedSongRowRenderTests.swift`.
- **Scroll-away feedback loop (issue #5):** moving the tools into the bar removes the large title, and restoring it changes `contentInsets.top` (116 ↔ 232pt) at an unchanged offset. The old `offset + inset > 24` check flipped on every inset change, so the main thread never went idle and the app was killed after scrolling down and back up with a profile selected. `ScrollAwayGate` only re-decides when the offset moves (≥ 0.5pt), measures from the smallest top inset seen at the current width (reset on a width change), and uses hysteresis (enter > 24pt, exit < 8pt). Regression: `ScrollAwayGateTests` and `SongsChromeJourneyTests/testScrollingBackToTopNearTheTopStaysResponsive`. The XCUITest needs `tools/mock_service.py --large-catalogue` exported as `TEST_RUNNER_FST_SONGS_SCROLL_FIXTURE_URL`; it skips on the two-song fixture, and the old logic fails it with "main thread busy for 30.0s". Debug a hang with host `sample <pid>`, because the xcresult spindumps had no samples.
- **Scroll-driven state must not re-run the Songs body (issue #8):** `listScrolled`, the passed section titles, the section bar's bottom edge and `toolsInBar` used to be `@State` on `SongsScreen`. They change while you scroll, mostly near the top (title collapse, first headers, bar appearing, tools moving), and each change re-ran the whole screen: re-filter and re-sort the catalogue, re-diff about 760 List rows and re-render every visible row. Bursts of these passes hung the app near the top. They now live in `SongsScrollChrome` (`@Observable`, no-op writes dropped, bar edge ignores < 0.5pt). `SongsScreen.body` never reads it; only `SongsSectionBar`, `SectionBarRowFade` and `SongsPageTools` do. An in-app stress pass (production anonymous, then the large fixture with a profile) went from 76 to 17 body passes, and from 158 body passes and 147 sorts to 12 and 1. Don't add new scroll- or geometry-driven `@State` to `SongsScreen`: put it on the chrome and read it in a small subview or modifier. Regression: `SongsScrollChromeTests` and `SongsChromeJourneyTests/testScrollStressNearTheTopDoesNotRebuildTheScreen`, which asserts at most 20 bodies and 10 sorts during the pass and a run loop awake span under 2 s. It needs the large fixture, like the #5 test.
- **System chrome must not rebuild the Songs page either (issue #325; iPhone, Duo, iPad, Mac):** the iOS 26 tab bar minimizes as the list scrolls down and expands at the top, and each change re-runs the section's navigation stack (`OnDemandSplitStack`), which builds a new `SongsScreen`. Its `openShop` closure made every copy unequal, so the whole filter/sort pipeline and List re-ran on the main thread during the large-title transition; the bar snapped expanded and collapsed and the rows jumped about 52 pt (the owner's "reset and re-scroll"). `SongsScreen` is `Equatable` (session identity, visible charts, contrast, visibility, whether `openShop` exists; the closure itself compares always-equal like `SplitOpenReporter`) and both mounts (`SongNavigationRoot`, `MacRootView`) apply `.equatable()`. Add every new value input to `==`; pass bindings and actions, never snapshots of state, so an equal page cannot hide a change. The publication boundary around the results keeps its focus state off the page for the same reason ([load-transition](../../patterns/load-transition.md) R9). The split stack also stores only its container's horizontal span (`OnDemandSplitPolicy.horizontalSpan(of:)`), so the tab bar's height change (673 ↔ 729 pt) no longer re-runs it at all (#383). Measure with a traced drive: no Songs body pass between touch-down and idle. Regressions: `SongsScreenEquatableTests`, `splitStackIgnoresTheContainersHeight`.
- **Section-title edge fade (issue #10):** the system soft scroll-edge effect fades content only under bars (navigation bar, toolbars), never under a custom floating title, so `SectionBarRowFade` masks each row (song rows, grid rows, in-list section titles, disclosures) with the shared pinned-title fade (`Design/PinnedHeaderEdgeFade.swift` `pinnedHeaderEdgeFadeRowMask`, the same `PinnedHeaderFadeMask` as the Notifications sheet's rows; never the whole List, see #383 below; [scroll-edge](../../patterns/scroll-edge.md) R1, R3, R5, #308). The mask starts at the title's bottom edge and stacks a linear `LinearGradient` band (40 pt, web `useScrollMask`) under a far-reaching shape. Rows are fully hidden behind the title text and fully opaque 40 pt below it. System Reduce Transparency, system Increase Contrast and the app's Reduce Transparency / Increase Contrast toggles (`ScrollEdgeHardEdge`) set the band to 0, which gives a hard edge. That matches the opaque `festivalGlass` fallback, so the title never sits next to see-through rows. Only rows above `PinnedHeaderEdgeFade.rowLimit` (the title's edge + 40 pt, `SongsScrollChrome.rowMaskLimit`) report their position, so rows further down never re-render while scrolling. Don't add a backing or glass behind the title: HIG Layout says "Prefer scroll-edge effects to solid/semi-opaque backgrounds beneath controls", and the title is part of the content layer. Regression: `PinnedHeaderEdgeFadeTests`. Before iOS 26 the opaque pinned headers stay; the bar there has no fade either.
- **No List-wide alpha mask under a large title (issue #383; iPhone, iPad, Mac):** on iOS 26 and 27 an alpha mask (any gradient) around the Songs `List` changes how SwiftUI hosts it: the List then takes its content insets from SwiftUI's safe area, which lags UIKit's. Near the top the tab bar expands as you release a drag (bottom inset 83 → 139 pt); the masked List briefly took the collapsed title's top inset again (222 → 170–183 pt), so the large title snapped closed and crept back to rest part-way (180–209 pt), or stayed collapsed. Rebuilding that mask mid-animation (a ramp band that fell to 0 pt, or a mask observing the moving bar) also made the List count its top inset twice (traced 444 pt). Bisected on the iOS 27 simulator: without the mask, or with an opaque one, the List keeps 222 pt; `ignoresSafeArea` on the mask, a shape filled with a gradient, or moving the bottom `safeAreaInset` to an overlay do not help. So the section-bar fade masks each row (`pinnedHeaderEdgeFadeRowMask`, like Notifications), never the List. The ramp band still keeps at least 1 pt (`PinnedHeaderFadeMask.bandHeight`), and at the top rows read only `SongsScrollChrome.rowFade(enabled:)`, the constant `.inactive`, so they don't observe the bar moving with the title. Duo's Songs has no large title or minimizing tab bar (a fixed 82 pt inset), so its List-wide `bottomChromeFade` cannot cause this. HIG Motion: "make feedback realistic and consistent with gestures and expectations" (should; `references/hig/motion.md`). Regressions: `SongsChromeJourneyTests/testSlowDragsNearTheTopKeepTheLargeTitleSteady` (large fixture; slow drags across the threshold must return to the expanded title with nothing pinned, collapse past it, keep the traced top inset ≤ the expanded one, flip the scroll-away state at most once per crossing and run no Songs body or sort; db7ecca4's List mask fails it at 194–209 pt, the earlier zero-band mask at 170 pt with a 444 pt inset), `PinnedHeaderEdgeFadeTests.pinnedHeaderRampBandIsNeverEmpty`, `pinnedHeaderRowLimitReachesOneRampBelowTheEdge`, `SongsScrollChromeTests.rowFadeAtTheTopIgnoresTheMovingBar`.
- **Measuring Songs hangs (Debug only):** `FST_DEBUG_STALL_LOG=<absolute path>` starts `MainThreadStallMonitor`. It rewrites a JSON report with `maxStallMs` (longest unit of work between run loop activities, sleep excluded), `maxAwakeMs` (catches a #5-style loop), stalls of 100 ms or more, `counters` (`songs.body`, `songs.sort`, `songs.scrolled.flip`) and `peaks` (`MainThreadStallMonitor.peak`; `songs.topInset`, the List's largest top content inset). `FST_DEBUG_SONGS_SCROLL_STRESS=1` replays `SongsScrollStress.plan` after load: 60 animated `scrollTo` jumps between the top and sections 1–3, plus trips 10–20 sections down and back. Use `ios_sim.py shot --wait 45 --env …` so XCUITest's accessibility snapshots (100–350 ms each on Songs) don't pollute the numbers. Its remaining 200–400 ms stalls are `UICollectionView` cell creation during long animated jumps, a driver artefact heavier than a finger fling. No crash report was ever found for #8; treat a report of a "crash" while scrolling as a possible hang first.
- UI tests: query `fst.songs.list`; see [xcuitest pitfalls](../../testing/apple/xcuitest.md).
- `primeFirstArtwork(for:)` only runs on the very first `.loading → .loaded` transition (`prior == nil` in `reload()`); pull-to-refresh and retries after an error that already had prior rows never re-block on artwork, matching the existing retain-on-error behavior.

## Root navigation-notice card (`fst.songs.navigation-notice`)

`SongsScreen`'s top-of-list notice card (2026-09-28 operator ask) is generic: it just shows whatever `navigationNotice` string the root passes it, and clears when dismissed or replaced. Root shell (`App/FestivalRootView.swift`) now sets that string only for a hidden instrument or a hidden Item Shop. The profile-change notice was removed earlier at the operator's request, and the publication-change notice ("Published scores changed. Returned to Songs…") was removed with its forced pop in issue #304: pages now refresh in place ([architecture](../../platforms/apple/architecture.md#publication-changes-refresh-in-place-issue-304)). The card itself needed no change.
