# Leaderboards overview — iPhone notes

> **What:** iPhone implementation state and decisions for the leaderboards overview cards. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (currently a stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/leaderboards/LeaderboardsOverviewPage.tsx`, `.../components/RankingCard.tsx`, `.../components/BandRankingCard.tsx`, `.../helpers/rankingHelpers.ts`, `.../helpers/bandRankingHelpers.ts`. Service: `FSTService/Api/RankingsEndpoints.cs:187` (`/api/rankings/{instrument}`) and `:680` (`/api/rankings/bands/{bandType}`) — both pure, keyless `GET`s (read-only DB query, no writes), confirmed by reading the handler bodies.

- Implemented: one top-ten card (`pageSize: 10`) per Settings-visible instrument (`fst.settings.show*` `@AppStorage` keys, read directly by the screen — no new init parameter, no edit to `FestivalRootView`) plus one card per band size (`BandType.allCases`, always shown — band visibility has no Settings toggle on the web app either). A `primaryAction` toolbar `Menu` picks the shared `RankingMetric`; band cards narrow it via `RankingMetric.bandMetric` (maps `maxscore` → `totalscore`, matching the web client's `coerceBandRankingMetric` fallback). Rows navigate to `AppRoute.player`/`.band`; "View All" goes to `.fullRankings`/`.bandRankings`. Glass cards (`festivalGlass(.card)`), five-row skeleton while loading, independent per-card retry on failure, inline empty text, pull-to-refresh.
- **PWA density parity (Lane PB, gap #9 in [apple-gaps.md](../../testing/pwa-reference/apple-gaps.md)):** each section is the web `RankingCard.tsx` layout. Header above the rows: 36 pt `InstrumentIcon` + bold name for instruments, **name only** for Duos/Trios/Quads, and **no metric subtitle** (operator, 2026-09-28; the metric is the toolbar menu). Then **each row is its own glass card** (`RankingRowSurface`, `festivalGlass(.card, cornerRadius: 12)`), with no outer card (no glass on glass). Rows are one line via the shared `RankingRowLayout`: `#rank`, truncating name, `728 / 729`, value in `BrandTokens.accentBlue` semibold (web `colRating` uses `accentBlueBright` `#4C7DFF`, not yet a contract token). All other text is `FestivalText.primary` (white-text rule, [architecture.md](../../platforms/apple/architecture.md)). Adjusted/Weighted add their Bayesian value as a second small line (web compact two-row percentile layout); accessibility Dynamic Type stacks the row (rank + name, then songs + value). **View all** is the shared purple button (`PurpleActionLabel`/`PurpleActionSurface`, `Features/Leaderboards/PurpleActionButton.swift`, used by every View full/View all button since operator batch 6.29: tinted interactive glass on 26, solid `accentPurple` pre-26 / Reduce Transparency / More Contrast) below the top ten, or below the selected player's spotlight row when they are outside it; its label carries the total, "View all rankings (868,901)" / "View all band rankings (N)" (`RankingsCountText`, Core `RankingsPager.swift`; bare label when the total is 0). Loaded rows fade in once (`festivalFadeInOnAppear`, Reduce Motion aware). Result: 10 Lead rows above the fold on iPhone 17 Pro, as in `leaderboards-top.png`. VoiceOver reads the songs column as "728 of 729 songs" (FC Rate: "N full combos of M songs"). Glass is opt-in (`glassSurface:`/`glassRows:`) so Compete's previews and Band Detail's skeleton, inside their own glass cards, stay flat; they do get the compact single-line row.
- **Selected-player spotlight (Lane L2, 2026-09-28):** each instrument card now highlights the selected player's row in place when they're already in the top ten (`AccountRankingRow(isSelected:)`, accent-purple fill/border mirroring the web's `playerEntryRow` — `RankingCard.tsx`'s `Colors.purpleHighlight`/`purpleHighlightBorder` → `BrandTokens.accentPurple`), or fetches their own row (`GET /api/rankings/{instrument}/{accountId}`, `FestivalSession.playerInstrumentRanking`, verified pure read) and shows it as a separate spotlight row below the top ten when they're not. The fetch is skipped entirely when the row is already visible (a deliberate efficiency deviation from the web, which always fetches `playerRanking` regardless — see `RankingCard.tsx:31-33`). States: no selection (nothing shown), pending (small "Loading your rank…" row), unranked ("Not yet ranked on `<instrument>`."), failed (`ServiceStatusInline` with retry/backoff), available (spotlight row). The pure in-top-ten/below/unranked decision is `RankingSpotlight.placement(selectedAccountId:visibleEntries:source:)` in `FestivalCore/RankingSpotlight.swift`, unit-tested independent of any view or network code. VoiceOver: the selected row's label is overridden to "Your rank, `<ordinal>`. `<name>`." (`RankingFormatting.ordinal`, `NumberFormatter.numberStyle = .ordinal`, e.g. "1,234th"); every other row keeps SwiftUI's default combined label.
- **No band spotlight (documented gap):** band cards do not get an equivalent "your band" spotlight this pass. The app has no persisted "selected band" identity yet — unlike the web client's `useSelectedProfile()`, which can resolve `profile?.type === 'band'`, native only ever has a *viewed* band (`AppRoute.band`'s `bandId`/`teamKey`), never a *selected* one it can carry onto an unrelated Leaderboards card. Porting this needs a native band-identity feature first (out of scope here); tracked as a Leaderboards follow-up.
- **Loading (operator batch 6.41, Lane AP5):** `LeaderboardsPreloader` reads every card (and the selected player's missing spotlight rows) in parallel; the page is only a spinner (`fst.leaderboards.loading`) until they settle, then the cards fade in with the web stagger. A metric change keeps the old cards until the new set is ready; failures keep per-card Retry. (The "Loading your rank" row now only appears on a later per-card retry.)
- **One row design (operator batch 7.4):** these row cards (Liquid Glass until issue #295, now the Songs material card) are the pattern for every leaderboard (Song Detail cards, song leaderboards, Compete). The player's row uses the web `purpleHighlight` fill + `purpleHighlightBorder` (`RankingRowSurface.playerFill/playerBorder`). Names truncate (web `colName`), never marquee (batch 7.7). Rows that open a player or band carry an in-card chevron (batch 7.12). Duos/Trios/Quads headers use the same `.title3` bold as instrument headers (batch 6.8: no size difference on iOS; there is no separate "Bands" heading).
- Simplified vs. web this pass: no rank-history chart, no band-combo filter, no quick-links rail — Wave 2 follow-up. No live reload on publication rollover (pull-to-refresh covers it); every read still goes through `FestivalAPI`'s publication-consistency pipeline.
- IDs: `fst.leaderboards.card.<instrument>`, `fst.leaderboards.card.<instrument>.view-all` / `fst.leaderboards.band-card.<bandType>.view-all` (label carries the count), `fst.leaderboards.band-card.<bandType>`, `fst.rankings.row.<accountId>`, `fst.band-rankings.row.<teamKey>`, `fst.rankings.rank-by-menu`, `fst.leaderboards.card.<instrument>.spotlight`/`.spotlight.loading`/`.spotlight.unranked`.
- Tests: `RankingsPagerTests.swift` (Core: count labels, spoken songs), XCUITest `LeaderboardsJourneyTests.testViewAllCountOpensFloatingPagerAndInstrumentSwitch` (footer label, push to the floating pager). `RankingsTests.swift`, `RankingSpotlightTests.swift` (Core: placement decision, ordinal formatting, page-for-rank) cover decoding, per-metric dispatch, page-count math and `RankingFormatting`. Hosted snapshots in `LeaderboardsHostedTests.swift` cover every spotlight state (inline/footer/unranked/pending/failed) via an extended `HostedRankingsTransport` (single-account endpoint + delay/failure toggles) and a `debugSelectedPlayer`-backed session helper — these currently only assert the render doesn't crash and produces a non-empty image (see the harness caveat below), not pixel content. `tools/ios_sim.py shot --tab leaderboards` against the live public service (2026-09-28) rendered real top-10 Lead/Duos rows correctly; re-verified 2026-09-28 with a selected lower-ranked live account (see log).
- **Hosted-render harness caveat (found 2026-09-28):** the macOS `NSHostingView`/offscreen-`NSWindow` hosted-snapshot harness (`NativeHostedSnapshot.swift`) renders full-screen iOS content (this page, Full Rankings, Band Rankings) as a nearly blank image — confirmed on both the pre-existing baseline test and the new spotlight tests, which are visually identical despite exercising different states. This is a pre-existing harness limitation (not introduced by this lane) affecting every "hosted render" test of a full-screen `ScrollView`/`List` page, not just Leaderboards; flagged separately for investigation rather than fixed here. Real visual verification for this pass came from the live simulator (`ios_sim.py drive`/`shot`).
- **Aligned columns (issue #37):** each card (with its spotlight row), Full Rankings (with its footer), Band Rankings and Compete share one rank and rating width per section (`LeaderboardRowColumns.rankings` / `.bandRankings`, [leaderboard row columns](../../controls/leaderboard-row-columns/ios.md)), replacing the fixed 40 pt rank minimum.
- **Load/reload fade (issue #71):** Leaderboards runs the shared `FestivalReloadGate` on load and on a Rank By, visible-instrument or selected-player change: old results leave at once, the spinner fades in, holds ≥400 ms, fades out (500 ms) and the results fade/stagger in; Reduce Motion swaps instantly. See [iPhone motion](../../design/apple/iphone.md#motion).
- **Row height (#90):** rankings rows, skeletons, the selected player's row and the spotlight/footer rows (cards, Full Rankings, Band Rankings) use the shared 48 pt minimum (`LeaderboardRowMetrics.minHeight`, was 44), matching the Solo chart, Song Detail previews and the web `entryRow`. See [leaderboard-row-columns/ios.md](../../controls/leaderboard-row-columns/ios.md).
