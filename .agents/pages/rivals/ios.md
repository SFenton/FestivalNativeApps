# rivals (`/rivals`) — iPhone notes

> **What:** iPhone implementation state and decisions for the selected player's rivals hub. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/rivals/RivalsPage.tsx`, `LeaderboardRivalsTab.tsx`, `components/RivalRow.tsx`, `helpers/comboUtils.ts`. Service: `FSTService/Api/RivalsEndpoints.cs` (`GET /api/player/{accountId}/rivals/{combo}`) and `LeaderboardRivalsEndpoints.cs` (`GET /api/player/{accountId}/leaderboard-rivals/{instrument}`) — both pure, keyless, unauthenticated `GET`s with `RequireRateLimiting("public")` and no `RequireAuthorization()`; confirmed by reading the handler bodies (they only read `IMetaDatabase`/`ResponseCacheService`, never write). The one side-effecting Rivals route, `POST .../rivals/recompute`, is `RequireAuthorization()`-gated and is never called from this app.

- Implemented: `RivalsScreen` (`Features/Rivals/RivalsScreen.swift`) — a native segmented `Picker` for Song/Leaderboard, then one `FestivalGlassSection` per Settings-visible instrument (`fst.settings.show*` `@AppStorage` keys via `VisibleInstrumentsReader`, matching `FestivalRootView`'s own visible-instrument computation). Each section (`RivalInstrumentSongSection`/`RivalInstrumentLeaderboardSection`) loads independently via its own `.task(id:)`, shows a 3-above/3-below preview with a "View All Rivals" row, and is skipped entirely when empty (matching the web hiding empty instrument sections). Leaderboard tab has a `Menu` for `RivalRankMetric` (`totalscore`/`adjusted`/`weighted`/`fcrate`/`maxscore`). Rows push `AppRoute.rivalDetail`; "View All" pushes `AppRoute.allRivals(category:)` with an encoded scope (see `RivalAllCategory` in `FestivalCore/Rivals.swift`). No player selected → `RivalsChooseProfileState` (`@Environment(\.openProfile)`).
- Simplified vs. web this pass: no "Common Rivals" section (rivals shared across every visible instrument — the web's `commonRivals` intersection in `RivalsPage.tsx`), no settings-derived multi-instrument "combo" scope section (e.g. Guitar+Bass or the Pro Drums family via `deriveRivalScopeFromSettings`), no "Find Rival" search sheet/FAB. Each per-instrument section is its own independent read instead of the web's Common Rivals cross-reference. These are Wave 2 follow-ups; the per-instrument sections (the bulk of the page) are fully live against the public service.
- Rivals data does **not** go through `FestivalSession`'s publication-pinned pipeline (`observe(publicationId:)`); it isn't part of the catalogue/score generation contract that pipeline protects, so a Rivals read never pauses or invalidates Songs state and vice versa.
- Navigation context bridge: the web reads `location.state` (React Router) to know which combo/leaderboard scope produced a tapped rival row; native `AppRoute` cases are plain `Hashable` values with no side channel. `RivalNavigationBridge` (`FestivalCore/Rivals.swift`, `@MainActor` singleton) stashes a `RivalRouteContext` keyed by rival account ID immediately before each `NavigationLink` push (`.simultaneousGesture(TapGesture()...)`) and is consumed once by the destination screen; a screen reached without a stashed context (deep link, cold start) falls back to merging every Settings-visible instrument.
- IDs: `fst.rivals.tab` (segmented control), `fst.rivals.rankBy` (metric menu), `fst.rivals.chooseProfile`.
- Tests: `RivalsTests.swift` (Core) — wire decoding against two live-captured fixtures (`contracts/fixtures/rivals-list-demo.json`, `leaderboard-rivals-demo.json`, `rivals-overview-demo.json`) and endpoint URL/validation coverage. No hosted-UI/XCUITest coverage yet. `tools/ios_sim.py shot --tab rivals` and `drive` verified against the live public service (2026-09-28) with sample account `e408c4613c8f4da5907090b390bda80c`.
