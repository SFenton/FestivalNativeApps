# rivals (`/rivals`) — iPhone notes

> **What:** iPhone implementation state and decisions for the selected player's rivals hub. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/rivals/RivalsPage.tsx`, `LeaderboardRivalsTab.tsx`, `components/RivalRow.tsx`, `helpers/comboUtils.ts`. Service: `FSTService/Api/RivalsEndpoints.cs` (`GET /api/player/{accountId}/rivals/{combo}`) and `LeaderboardRivalsEndpoints.cs` (`GET /api/player/{accountId}/leaderboard-rivals/{instrument}`) — both pure, keyless, unauthenticated `GET`s with `RequireRateLimiting("public")` and no `RequireAuthorization()`; confirmed by reading the handler bodies (they only read `IMetaDatabase`/`ResponseCacheService`, never write). The one side-effecting Rivals route, `POST .../rivals/recompute`, is `RequireAuthorization()`-gated and is never called from this app.

- Implemented: `RivalsScreen` (`Features/Rivals/RivalsScreen.swift`) — a native segmented `Picker` for Song/Leaderboard, a "Common Rivals" section, a cross-instrument "Combo"/Pro-Drums-family section when Settings' visible instruments derive one, then one `FestivalGlassSection` per Settings-visible instrument (`fst.settings.show*` `@AppStorage` keys via `VisibleInstrumentsReader`, matching `FestivalRootView`'s own visible-instrument computation). Each section loads independently via its own `.task(id:)`, shows a 3-above/3-below preview (Common/Combo/per-instrument) with a "View All Rivals" button below the card, and is skipped entirely when empty. Leaderboard tab has a `Menu` for `RivalRankMetric` (`totalscore`/`adjusted`/`weighted`/`fcrate`/`maxscore`). Rows push `AppRoute.rivalDetail`; "View All" pushes `AppRoute.allRivals(scope:)`. A toolbar "Find Rival" button (`fst.rivals.findRival`) opens `FindRivalSheet` (account-name search, same endpoint as Profile's Find Player). No player selected → `RivalsChooseProfileState` (`@Environment(\.openProfile)`).
- **Common Rivals / Combo (landed 2026-09-28):** `RivalCommonRivals.intersect` (`FestivalCore/Rivals.swift`) ports the web's `commonRivals` `useMemo` verbatim — a rival must appear in *every* loaded instrument's own list to qualify, direction by majority vote, highest-`sharedSongCount` entry represents the rival, each group sorted by `rivalScore` descending. `RivalCombo`/`RivalComboScope` port `comboUtils.ts`/`combos.ts`'s bitmask system (`deriveScope(visible:)`: the Pro Drums family special case first, then a within-group hex combo, else `nil`); a combo/Pro-Drums scope is a genuinely different server-computed list (`GET /api/player/{accountId}/rivals/{token}`, `token` a hex ID or `pro_drums`), not a client-side merge — see `RivalsEndpoint.comboList`/`.comboDetail` in `FestivalAPI+Rivals.swift`. `CompeteScreen` intentionally does not adopt either section (matches its own `ios.md`/the web's `CompetePage`, which has neither).
- **Find Rival (landed 2026-09-28):** `FindRivalSheet.swift` reuses the already-allowlisted `GET /api/account/search?q=&limit=` (`ProfileSearch.swift`) rather than a Rivals-specific endpoint. A selected result pushes `AppRoute.rivalDetail(rivalId:name:scope: nil)`; the destination reads the web's Settings scopes with `allowLiveFallback=true` for a `nil` scope (`RivalDetailScopes.settingsScopes`, #95).
- Rivals data does **not** go through `FestivalSession`'s publication-pinned pipeline (`observe(publicationId:)`); it isn't part of the catalogue/score generation contract that pipeline protects, so a Rivals read never pauses or invalidates Songs state and vice versa.
- **Typed scope, no navigation bridge (landed 2026-09-28):** the web reads `location.state` (React Router) to know which combo/leaderboard scope produced a tapped rival row. An earlier native pass filled that gap with `RivalNavigationBridge`, a process-lifetime `@MainActor` singleton keyed by rival account ID and consumed once — but a singleton stash breaks any route reached without a preceding stash (a deep link, restored navigation state, or `DebugLaunchRoute`), and could desync across independent stacks. It has been **removed**. `RivalScope` (`FestivalCore/Rivals.swift`) — `.song(instruments:)`, `.leaderboard(instrument:rankBy:)`, `.combo(token:instruments:)` — is now a typed, `Hashable` payload carried directly on `AppRoute.allRivals(scope:)`/`.rivalDetail(rivalId:name:scope:)`/`.rivalry(rivalId:mode:name:scope:)`. Every way of reaching a rival route now carries the same information a tap would have stashed; a `nil` scope (no context at all) reads the Settings scopes (`FestivalSession.rivalDetail(forScope:rivalId:visibleInstruments:)`). Hub rows open with the Settings scope like the web (`RivalDetailScopes.hubScope`; see [rival-detail/ios.md](../rival-detail/ios.md)). `DebugLaunchRoute` parses `RivalScope.debugToken` (`song:<instrument>[,...]` / `leaderboard:<instrument>:<rankBy>` / `combo:<token>:<instrument>[,...]`) for `allRivals:`/`rivalDetail:`/`rivalry:` debug routes.
- Quick Links (landed 2026-09-28): song-tab sections `common`/`combo`/`<instrument>` register and deregister themselves as their independent loads settle (no explicit array to rebuild on tab change); leaderboard tab registers `<instrument>` only. See [quick-links/ios.md](../../controls/quick-links/ios.md).
- IDs: `fst.rivals.tab` (segmented control), `fst.rivals.rankBy` (metric menu), `fst.rivals.chooseProfile`, `fst.rivals.findRival` (toolbar button), `fst.rivals.common.view-all`, `fst.rivals.combo.view-all`, `fst.rivals.song.<instrument>.view-all`, `fst.rivals.leaderboard.<instrument>.view-all`.
- Tests: `RivalsTests.swift` (Core) — wire decoding against live-captured, anonymized fixtures (real gamertags and account IDs replaced with synthetic ones, 2026-09-29) (`contracts/fixtures/rivals-list-demo.json`, `leaderboard-rivals-demo.json`, `rivals-overview-demo.json`), `RivalScope`/`RivalCombo`/`RivalCommonRivals` unit coverage, and endpoint URL/validation coverage (including the new combo endpoints). No hosted-UI/XCUITest coverage yet. `tools/ios_sim.py shot --tab rivals` and `drive` verified against the live public service (2026-09-28) with sample account `195e93ef108143b2975ee46662d4d0e1`.
- Per-instrument sections (song and leaderboard tabs) put `InstrumentSectionHeader` ("<Instrument> Rivals", web `InstrumentHeader` SM) above the glass card, not a title inside it (2026-09-28, Lane AP2); each section fades in when its read completes (`festivalFadeIn`).
- **No "N shared" count (owner decision, issue #40, 2026-10-01):** `RivalRowContent` (`Features/Rivals/RivalsSupport.swift`) deliberately omits the web `RivalRow`'s trailing `sharedSongCount` / "shared" column and its VoiceOver phrase: the count is always ahead + behind. The ahead/behind pills and disclosure chevron stay. Every rival row (Rivals, All Rivals, first-run demo) shares this view. `RivalsRenderTests` asserts the rows expose "ahead"/"behind" and never "shared".
- **"View All Rivals" = "View Full Leaderboard" (issue #41, 2026-10-01):** every section's link is `RivalsViewAllButton` (`Features/Rivals/RivalsSupport.swift`), the shared purple `PurpleActionLabel` (44 pt, Liquid Glass with an opaque purple fallback for Reduce Transparency and the in-app contrast/transparency toggles), placed under the glass card like Compete's "View Full Leaderboard" rather than as a plain-text last row inside it. Compete's Rivals section, Duo, iPad and Mac reuse these sections. The web uses one `viewAllButton` for both; Android already matched (6.29). HIG basis (Design principles): "Keep visual and interaction behavior consistent so people learn quickly and can predict new interactions." Rival Detail's in-card "See All" rows keep `RivalViewAllRow`. Tests: `rivalsViewAllButtonMatchesViewFullLeaderboardStyle` (pixel-identical to `PurpleActionLabel`) and the section render tests' `.view-all` identifiers.
