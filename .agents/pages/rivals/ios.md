# rivals (`/rivals`) — iPhone notes

> **What:** iPhone implementation state and decisions for the selected player's rivals hub. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/rivals/RivalsPage.tsx`, `LeaderboardRivalsTab.tsx`, `components/RivalRow.tsx`, `helpers/comboUtils.ts`. Service: `FSTService/Api/RivalsEndpoints.cs` (`GET /api/player/{accountId}/rivals/{combo}`) and `LeaderboardRivalsEndpoints.cs` (`GET /api/player/{accountId}/leaderboard-rivals/{instrument}`) — both pure, keyless, unauthenticated `GET`s with `RequireRateLimiting("public")` and no `RequireAuthorization()`; confirmed by reading the handler bodies (they only read `IMetaDatabase`/`ResponseCacheService`, never write). The one side-effecting Rivals route, `POST .../rivals/recompute`, is `RequireAuthorization()`-gated and is never called from this app.

- Implemented: `RivalsScreen` (`Features/Rivals/RivalsScreen.swift`) — a native segmented `Picker` for Song/Leaderboard, a "Common Rivals" section, a cross-instrument "Combo"/Pro-Drums-family section when Settings' visible instruments derive one, then one `FestivalGlassSection` per Settings-visible instrument (`fst.settings.show*` `@AppStorage` keys via `VisibleInstrumentsReader`, matching `FestivalRootView`'s own visible-instrument computation). Each section loads independently via its own `.task(id:)`, shows a 3-above/3-below preview (Common/Combo/per-instrument) with a "View All Rivals" row, and is skipped entirely when empty. Leaderboard tab has a `Menu` for `RivalRankMetric` (`totalscore`/`adjusted`/`weighted`/`fcrate`/`maxscore`). Rows push `AppRoute.rivalDetail`; "View All" pushes `AppRoute.allRivals(scope:)`. A toolbar "Find Rival" button (`fst.rivals.findRival`) opens `FindRivalSheet` (account-name search, same endpoint as Profile's Find Player). No player selected → `RivalsChooseProfileState` (`@Environment(\.openProfile)`).
- **Common Rivals / Combo (landed 2026-09-28):** `RivalCommonRivals.intersect` (`FestivalCore/Rivals.swift`) ports the web's `commonRivals` `useMemo` verbatim — a rival must appear in *every* loaded instrument's own list to qualify, direction by majority vote, highest-`sharedSongCount` entry represents the rival, each group sorted by `rivalScore` descending. `RivalCombo`/`RivalComboScope` port `comboUtils.ts`/`combos.ts`'s bitmask system (`deriveScope(visible:)`: the Pro Drums family special case first, then a within-group hex combo, else `nil`); a combo/Pro-Drums scope is a genuinely different server-computed list (`GET /api/player/{accountId}/rivals/{token}`, `token` a hex ID or `pro_drums`), not a client-side merge — see `RivalsEndpoint.comboList`/`.comboDetail` in `FestivalAPI+Rivals.swift`. `CompeteScreen` intentionally does not adopt either section (matches its own `ios.md`/the web's `CompetePage`, which has neither).
- **Find Rival (landed 2026-09-28):** `FindRivalSheet.swift` reuses the already-allowlisted `GET /api/account/search?q=&limit=` (`ProfileSearch.swift`) rather than a Rivals-specific endpoint. A selected result pushes `AppRoute.rivalDetail(rivalId:name:scope: nil)`; the destination screen's `nil`-scope fallback (merge every Settings-visible instrument) stands in for the web's settings-derived scope resolution.
- Rivals data does **not** go through `FestivalSession`'s publication-pinned pipeline (`observe(publicationId:)`); it isn't part of the catalogue/score generation contract that pipeline protects, so a Rivals read never pauses or invalidates Songs state and vice versa.
- **Typed scope, no navigation bridge (landed 2026-09-28):** the web reads `location.state` (React Router) to know which combo/leaderboard scope produced a tapped rival row. An earlier native pass filled that gap with `RivalNavigationBridge`, a process-lifetime `@MainActor` singleton keyed by rival account ID and consumed once — but a singleton stash breaks any route reached without a preceding stash (a deep link, restored navigation state, or `DebugLaunchRoute`), and could desync across independent stacks. It has been **removed**. `RivalScope` (`FestivalCore/Rivals.swift`) — `.song(instruments:)`, `.leaderboard(instrument:rankBy:)`, `.combo(token:instruments:)` — is now a typed, `Hashable` payload carried directly on `AppRoute.allRivals(scope:)`/`.rivalDetail(rivalId:name:scope:)`/`.rivalry(rivalId:mode:name:scope:)`. Every way of reaching a rival route now carries the same information a tap would have stashed; a `nil` scope (no context at all) falls back to merging every Settings-visible instrument (`FestivalSession.rivalDetail(forScope:rivalId:visibleInstruments:)`). `DebugLaunchRoute` parses `RivalScope.debugToken` (`song:<instrument>[,...]` / `leaderboard:<instrument>:<rankBy>` / `combo:<token>:<instrument>[,...]`) for `allRivals:`/`rivalDetail:`/`rivalry:` debug routes.
- Quick Links (landed 2026-09-28): song-tab sections `common`/`combo`/`<instrument>` register and deregister themselves as their independent loads settle (no explicit array to rebuild on tab change); leaderboard tab registers `<instrument>` only. See [quick-links/ios.md](../../controls/quick-links/ios.md).
- IDs: `fst.rivals.tab` (segmented control), `fst.rivals.rankBy` (metric menu), `fst.rivals.chooseProfile`, `fst.rivals.findRival` (toolbar button).
