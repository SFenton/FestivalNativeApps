# Full rankings — iPhone notes

> **What:** iPhone implementation state and decisions for the paginated full rankings and band rankings pages. **Read when:** changing either page on iPhone. Behavior: [spec.md](spec.md) (currently a stub — this file is the source of truth for what's actually built until spec.md is promoted; band-rankings/spec.md is a separate stub covering the same screen).

Source: `FortniteFestivalWeb/src/pages/leaderboards/FullRankingsPage.tsx`, `.../BandRankingsPage.tsx`, `.../helpers/rankingHelpers.ts` (`LEADERBOARD_PAGE_SIZE = 25`). Service: same two pure `GET`s as [leaderboards/ios.md](../leaderboards/ios.md), requested here with `pageSize: 25` and a specific `page`.

- Implemented: `FullRankingsScreen` (`AppRoute.fullRankings`) and `BandRankingsScreen` (`.bandRankings`) both render a native `List` (rows → `.player`/`.band`) plus the shared `RankingsPagerView` — the same First/Previous/`page / totalPages`/Next/Last control as the Solo chart ([song-leaderboard/ios.md](../song-leaderboard/ios.md)), so paging is identical everywhere. `FullRankingsScreen` adds an instrument switcher (scoped to Settings-visible instruments, keeping the current chart selectable even if just hidden) and the metric `Menu`; `BandRankingsScreen` adds a band-size switcher and a four-metric menu (no Max Score for bands). Switching any picker resets to page 1. `totalPages` = `ceil(totalAccounts|totalTeams / pageSize)`, always ≥1. Stale-response guard: a superseded request's result is dropped by comparing a `RequestKey` before applying it (same pattern as the Solo chart).
- **Shared pinned pager, Full Rankings (issue #294, 2026-10):** Full Rankings now uses the Song Leaderboard pattern ([song-leaderboard/ios.md](../song-leaderboard/ios.md)), not a page-specific floating bar. A `ScrollView` + `LazyVStack` of the compact row cards ([leaderboards/ios.md](../leaderboards/ios.md)) sits above a bottom chrome in `.safeAreaInset(edge: .bottom)`, outside the reload gate. The chrome is the spotlight footer plus the shared `RankingsPagerView(idPrefix: "fst.full-rankings")`: `« ‹ 1 / 34,691 › »` with spoken "First page" … "Last page". Its `page / total` badge is one adjustable element ("Page, 2 of 48"; swipe up/down pages). Rows fade out above the chrome (the shared `bottomChromeFade(chromeTop:distance:in:)` modifier, measured in the `fst.full-rankings.page` space; #305, #308), exactly as on Song Leaderboard; since the #293 merge it shares that page's end spacing too: no reserved bottom margin, the fade shrinks as the last row arrives (the modifier's `BottomFadeDistanceReader`), and `PinnedChromeSpacing` rests the last row one 6 pt row gap above the footer or pager and the footer one gap above the pager (the footer's own vertical padding was removed). The pinned bar title keeps `marqueeWrapsAtAccessibilitySizes` off so it stays one line at accessibility sizes. `body` reads `bottomChromeTop` and passes it to the mask: read only inside the mask's lazy `GeometryReader`, the first page kept an opaque mask (rows drawn behind the pager) until a scroll re-rendered the page (live iPhone 17 Pro capture, 2026-10-04; Song Leaderboard has the same read pattern and is left to #293). The page total survives page loads (`shownEntries`/`board` cleared only on an instrument or Rank By switch). On the Duo vertical bar the same `RankingsPagerView` stays under the board, never in the rail (#345, superseding B2); unfolded, `PagerScreenPlacement` puts it on the screen beside the bar. HIG design principles: "Keep visual and interaction behavior consistent so people learn quickly and can predict new interactions". The instrument switcher left the floating pill: it is a toolbar `Menu` (`fst.full-rankings.instrument-menu`, label "Instrument", value the chart name) whose label is the chart icon (`InstrumentIcon.menuImage`), grouped with Rank By in the `.festivalPageAction` slot (iPhone: the tab-bar accessory, below). On Mac and iPad it is also View › Instrument ▸ (`MacInstrumentCommands`, `.macInstrumentCommands`): HIG Toolbars › macOS, "Every toolbar item must also be a menu-bar command because people can customize or hide the toolbar". `RankingsFloatingBar`/`RankingsGlassPager` now serve only Band Rankings (unchanged: band pill with `person.3.fill`, pager capsule, `ViewThatFits` fallbacks). Lists keep `rankingsListRailClearance` (`DeviceLayout.cutoutInsets.trailing`, camera only).
- **Title with instrument icon (issue #294):** the first scroll item is `InstrumentPageTitle(.header)` (`Common/InstrumentPageTitle.swift`, shared with song boards beside Song Detail since #342): the chart icon (`@ScaledMetric` 36 pt relative to `.largeTitle`, decorative, `accessibilityHidden`) left of "Lead Rankings" in `.largeTitle.bold()`, combined into one header element (`fst.full-rankings.title`). The bar uses `.navigationBarTitleDisplayMode(.inline)` with `navigationTitle` kept for the bar identifier, back menu and window title. Once the header scrolls under the bar (`SongDetailPinnedTitlePolicy.isHeroHidden`), the principal slot shows `InstrumentPageTitleToolbarItem` (`InstrumentPageTitle(.pinned)`): a 24 pt (`.headline`-relative) icon plus a `.headline` `MarqueeText` (`fst.full-rankings.pinned-title`). Before that it shows a 1×1 hidden placeholder, so the bar never falls back to plain title text and there's no opacity-0 copy for the Dynamic Type audit. This is the same artwork-plus-title swap as Song Leaderboard. The principal title is skipped on the Duo vertical bar (custom views aren't drawn in the rail), so folded Duo shows the system inline title above the icon header, as Song Detail and Song Leaderboard do. HIG Icons: "Match icon weight to adjacent text"; Toolbars › iOS: the title condenses to the bar as people scroll. On macOS the window title stays text and the in-content header carries the icon.
- **Ranked count:** first scroll line under the large title, "868,901 ranked players" / "N ranked bands" (web `PageHeader` subtitle, `rankings.totalRanked`), `RankingsCountHeader`: `.subheadline` semibold, primary white (`fst.full-rankings.ranked-count`, `fst.band-rankings.ranked-count`). Not `navigationSubtitle`: the system subtitle rendered too small (operator, 2026-09-28). Title stays "Lead Rankings" (web: "Lead Leaderboards").
- **Text colour:** `FestivalText.primary` for every label (songs column, Bayesian line, empty/unranked text); disabled pager symbols use `FestivalText.disabled`. Each loaded page's rows stagger in once, like the Solo board (#323): `festivalFadeIn(staggerIndex:)` inside the page's `festivalScrollFadeInScope(fadeScope, resetKey: rowsReveal)`, re-armed when the reload gate reveals a page. The title, ranked count and empty text fade in with the first row. The footer's jump to the player's page scrolls through `SelectedRowReveal` with the scope and the row's index, so the row it reaches fades in with the rush ([load-transition](../../patterns/load-transition.md) R5). Test: `selectedRowRevealFadesTheRowItReaches`.
- **Tab-bar accessory (issue #92 with #294):** on iPhone (iOS 26.1+, horizontal tab bar) the instrument switcher and Rank By are page tools in the accessory (`festivalPageTool`, `PageToolOrder.primary`/`.secondary`), Instrument · Rank By | bell (avatar in the header, issue #300); both are `PageToolMenu`s, so in the accessory they open a choice sheet (the instrument sheet lists the Settings-visible charts with their icons, `fst.full-rankings.instrument.<chart>`). Where `\.pageToolsRegistry` is nil (Duo rail, iPad, iOS < 26.1, Mac) they stay one `.festivalPageAction` toolbar group. The pinned pager (Band Rankings: the floating bar) stacks above the accessory (safe-area inset), never inside it: a five-control pager doesn't fit beside the account items, least of all when the accessory goes inline beside the minimized tab bar ([nav-accessories.md](../../design/apple/nav-accessories.md)). The cost is two stacked bottom bars while the tab bar is expanded.
- **Selected-player footer, `FullRankingsScreen` only (Lane L2; issue #318):** the selected player's own row (`playerInstrumentRanking`, independent of `page`, like the web's separate `playerRanking` query) is pinned in the bottom inset directly above the shared pager on **every** page, including the page whose rows already show it highlighted, exactly as Song Leaderboard pins its footer (web `FullRankingsPage`: `hasPlayerFooter = !!playerRanking`; [leaderboard-row](../../patterns/leaderboard-row.md) R5, R7). `RankingSpotlight.pinnedFooter` decides it and never returns `.inline`; the page's own row stands in while the per-account read is pending or failed. Pending, unranked and failed footers keep their loading row, "not yet ranked" capsule and inline Retry. The row is `AccountRankingRow(isSelected: true, cardSurface: true, opensProfile: false)` with `PinnedFooterBacking`, in the page's shared columns; the whole row is the control (`SelectedRowAction.footer`): off this page a button jumps to the player's page and `SelectedRowReveal` centres their row (`fst.full-rankings.spotlight-jump`, "Your rank, 57th. Jump to your position."); on it a link opens Statistics (`fst.full-rankings.spotlight-open`, "… Open your statistics.", web `getPlayerProfileRoute`). The Leaderboards overview cards keep `RankingSpotlight.placement` and still hide a player already in their top ten. No selected-band pinned row: same "no selected-band identity natively yet" gap as [leaderboards/ios.md](../leaderboards/ios.md), not ported for `BandRankingsScreen`. HIG Lists and tables: "Provide appropriate selection feedback."
- Simplified vs. web: no band-combo filter. Picker changes update `@State` in place rather than pushing a new `AppRoute`, since neither page has the Solo chart's deep-link-bookmark-correctness requirement.
- IDs: `fst.band-rankings.pager` (capsule), `fst.full-rankings.page-*` (`first`, `previous`, `info`, `next`, `last`), `fst.full-rankings.title`, `fst.full-rankings.pinned-title`, `fst.full-rankings.instrument-menu`, `fst.band-rankings.page-*`, `fst.band-rankings.band-type-menu`, `fst.band-rankings.rank-by-menu`, shared `fst.rankings.rank-by-menu`, `fst.full-rankings.spotlight-footer`/`.spotlight-jump`/`.spotlight-open`/`.spotlight-footer.unranked`/`.spotlight-footer.loading`.

- **One bottom fade for every board (issue #305):** Solo, Full Rankings, the band song leaderboard and Band Rankings share `bottomChromeFade(chromeTop:distance:in:)` and `reportsBottomChromeTop(in:_:)` (`Design/BottomChromeFade.swift`), with or without a spotlight footer. Band Rankings had no mask, so rows ran visibly under its floating glass pager; it now fades above `RankingsFloatingBar` (measured in `fst.band-rankings.page`). Each screen still reads `bottomChromeTop` at the top of its own `body` and passes the value: read only inside the `FestivalReloadGate` closure, the band boards kept an opaque mask until a scroll re-rendered them (same trap as #294). `BottomFadeDistanceReader` now measures the scroll view by `ScrollGeometry.visibleRect.height`: a `ScrollView` reports `containerSize` without its top and bottom safe-area insets (623 of 874 pt on iPhone 17 Pro), which counted the bottom inset twice, so on Full Rankings the fade never shrank and the resting last row stayed faded (#293 was measured on Solo's `List`, where both are the full height). Test: `contentOverflowReachesZeroWithFullScrollViewHeight`. Checked live on iPhone 17 Pro (Full Rankings Lead with SFentonX, Band Rankings Duos; mid-scroll and end) and iPad (Band Rankings); Mac compiled only (`mac_app.py build`). HIG Layout / Scroll views as in [song-band-leaderboard/ios.md](../song-band-leaderboard/ios.md). **R7 (#305 review):** `BottomChromeFade` reads system Reduce Transparency and Increase Contrast plus the app's Less Transparency and Increase Contrast (`fst.accessibility.lessTransparency` / `moreContrast`, as `SectionBarRowMask` and `ModalPinnedHeaderFade` do) and draws a hard cut at the chrome top when any is on. The hosted test harness forces Reduce Transparency unless `forceGlassFallback: false`, so fade pixel tests must opt out. `BottomChromeFadeHostedTests` scrolls Song Band and Band Rankings (no footer) through mid-scroll and the end of page 1 in every mode.
- **Load/reload fade (issue #71):** Full Rankings and Band Rankings run the shared `FestivalReloadGate` on load and on an instrument, Rank By or page change: old results leave at once, the spinner fades in, holds ≥400 ms, fades out (500 ms) and the results fade/stagger in; Reduce Motion swaps instantly. See [iPhone motion](../../design/apple/iphone.md#motion).
- **Opened from Leaderboards on a split (issue #352, agent decision A; owner may override with `/choose`):** on iPad landscape, the iPhone Duo inner display and the Mac, View All Rankings opens this page in the trailing pane beside the overview as its sub-page (the View All button stays selected); a player row opens the full profile over both halves, and its Back returns to the split with the board and its page kept. Portrait and compact push it as before. Rules: [split-view.md](../../design/apple/split-view.md), [view-all-cta](../../patterns/view-all-cta.md) R8. Tests: `IPadShellJourneyTests.testFullRankingsOpensBesideLeaderboards`, `MacPagesHostedTests.macFullRankingsSplitsOnDemand`.
