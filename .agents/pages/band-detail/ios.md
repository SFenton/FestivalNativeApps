# Band detail — iPhone notes

> **What:** iPhone implementation state and decisions for `/bands/:bandId`. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md).

Source: `FortniteFestivalWeb/src/pages/band/BandPage.tsx` (Members, Summary, Statistics, Rank History, Songs sections). Service: the web page calls `GET /api/bands/{bandId}` (`FSTService/Api/RankingsEndpoints.cs:811`) — **this app never calls it.** Its handler unconditionally calls `GlobalLeaderboardPersistence.GetBandConfigurations`, which calls `EnsureBandTeamConfigurations`, which runs a `DELETE`+`INSERT` transaction against `band_team_configurations` on a cache miss (`GlobalLeaderboardPersistence.cs:4192-4206`, `BandLeaderboardPersistence.cs:1028-1137`) — a write side effect from a GET, in the same family as the already-blocked band-search fallback and band sync-status reads. This was found while implementing this page and is not yet in [service-safety.md](../../platforms/service-safety.md)'s table; treat `/api/bands/{bandId}` as blocked pending an explicit service-owner review, the same as band search and sync-status.

One consequence: `bandId` is a one-way SHA-256 hash of `bandType:teamKey` (`FSTService/Persistence/BandIdentity.cs`), so nothing client-side can recover `bandType`/`teamKey` from a bare `bandId` without that unsafe endpoint.

- Implemented: reads the same pure `GET /api/rankings/bands/{bandType}?teamKey=&page=1&pageSize=1` board `BandRankingsScreen` uses (`FestivalAPI.bandProfile`), which returns a full `BandTeamRankingDto` including `members[].instruments` (via a read-only join, `MetaDatabase.cs:16478`) and `configurations` (Duos-only with a `combo` filter, `ShouldAttachBandRankingConfigurations`, `MetaDatabase.cs:16565`). Sections (rebuilt for web parity, #555): Members (`BandMemberCard`: initial, name, instrument icons, chevron; one button "View {name}, {instruments}"), Summary (Type, Appearances, Members) and Statistics (web `StatBox` order and links, through the player profile's `PlayerStatGrid` with `identifierPrefix: "fst.band"`), Rank History (`/api/rankings/bands/{bandType}/{teamKey}/history`, drawn by the shared `RankHistoryCharts` for the toolbar's `BandRankByMenu` metric), Five Best Songs and Five Worst Songs (`/api/rankings/bands/{bandType}/{teamKey}/songs`, `BandSongRow`; handles its 503-while-unpublished state via the existing `FestivalAPIError.unavailable`). `AppRoute.band` carries additive optional `bandType`/`teamKey` (default `nil`) alongside the original `bandId`/`name`, populated by every row that already knows them (player bands, song band leaderboard, band rankings).
- Not implemented — **and not implementable without the blocked endpoint**: opening this screen from a bare `bandId` alone (e.g. a hypothetical universal link or the `band:<id>` debug route with no `bandType`/`teamKey`). Shows an explicit `FestivalEmptyState` ("Band Not Available … open from Player Bands, Band Rankings or a song's Band Scores") instead of guessing or silently failing.
- No "select as band profile" action: `FestivalSession` only models a selected *player* identity (`SelectedPlayerIdentity`). Adding a parallel selected-band concept is a cross-cutting session change (new persisted identity kind, `festivalRootChrome` profile bubble, tab-visibility rules) out of this page's scope; reported to the orchestrator rather than half-built here.
- **Best/Worst Songs now cross-reference the catalog** (Lane P follow-up, 2026-09-28): a `.task` loads `session.catalog()` into a `songId → Song` lookup (same `songsById` pattern as `RivalryScreen`/`ShopScreen`), and each row shows the resolved title/artist/`ArtworkTile` album art with a `NavigationLink` to `AppRoute.songDetail(song)`. A song the lookup hasn't resolved (not yet loaded, or removed from a newer catalogue) falls back to the raw `songId` as a plain, non-navigable row — the same defensive shape the raw-ID rows always had, never a broken link.
- **Quick Links** (`members`, `summary`, `statistics`, `rank-history`, `songs`, matching the spec order/icons): eager `VStack`, sections tagged with `.quickLinkSection` and discovered in tree order. Pushed page, so no `FestivalRootTrailingItems`/root chrome — just `QuickLinksToolbarItem` beside the existing `BandRankByMenu`.
- **Header (#555):** `festivalNavigationTitle(name)` with `.navigationBarTitleDisplayMode(.large)` on iPhone, iPad and Duo, whichever page pushed it (Band Rankings and song boards are inline themselves), collapsing to inline on scroll; the first content row is the subtitle `fst.band.subtitle` "{type} • {N} appearances" (`BandPageFormatting.subtitle`), the Band Rankings `RankingsCountHeader` precedent. HIG Toolbars: "Use a large title to help people stay oriented" (should). A long band name truncates in the system large title; no public API makes it multiline, VoiceOver reads it whole and the Members cards name everyone.
- **Statistics links (#555):** Best Rank opens Song Detail for the band's best song (`PlayerStatLink.bandSongDetail`); the rank tiles open Band Rankings for that metric at the band's page (`AppRoute.bandRankings(bandType:rankBy:page:)`, `PlayerStatLinks.bandRank`, 25 per page). Songs Played and Full Combos stay plain: there is no selected band to filter Songs by.
- **Agent decisions (#555, owner may override with `/choose`):** song percentiles bucket from rank/total (spec R4); Mac stacks Summary above Statistics like the web (the old side-by-side layout is gone); Rank History is a glass card with its title inside like the player `PlayerRankHistoryCard`, the other sections use `FestivalSectionHeader` over cards.
- Simplified vs. web: no instrument-combo picker (`BandInstrumentFilterModal`/`BandInstrumentFilterPicker`) — `configurations` is fetched with no `combo` filter, so it is empty for every band size except when a future picker supplies one.
- IDs: `fst.band.unresolved`, `fst.band.members-section`, `fst.band.member.<accountId>`, `fst.band.summary-section`, `fst.band.statistics-section`, `fst.band.subtitle`, `fst.band.history-section`, `fst.band.songs-section`, `fst.band.best-songs`, `fst.band.worst-songs`, `fst.band.{best,worst}-songs-empty`, `fst.band.song-row.<songId>`, stat tiles `fst.band.stat.{summary,statistics}.<tile>`.
- Experimental Ranks (spec R5, #557 review): `BandDetailScreen` reads `@AppStorage(ExperimentalRanks.storageKey)` and the canonical `BandRankingMetric.coerced(experimentalRanks:)`; while off it hides `BandRankByMenu` (toolbar and iPhone page tools) and publishes no Mac View › Rank By (`macRankByCommands(_:isEnabled:)`), and `statisticsTiles(…, experimentalRanks:)` drops the Adjusted, Weighted and FC Rate rank tiles. `BandRankByMenu` and the Mac band options list `BandRankingMetric.menuOrder` (Total Score first). The Apple Settings switch itself lands with #541, so until then the page shows Total Score only.
- Tests: `BandsTests.swift` (Core) covers `BandDetail`/`BandProfileEnvelope` decoding from the rankings-by-teamKey envelope, rank/rating dispatch, rank-history decoding and metric ranking, and song-extremes decoding. `BandPageFormattingTests` (Core: title, subtitle, stat text, history status, chart value kinds, percentile buckets, rank links). Hosted coverage: `BandsRenderTests.swift` (unresolved, loaded with history/catalog-linked songs, loaded with empty history/songs, 503 failed, and `bandDetailReadsSectionsInWebOrderWithLabelledTargets` reading order, labels and 44 pt targets at Large and AX3), `BandDetailContentTests` (tiles with Experimental Ranks off and on, links, member and song row labels, chart points and VoiceOver values), `bandDetailExperimentalRankTilesFollowTheSettingLive` (hosted: off → on → off on the open page), `BandPageFormattingTests.bandMetricGateFollowsExperimentalRanks` (Core gate). XCUITest (`BandsJourneyTests`): `testBandRankingsRowOpensBandDetailThenSong`; `testBandDetailShowsLargeTitleSubtitleAndWebSections` (setting off: large title collapses, subtitle under the bar, every section, no Rank By, Total Score Rank the only rank tile, `performAccessibilityAudit` for every type but Dynamic Type at the top and the bottom; waivers: content under the bottom chrome fade, contrast estimates re-measured on the rendered screenshot (≥4.5:1), a contrast issue with no element (an unresolvable node beside the rank chart) only when every text in the content band renders ≥4.5:1 (`unattributed-contrast-page-floor`, [accessibility](../../testing/apple/accessibility.md)), and the system title's truncation of a long band name); `testBandDetailRankByFollowsExperimentalRanks` (setting on: a labelled ≥44 pt Rank By reading Adjusted, choices Total Score first, picking Total Score applies, experimental tiles shown); `testBandDetailScalesToTheLargestTextSize` (always launches AX3: Dynamic Type, clipped-text and hit-region audits at the header and at each lower section; subtitle, member card, Summary and Statistics tiles, chart and Best/Worst song rows reachable, inside the window, ≥44 pt where targets and taller than at the default size; texts the default-size Dynamic Type probe flags, or that the AX3 probe flags, must grow ≥1.35×).
