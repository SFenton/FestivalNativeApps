# Band detail — iPhone notes

> **What:** iPhone implementation state and decisions for `/bands/:bandId`. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (currently a stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/band/BandPage.tsx` (Members, Summary, Statistics, Rank History, Songs sections). Service: the web page calls `GET /api/bands/{bandId}` (`FSTService/Api/RankingsEndpoints.cs:811`) — **this app never calls it.** Its handler unconditionally calls `GlobalLeaderboardPersistence.GetBandConfigurations`, which calls `EnsureBandTeamConfigurations`, which runs a `DELETE`+`INSERT` transaction against `band_team_configurations` on a cache miss (`GlobalLeaderboardPersistence.cs:4192-4206`, `BandLeaderboardPersistence.cs:1028-1137`) — a write side effect from a GET, in the same family as the already-blocked band-search fallback and band sync-status reads. This was found while implementing this page and is not yet in [service-safety.md](../../platforms/service-safety.md)'s table; treat `/api/bands/{bandId}` as blocked pending an explicit service-owner review, the same as band search and sync-status.

One consequence: `bandId` is a one-way SHA-256 hash of `bandType:teamKey` (`FSTService/Persistence/BandIdentity.cs`), so nothing client-side can recover `bandType`/`teamKey` from a bare `bandId` without that unsafe endpoint.

- Implemented: reads the same pure `GET /api/rankings/bands/{bandType}?teamKey=&page=1&pageSize=1` board `BandRankingsScreen` uses (`FestivalAPI.bandProfile`), which returns a full `BandTeamRankingDto` including `members[].instruments` (via a read-only join, `MetaDatabase.cs:16478`) and `configurations` (Duos-only with a `combo` filter, `ShouldAttachBandRankingConfigurations`, `MetaDatabase.cs:16565`). Sections: Members (name + instrument icons), Summary (rank/rating/coverage), Statistics (songs played, full combos, accuracy, stars, best/avg rank), Rank History (`/api/rankings/bands/{bandType}/{teamKey}/history`, recent snapshots ranked by the toolbar's `BandRankByMenu` metric), Best & Worst Songs (`/api/rankings/bands/{bandType}/{teamKey}/songs`, handles its 503-while-unpublished state via the existing `FestivalAPIError.unavailable`). `AppRoute.band` carries additive optional `bandType`/`teamKey` (default `nil`) alongside the original `bandId`/`name`, populated by every row that already knows them (player bands, song band leaderboard, band rankings).
- Not implemented — **and not implementable without the blocked endpoint**: opening this screen from a bare `bandId` alone (e.g. a hypothetical universal link or the `band:<id>` debug route with no `bandType`/`teamKey`). Shows an explicit `FestivalEmptyState` ("Band Not Available … open from Player Bands, Band Rankings or a song's Band Scores") instead of guessing or silently failing.
- No "select as band profile" action: `FestivalSession` only models a selected *player* identity (`SelectedPlayerIdentity`). Adding a parallel selected-band concept is a cross-cutting session change (new persisted identity kind, `festivalRootChrome` profile bubble, tab-visibility rules) out of this page's scope; reported to the orchestrator rather than half-built here.
- **Best/Worst Songs now cross-reference the catalog** (Lane P follow-up, 2026-09-28): a `.task` loads `session.catalog()` into a `songId → Song` lookup (same `songsById` pattern as `RivalryScreen`/`ShopScreen`), and each row shows the resolved title/artist/`ArtworkTile` album art with a `NavigationLink` to `AppRoute.songDetail(song)`. A song the lookup hasn't resolved (not yet loaded, or removed from a newer catalogue) falls back to the raw `songId` as a plain, non-navigable row — the same defensive shape the raw-ID rows always had, never a broken link.
- **Quick Links** (`members`, `summary`, `statistics`, `rank-history`, `songs`, matching the spec order/icons): eager `VStack`, sections tagged with `.quickLinkSection` and discovered in tree order. Pushed page, so no `FestivalRootTrailingItems`/root chrome — just `QuickLinksToolbarItem` beside the existing `BandRankByMenu`.
- Simplified vs. web this pass: no instrument-combo picker (`BandInstrumentFilterModal`/`BandInstrumentFilterPicker`) — `configurations` is fetched with no `combo` filter, so it is empty for every band size except when a future picker supplies one; no rank-history chart, just a ranked list of recent snapshots.
- IDs: `fst.band.unresolved`, `fst.band.members-section`, `fst.band.member.<accountId>`, `fst.band.summary-section`, `fst.band.statistics-section`, `fst.band.history-section`, `fst.band.history-row.<date>`, `fst.band.songs-section`, `fst.band.song-row.<songId>`.
- Tests: `BandsTests.swift` (Core) covers `BandDetail`/`BandProfileEnvelope` decoding from the rankings-by-teamKey envelope, rank/rating dispatch, rank-history decoding and metric ranking, and song-extremes decoding. Hosted coverage: `BandsRenderTests.swift` (unresolved, loaded with history/catalog-linked songs, loaded with empty history/songs, 503 failed); XCUITest: `BandsJourneyTests.testBandRankingsRowOpensBandDetailThenSong` (Lane U4, 2026-09-28).
