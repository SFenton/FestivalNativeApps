# rivalry (`/rivals/:rivalId/rivalry`) — iPhone notes

> **What:** iPhone implementation state and decisions for the full song list of one rivalry category. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/rivals/RivalryPage.tsx`. Reached from a `RivalDetailScreen` category's "View All" via `AppRoute.rivalry(rivalId:mode:name:)`, where `mode` is a `RivalCategory.key` (`closest_battles`, `almost_passed`, `slipping_away`, `barely_winning`, `pulling_forward`, `dominating_them`) — see [rival-detail/ios.md](../rival-detail/ios.md).

- Implemented: `RivalryScreen` (`Features/Rivals/RivalryScreen.swift`) re-fetches the same rival detail as `RivalDetailScreen` via the shared `FestivalSession.rivalDetail(forScope:rivalId:visibleInstruments:)` resolver, re-runs `RivalCategorization.categorize` and renders every song in the requested bucket inside one `FestivalGlassSection` (no 5-song cap). Toolbar (iPhone: floating page tool, #632) "View Profile" pushes `AppRoute.player`; song rows push `AppRoute.songDetail` when resolvable against the loaded catalogue, same as the detail page.
- **No Quick Links (owner, #545).** The page is one list of songs, so it offers no Quick Links on iPhone, iPad, Mac or Duo (shared screen): View Profile is its only page tool. The web's per-song mobile links are deliberately not mirrored ([quick-links](../../patterns/quick-links.md) R3 owner-approved variant). HIG Toolbars: "Put only essential actions in the main area". Tests: hosted `RivalsRenderTests.rivalryOffersViewProfileButNoQuickLinks`, journey `QuickLinksOrderJourneyTests.testRivalryOffersNoQuickLinks`.
- **Scope forwarding, no re-stash (landed 2026-09-28):** `AppRoute.rivalry(rivalId:mode:name:scope:)` carries the same `RivalScope?` `RivalDetailScreen` received on its own push — `RivalDetailScreen`'s category "View All" forwards it unchanged. There is no `RivalNavigationBridge` consume-and-re-stash step to reason about any more (removed; see [rivals/ios.md](../rivals/ios.md)): both screens simply read the scope `AppRoute` already carries, so popping back to `RivalDetailScreen` and pushing a different category still resolves identically.
- **Song rows (#558):** the same `RivalSongRowContent` as Rival Detail, with album art and "#rank Name" status pills ([rival-rows](../../patterns/rival-rows.md) R3–R5; see [rival-detail/ios.md](../rival-detail/ios.md)).
- Simplified vs. web this pass: no sort control (the web's `RivalDetailPage`/`RivalryPage` don't expose one either at this route — sorting is a `rivalDetailFetch` parameter this app doesn't currently vary from `closest`).
- Song rows use the shared `RivalSongRowContent`, read as "<song>, <instrument>, you rank N, <rival> ranks M, <who leads>" (#444, #558; [rival-detail/ios.md](../rival-detail/ios.md)).
- Tests: covered by `RivalsTests.swift`'s `RivalCategorization`/`RivalDetailResponse` coverage (see [rival-detail/ios.md](../rival-detail/ios.md)); no rivalry-specific Core logic beyond category lookup by key.
- **Page title (#604, 2026-10-11):** the page leads with R18's `InstrumentPageTitle(.header)` (`fst.rivalry.title`): the section ("Closest Battles"; `RivalryScreen.title(for:)`) over the rival's name ("Rival" until known), no icon. One heading, read "section, name"; it pins to the bar as `fst.rivalry.pinned-title` once it scrolls away, and the Duo vertical bar keeps the system title. Rule: [page-tools-and-nav-chrome R23](../../patterns/page-tools-and-nav-chrome.md). Shared Swift: iPadOS, iPhone Duo and macOS get the same heading.
