# rival-detail (`/rivals/:rivalId`) — iPhone notes

> **What:** iPhone implementation state and decisions for one rival's shared-song breakdown. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/rivals/RivalDetailPage.tsx`, `helpers/rivalCategories.ts`, `helpers/rivalDetailFetch.ts`. Service: `GET /api/player/{accountId}/rivals/{combo}/{rivalId}` and `GET /api/player/{accountId}/leaderboard-rivals/{instrument}/{rivalId}` (`RivalsEndpoints.cs`/`LeaderboardRivalsEndpoints.cs`) — both public, keyless, read-only.

- Implemented: `RivalDetailScreen` (`Features/Rivals/RivalDetailScreen.swift`) ports `categorizeRivalSongs` verbatim as `RivalCategorization.categorize` (`FestivalCore/Rivals.swift`): Closest Battles (top 5 by `|rankDelta|`), then direction-split Almost Passed/Slipping Away (rival leads) and Barely Winning/Pulling Forward/Dominating Them (player leads), each a non-empty-only `FestivalGlassSection` with a 5-song preview and a "See All" push to `RivalryScreen`. A toolbar "View Profile" action pushes `AppRoute.player`; a "Quick Links" menu (`rival-category:<key>` per non-empty category) sits beside it. Song rows push `AppRoute.songDetail(Song)` when the tapped song is found in a lazily loaded `session.catalog()` lookup (native `AppRoute.songDetail` needs a full `Song` value, not just an ID); otherwise the row is inert content only.
- **Typed scope, no navigation bridge (landed 2026-09-28):** `AppRoute.rivalDetail(rivalId:name:scope:)` carries a `RivalScope?` directly (`.song(instruments:)`, `.leaderboard(instrument:rankBy:)` or `.combo(token:instruments:)`); `FestivalSession.rivalDetail(forScope:rivalId:visibleInstruments:)` (`App/FestivalSession+Rivals.swift`) resolves it — merging instruments via `combinedRivalDetail` (song source, sequential rather than a `TaskGroup` to avoid capturing the `@MainActor` session in a `@Sendable` closure), reading `leaderboardRivalDetail` (leaderboard source) or `rivalComboDetail` (combo source). A `nil` scope (deep link, cold start, `DebugLaunchRoute` with no scope, or `FindRivalSheet`'s arbitrary search result) merges every Settings-visible instrument instead of failing. The earlier `RivalNavigationBridge` singleton this screen read is gone — see [rivals/ios.md](../rivals/ios.md).
- Simplified vs. web this pass: no live gaps request (`includeGaps`/`allowLiveFallback` query params) — `songsToCompete`/`yourExclusiveSongs` only populate when the service already computed them, which this app never explicitly requests, so those sections are effectively unused today.
- IDs: `fst.rivalDetail.viewProfile`.
- Tests: `RivalCategorization` covered by `RivalsTests.swift` (`categorizationSplitsByDirectionAndMagnitude`, empty-input case). `RivalDetailResponse`/`RivalIdentity` decode coverage for both the song-combo and leaderboard-detail wire shapes (the latter omits `combo`/`offset`/`limit`, adds `instrument`/`rankBy`, decoded through the one shared type), plus the new combo-scoped endpoint URL coverage.
  - **Re-checked 2026-09-28 (this lane):** both detail endpoints are live and return HTTP 200 for the sample account outside an active scrape window — direct `curl` against production decoded exactly the `RivalDetailResponse` shape (song-combo: `rival`/`combo`/`source`/`totalSongs`/`offset`/`limit`/`sort`/`songs[]`; leaderboard: `rival`/`instrument`/`rankBy`/`totalSongs`/`sort`/`songs[]`, no `combo`/`offset`/`limit`), confirmed via `tools/ios_sim.py drive` loading a real `RivalDetailScreen` for account `195e93ef108143b2975ee46662d4d0e1` vs. rival `f1c749eb07c32578cfa3e59ec38c03a8` ("Fixture Rival Golf", `Lead Rivals` → tap). **New finding:** partway through this same session, the same endpoints started returning HTTP 503 again with a new response header, `x-fst-public-read-freeze-reason: scrape` (`Retry-After: 30`, `Cache-Control: no-store`) — the list endpoints (`/rivals/{instrument}`, `/leaderboard-rivals/{instrument}`) kept returning 200 with the same header present, so the freeze is specific to the heavier per-song detail computation during an active scrape, not a general outage. This is the same 503 previously observed (2026-09-27) with only a bare `Retry-After`; the freeze-reason header is new information, not a new failure mode. `RivalsAPIError.unavailable(retryAfter:)` and the screen's `ServiceUnavailableView` + retry already handle it correctly — confirmed live via `drive` (screenshot showed "Rivals Unavailable — Rivals data is temporarily unavailable. Try again shortly." with a working Retry button once the freeze started). Per `AGENTS.md`/`service-safety.md`'s "never copy production payloads … into fixtures", `rival-detail-demo.json`/`leaderboard-rival-detail-demo.json` remain the existing hand-authored fixtures rather than a captured real payload; they already match the verified live shape.
