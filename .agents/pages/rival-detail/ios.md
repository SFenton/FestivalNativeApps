# rival-detail (`/rivals/:rivalId`) — iPhone notes

> **What:** iPhone implementation state and decisions for one rival's shared-song breakdown. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/rivals/RivalDetailPage.tsx`, `helpers/rivalCategories.ts`, `helpers/rivalDetailFetch.ts`. Service: `GET /api/player/{accountId}/rivals/{combo}/{rivalId}` and `GET /api/player/{accountId}/leaderboard-rivals/{instrument}/{rivalId}` (`RivalsEndpoints.cs`/`LeaderboardRivalsEndpoints.cs`) — both public, keyless, read-only.

- Implemented: `RivalDetailScreen` (`Features/Rivals/RivalDetailScreen.swift`) ports `categorizeRivalSongs` verbatim as `RivalCategorization.categorize` (`FestivalCore/Rivals.swift`): Closest Battles (top 5 by `|rankDelta|`), then direction-split Almost Passed/Slipping Away (rival leads) and Barely Winning/Pulling Forward/Dominating Them (player leads), each a non-empty-only `FestivalGlassSection` with a 5-song preview and a "See All" push to `RivalryScreen`. A toolbar "View Profile" action pushes `AppRoute.player`. Song rows push `AppRoute.songDetail(Song)` when the tapped song is found in a lazily loaded `session.catalog()` lookup (native `AppRoute.songDetail` needs a full `Song` value, not just an ID); otherwise the row is inert content only.
- Combo/leaderboard scope resolution: reads `RivalNavigationBridge.shared.consume(forRivalId:)` (see [rivals/ios.md](../rivals/ios.md)) to learn which instrument(s)/leaderboard scope produced the tapped row, then calls `FestivalSession.combinedRivalDetail(instruments:rivalId:)` (song source, merges and dedupes songs across instruments sequentially — deliberately not a `TaskGroup`, to avoid capturing the `@MainActor` session in a `@Sendable` closure) or `.leaderboardRivalDetail(instrument:rivalId:rankBy:)` (leaderboard source). No stashed context (deep link, cold start) → merges every Settings-visible instrument instead of failing.
- Simplified vs. web this pass: no multi-combo merge beyond simple instrument-set union (the web's `fetchCombinedRivalDetail` also supports hex-bitmask "combo" scopes this app doesn't query — see [rivals/ios.md](../rivals/ios.md)); no live gaps request (`includeGaps`/`allowLiveFallback` query params) — `songsToCompete`/`yourExclusiveSongs` only populate when the service already computed them, which this app never explicitly requests, so those sections are effectively unused today.
- IDs: `fst.rivalDetail.viewProfile`.
- Tests: `RivalCategorization` covered by `RivalsTests.swift` (`categorizationSplitsByDirectionAndMagnitude`, empty-input case). `RivalDetailResponse`/`RivalIdentity` decode coverage for both the song-combo and leaderboard-detail wire shapes (the latter omits `combo`/`offset`/`limit`, adds `instrument`/`rankBy`, decoded through the one shared type). Live captures of the detail endpoints returned HTTP 503 "Published data unavailable" while this was built (2026-09-27, confirmed via direct `curl` against production with `Retry-After: 30`) — `rival-detail-demo.json`/`leaderboard-rival-detail-demo.json` fixtures are hand-authored to the verified `RivalsEndpoints.cs`/`LeaderboardRivalsEndpoints.cs` serialization shape rather than a live capture; `RivalsAPIError.unavailable(retryAfter:)` is exercised by the screen's `ServiceUnavailableView` + retry, matching that observed production behavior.
