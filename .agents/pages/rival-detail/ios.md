# rival-detail (`/rivals/:rivalId`) — iPhone notes

> **What:** iPhone implementation state and decisions for one rival's shared-song breakdown. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/rivals/RivalDetailPage.tsx`, `helpers/rivalCategories.ts`, `helpers/rivalDetailFetch.ts`. Service: `GET /api/player/{accountId}/rivals/{combo}/{rivalId}` and `GET /api/player/{accountId}/leaderboard-rivals/{instrument}/{rivalId}` (`RivalsEndpoints.cs`/`LeaderboardRivalsEndpoints.cs`) — both public, keyless, read-only.

- Implemented: `RivalDetailScreen` (`Features/Rivals/RivalDetailScreen.swift`) ports `categorizeRivalSongs` verbatim as `RivalCategorization.categorize` (`FestivalCore/Rivals.swift`): Closest Battles (top 5 by `|rankDelta|`), then direction-split Almost Passed/Slipping Away (rival leads) and Barely Winning/Pulling Forward/Dominating Them (player leads), each a non-empty-only `FestivalGlassSection` with a 5-song preview, followed by the shared purple "View All" push to `RivalryScreen`. A toolbar "View Profile" action pushes `AppRoute.player`; a "Quick Links" menu (`rival-category:<key>` per non-empty category) sits beside it. Song rows push `AppRoute.songDetail(Song)` when the tapped song is found in a lazily loaded `session.catalog()` lookup (native `AppRoute.songDetail` needs a full `Song` value, not just an ID); otherwise the row is inert content only.
- **Typed scope, no navigation bridge (landed 2026-09-28):** `AppRoute.rivalDetail(rivalId:name:scope:)` carries a `RivalScope?` directly (`.song(instruments:)`, `.leaderboard(instrument:rankBy:)` or `.combo(token:instruments:)`); `FestivalSession.rivalDetail(forScope:rivalId:visibleInstruments:)` (`App/FestivalSession+Rivals.swift`) resolves it — merging instruments via `combinedRivalDetail` (song source, sequential rather than a `TaskGroup` to avoid capturing the `@MainActor` session in a `@Sendable` closure), reading `leaderboardRivalDetail` (leaderboard source) or `rivalComboDetail` (combo source). Scope tokens come from `RivalDetailScopes` (below); a `nil` scope (deep link, cold start, `DebugLaunchRoute` with no scope, or `FindRivalSheet`'s arbitrary search result) reads the Settings scopes instead of failing. The earlier `RivalNavigationBridge` singleton this screen read is gone — see [rivals/ios.md](../rivals/ios.md).
- **Web scope and query parity (#95, 2026-10-02):** `RivalDetailScopes` (`FestivalCore/RivalDetailScopes.swift`) ports `resolveRivalCombos`/`deriveRivalScope(s)FromSettings`. Every Rivals hub row (Common, Combo and per-instrument sections) opens with `hubScope(visible:)` = the Settings combo, else the first visible instrument, else `Solo_Guitar` (web `RivalsPage.navigateToRival`). All Rivals keeps its list's scope; Compete keeps its instrument; `nil` (Find Rival/deep link) reads `settingsScopes` (pad combo, Pro Strings combo, `pro_drums`) with `allowLiveFallback=true`. The query is the web's `limit=0&sort=closest` (`offset` only when > 0). Multi-scope reads merge with `RivalDetailResponse.combined` and fail only when every scope fails (`fetchCombinedRivalDetail`).
- **Publish-freeze fallback (#95):** while the service publishes, detail answers 503 for any key not already in its `RivalsCache` this publication (see [spec.md](spec.md)). On a 503 (`publicReadFrozen`/`unavailable`), `FestivalSession.rivalDetail(forScope:…)` rebuilds the comparison from the prewarmed `/rivals/all` samples (`RivalDetailFallback`, `source: "rivals-all"`, titles from the catalogue, `rankDelta = rr − ur`, closest-sorted). Without samples for that rival it rethrows, so the page keeps `ServiceStatusView`'s auto-retry and Retry Now (HIG `writing.md`: "Provide clear next steps on any blank screens, with a button or link if possible"; `loading.md`: "Show something quickly"). Shared Swift: the same path serves iPadOS, iPhone Duo and macOS.
- Still not requested: `includeGaps`, so `songsToCompete`/`yourExclusiveSongs` only populate when the service already computed them.
- **Category "View All" (#321, 2026-10-06):** each category card ends (inside the card as its `action:`, #382, as the Rivals hub's View All Rivals) with `PurpleActionLink(title: "View All", …, card: category.title)`, the shared [view-all-cta](../../patterns/view-all-cta.md) button, spoken "View All, <category>". The private white `RivalViewAllRow` is gone, and the copy is never "See All" (`section-headers/apple-see-all-copy` guard). The Duo rivalry pane's cards (`RivalDualDetailPane`) do the same. HIG Buttons: hit region "at least 44x44 pt"; "use a few words in title-style capitalization" (`references/hig/buttons.md`).
- **Song cards: art and status pills (#558, 2026-10-09).** Every song row is the shared `RivalSongRowContent` ([rival-rows](../../patterns/rival-rows.md)): the song's album art (shared `ArtworkTile`, 44 pt, from the `songsById` catalogue lookup, decorative and hidden from VoiceOver) leads the row, above the instrument icon when there is one; the column is vertically centred, so art alone sits in the middle. The bottom line is two `RivalStatusPill`s, "#rank You" and "#rank Rival", green for the leader and red for the trailer (neutral when tied; agent decision rival-rows R3, owner may override with `/choose`). One VoiceOver element reads "Song, you rank 12, Rival ranks 13, you lead"; the pills stack and wrap at accessibility sizes. HIG Color: "Avoid relying solely on color" (should); HIG Typography: "Keep text truncation to a minimum as font size increases" (should) (`references/hig/color.md`, `typography.md`). Shared Swift: Rivalry, the Duo `RivalDualCategoryCard`, iPad and Mac get the same row.
