# Solo leaderboard — iPhone notes

> **What:** iPhone implementation state and decisions for the Solo chart. **Read when:** changing the Solo page on iPhone. Behavior: [spec.md](spec.md).

- Implemented: 25-row pages via the shared `RankingsPagerView`: since operator batch 7.5 the web's `FixedLeaderboardPagination` — one centred row of 44 pt frosted circle arrows (first, previous, next, last; spoken "First page" etc.) around a "page / total" badge (opaque frosted plates). Since issue #93 the pager and footer float with no band behind them; see the issue #93 bullet. Same `fst.song-leaderboard.page-*` IDs; the badge keeps its "1 / N" label.
- Nav chrome (operator batch 7.2, Lane AP5): the song header (art, title, artist, instrument icon + label / entry total) is the List's first row with no card behind it; once it scrolls under the bar a `.principal` item fades in with 28 pt art, the title and the instrument (`fst.song-leaderboard.pinned-title`, hidden from VoiceOver until then), like Song Detail. The List's own offset decides it (`songHeaderScrollAway`, issue #315 review): the header row's geometry stopped reporting when the List recycled the row, so the title never pinned. Rows use the one leaderboard row design (48 pt glass `RankingRowSurface`, player row web purple, bold rank and name, in-card chevron). Long names stay on one line and scroll (`LeaderboardNameText`, issue #292; they used to wrap and grow the row); see [leaderboards/ios.md](../leaderboards/ios.md). Rows are buttons that append to the tab's path rather than `NavigationLink`s, so the List draws no second disclosure indicator outside the card. The header has no card and, since issue #293, no gradient band either: like Song Detail's header it sits straight on the shared dimmed song backdrop (`festivalBackground(.song)`), which keeps it legible, 20 pt below the bar edge. The page-1 audit's unidentified (frame nil) contrast issues come from rows dimmed by the bottom fade (issue #93: a hard cut instead of the fade reports none), so `auditSoloPage` accepts contrast only inside that band.
- Rows now navigate: tapping opens `AppRoute.player`, or `.statistics` for the currently selected player — closing the previously-open "rows cannot open player profiles" gap. `SongLeaderboardEntryRow`'s own initializer is unchanged, so Song Detail's preview keeps working.
- Accuracy/FC via the shared row ([score-accuracy/ios.md](../../controls/score-accuracy/ios.md)); the full List keeps separate row and `fst.score.accuracy.*` IDs.
- **Song title fills the width (issue #315, pattern [song-header](../../patterns/song-header.md)):** the header is the shared `SongHeaderRow` (also the Band Song Leaderboard's); its title, artist and instrument/entries lines come from `SongHeaderText` (title `.title3.bold()`): each is one line that fills the width beside the 80 pt art and scrolls with `MarqueeText` only when it overflows, in lockstep (`marqueeSync`, web `SongInfoHeader`). A plain wrapping `Text` beside a `Spacer` wrapped "Through the Fire / and Flames" beside empty space. Reduce Motion tail-truncates; accessibility sizes wrap (HIG `typography.md`, *should*: "Keep text truncation to a minimum as font size increases"; `accessibility.md`: "reduce automatic and repetitive animation"). The pinned bar title is the shared `SongBarTitleToolbarItem` (`SongBarTitle`, instrument caption), as wide as the bar leaves between its items (no fixed cap; HIG `toolbars.md`, *should*: define what moves to overflow as width narrows). Debug: `FST_DEBUG_SONG=<title or id>` with `FST_DEBUG_SONG_INSTRUMENT=<Solo_Guitar…>` pushes this page directly. Tests: hosted `SongHeaderTextTests` (one line, full width, AX wrap, bar-title width, List scroll-away); iOS `SongHeaderJourneyTests` (landscape, `--long-titles` fixture: the pinned title spans the bar). The pinned bar title is iOS/iPadOS only; the Mac keeps its window title so trailing toolbar actions never move to overflow (song-header R4, macOS decision).
- AccessibilityXXXL: the fixed song header left no usable List viewport and `99,900` wrapped into `99,90` + `0`. The header/disclosure now scroll above scores inside the same List, and rank/name, whole score and accuracy each get a full-width line; ordinary sizes keep compact columns.
- A live probe decoded one real 25-row Lead chart (2026-09-25); tapping into a live Solo page on device is not yet shown.
- **Selected-player spotlight (Lane L2, 2026-09-28):** the selected player's row gets an accent-purple border overlay when it's on the current page (`.overlay { RoundedRectangle.stroke(BrandTokens.accentPurple) }` at the `SoloLeaderboardScreen` call site — `SongLeaderboardEntryRow` itself is untouched, so Song Detail's preview keeps working). A pinned footer below the `List` (above `RankingsPagerView`), drawn exactly like a list row so its rank, name, score and accuracy share the rows' columns (operator batch 7.3), shows the selected player's score for *this exact song/instrument* whenever they have one, sourced entirely from the already-loaded `FestivalSession.selectedPlayerScores[song.songId]?[instrument]` — **no extra network read**, matching the web's `playerData.scores.find(...)` (`LeaderboardPage.tsx:88-91`). Tapping the footer opens Statistics, matching the web's footer (`navigate('/statistics')`, `LeaderboardPage.tsx:476-500`). **Native addition beyond web:** when the selected player's row isn't on the visible page, the footer row itself becomes the jump button (`fst.song-leaderboard.spotlight-jump`, label "Your rank, `<ordinal>`. Jump to your position.") and calls `move(to:focusSelected: true)` to re-page straight to it and scroll the row to the centre (issue #307: `SelectedRowAction.footer`, shared with the band board; the on-page footer is `fst.song-leaderboard.spotlight-open`, label "Your rank, `<ordinal>`. Open your statistics.", both from `SelectedRowAction.footerLabel(for:rank:)`). The row is the shared `SelectedScoreFooterRow` (`Features/SongLeaderboard/SelectedScoreFooterRow.swift`), which the band board's footer reuses — the real web footer never repaginates (it's a fixed portal over whatever page is loaded), so this is a deliberate native improvement for a paginated `List`, not parity. IDs: `fst.song-leaderboard.spotlight-footer`, `fst.song-leaderboard.spotlight-jump`, `fst.song-leaderboard.spotlight-open`. VoiceOver: the footer's label names the rank (`RankingFormatting.ordinal`) and the destination; the main list's highlighted row keeps its default combined label (its `.accessibilityElement(children: .contain)` container isn't a good fit for a full-label override — deferred, border-only highlight there for now). Hosted in `SoloLeaderboardSpotlightHostedTests.swift` (visible/highlighted, off-page/jump-control, and no-selection states), built via the real `selectPlayer`/`viewPlayer` path so the score index is never hand-assembled.
- Open: announced page change and stable VoiceOver focus (unchanged by the 2026-09-28 nav pass — `soloLeaderboardVisualStates` was re-run and still passes, which does not by itself certify either); full accessibility-label override for the highlighted main-list row (see above). Warm-offline "last seen scores" banners predate online-only — remove, don't extend.
- **Aligned columns (issue #37):** the page's rows and the pinned footer share one rank and score width (`LeaderboardRowColumns`, [leaderboard row columns](../../controls/leaderboard-row-columns/ios.md)), so `#9`/`#10`/`#1,234` names start on the same x; the season pill shows from 520 pt of chart width (landscape), like the web's viewport rule.
- **Load/reload fade (issue #71):** The Solo leaderboard runs the shared `FestivalReloadGate` on load and on a page change: old results leave at once, the spinner fades in, holds ≥400 ms, fades out (500 ms) and the results fade/stagger in; Reduce Motion swaps instantly. See [iPhone motion](../../design/apple/iphone.md#motion).
- **Floating chrome (issue #93):** four fixes, matching the web's portalled footer and `useScrollFade`.
  - *No title before scroll:* the `.principal` slot keeps a 1×1 hidden placeholder until the header scrolls away. An empty slot let iOS fall back to `navigationTitle` and show "Mister Papi" at the top, unlike Song Detail. The placeholder is not an opacity-0 copy, which failed Dynamic Type audits. `navigationTitle` stays for the back menu and the window title.
  - *No purple band:* the footer and pager sit in a bottom `safeAreaInset` with no background. Content may "scroll and peek through while preserving control and navigation legibility" ([HIG materials](https://developer.apple.com/design/human-interface-guidelines/materials)).
  - *Rows fade beneath the footer:* the shared `bottomChromeFade(chromeTop:distance:in:)` modifier (`Design/BottomChromeFade.swift`, `ScrollEdgeFade.bottom` stops, 36 pt, web `useScrollFade`; [scroll-edge](../../patterns/scroll-edge.md) R1, #305, #308) ends its gradient at the measured chrome top in the `fst.song-leaderboard.page` space. Never build a feature-local `.mask` for it. Reduce Transparency or Increase Contrast makes it a hard cut at the chrome top. This is a manual scroll-edge effect for a custom bar: "With custom bars, you might add one manually if needed" ([HIG scroll views](https://developer.apple.com/design/human-interface-guidelines/scroll-views)). Issue #293 removed the List's former 36 pt bottom content margin, which left a ~50 pt dead band under the last row. The fade now shrinks with the List's remaining scroll (`ScrollEdgeFade.contentOverflow` → `bottomDistance`, read by the modifier's `BottomFadeDistanceReader` through the shared `onScrollEdgeReading`: `onScrollGeometryChange` on iOS 18 / macOS 15+, the platform scroll view on iOS 17 / macOS 14, #308 review), so it is gone at the end of the list, like the web's `atBottom`. A frame reader on the last row did not work: List cells did not report their moving frame while scrolling, so the resting last row stayed faded.
  - *Legibility:* the pager plates are already opaque. With Reduce Transparency or Increase Contrast, the footer row also gets an opaque `appBackground` backing.
  - *Chrome persists while paging:* the chrome lives outside `FestivalReloadGate` and is built from `shownPayload` (the last loaded page), so only the rows fade or spin. During a load the footer decides "on this page" by rank (`LeaderboardPaging.isSelectedOnPage`).
  - *End spacing (issue #293):* `PinnedChromeSpacing` pads the footer and pager so the last row rests one row gap (8 pt, two 4 pt row insets) above the footer, or above the pager with no selected player or no score here, and the footer rests 8 pt above the pager. On the Duo vertical bar (no pager) the footer keeps 8 pt below it. `RankingsPagerView` takes a `topPadding` (default 8, so other boards are unchanged). HIG [layout](https://developer.apple.com/design/human-interface-guidelines/layout): "Group related information/functions using negative space"; "Prefer scroll-edge effects to solid/semi-opaque backgrounds beneath controls."
  - *Shared with every board (issue #305):* the mask and `BottomFadeDistanceReader` moved to `bottomChromeFade` (`Design/BottomChromeFade.swift`), also used by Full Rankings, the band song leaderboard and Band Rankings, which had no fade (that was the issue's "no player score" case: band boards never show a footer). The fade never depended on the footer here. `body` reads `bottomChromeTop` and passes it in. The reader now uses `visibleRect.height`, which equals the List's `containerSize` (same behaviour here) but not a `ScrollView`'s ([full-rankings/ios.md](../full-rankings/ios.md)). Rechecked live with SFentonX (Zombie, Lead, #503 footer): unchanged.
  - *Tests:* `ScrollEdgeFadeTests` (including `bottomFadeDistanceShrinksAtListEnd`, `pinnedChromeKeepsRowGap`). Checked live on iPhone with SFentonX (24K Magic, Lead).
- **Player row fades with the others (issue #295):** each non-selected row drew its own Liquid Glass card, and under a live `glassEffect` those rows skipped their `detailStaggeredFadeIn` and showed with the reload gate's reveal. The selected player's purple row has no card, so it alone ran its stagger (0.625 s on row 5) and arrived after the rows below it. `RankingRowSurface` now draws `festivalRowCard(cornerRadius: 12)` (the Songs material card, fitted to the same glass look), so every row runs one reveal in order; Reduce Motion still shows them at once. HIG Materials: "Don't use Liquid Glass in the content layer. Use standard materials for content-layer elements" ([liquid-glass.md](../../design/apple/liquid-glass.md)); HIG Motion: motion stays brief, consistent and optional. The pinned footer is unchanged (issue #93). Checked live on iPhone (SFentonX, Don't Fear the Reaper, Lead).
- **One selected-row rule (issue #307):** solo and band boards treat the selected profile's row alike (`SelectedRowAction` in FestivalCore). A selected row shown *apart* from the page (Song Detail's appended row, or a footer while the row is on another page) jumps to its position: the page containing its rank, with the row highlighted and scrolled to the centre (`SelectedRowReveal`: after the first rows' fade-in, instant under Reduce Motion). A selected row already on screen opens the profile: Statistics for a player, Band Detail for a band. Every other row opens that player or band. HIG [lists and tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables): "Provide appropriate selection feedback"; HIG [VoiceOver](https://developer.apple.com/design/human-interface-guidelines/voiceover): "Provide alternative labels for all key interface elements"; footer labels name the destination (`SelectedRowAction.footerLabel(for:rank:)`: "Jump to your position" / "Open your statistics" / "Jump to your band's position" / "Open band"). Both boards pin their footer with the shared `SelectedScoreFooterRow`. The Solo board takes `focusSelected` on `.songLeaderboard`; tests: `selectedFooterJumpsOffPageAndOpensProfileOnPage`, `selectedFooterLabelsNameTheDestination`, `previewRowsRouteToProfilesLikeTheWeb`.
