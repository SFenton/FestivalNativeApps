# compete (`/compete`) — iPhone notes

> **What:** iPhone implementation state and decisions for the Compete phone hub. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/compete/CompetePage.tsx`. This is the phone tab shown once a player is selected (`FestivalSection.compete`, wired up by Lane A's `FestivalRootView`); `CompeteScreen` receives `festivalRootChrome` from `FestivalRootView.tabStack(_:)` externally and must not apply it again itself.

- Implemented: `CompeteScreen` (`Features/Compete/CompeteScreen.swift`) with two `FestivalSectionHeader` groups:
  - **Leaderboards** — `CompeteInstrumentLeaderboardSection` per Settings-visible instrument: a live Top-5 `totalscore` preview via `session.rankings(instrument:rankBy:page:pageSize:)`, reusing Lane L's `AccountRankingRow`/`RankingsSkeletonRows`/`RankLoadState` (`Features/Leaderboards/RankingsSupport.swift`) so the cards render identically to `LeaderboardsScreen`'s own overview cards. "View Full Leaderboard" pushes `AppRoute.fullRankings(instrument:rankBy: "totalscore")`.
  - **Rivals** — reuses `RivalInstrumentSongCard` from `Features/Rivals/RivalsScreen.swift` (the card `RivalInstrumentSongSection` draws on the Rivals hub, fed by `CompeteHubModel`; same per-instrument rivals preview, "View All Rivals" push) for every Settings-visible instrument, passing `emptyMessage: "No rivals found for \(instrument.label) yet."` (matches the web's `compete.noRivalsSubtitle`) so an empty result renders that sentence instead of hiding — unlike `RivalsScreen`, which leaves `emptyMessage` nil and hides empty per-instrument sections (fixed 2026-09-28: previously Compete's "Rivals" header could show with nothing under it when every visible instrument had no rivals).
  No player selected → `RivalsChooseProfileState`.
- **Your rank row jumps to the board (#370, 2026-10-08; owner-approved variant of [leaderboard-row](../../patterns/leaderboard-row.md) R7):** when the selected player ranks outside a card's Top 5, their own highlighted row follows it (web `CompetePage` `playerEntry`). `CompeteHubModel` reads it (`session.playerInstrumentRanking`, allowlisted `/api/rankings/{instrument}/{accountId}`) with the preview, inside the same page gate, so the card reveals with it; unranked or a failed read shows no row, as on the web. Unlike the web, which links it to the profile, it opens `AppRoute.fullRankings(instrument:rankBy: "totalscore", page:, focusSelected: true)` on the page holding the rank (`CompetePreviewSpotlight`, `SelectedRowAction.preview` with `FullRankingsScreen.pageSize`), where `FullRankingsScreen` reveals the row through `SelectedRowReveal`; rank 0 opens Statistics. VoiceOver: "Your rank, 45th. Jump to your position." The Top 5 rows, the selected player's included, still open profiles. The card's column plan includes the row (web `computeRankWidth` with `playerEntry`). The iPhone hub, iPad and Mac (same `CompeteScreen`) and the Duo carousel (`CompeteDualSource.swift`) share the section. HIG: Lists and tables "Provide appropriate selection feedback"; VoiceOver "be sure to keep labels current as interface and content change". Tests: `competePreviewShowsYourRankRowThatJumpsToYourPosition` (hosted), `competePreviewSpotlightOpensThePageWithTheRank`, `competePreviewSpotlightWithoutRankOpensStatistics`, `SelectedRowRevealHostedTests` `fullRankingsArrival`.
- Simplified vs. web this pass: no settings-derived multi-instrument "combo" ranking scopes (`resolveSupportedRankingScopes`), only single-instrument scopes. `CompeteInstrumentLeaderboardSection` reuses Lane L's *components* (read-only) but is this lane's own file/type — no edits to `Features/Leaderboards/**`. Compete intentionally does **not** adopt Rivals' Common Rivals/Combo sections — matches both this screen's own prior scope and the web's `CompetePage`, which has neither.
- **Quick Links + toolbar chrome (landed 2026-09-28):** Compete is a genuine `TabView` root (unlike Rivals, Rival Detail and Rivalry, which are reached as pushed pages from the drawer), so it follows the [Toolbar order rule](../../controls/app-navigation/ios.md#toolbar-order-rule-tab-roots) fully: `QuickLinksToolbarItem` (default `.topBarTrailing` placement) precedes `FestivalRootTrailingItems(session:)` in its own `.toolbar`, and the whole view applies `.festivalProvidesRootTrailingItems()` so the shared bell/avatar capsule stays rightmost. Two coarse sections register on the section containers themselves (not per-instrument): `leaderboards` "Leaderboards" (`trophy.fill`) and `rivals` "Rivals" (`person.2.fill`). `RivalInstrumentSongCard` (shared with `RivalsScreen`) is instantiated with `registersQuickLink: false` here so its own per-instrument tag doesn't also register into Compete's coarser controller. Verified live via `tools/ios_sim.py drive --route compete` + `tap:fst.quick-links.open`: the menu shows exactly "Leaderboards"/"Rivals", and the bell/avatar capsule stays at the trailing edge.
- **One leaderboard design (operator batch 7.4/7.6/7.7, Lane AP5):** no card around a preview; each row its own material card (`AccountRankingRow(cardSurface: true)`, issue #291, the selected player's web purple, bold), long names scroll in place (`LeaderboardNameText`, issue #292; see [leaderboards/ios.md](../leaderboards/ios.md)), and "View Full Leaderboard" is the shared purple `PurpleActionLabel`.
- **Loading (#354, 2026-10-08; supersedes the per-card spinners of #35):** the page loads like web `CompetePage` (`usePageTransition` waits for every leaderboard and rivals query, or for every leaderboard to fail) through the shared `FestivalReloadGate` ([load-transition](../../patterns/load-transition.md) R1, like `LeaderboardsScreen`). `CompeteHubModel` (`Features/Compete/CompeteHubModel.swift`) owns every Top-5 and rivals read; `CompeteLoadProgress` (FestivalCore) decides readiness. Until then the page shows one centred `FestivalLoadingView` (VoiceOver "Loading Compete", `fst.compete.loading`), with no section or instrument headers and no cards. The spinner then fades and the Leaderboards header, each instrument card, the Rivals header and each rivals card fade in on one reading-order stagger, inside a `festivalFadeInScope()` so a scroll rushes the rest (R5). Agent decision: the stagger runs per section (an instrument's header, rows and button fade as one item), like the Leaderboards overview cards, rather than per row as on the web and Android; with the 8-item cap the visible difference is small. Every leaderboard failing replaces the page with `ServiceStatusView` "Compete unavailable" (web `allLeaderboardsErrored`); a single failed card keeps its `ServiceStatusInline` error. A card's Retry, its auto-retry or the page Retry re-reads only what did not load and reruns the gate's swap, so no card ever spins under its header (same as Android). The cards (`CompeteInstrumentLeaderboardSection`, `RivalInstrumentSongCard`) are presentational and never show a spinner. The Duo carousels (`CompeteDualSource.swift`, shelved with dual-source) read the same model and stagger the same way (#354 review): inside `festivalNestedFadeInScope()`, the Leaderboards pane header, its on-screen cards, the Rivals pane header and its cards fade in in reading order (`CompeteDualSourceEntrance`, through `DualSourcePane(entranceIndex:)` and `HorizontalCarousel(entranceIndex:)`), and a swipe rushes the rest. The Rivals header's index counts the leaderboard cards on screen, computed from `DualSourceLayout`'s region width (`dualSourceRegionWidth`) on the pane's first build, so the first scheduled fade is already right (the fade never reschedules). The Duo inline title is set on the hub, outside the gate, so the title doesn't jump from large to inline when the spinner gives way (`CompeteTitleDisplayMode`). HIG basis: Loading ("Use progress indicators when loading takes more than a moment"), Progress indicators ("Consistent location — pick a spot and use it consistently"), Motion ("Add motion purposefully"; Reduce Motion is handled by the gate). Tests: `CompeteLoadProgressTests`; hosted `competeScreenShowsOnePageSpinnerUntilEveryReadSettles` (fails on the old per-card spinners), `competeScreenShowsPageErrorWhenEveryLeaderboardFails`, `competeDuoPanesLoadBehindOneSpinnerThenStagger` (Duo panes), `CompeteDualSourceEntranceTests`.
- **Back keeps the page (#39, 2026-10-01; one page key since #354):** `CompeteHubModel` remembers its fully loaded `CompetePageLoadKey` (visible instruments, selected account, publication revision) in a `ReappearanceLoadGate`, so a return shows the page at once, with no spinner. Back from View Full Leaderboard or a rival page therefore keeps the rows, the layout and the scroll position. Before the fix, `.task(id:)` restarted on reappearance and reset each card to its spinner, so every card collapsed, re-expanded and faded in again under the pop. A failed or cancelled load still retries on return, and a new publication or account reloads. Tests: `competeKeepsLoadedLeaderboardsWhenItReappears` (hosted; fails without the gate) and `ReappearanceLoadGateTests`. See [architecture](../../platforms/apple/architecture.md#reappearance-keeps-loaded-content).
- **No Leaderboards overview link (#36, 2026-10-01):** the web's `CompetePage` links each scope only to its own full board (header "See All" and "View Full Leaderboards" → `Routes.fullRankings`); it never links to the overview. The iPhone hub's extra "Leaderboards Overview" row and the Duo carousel's Overview card and Leaderboards-pane See All were removed. Each instrument's "View Full Leaderboard" still pushes `AppRoute.fullRankings`; the overview stays in the drawer, like the web sidebar. HIG basis (Designing for iOS): "Limit onscreen controls to keep primary content and tasks prominent". Tests: `CompeteRenderTests` and `competeDualShowsLeaderboardsAboveRivals` assert the label is absent; `RivalsJourneyTests.testCompeteHasNoOverviewButtonAndViewFullLeaderboardPushesFullRankings` taps through to "Lead Rankings". In XCUITest the section's container identifier overrides the link's `.view-all` identifier, so match the "View Full Leaderboard" label.
- **Songs column fits or hides (#38, 2026-10-01):** on a portrait iPhone the songs played/total column squeezed usernames (the bold selected name truncated, e.g. "Fixture Play…"). Each leaderboard card now shows songs only when its longest name fits beside them; otherwise the whole card hides them, so columns stay aligned, and VoiceOver reads them as the row's value. Mechanism and tests: [leaderboard-row-columns/ios.md](../../controls/leaderboard-row-columns/ios.md). HIG basis: Lists and tables "Keep item text succinct."; Typography "Where width is constrained, inline items … can crowd text into truncation or overlap".
- Known pre-existing quirk: the card's outer `accessibilityIdentifier` (`fst.compete.leaderboard-card.<instrument>`) overrides the inner `.view-all` ID on device, so drive scripts must tap "View Full Leaderboard" by label.
- IDs: `fst.compete.loading` (page spinner), `fst.compete.leaderboard-card.<instrument>`, `fst.compete.leaderboard-card.<instrument>.view-all`, `fst.compete.leaderboard-card.<instrument>.spotlight` (your rank row; on device the card ID may override it too, so tap it by its label); rival rows reuse `RivalRowContent`'s combined accessibility label with no additional identifiers.
- Tests: covered indirectly by `RivalsTests.swift` (Rivals Core models/endpoints) and Lane L's `RankingsTests.swift` (Rankings Core models/endpoints), and `CompeteLoadProgressTests`; the hosted `CompeteRenderTests` cover the cards. `tools/ios_sim.py shot`/`drive --tab compete` verified real Top-5 rows and rival previews against the live public service (2026-09-28).
- Leaderboard previews use `InstrumentSectionHeader` (web SM, 36 pt icon) above each card; the page's stagger fades each card in once the page loads (#354).
