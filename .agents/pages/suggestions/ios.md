# Suggestions — iPhone notes

> **What:** iPhone implementation state and decisions for the Suggestions tab. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (still a stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/suggestions/SuggestionsPage.tsx`, `.../suggestionsHelpers.ts`, `.../modals/SuggestionsFilterModal.tsx`, `.../components/{CategoryCard,VirtualizedSuggestionsList,SuggestionsLoadSentinel}.tsx`; core algorithm `packages/core/src/suggestions/{suggestionGenerator.ts (2221 lines),suggestionFilterConfig.ts}`. Suggestions are entirely client-computed from the catalogue (`GET /api/songs`) and the selected player's own compact score index (`GET /api/player/{accountId}`) — both pure, keyless, already-fetched reads; no suggestion-specific endpoint exists.

## Implemented

- **`FestivalCore/SuggestionGenerator.swift`**: a from-scratch Swift port of the web `SuggestionGenerator` class — same seeded PRNG (Mulberry32, bit-for-bit via `SeededSuggestionRng`), same anti-repetition session state (`sessionShownSongs`, per-category `used` history, skip-streak-smoothed `shouldEmit` probability table), same `selectNewFirst` new-first-with-fallback selection, same decade-variant re-titling (`buildDecadeVariant`). Ported category families: `near_fc_any`/`near_fc_relaxed`/`unfc_<instrument>`/`samename_nearfc`, star progress (`almost_six_star`/`star_gains`/`more_stars`), unplayed (`unplayed_any`/`unplayed_<instrument>`/`first_plays_mixed`), `variety_pack`, `artist_sampler_*`/`artist_unplayed_*`, `samename_*`, `almost_elite(+instrument)`, `pct_push(+instrument)`, `stale_global_N`/`stale_<instrument>_N`, percentile improvement (`same_pct_improve`/`same_pct_<bucket>`/`pct_improve_<bucket>`/`pct_improve_<instrument>_<bucket>`/`improve_rankings_<instrument>`), `near_max_<5k|10k|15k>` (CHOpt theoretical-max-score gap, `nearMaxCandidates`/`nearMaxScore`/`nearMaxScoreDecade`, using `Song.maxScore(for:)` landed in `0dfd1e1`) — each with its decade sibling where the web has one — and, landed this pass, the ten `song_rival_*` pipelines (see below).
- **Rival-driven suggestions (`song_rival_*`), landed this pass**: `FestivalCore/SuggestionRivalData.swift` ports `buildRivalDataIndexFromRivalsAll` (`FortniteFestivalWeb/src/utils/suggestionAdapter.ts:165`) as `RivalDataIndex.build(from:combo:limit:)`, building `RivalInfo`/`RivalSongMatch`/`RivalDataIndex` (`songRivals`, `byRival`, `closestRivalBySong`) straight from `RivalsAllResponse` (`FestivalAPI.rivalsAll(accountId:)`, landed by Lane K). `SuggestionGenerator.setRivalData(_:)` mirrors the web method exactly: called before the pipeline list is built (the normal native flow — see `FestivalSession+Suggestions.swift` below), the ten rival pipelines join the one startup shuffle like every other family; called after (a slow fetch resolving once a page is already showing), it shuffles just the rival pipelines and splices them at the front of the remaining queue. Ported pipelines: `songRivalGap`/`Protect`/`Slipping`/`Dominate` (per-rival rank-delta thresholds), `songRivalBattleground` (2+ rivals clustered within 10 ranks — Swift iterates its two internal dictionaries in *sorted key* order rather than the web's Map insertion order, since Swift's per-process hash-seed randomization makes dictionary order non-reproducible across launches; deterministic within one run, same caveat as `near_max_*` below), `songRivalSpotlight` (curated per-rival mix — the one family gated only on "already emitted," no `shouldEmit` roll, ported as-is), and the four cross-pollination families `songRivalNearFc`/`Stale`/`StarGains`/`PctPush` (annotate an existing near-FC/star/percentile-push/stale candidate with its closest rival). `SuggestionSongItem` gained `rivalName`/`rivalAccountId`/`rivalRankDelta` (web's same three fields) for these; `SuggestionCategoryType.songRivals` is the one new filter type (label "Song Rivals").
- **`lb_rival_*` ("Leaderboard Rivals") is not ported — and isn't real on the web either.** `suggestionFilterConfig.ts` reserves a `LeaderboardRivals` filter type and an `lb_rival_*` key prefix, and `RivalDataIndex` carries matching `leaderboardRivals`/`leaderboardRivalIndex` fields, but `buildRivalDataIndexFromRivalsAll` always leaves those empty and `SuggestionGenerator.rivalPipelines()` never calls anything that produces an `lb_rival_*` key (confirmed by searching the web `suggestionGenerator.ts` source for `lb_rival` and for any `leaderboardRival*` builder — none exist). That filter category is consequently dead code on the web today; this port therefore has no `.leaderboardRivals` case at all rather than adding an always-empty one. If the web ever wires up a real leaderboard-rival pipeline, this doc and `RivalDataIndex` are the places to extend.
- Band suggestions (`band_*`) remain unported: Suggestions here is solo-profile only; band mode is a separate `mode: 'band'` branch on the web that needs a selected-band context this app doesn't have.
- **`FestivalCore/SuggestionFilterSettings.swift`**: persisted filter draft mirroring `SuggestionsFilterDraft` — per-instrument visibility plus a global + per-instrument toggle per `SuggestionCategoryType` (13 types now that `songRivals` is ported). Storage is minimal-diff (`Set<String>` of *disabled* keys only), so an untouched filter round-trips to empty `Data`, matching `SongPlayerScoreFilter`'s convention. `SuggestionCategoryFilter.visible(_:effectiveInstruments:filter:)` applies it to already-generated categories in one pass (equivalent to the web's `shouldShowCategory`+`filterCategoryForInstruments`+`shouldShowCategoryType`+`filterCategoryForInstrumentTypes` pipeline), trimming a multi-instrument category's songs rather than always dropping the whole category. The filter sheet iterates `SuggestionCategoryType.allCases`, so `songRivals` needed no UI changes to appear there.
- **`SuggestionsScreen`**: one `FestivalGlassSection` glass card per category (`.agents/design/apple/liquid-glass.md` — "Settings, Profile, Statistics, Suggestions, Rivals, Leaderboard groups: one card per group"), flat rows inside (`SuggestionSongRowView`: artwork tile, title/artist, star row, FC badge, accuracy percent, "Top N%" when a rank is known). `LazyVStack` in a `ScrollView` with `onAppear`-triggered `loadMore()` on the third-from-last visible card (web "virtualized incremental loads"), 10 categories per page (`SuggestionsViewModel.pageSize`). Toolbar filter button (gold tint when `filter.isActive()`) opens `SuggestionsFilterSheet` (`.festivalSheet(.large)`, staged draft + Apply/Cancel-with-discard-confirmation). Cancel/Apply are semantic `.cancellationAction`/`.confirmationAction` toolbar items (app modal standard, fixed 2026-09-28 from a custom `safeAreaInset` footer), not `SongsFilterSheet`'s still-custom one. "Start New Mix" button once a mix is exhausted (`SuggestionGenerator.resetForEndless()`). Rows push `AppRoute.songDetail(item.song)`.
- **`FestivalSession+Suggestions.swift`**: `SuggestionsViewModel` owns one `SuggestionGenerator` per (selected accountId, catalogue's observed publication) pair; changing either invalidates and rebuilds it (fresh mix, matching the web's `suggestionCacheKey`). Changing the filter only re-derives `visibleCategories(appVisibleInstruments:)` from the already-generated list — no regeneration, matching the web's separate generation/filtering split.
- **Card parity pass (2026-09-28, Lane AP2):** `SuggestionCategoryCardView` follows web `CategoryCard`: title, description and the category's instrument icon (`SuggestionRowLayout.categoryInstrument`, 36 pt) sit above the glass card; rows show art, title and "artist · year" (web `SongInfo`), then metadata by `SuggestionRowLayout.forCategory` (web `getRowLayout`): instrument status chips, row instrument icon (+ `StarRating` on `star_gains*`), percentile pill + icon, season pill (current season highlighted), accuracy badge (floored, max 99%), rival badge (`#4285F4`) + signed delta + icon, or nothing for discovery lists. Metadata wraps to a right-aligned second line on compact widths unless it is only an icon/pill (web `twoRow`/`iconOnly`). Rows fall back to the category instrument for their icon, since web items carry it. Cards fade in staggered 125 ms. The filter sheet now applies each toggle live (`onChange`), with a single trailing Done (`fst.suggestions.filter.done`) in the `festivalSheet` look; no Cancel/Apply/discard dialog.
- **Rival name badge, native deviation (2026-10-01, issue #29):** single-rival cards (`song_rival_spotlight_`/`gap_`/`protect_`/`slipping_`/`dominate_`) name the rival in their title, so rows drop the web's per-row name badge and show only the signed delta + icon (`SuggestionRowLayout.showsRivalName`). Mixed-rival cards (`song_rival_battleground` and the cross-pollination families) keep the badge. When the badge is hidden, the delta's VoiceOver label names the rival ("1 rank behind TempoTide", `rivalDeltaAccessibilityLabel`), so each combined row still says which rival it is about.
- **Batch fade (issue #30):** only newly generated cards fade. `SuggestionsViewModel` bumps `batchGeneration` and records `latestBatchIds` per batch; `FadeStagger.batchIndexes` staggers that batch in display order (125 ms, first ~8) until it settles. Cards from earlier batches, or rebuilt by the `LazyVStack` while scrolling, appear without a fade.
- **Filter and Search stay in the bar (issue #13):** both are real `.topBarTrailing` toolbar items (Filter before `FestivalRootTrailingItems`), so they stay anchored in the navigation bar row at the top and while scrolled; the large title collapses under them and returns at the top natively. The system omits the small inline "Suggestions" title while scrolled because there is no room beside drawer + Filter + Search + bell + avatar (checked on iOS 26.5 and 27); that is expected, not a bar that stopped tracking. A single persistent `ScrollView` and removing `.refreshable` changed nothing. Regression: `SuggestionsJourneyTests/testSuggestionsFilterAndSearchStayInTheBarWhileScrolled` (scrolls with the large fixture as `TEST_RUNNER_FST_SONGS_SCROLL_FIXTURE_URL`).
- States handled: no selected profile (Choose Profile via `\.openProfile`, `StatisticsScreen`'s pattern), scores syncing (202), player load failure (retry), catalogue load failure (retry), initial loading, empty (no scores yet vs. filtered-to-empty), loaded list, exhausted-mix footer.

- **Filter Instrument-Specific accordion (#561):** choosing a chart in the sheet's `InstrumentSelector` grows the section, then its per-chart switches fade in; clearing it fades them out, then the section shrinks; choosing another chart swaps them in place (`festivalAccordion(_:follows:)` on the selector, `FestivalAccordionContent` for the switches; pattern [accordion](../../patterns/accordion.md)). HIG: `disclosure-controls.md`, `motion.md`, `accessibility.md`. Journey: `testSuggestionsFilterInstrumentSelectorRevealsPerInstrumentToggles`.

## Simplified vs. web this pass

- Band categories unported (see above); rival categories (`song_rival_*`) landed this pass, `near_max_*` landed the pass before.
- `RivalDataIndex.build(from:)` is always called with `combo: nil` (every combo merged, web default `limit: 5`) — no instrument-combo picker feeding it, since Suggestions has no such control. `AllRivalsScreen`'s own combo picker is a separate, unrelated control.
- The rival read (`session.client().rivalsAll(accountId:)`) is best-effort and fetched only when the generator itself is (re)built, not on every `ensureLoaded` call — unlike the web's `useQuery`-driven live re-injection (`useSuggestions.ts`'s second `useEffect`, which calls `generator.setRivalData(rivalData)` again whenever the query's data updates), this native port doesn't re-inject fresh rival data into an already-built generator mid-session. `SuggestionGenerator.setRivalData(_:)`'s "already initialized" splice path exists and is unit-tested, but nothing in `FestivalSession+Suggestions.swift` calls it a second time for the same generator yet.
- There's no first-run slide deck (`suggestionsSlides`) and no `SUGGESTIONS_CATEGORY_LIMIT` mix-limit banner distinct from "Start New Mix" — the two are collapsed into one footer state (`hasMore == false`).
- No scroll-position restoration (`suggestionsScrollRestoration.ts`) or cross-tab session cache (`suggestionsSessionCache.ts`) — a fresh mix builds each time the tab's source identity changes.

## Known seam gaps (flagged for the orchestrator, not fixed here)

- ~~`SuggestionsScreen` computes Settings-visible instruments itself~~ — fixed this pass (Lane G2): `FestivalRootView.content(for:)` now passes its `visibleInstruments` into `SuggestionsScreen(session:visibleInstruments:)` like every other `tabStack` hub, and `AppRouteDestination`'s `.suggestions` case (the pushed-route destination, e.g. from the drawer) does the same with its own in-scope `visibleInstruments`. `SuggestionsScreen` no longer reads the nine `fst.settings.show*` keys itself; it derives the filter sheet's ordered `[Instrument]` list from the injected `Set<Instrument>` via `Instrument.allCases.filter(visibleInstruments.contains)` (same technique `LeaderboardsScreen` uses, which still has its own independent `@AppStorage` reads — out of this lane's ownership to fix).
- `SuggestionFilterSettings.storageKey` (`"fst.suggestions.filter"`) is a new persisted `@AppStorage` key; Settings' "Reset Settings" registry (Lane A, `dec1cbf`) should include it alongside `SongPlayerScoreFilter.storageKey` so a full reset clears it too. Still open — Settings is out of this lane's ownership.

## Scroll cost (issue #28)

- Rows rebuilt by the `LazyVStack` draw already decoded covers in their first frame (`FestivalSession.cachedArtwork(raw:maxPixels:)` read in `ArtworkTile.init`), so they skip the spinner and the second layout pass when the async lookup returns.
- A static `MarqueeText` draws its sizing `Text` directly (two texts per marquee instead of three); the overlay track exists only while it scrolls.
- What remains per incoming card is SwiftUI building its five rows and the glass card at once (~20 ms on the Debug simulator with XCUITest accessibility on). XCUITest swipes also add 55–75 ms accessibility snapshots, so judge hitches on a device with Instruments, not from a `drive` trace.

## Tests

`SuggestionGeneratorTests.swift` (Core): 75 tests covering every ported category family — including `near_max_5k`/`10k`/`15k` (first-tier collection, exclusive gap-boundary tiers, its decade variant, and a fixed-seed determinism check), the ten `song_rival_*` pipelines (each family's own gating condition — rank-delta thresholds for `gap`/`protect`/`slipping`/`dominate`, the 2+-rivals-within-10-ranks cluster for `battleground`, the emitted-only gate for `spotlight`, the closest-rival annotation + underlying predicate for the four cross-pollination families — plus "no rival categories without rival data," the late-`setRivalData` splice path, and a fixed-seed determinism check for `song_rival_gap`) — RNG determinism, session anti-repetition (no-repeat within a mix, exhaustion, `resetForEndless`), decade-variant retitling/isolation, the `shouldEmit` skip-streak force-emit path, and `selectNewFirst`'s exhausted-history reset — 95.71% line coverage (SuggestionGenerator.swift alone; `RivalDataIndex.build`'s five own tests live in the same file). `SuggestionFilterSettingsTests.swift` (Core): defaults/persistence/toggle-cascade/category-filtering, generic over `SuggestionCategoryType.allCases` so `songRivals` is covered without any test changes — 100% line coverage. `SuggestionModels.swift`: 97.14%. `SuggestionRivalData.swift`: 97.06%. Combined Suggestions-Core line coverage 96.13% (`xcrun llvm-cov report` against `FestivalCoreTests.xctest`, 2026-09-28), above the 95% lane bar.

Rival-fixture note: `song_rival_*` pipelines still run `shouldEmit`/`selectNewFirst` against the *shared* `sessionShownSongs` set, so a bare all-zero-score fixture song is prime "unplayed" bait for an unrelated generic pipeline (see this file's own top-of-file comment on redundant/inert fixtures) — `inertRivalSong(s)` (a six-star full-combo song on every chart, safe from every generic predicate) covers the rival families that don't need a real predicate-matching score (`gap`/`protect`/`battleground`/`slipping`/`dominate`); the four cross-pollination families still need a real matching score, so those use `signalSongs` with enough redundant candidates to outlast the generic families matching the same shape.

On "PRNG parity": the web's own guarantee is that a fixed Mulberry32 seed reproduces a fixed shuffle order for a fixed source, not that native and web emit byte-identical output — the two `ensurePipelines()` pipeline lists were already built in different shapes before this pass (native nests several per-instrument families inside one `for instrument in Instrument.allCases` loop; the web appends per-instrument families as separate flat sections), so their pre-shuffle index order — and therefore which category lands at which shuffled position for a shared seed — already diverged prior to this lane. `nearMaxScoreIsDeterministicForAFixedSeed`/`songRivalGapIsDeterministicForAFixedSeed` verify the practically achievable, testable form of that guarantee from Swift alone: same seed + same source ⇒ identical category contents on repeat. A literal cross-language diff would need a much larger pipeline-ordering refactor, out of this lane's narrow scope. `songRivalBattleground`'s two internal dictionaries add one more native-only ordering difference (sorted-key iteration instead of the web's Map insertion order — see "Implemented" above); its own determinism only needs the same-process guarantee, which sorted-key iteration still gives.
