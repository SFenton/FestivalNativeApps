# Suggestions — iPhone notes

> **What:** iPhone implementation state and decisions for the Suggestions tab. **Read when:** changing this page on iPhone. Behavior: [spec.md](spec.md) (still a stub — this file is the source of truth for what's actually built until spec.md is promoted).

Source: `FortniteFestivalWeb/src/pages/suggestions/SuggestionsPage.tsx`, `.../suggestionsHelpers.ts`, `.../modals/SuggestionsFilterModal.tsx`, `.../components/{CategoryCard,VirtualizedSuggestionsList,SuggestionsLoadSentinel}.tsx`; core algorithm `packages/core/src/suggestions/{suggestionGenerator.ts (2221 lines),suggestionFilterConfig.ts}`. Suggestions are entirely client-computed from the catalogue (`GET /api/songs`) and the selected player's own compact score index (`GET /api/player/{accountId}`) — both pure, keyless, already-fetched reads; no suggestion-specific endpoint exists.

## Implemented

- **`FestivalCore/SuggestionGenerator.swift`**: a from-scratch Swift port of the web `SuggestionGenerator` class — same seeded PRNG (Mulberry32, bit-for-bit via `SeededSuggestionRng`), same anti-repetition session state (`sessionShownSongs`, per-category `used` history, skip-streak-smoothed `shouldEmit` probability table), same `selectNewFirst` new-first-with-fallback selection, same decade-variant re-titling (`buildDecadeVariant`). Ported category families: `near_fc_any`/`near_fc_relaxed`/`unfc_<instrument>`/`samename_nearfc`, star progress (`almost_six_star`/`star_gains`/`more_stars`), unplayed (`unplayed_any`/`unplayed_<instrument>`/`first_plays_mixed`), `variety_pack`, `artist_sampler_*`/`artist_unplayed_*`, `samename_*`, `almost_elite(+instrument)`, `pct_push(+instrument)`, `stale_global_N`/`stale_<instrument>_N`, percentile improvement (`same_pct_improve`/`same_pct_<bucket>`/`pct_improve_<bucket>`/`pct_improve_<instrument>_<bucket>`/`improve_rankings_<instrument>`), and `near_max_<5k|10k|15k>` (CHOpt theoretical-max-score gap, `nearMaxCandidates`/`nearMaxScore`/`nearMaxScoreDecade`, using `Song.maxScore(for:)` landed in `0dfd1e1`) — each with its decade sibling where the web has one.
- **Not ported this wave**: rival-driven pipelines (`song_rival_*`, `lb_rival_*`) and band suggestions (`band_*` — Suggestions here is solo-profile only; band mode is a separate `mode: 'band'` branch on the web that needs a selected-band context this app doesn't have). Rivals were re-checked this pass (Lane G2): the web builds its generator's `rivalData` (`RivalDataIndex`, a `closestRivalBySong`/`byRival` cross-instrument index) via `buildRivalDataIndexFromRivalsAll` (`FortniteFestivalWeb/src/utils/suggestionAdapter.ts:165`) from one combined read, `GET /api/player/{accountId}/rivals/all` (`FortniteFestivalWeb/src/api/client.ts:669` — keyless, same shape family as the already-allowlisted per-instrument rivals endpoints). `FestivalAPI+Rivals.swift` on `master` (Lane R2, still landing) only exposes the four per-instrument/per-song reads (`rivalsList`, `rivalDetail`, `leaderboardRivals`, `leaderboardRivalDetail`) — `AllRivalsScreen` itself says as much ("covers the single-instrument song and leaderboard scopes", not the multi-instrument combo view). There is no reusable native read of the combined `/rivals/all` shape yet, so porting `song_rival_*`/`lb_rival_*` stays follow-on work for whichever lane adds that endpoint (likely R2), not something this lane can wire up from what exists today. Not a service-safety concern either way — `/rivals/all` is the same keyless-GET family already on the allowlist.
- **`FestivalCore/SuggestionFilterSettings.swift`**: persisted filter draft mirroring `SuggestionsFilterDraft` — per-instrument visibility plus a global + per-instrument toggle per `SuggestionCategoryType` (12 types now that `nearMax` is ported; rival types remain omitted since they're unported). Storage is minimal-diff (`Set<String>` of *disabled* keys only), so an untouched filter round-trips to empty `Data`, matching `SongPlayerScoreFilter`'s convention. `SuggestionCategoryFilter.visible(_:effectiveInstruments:filter:)` applies it to already-generated categories in one pass (equivalent to the web's `shouldShowCategory`+`filterCategoryForInstruments`+`shouldShowCategoryType`+`filterCategoryForInstrumentTypes` pipeline), trimming a multi-instrument category's songs rather than always dropping the whole category.
- **`SuggestionsScreen`**: one `FestivalGlassSection` glass card per category (`.agents/design/apple/liquid-glass.md` — "Settings, Profile, Statistics, Suggestions, Rivals, Leaderboard groups: one card per group"), flat rows inside (`SuggestionSongRowView`: artwork tile, title/artist, star row, FC badge, accuracy percent, "Top N%" when a rank is known). `LazyVStack` in a `ScrollView` with `onAppear`-triggered `loadMore()` on the third-from-last visible card (web "virtualized incremental loads"), 10 categories per page (`SuggestionsViewModel.pageSize`). Toolbar filter button (gold tint when `filter.isActive()`) opens `SuggestionsFilterSheet` (`.festivalSheet(.large)`, staged draft + Apply/Cancel-with-discard-confirmation, mirroring `SongsFilterSheet`). "Start New Mix" button once a mix is exhausted (`SuggestionGenerator.resetForEndless()`). Rows push `AppRoute.songDetail(item.song)`.
- **`FestivalSession+Suggestions.swift`**: `SuggestionsViewModel` owns one `SuggestionGenerator` per (selected accountId, catalogue's observed publication) pair; changing either invalidates and rebuilds it (fresh mix, matching the web's `suggestionCacheKey`). Changing the filter only re-derives `visibleCategories(appVisibleInstruments:)` from the already-generated list — no regeneration, matching the web's separate generation/filtering split.
- States handled: no selected profile (Choose Profile via `\.openProfile`, `StatisticsScreen`'s pattern), scores syncing (202), player load failure (retry), catalogue load failure (retry), initial loading, empty (no scores yet vs. filtered-to-empty), loaded list, exhausted-mix footer.

## Simplified vs. web this pass

- Rival/band categories unported (see above); `near_max_*` landed this pass.
- Filter sheet edits are staged with a discard-confirmation Cancel, but there's no first-run slide deck (`suggestionsSlides`) and no `SUGGESTIONS_CATEGORY_LIMIT` mix-limit banner distinct from "Start New Mix" — the two are collapsed into one footer state (`hasMore == false`).
- No scroll-position restoration (`suggestionsScrollRestoration.ts`) or cross-tab session cache (`suggestionsSessionCache.ts`) — a fresh mix builds each time the tab's source identity changes.

## Known seam gaps (flagged for the orchestrator, not fixed here)

- ~~`SuggestionsScreen` computes Settings-visible instruments itself~~ — fixed this pass (Lane G2): `FestivalRootView.content(for:)` now passes its `visibleInstruments` into `SuggestionsScreen(session:visibleInstruments:)` like every other `tabStack` hub, and `AppRouteDestination`'s `.suggestions` case (the pushed-route destination, e.g. from the drawer) does the same with its own in-scope `visibleInstruments`. `SuggestionsScreen` no longer reads the nine `fst.settings.show*` keys itself; it derives the filter sheet's ordered `[Instrument]` list from the injected `Set<Instrument>` via `Instrument.allCases.filter(visibleInstruments.contains)` (same technique `LeaderboardsScreen` uses, which still has its own independent `@AppStorage` reads — out of this lane's ownership to fix).
- `SuggestionFilterSettings.storageKey` (`"fst.suggestions.filter"`) is a new persisted `@AppStorage` key; Settings' "Reset Settings" registry (Lane A, `dec1cbf`) should include it alongside `SongPlayerScoreFilter.storageKey` so a full reset clears it too. Still open — Settings is out of this lane's ownership.
- Rival-driven `song_rival_*`/`lb_rival_*` need a native reusable read of `GET /api/player/{accountId}/rivals/all` (see "Not ported this wave" above); none exists in `FestivalAPI+Rivals.swift` yet.

## Tests

`SuggestionGeneratorTests.swift` (Core): 53 tests covering every ported category family — including `near_max_5k`/`10k`/`15k` (first-tier collection, exclusive gap-boundary tiers, requiring catalogue `maxScores` and a positive player score, its decade variant, and a fixed-seed determinism check) — RNG determinism, session anti-repetition (no-repeat within a mix, exhaustion, `resetForEndless`), decade-variant retitling/isolation, the `shouldEmit` skip-streak force-emit path, and `selectNewFirst`'s exhausted-history reset — 96.08% line coverage (SuggestionGenerator.swift alone). `SuggestionFilterSettingsTests.swift` (Core): defaults/persistence/toggle-cascade/category-filtering, generic over `SuggestionCategoryType.allCases` so `nearMax` is covered without any test changes — 100% line coverage. `SuggestionModels.swift`: 96.92%. Combined Suggestions-Core line coverage 96.36% (`xcrun llvm-cov report` against `FestivalCoreTests.xctest`, 2026-09-28), above the 95% lane bar.

On "PRNG parity": the web's own guarantee is that a fixed Mulberry32 seed reproduces a fixed shuffle order for a fixed source, not that native and web emit byte-identical output — the two `ensurePipelines()` pipeline lists were already built in different shapes before this pass (native nests several per-instrument families inside one `for instrument in Instrument.allCases` loop; the web appends per-instrument families as separate flat sections), so their pre-shuffle index order — and therefore which category lands at which shuffled position for a shared seed — already diverged prior to this lane. `nearMaxScoreIsDeterministicForAFixedSeed` verifies the practically achievable, testable form of that guarantee from Swift alone: same seed + same source ⇒ identical category contents on repeat. A literal cross-language diff would need a much larger pipeline-ordering refactor, out of this lane's narrow scope.

No hosted-UI/XCUITest coverage yet (Wave 1 policy: UX tests land at feature completion). `python3 tools/ios_sim.py shot --tab suggestions --env FST_DEBUG_PROFILE=<id>:<name>` against the live public service (2026-09-28) rendered real generated categories; `drive` used to confirm incremental loading and the filter sheet.
