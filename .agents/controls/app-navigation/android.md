# App navigation — Android notes

> **What:** Android shell navigation implementation. **Read when:** changing tabs, rail, drawers or deep links on Android. Spec: [spec.md](spec.md); chrome decisions: [design/android.md](../../design/android.md).

- Tabs from `FestivalTabPolicy` (unit-tested port of Apple's); selected tab derived from the back stack; re-tap pops to root; per-tab history restored except Statistics; a profile change resolves Compete↔Leaderboards slots.
- `NavigationSuiteScaffoldLayout` + `NavigationSuite` with the policy's type (`ui/shell/FestivalApp.kt` `suiteType`): short bar / wide rail (`FestivalRail`) / permanent drawer; modal drawer from the top-bar hamburger (bar layouts) or rail header, gestures only while open. Test tags `fst.nav.bar|rail|rail.profile|permanent-drawer|drawer|drawer-sheet|profile|back|tab.<section>|drawer.<entry>`; Compose tags double as UIAutomator resource ids (`testTagsAsResourceId` on the root).
- **Drawer = web sidebar** (`core/shell/DrawerPolicy.kt`, operator 2026-09-28): Songs · Suggestions* · Statistics* · Rivals† · Leaderboards · Item Shop‡ (* any profile, † player, ‡ unless Hide Item Shop), then a footer with the player row (name → Statistics, **Deselect**) or **Select Profile**, and **Settings last**. A row switches tabs when that tab is visible at this width, else pushes the non-root twin (`LeaderboardsRoute`, `RivalsRoute`, `StatisticsRoute`, `SuggestionsRoute`). No Bands or Licenses rows: Bands is reached from search and leaderboard links, Licenses from Settings. The modal and permanent drawers share `DrawerContent`.
- **Rail**: menu button in a 64 dp header row level with the top app bar, main tabs **top-aligned** directly below it (operator 2026-09-28: opening the drawer reads as the rail expanding), then **Profile** (initials/person glyph → profile sheet) and **Settings** pinned to the bottom edge. No container color (batch 6.19): the backdrop shows through. Material's `WideNavigationRail` content cannot split destinations between top and bottom, so `FestivalRail` is a plain column of `NavigationSuiteItem`s (collapsed wide-rail type, 96 dp). At ≥ 1.3× text every rail item, Profile included, is icon-only; the avatar carries "Profile: <name>" (issue #101).
- **Large text drawer** (issues #101, #102): the permanent drawer is 280 dp, or M3's 360 dp standard drawer width at font scale ≥ 1.3 (`AdaptiveLayoutPolicy.permanentDrawerWidth`; at 2.0 the 280 dp drawer broke "Leaderboards" and the player's name mid-word), and the drawer's **Deselect** stacks under the profile name at ≥ 1.3×, so labels never break mid-word.
- **Display cutouts** (issue #101): `ui/common/PaneInsets.kt` gives each pane only the cutout/system insets on its own edges, so a landscape cutout pads the list pane and its top app bar, not the detail pane.
- **Drawer alignment**: every drawer starts its first entry 64 dp below the status bar (`PAGE_CONTENT_TOP_DP`), level with the rail's first destination and the page's first content row (Songs search field). The modal drawer puts "Festival Score Tracker" in that header row; the **permanent (tablet) drawer has no title and a transparent container** (operator 2026-09-28).
- **Drawer corners** (issue #55, Android check of Apple #17): the modal drawer sheet is concentric with the display corners using only public API: `WindowInsets.getRoundedCorner` (API 31+) via `ui/shell/DrawerShape.kt` `rememberConcentricDrawerShape()` (re-read on layout and configuration changes). `core/shell/DrawerCornerPolicy.kt` gives each sheet corner touching a rounded display corner `min(dx, dy)` from the corner's centre to the sheet edges, capped at the display radius, never below Material's `DrawerDefaults.shape` (`CornerLargeEnd`: square start, 16 dp end); RTL mirrors. No corners reported (API < 31, square displays, a window away from the display corners, Robolectric) → exactly `DrawerDefaults.shape`. FST_Phone (Pixel 9 profile) reports 132 px (≈50 dp) at every corner: start corners become 132 px, end corners stay 16 dp (the 360 dp sheet ends left of the right-hand corner centres). Visible in captures and during predictive back, where M3 scales the sheet off the top/bottom edges. Scrim, insets, gestures, predictive back and TalkBack are unchanged (only `drawerShape` is passed). Tests: `DrawerCornerPolicyTest`, `DrawerShapeTest`, device `DrawerCornersDeviceTest` (skips without reported corners).
- **Chrome colors** (batch 6.6): `ChromeColors` wraps bar, rail and drawers in a scheme whose `onSurfaceVariant`/`secondary` are white, so unselected and selected labels/icons are white (selection = purple indicator). The top app bar stays transparent in every scroll state (batch 6.20); content is clipped below it.
- **Notifications badge** (batch 6.23): the gold count badge is a sibling of the bell `IconButton` (start 22 dp, top 6 dp inside the 48 dp button), because the button clips its content to its circular state layer.
- **Floating toolbar (compact windows, < 600 dp)** — `ui/common/FloatingToolbar.kt`: an M3 Expressive floating toolbar (Material 3 1.4 stable has no public `HorizontalFloatingToolbar`, so the shell draws the equivalent 64 dp elevated pill 16 dp above the bottom bar; tag `fst.nav.floating-toolbar`). **End-aligned** (16 dp from the trailing edge, where the web's mobile FAB dock sits), not centred: M3 allows one FAB per screen and M3 Expressive groups related actions in one floating toolbar that may sit at the edge, so every page shares this single toolbar rather than adding FABs. Pages just pass their contextual actions (Quick Links, Sort, Filter, Find…) as `FestivalScreen(actions = { … })`: on compact windows they render in the floating toolbar; on medium and wider windows they stay in the top app bar. **Global search is always in the top app bar** (operator 2026-09-28), before the bell and avatar. A page whose actions are all conditional registers empty content, which the toolbar measures but does not place (no empty pill). Screens outside `FestivalScreen` use `FloatingToolbarContent { … }` (no-op when `LocalShellActions.current.floatingToolbar == null`). Latest composed registration wins, so the entering screen owns it during transitions. `shell.bottomPadding` already reserves the toolbar's height. **Hide on scroll** (M3 "exit always"): `FloatingToolbarScrollState` is a nested-scroll connection on the shell content; the toolbar slides off the bottom as content scrolls toward its end and back as soon as it scrolls back, following the finger (offset read only in `graphicsLayer`), resets on every navigation and never hides while TalkBack touch exploration is on. Its slide is clipped to the shell content's bottom edge (`matchParentSize().clipToBounds()` host, issue #102): the bottom bar is 0.96 alpha, so an unclipped hidden pill showed through it. Pages that must keep their actions reachable pass `FestivalScreen(pinActions = true)` / `FloatingToolbarContent(pinned = true)` (M3 "always visible" toolbar): `FloatingToolbarHost.pinned` follows the latest registration and disables hide on scroll while that page owns the toolbar. Songs and Suggestions pin (issue #52); every other page keeps hide on scroll. **Reading order:** the toolbar reads after the page content (traversal index 1) by default; a page whose content never ends (Suggestions' endless feed, issue #112) passes `FestivalScreen(actionsReadFirst = true)` / `FloatingToolbarContent(readFirst = true)`, which makes the top app bar a traversal group at −2 and the toolbar −1, so TalkBack and keyboard focus reach its actions right after the top bar (`FloatingToolbarHost.readFirst` follows the latest registration). Top bar on compact: menu/back, title, search, bell (only while a profile is selected), avatar.
- **Top-bar overflow** (`ui/common/TopBarActions.kt`): on medium+ windows the top bar keeps search, the bell and the avatar; page actions (Quick Links, Sort, Filter…) stay inline until the title would truncate at the pane's real width (narrow list panes: book half-open, passport unfolded), then move behind a ⋮ button (`fst.nav.overflow`) whose menu shows them as a row (`fst.nav.overflow-menu`). They return inline once the pane is wider than where they collapsed. Page actions are composed once (inline or in the menu), so their own dropdown/sheet state is not duplicated. Test: `TopBarActionsUiTest` (430 dp, native graphics for real text widths).
- Shell seams for feature screens: `LocalShellActions` (`navigate`, `back`, `openProfile`, `search`, `notifications` slot), `RegisterPageFind { … }` (Ctrl+F; `ui/shell/ShellKeyboard.kt`). Activity shortcuts: Ctrl+K / Search key → global search, Ctrl+F → page find else global search.
- Predictive back: `enableOnBackInvokedCallback`, Navigation-Compose's built-in back animation, Material drawer/search/sheet back handling. The modal drawer must use the `ModalDrawerSheet(drawerState = …)` overload — without it system back left the app with the drawer open (fixed 2026-09-28, `ShellUiTest.systemBackClosesTheOpenDrawerInsteadOfLeaving`). The only shell `BackHandler` closes the Songs detail pane on expanded windows (list-detail back → list).
- Debug deep links: `FST_DEBUG_TAB` / `FST_DEBUG_ROUTE` ([platforms/android.md](../../platforms/android.md)).
- **Active icon** (issue #132, M3 "Use filled icons for active state, outlined for inactive"): `FestivalSection.icon(selected)` / `DrawerEntry.icon(active)` give the selected bar item, rail item and drawer entry the filled glyph, every other item the outlined one (`SectionIconTest`).
- **Drawer header and TalkBack group** (issue #132): the modal drawer's title row is a 64 dp-minimum `heading()` (`fst.nav.drawer-header`) inside the entries' scroll column, so a wrapped title at 2.0× pushes "Songs" down instead of overlapping it (`LargeTextDrawerHeaderUiTest`). The drawer sheet (`fst.nav.drawer-sheet`) is one traversal group, so the permanent drawer's footer (player row, Deselect profile, Settings) is read with the menu, not after the page.
- Open: predictive-back animation audit, TalkBack traversal order of pages other than Songs and Suggestions, publication-change route clearing notice.

States: `songs`, `leaderboards`, `settings`, `player` (Suggestions/Statistics/Compete or Rivals tabs, avatar, drawer player row + Deselect) and `reselect` (re-tap pops to root, switching restores per-tab history) were reached in each layout. **`band` is not reachable** from navigation: there is no Bands row and band search is blocked by [service-safety](../../platforms/service-safety.md); its tab/drawer policy is covered by `NavigationPolicyTest` / `DrawerPolicyTest`.

**Material 3** (`material-3` skill, `references/navigation-patterns.md`): bar < 600 dp, rail 600–1199 dp, permanent drawer ≥ 1200 dp matches "Compact → Navigation Bar; Medium → Navigation Rail; Expanded+ → Navigation Drawer (side) or Rail"; filled active / outlined inactive icons; 48 dp targets. Deliberate deviations: icon-only bar and rail at ≥ 1.3× text (M3 "Always show labels", overridden by issue #101 because 2.0× labels broke mid-word; names stay spoken); bar at `cardBackground` 0.96 alpha and transparent drawers/rail instead of `surface-container` (operator 2026-09-28); custom `FestivalRail` (M3's rail cannot pin Profile/Settings to the bottom); bar does not hide on scroll (optional in M3; the floating toolbar does); dark-only brand scheme.

**Accessibility**: real TalkBack walks (`tools/android/talkback_walk.py`): phone drawer reads title heading, Songs (selected) … Item Shop, "Profile: SFentonX", Deselect profile, Settings, then the scrim's "Close navigation menu"; tablet rail reads top-bar actions, menu, rail tabs, Profile, Settings, then panes; tablet permanent drawer reads top bar, tabs, Profile, Deselect profile, Settings, then the page. Every item has a Tab or Button role and the selected tab announces "selected"; Compose exposes no click action on the selected `Role.Tab` (re-tap pops to root for touch users; TalkBack users use Back). Targets ≥ 48 dp; white labels on the purple indicator/dark chrome meet contrast; 2.0× content does not clip; animator 0 removes drawer/tab motion. Tests: Robolectric `AppNavigationStatesUiTest` (compact, medium rail, expanded drawer), `LargeTextDrawerHeaderUiTest`, `SectionIconTest`; connected `ShellAccessibilityJourneyTest` 8/8 on FST_Phone, FST_Tablet and FST_Book_Fold (`JourneyHarness.awaitAccessibilityTree` waits for UiAutomation's node cache to reach the new page before logging reading order). Coverage 98.0% logic / 94.9% UI lines.
