# App navigation — Android notes

> **What:** Android shell navigation implementation. **Read when:** changing tabs, rail, drawers or deep links on Android. Spec: [spec.md](spec.md); chrome decisions: [design/android.md](../../design/android.md).

- Tabs from `FestivalTabPolicy` (unit-tested port of Apple's); selected tab derived from the back stack; re-tap pops to root; per-tab history restored except Statistics; a profile change resolves Compete↔Leaderboards slots.
- `NavigationSuiteScaffoldLayout` + `NavigationSuite` with the policy's type (`ui/shell/FestivalApp.kt` `suiteType`): short bar / wide rail (`FestivalRail`) / permanent drawer; modal drawer from the top-bar hamburger (bar layouts) or rail header, gestures only while open. Test tags `fst.nav.bar|rail|rail.profile|permanent-drawer|drawer|drawer-sheet|profile|back|tab.<section>|drawer.<entry>`; Compose tags double as UIAutomator resource ids (`testTagsAsResourceId` on the root).
- **Drawer = web sidebar** (`core/shell/DrawerPolicy.kt`, operator 2026-09-28): Songs · Suggestions* · Statistics* · Rivals† · Leaderboards · Item Shop‡ (* any profile, † player, ‡ unless Hide Item Shop), then a footer with the player row (name → Statistics, **Deselect**) or **Select Profile**, and **Settings last**. A row switches tabs when that tab is visible at this width, else pushes the non-root twin (`LeaderboardsRoute`, `RivalsRoute`, `StatisticsRoute`, `SuggestionsRoute`). No Bands or Licenses rows: Bands is reached from search and leaderboard links, Licenses from Settings. The modal and permanent drawers share `DrawerContent`.
- **Rail**: menu button in a 64 dp header row level with the top app bar, main tabs **top-aligned** directly below it (operator 2026-09-28: opening the drawer reads as the rail expanding), then **Profile** (initials/person glyph → the selected profile's Statistics, or the profile sheet with no profile; issue #290) and **Settings** pinned to the bottom edge. No container color (batch 6.19): the backdrop shows through. Material's `WideNavigationRail` content cannot split destinations between top and bottom, so `FestivalRail` is a plain column of `NavigationSuiteItem`s (collapsed wide-rail type, 96 dp). At ≥ 1.3× text every rail item, Profile included, is icon-only; the avatar carries "Profile: <name>" (issue #101).
- **Large text drawer** (issues #101, #102): the permanent drawer is 280 dp, or M3's 360 dp standard drawer width at font scale ≥ 1.3 (`AdaptiveLayoutPolicy.permanentDrawerWidth`; at 2.0 the 280 dp drawer broke "Leaderboards" and the player's name mid-word), and the drawer's **Deselect** stacks under the profile name at ≥ 1.3×, so labels never break mid-word.
- **Display cutouts** (issue #101): `ui/common/PaneInsets.kt` gives each pane only the cutout/system insets on its own edges, so a landscape cutout pads the list pane and its top app bar, not the detail pane.
- **Drawer alignment**: every drawer starts its first entry 64 dp below the status bar (`PAGE_CONTENT_TOP_DP`), level with the rail's first destination and the page's first content row (Songs search field). The modal drawer puts "Festival Score Tracker" in that header row; the **permanent (tablet) drawer has no title and a transparent container** (operator 2026-09-28).
- **Drawer corners** (issue #55, Android check of Apple #17): the modal drawer sheet is concentric with the display corners using only public API: `WindowInsets.getRoundedCorner` (API 31+) via `ui/shell/DrawerShape.kt` `rememberConcentricDrawerShape()` (re-read on layout and configuration changes). `core/shell/DrawerCornerPolicy.kt` gives each sheet corner touching a rounded display corner `min(dx, dy)` from the corner's centre to the sheet edges, capped at the display radius, never below Material's `DrawerDefaults.shape` (`CornerLargeEnd`: square start, 16 dp end); RTL mirrors. No corners reported (API < 31, square displays, a window away from the display corners, Robolectric) → exactly `DrawerDefaults.shape`. FST_Phone (Pixel 9 profile) reports 132 px (≈50 dp) at every corner: start corners become 132 px, end corners stay 16 dp (the 360 dp sheet ends left of the right-hand corner centres). Visible in captures and during predictive back, where M3 scales the sheet off the top/bottom edges. Scrim, insets, gestures, predictive back and TalkBack are unchanged (only `drawerShape` is passed). Tests: `DrawerCornerPolicyTest`, `DrawerShapeTest` (incl. the `windowCorners` mapping of reported 132 px and radius-0 corners), device `DrawerCornersDeviceTest` (skips without reported corners), and the `@DeviceCi` ATF journey `DrawerCornersAccessibilityJourneyTest` (issue #419). The modal sheet is tagged `fst.nav.modal-drawer`. **Rule:** drawer content must stay wholly inside the sheet's drawn outline. At the device text size and 200 %, every row and the title shown in the scroll viewport sit inside the concentric outline, rows are ≥ 48 dp, entries are tabs (Songs selected), TalkBack reads title → entries → profile row → Deselect → Settings, text grows and Settings scrolls fully into view. The 12 dp start and 16 dp bottom content padding is what keeps the footer clear of a 132 px corner, so removing it fails the journey. Never build test insets with `WindowInsets.Builder().setRoundedCorner` under Robolectric (sdk 34): it mutates the shared `RoundedCorners.NO_ROUNDED_CORNERS` static and leaks corners into every later window in the JVM; `windowCorners` takes a lookup lambda instead. Issue #163 validation below.
- **Chrome colors** (batch 6.6): `ChromeColors` wraps bar, rail and drawers in a scheme whose `onSurfaceVariant`/`secondary` are white, so unselected and selected labels/icons are white (selection = purple indicator). The top app bar stays transparent in every scroll state (batch 6.20); content is clipped below it.
- **Notifications badge** (batch 6.23): the gold count badge is a sibling of the bell `IconButton` (start 22 dp, top 6 dp inside the 48 dp button), because the button clips its content to its circular state layer.
- **Floating toolbar (every window size, issue #576)** — `ui/common/FloatingToolbar.kt`: an M3 Expressive floating toolbar (Material 3 1.4 stable has no public `HorizontalFloatingToolbar`, so the shell draws the equivalent 64 dp elevated pill 16 dp above the bottom bar; tag `fst.nav.floating-toolbar`). **End-aligned** (16 dp from the trailing edge, where the web's mobile FAB dock sits), not centred: M3 allows one FAB per screen and M3 Expressive groups related actions in one floating toolbar that may sit at the edge, so every page shares this single toolbar rather than adding FABs. Pages just pass their contextual actions (Quick Links, Sort, Filter, Find…) as `FestivalScreen(actions = { … })`, and they render in the floating toolbar at every window size, posture and orientation (owner-approved variant #576, [page-tools-and-nav-chrome](../../patterns/page-tools-and-nav-chrome.md) R4; #309 had put them in the top app bar at 600 dp and wider). `FestivalScreen` reports its pane's horizontal span, and `core/shell/FloatingToolbarPlacement` bounds the pill to that pane, the horizontal `safeDrawing` insets and the side of a separating vertical hinge the pane ends on, so a two-pane list-detail keeps it over the list and it never straddles a fold. On rail and drawer layouts it sits above the system navigation bar (`toolbarLift`); `shell.bottomPadding` reserves its height plus both 16 dp margins and that lift on every layout, so the last row scrolls clear. **Global search is always in the top app bar** (operator 2026-09-28), before the bell and avatar. A page whose actions are all conditional registers empty content, which the toolbar measures but does not place (no empty pill). Screens outside `FestivalScreen` use `FloatingToolbarContent { … }` (no-op when `LocalShellActions.current.floatingToolbar == null`). Latest composed registration wins, so the entering screen owns it during transitions. `shell.bottomPadding` already reserves the toolbar's height. **Hide on scroll** (M3 "exit always"): `FloatingToolbarScrollState` is a nested-scroll connection on the shell content; the toolbar slides off the bottom as content scrolls toward its end and back as soon as it scrolls back, following the finger (offset read only in `graphicsLayer`), resets on every navigation and never hides while TalkBack touch exploration is on. Its slide is clipped to the shell content's bottom edge (`matchParentSize().clipToBounds()` host, issue #102): the bottom bar is 0.96 alpha, so an unclipped hidden pill showed through it. Pages that must keep their actions reachable pass `FestivalScreen(pinActions = true)` / `FloatingToolbarContent(pinned = true)` (M3 "always visible" toolbar): `FloatingToolbarHost.pinned` follows the latest registration and disables hide on scroll while that page owns the toolbar. Songs and Suggestions pin (issue #52); every other page keeps hide on scroll. **Reading order:** the toolbar reads after the page content (traversal index 1) by default; a page whose content never ends (Suggestions' endless feed, issue #112) passes `FestivalScreen(actionsReadFirst = true)` / `FloatingToolbarContent(readFirst = true)`, which makes the top app bar a traversal group at −2 and the toolbar −1, so TalkBack and keyboard focus reach its actions right after the top bar (`FloatingToolbarHost.readFirst` follows the latest registration). Top bar on every window: menu/back, title, search, bell (only while a profile is selected), avatar.
- **Top-bar overflow** (`ui/common/TopBarActions.kt`): only for a `FestivalScreen` composed outside the shell (previews, isolated tests; `LocalShellActions.current.floatingToolbar == null`), since the app's shell floats page tools at every size (#576). There the top bar keeps search, the bell and the avatar; page actions (Quick Links, Sort, Filter…) stay inline until the title would truncate at the pane's real width (narrow list panes: book half-open, passport unfolded), then move behind a ⋮ button (`fst.nav.overflow`) whose menu shows them as a row (`fst.nav.overflow-menu`). They return inline once the pane is wider than where they collapsed. Page actions are composed once (inline or in the menu), so their own dropdown/sheet state is not duplicated. The menu closes when its popup window gets focus back after a sheet, dialog or nested menu that one of its actions opened has closed (`OverflowRefocusRule`, issue #160): before that, Sort/Filter/Quick Links left the action row open over the Songs search field after their sheet closed. Closing it on tap instead would dispose Quick Links, whose open state lives in the action. Test: `TopBarActionsUiTest` (430 dp, native graphics for real text widths; `overflowMenuClosesAfterTheActionsWindowCloses` hands window focus to the top-most window because Robolectric never moves it).
- **Title icon** (issue #294): `FestivalScreen(titleIcon = { size -> … })` puts a decorative icon before the title (`fst.nav.title-icon`, title text `fst.nav.title`), sized to the bar title style's line height (M3 Title Large: 28 dp at 1.0×, scaling with the font) with 12 dp before the text. The title text still ellipsizes and drives the overflow check. Instrument Leaderboards and single-chart All Rivals (#557) use it for the chart icon ([page-tools-and-nav-chrome](../../patterns/page-tools-and-nav-chrome.md) R18). Tests: `FullRankingsTitleIconUiTest`, `AllRivalsUiTest`.
- Shell seams for feature screens: `LocalShellActions` (`navigate`, `back`, `openProfile`, `search`, `notifications` slot), `RegisterPageFind { … }` (Ctrl+F; `ui/shell/ShellKeyboard.kt`). Activity shortcuts: Ctrl+K / Search key → global search, Ctrl+F → page find else global search.
- Predictive back: `enableOnBackInvokedCallback`, Navigation-Compose's built-in back animation, Material drawer/search/sheet back handling. The modal drawer must use the `ModalDrawerSheet(drawerState = …)` overload — without it system back left the app with the drawer open (fixed 2026-09-28, `ShellUiTest.systemBackClosesTheOpenDrawerInsteadOfLeaving`). The only shell `BackHandler` closes the Songs detail pane on expanded windows (list-detail back → list).
- **One page parent at every width** (issue #106): the pages always sit inside `ModalNavigationDrawer`, also beside the permanent drawer, where the modal sheet stays closed, gesture-less and empty. Hosting them bare in the permanent layout rebuilt the NavHost whenever the window crossed 1200 dp (tablet rotation, unfolding, resizing), resetting every page's scroll and `remember` state (the activity handles configuration changes, so nothing else restored it). Lazy pages keep their first visible item across the switch. Do not swap the sheet's content for nothing or move the pages with `movableContentOf`: a 0 px sheet re-anchored as open, and the moved NavHost's back callback outranked the drawer's (Back popped the page under an open drawer after a portrait launch). Material also re-targets the drawer to the anchor nearest its old pixel offset when the sheet width changes, so a display-size (density) change such as FST_Resizable desktop → phone reopened a closed drawer; `FestivalShell` re-closes a closed drawer one frame after a layout or density change. The same structure keeps an open license or Filter sheet open across the switch (issues #122, #126; `ui/ShellLayoutStateUiTest`). Tests: `ui/profile/ProfileResizeUiTest` (Robolectric, `LocalWindowInfo`/`LocalDensity` overrides; `RuntimeEnvironment.setQualifiers` recreates the activity, so it cannot test this).
- Debug deep links: `FST_DEBUG_TAB` / `FST_DEBUG_ROUTE` ([platforms/android.md](../../platforms/android.md)).
- **Active icon** (issue #132, M3 "Use filled icons for active state, outlined for inactive"): `FestivalSection.icon(selected)` / `DrawerEntry.icon(active)` give the selected bar item, rail item and drawer entry the filled glyph, every other item the outlined one (`SectionIconTest`).
- **Drawer header and TalkBack group** (issue #132): the modal drawer's title row is a 64 dp-minimum `heading()` (`fst.nav.drawer-header`) above the entries, so a wrapped title at 2.0× pushes "Songs" down instead of overlapping it (`LargeTextDrawerHeaderUiTest`). The drawer sheet (`fst.nav.drawer-sheet`) is one traversal group, so the permanent drawer's footer (player row, Deselect profile, Settings) is read with the menu, not after the page.
- **Whole-sheet scroll** (issue #162): the sheet is one `fillMaxHeight().verticalScroll()` column with `Arrangement.SpaceBetween` (header + entries, then divider + player row + Settings). When everything fits the footer stays pinned to the bottom; when it does not (phone landscape at 2.0×, about 340 dp tall) the whole sheet scrolls. A pinned footer previously took about 200 dp there and left less than one destination row visible ("Songs" cut in half). `ShellDrawerUiTest.shortLargeTextSheetScrollsAsOneListAndTallSheetKeepsTheFooterAtTheBottom`.
- **Player row** (issues #54, #162): the selected player is a plain `DrawerItem` (outlined Person icon, display name, same Label Large typography, colour, 56 dp height and icon column as the destinations) with no "Selected Player" caption; TalkBack reads "Profile: <name>", Tab role, matching the avatar and rail Profile labels (Apple's VoiceOver "<name>, Selected Player" is not copied: the following "Deselect profile" button gives the context). `ShellDrawerUiTest.playerRowShowsOnlyTheNameStyledLikeTheOtherRows`; connected `ShellAccessibilityJourneyTest.appNavigationPlayerStates`.
- Open: predictive-back animation audit, TalkBack traversal order of pages other than Songs and Suggestions, publication-change route clearing notice.

**Accessibility**: real TalkBack walks (`tools/android/talkback_walk.py`): phone drawer reads title heading, Songs (selected) … Item Shop, "Profile: SFentonX", Deselect profile, Settings, then the scrim's "Close navigation menu"; tablet rail reads top-bar actions, menu, rail tabs, Profile, Settings, then panes; tablet permanent drawer reads top bar, tabs, Profile, Deselect profile, Settings, then the page. Targets ≥ 48 dp; white labels on the purple indicator/dark chrome meet contrast; 2.0× content does not clip; animator 0 removes drawer/tab motion. Tests: Robolectric `AppNavigationStatesUiTest` (compact, medium rail, expanded drawer), `LargeTextDrawerHeaderUiTest`, `SectionIconTest`; connected `ShellAccessibilityJourneyTest` 8/8 on FST_Phone, FST_Tablet and FST_Book_Fold (`JourneyHarness.awaitAccessibilityTree` waits for UiAutomation's node cache to reach the new page before logging reading order). Coverage 98.0% logic / 94.9% UI lines.

## Drawer corners validation (issue #163, live service, 2026-10-05)

Debug APK on the public HTTPS service with `SFentonX` (`FST_DEBUG_PROFILE`) and the drawer open at launch (`FST_DEBUG_DRAWER`), animator 0 except the motion clip. Reported corners come from `dumpsys window` (`mRoundedCorners`), which is what `WindowInsets.getRoundedCorner` returns.

**Material 3** (`material-3` skill, `references/typography-and-shape.md` "Corner Radius Scale": "`large` | 16 | … | FAB, extended FAB, nav drawer"; `references/navigation-patterns.md` "Modal Drawer (Overlay): Overlays content with a scrim. Used on smaller screens"): the navigation drawer uses shape role `large` (16 dp), which Compose ships as `DrawerDefaults.shape` (square start, 16 dp end). Deliberate deviation (#55): where the display reports rounded corners, the start corners grow to stay concentric with them; the end corners and every other drawer token stay at Material's values, and without reported corners the shape is exactly `DrawerDefaults.shape`. Only `drawerShape` changes, so the scrim, insets, gestures, predictive back and TalkBack order (title heading, entries, footer, then "Close navigation menu") are unchanged from the #132 walk above.
