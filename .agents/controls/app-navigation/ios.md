# App navigation — iPhone notes

> **What:** the iPhone shell as built and planned. **Read when:** changing the iPhone tab shell or toolbar profile action (Lane A owns `App/Shell`, orchestrator owns `AppRoute`). Rules: [spec.md](spec.md); chrome: [design/apple/iphone.md](../../design/apple/iphone.md).

- `TabView` (Liquid Glass on iOS 26+, `.tabItem` fallback) with tabs from `FestivalTabPolicy` mirroring web `BottomNav`: Songs · Suggestions* · Leaderboards / Compete* · Statistics* · Settings (*with a profile), then a trailing **Search** tab (issue #92, [global-search](../global-search/ios.md)). The search tab counts toward the five-tab limit, so compact phone tabs drop Statistics (`FestivalTabPolicy.fittingSearchTab`; the drawer pushes it). Each section keeps its own `AppRoute` path; re-tap pops to root; Statistics resets on leave. `AppRoute` models all 24 web routes; unported pages show placeholders.
- `festivalRootChrome(session:)` on every tab root: leading hamburger drawer (`App/Shell/FestivalDrawer.swift`, mirrors the web Sidebar) and trailing profile avatar, via root-owned `openDrawer` / `openProfile` environment actions ([liquid-glass.md](../../design/apple/liquid-glass.md)).
- The profile avatar opens the selection sheet without changing the active section ([profile-selection/ios.md](../profile-selection/ios.md)). Debug: `FST_DEBUG_DRAWER`, `FST_DEBUG_SHEET=profile`, `FST_DEBUG_PROFILE`, `FST_DEBUG_ANONYMOUS`, `FST_DEBUG_KEEP_PROFILE_ROUTES=1`.
- A verified generation change currently **clears** retained `Song`-valued routes with a persistent visible explanation (they pin the older catalogue). TODO: carry song IDs and re-resolve against the new catalogue.
- **Selecting or deselecting a profile never navigates** (operator, 2026-09-28): no path is cleared and pages refresh in place. When the tab set changes, `FestivalTabPolicy.adapt` keeps the active tab if still visible; a slot swap (Leaderboards ↔ Compete, Rivals → Compete) carries the nested path, so selecting from Leaderboards › Player stays on that page; a vanished tab moves to its nearest visible predecessor (Statistics → Leaderboards, Suggestions → Songs).
- Open: drawer swipe / VoiceOver dismissal and tab re-tap are untested on device; band tab rules are unit-tested only ([PROGRESS.md](../../../PROGRESS.md)).

## Toolbar order rule (tab roots)

Profile avatar must be the **rightmost** item, with the bell just before it (web header parity).
**iPhone tab bar (owner, #632; replaces the #92/#300 tab-bar accessory; [page-tools-and-nav-chrome R28](../../patterns/page-tools-and-nav-chrome.md)):** each page tool is its own 44 pt Liquid Glass circle floating above the tab bar (`floatingPageTools(isSelected:)`, `FloatingPageToolsBar` in `App/Shell/FloatingPageTools.swift`): page actions in page order then Quick Links, laid out from the trailing edge 16 pt in, 10 pt apart, fading up right to left with the page's loaded content like web `MobileFloatingActionButton`, staying put when the tab bar minimizes and hidden while Notifications, a sheet or the Search tab covers them (Reduce Motion: no fades). The bell and the avatar share one glass pill trailing in the navigation bar (Profile trailing-most, 30 pt monogram; `FestivalRootTrailingItems` and `.pageTrailingItems()` where `\.pageToolsRegistry` is set), so the header shows the drawer or Back, the leading title (`festivalTitleDisplayMode`: inline title, `toolbarRole(.editor)`), the player page's Select/Switch and the bell · avatar pill. Pages register their tools with `.festivalPageTool(token:order:isEnabled:)`; `pageToolsScope()` (applied by `FestivalTabStack`) keeps only the front page's. The bell and avatar sheets and page-tool menu sheets are presented by the root (`openNotifications`, `openProfile`, `PageToolInlineMenuSheet`). Details: [nav-accessories.md](../../design/apple/nav-accessories.md).

Elsewhere (Duo vertical bar, iPad, iOS < 26.1), since issue #92 the trailing side is **two Liquid Glass groups**: page tools (page actions in page order, then Quick Links) and account (bell when a profile is selected, then avatar), split by one `ToolbarSpacer(.fixed)` in horizontal bars. Songs reads Sort · Filter · Quick Links | bell · avatar. HIG Toolbars (`apple-hig/references/hig/toolbars.md`): "Trailing: important always-available items"; "generally use no more than three groups". `RootChromeTrailingGroups` encodes the split (`RootChromeTrailingGroupsTests`); pages without tools show one account group. The Duo vertical bar adds no fixed spacer ([duo.md](../../design/apple/duo.md) "Toolbar rules").
On iOS/iPadOS 26+ the selected player's monogram is drawn without glass at the 44 pt item size, so the account group's glass holds only the bell and the avatar stands beside it as its own filled circle (issue #311, [nav-accessories.md](../../design/apple/nav-accessories.md) rule 11; HIG `toolbars.md`, `materials.md`).
**Account-button accessibility (issue #394, for #14; [page-tools-and-nav-chrome](../../patterns/page-tools-and-nav-chrome.md) R17):** the bell and Profile are two separate buttons in two system containers, read in screen order (measured from the iPhone's accessibility hierarchy): Open Navigation (or Back) → the title → **bell** → **Profile** (the navigation bar's last button) → the page → the floating "Page Tools" (Sort → Filter → … → Quick Links) → the tab bar (#632; before it the bell was the accessory's last button, read after the page). Every navigation bar (iPhone, Duo, iPad) lists bell then Profile (`RootChromeTrailingGroups`). The bell's label carries the exact unread count ("Notifications, N unread", also above the 9+ badge cap) with no value; its badge digit and glyph are inside its one element. Profile reads "Profile: ‹name›" with the hint "Opens your statistics", or "Choose Profile" with "Opens profile selection"; anonymous shows no bell. Each keeps a 44 pt hit region at every text size. HIG VoiceOver: "VoiceOver reads in the active language and locale's order (US English: top-to-bottom, left-to-right)", so the floating tools at the bottom read after the page. Never set `accessibilitySortPriority` on shell chrome: the XCUITest hierarchy ignores it (a mutation on the bell passed unseen), so it would change VoiceOver's order untested. Tests: `NavButtonHitRegionJourneyTests` `testAccountButtonsReadInProductionChromeOrder` (Songs), `…OnPushedPage` (Full Rankings), `testChooseProfileReadsAloneInProductionChrome` and `testAccountButtonsStaySeparateAndLabelledAtLargestTextSize` (AX XXXL, scoped audit, near-miss taps) walk the production hierarchy; the hosted `RootAccountButtonsAccessibilityTests` (CI) pins each button's label, hint, value and badge at component level. HIG `voiceover.md`: "Provide alternative labels for all key interface elements … keep labels current"; `buttons.md`: "the hit region is at least 44x44 pt".
SwiftUI lays out items from an outer `.toolbar` modifier (the root chrome) *before* the page's own items, so:

- A tab root **with** its own trailing actions ends its `.toolbar { … }` with `FestivalRootTrailingItems(session: session)` and applies `.festivalProvidesRootTrailingItems()`; the chrome then adds only the drawer button. Also add the section to `FestivalRootView.rootProvidesTrailingItems` (or pass `festivalRootChrome(…, providesTrailingItems: true)` where the page applies its own chrome, like Songs): the preference alone arrives an update late, so the first pass adds and removes a second bell/avatar.
- Use `placement: .festivalPageAction` (`.topBarTrailing` on iOS, `.primaryAction` elsewhere) for page actions on tab roots **and pushed pages**. iOS pins `.primaryAction` to the far trailing edge, after every `.topBarTrailing` item, whichever modifier added it.
- Tab roots **without** their own actions do nothing; `festivalRootChrome` adds the bell + avatar itself.

## Toolbar order rule (pushed pages)

Pushed pages never show the root chrome; `FestivalTabStack` applies `.pageTrailingItems()` (`PageTrailingItems`) to every destination, which adds the bell (selected profile) and the avatar from an *outer* modifier as the **only** `.primaryAction` items, after a `ToolbarSpacer(.fixed, placement: .primaryAction)` (iOS 26+): `[Back] … [page actions + Quick Links] | [bell · avatar]`. Before issue #85 the outer items used `.primaryAction` alongside the page's and the avatar sat mid-capsule; page actions now use `.festivalPageAction`. `PushedPageAvatarPlacementTests` fails if any page outside the Mac shell uses `.primaryAction` again. Accessibility (#437): `NavButtonHitRegionJourneyTests` `testProfileStaysTheLastBarButtonOnSongDetail`, `…OnPushedPagesWithActions` and `testChooseProfileStaysLastOnSongDetailAtLargestTextSize` require one labelled Profile button as the bar's last and rightmost button on Song Details, Item Shop and the player page, hittable with a 44 × 44 pt hit region (the monogram: 44 pt frame height, plus near-miss taps, a scoped `.hitRegion` audit and no overlapping page action on Song Details and Item Shop; Choose Profile, a 36 pt system glass circle, by near-miss taps and the `.hitRegion` audit), at AX XXXL too (`page-tools-and-nav-chrome` R17; HIG Buttons: "the hit region is at least 44x44 pt"). A pushed root screen that ends with `FestivalRootTrailingItems` sets `FestivalRootTrailingProvidedKey`, and the outer items step aside.

## Search tab, no dock

Issue #92 removed the header Search button and the custom accessory dock (`FloatingPageControls`, `.festivalTabAccessory`). Global search is the trailing Search tab (`RootTab.search`, `RootTabTransition`); page tools float as individual glass circles above the tab bar on iPhone (#632; top-bar items elsewhere); Songs has the pinned "Filter Songs" field. Only a window too narrow for the circles folds Songs' Sort and Filter into one control (`FloatingPageToolsFit`; bars: `SongsToolbarFold`). The horizontal tab bar minimizes on scroll (`RootTabBarBehavior`). Details: [nav-accessories.md](../../design/apple/nav-accessories.md), [global-search](../global-search/ios.md).

## Drawer

Mirrors the web sidebar: Songs, Suggestions*, Statistics*, Rivals*, Leaderboards, Item Shop (*player; a visible tab switches, otherwise pushes), current destination highlighted (`DrawerMenu.isCurrent`); footer pinned at the bottom: the profile row (name → profile, Deselect) or Select Profile, then Settings. No Bands or Licenses rows (operator, 2026-09-28). The drawer stays (agent decision #338, [page-tools-and-nav-chrome R13](../../patterns/page-tools-and-nav-chrome.md)): on the phone it is the only route to Item Shop and, with a player, to the Leaderboards and Rivals overviews and Deselect; tabs and the Profile button cover the rest.

The player row uses `DrawerRow`'s metrics (`.body`, primary text, avatar in the symbol column, 14 pt gap) and shows only the name: no "Selected Player" caption (issue #16, 2026-10-01). VoiceOver still reads "‹name›, Selected Player" (`DrawerMenu.selectedPlayerAccessibilityLabel`).

### Drawer corners

Issue #17 (2026-10-01): the panel follows the display corners with public API only. On iOS 26+ `DrawerCorners.panelShape` is `ConcentricRectangle(corners: .concentric(minimum: .fixed(26)), isUniform: false)` at the window root, so each corner is the display/window corner radius minus its distance from that corner. The system supplies the hardware shape per device, per Duo display and per rotation. Corners far from a display corner, such as the trailing corners or a Duo hinge-side corner, use the 26 pt minimum, which is the 14 pt row highlight plus the 12 pt content inset. That keeps the panel concentric with its own rows. The scrim cut-out (`DrawerPlacement.cutoutPadding`) has the same layout frame as the panel so both resolve the same radii. iOS 17–25 has no public API for the display radius and keeps a fixed 44 pt. Never read `_displayCornerRadius` (private API; App Review).

Measured (`FST_DEBUG_DRAWER_RADII=1` shows the panel frame and `GeometryProxy.concentricCornerRadii` on iOS 27): iPhone 18 Pro leading corners 54 pt (display ≈62 pt − 8 pt margin); iPhone 17e, the iPhone 13 display geometry, 39.3 pt (≈47.3 − 8). Display radii were taken from the simulator framebuffer masks: 18/17 Pro ≈62.6 pt, 13/17e ≈47.8 pt, Duo outer 8 hinge side / ≈58 outer side, Duo inner ≈53.

### Drawer accessibility (#396)

Rules, enforced by the tests below:
- Each drawer control is a target of at least 44×44 pt (HIG Buttons: "the hit region is at least 44x44 pt"). Deselect uses `.controlSize(.large)`; the regular bordered size was 34 pt tall.
- Deselect is white on the brand red fill (`.borderedProminent`, `BrandTokens.statusRed`, ≈ 5.6:1), like the web `btnDanger` and Settings' Reset. Red text on the bordered tint depends on what the glass shows: it measured 4.46:1 over the large catalogue's artwork. Agent decision (#489, 2026-10-12; the owner may override with `/choose`). HIG Accessibility contrast table: "Up to 17 pt | All | 4.5:1".
- The symbol column (`DrawerRow.iconWidth`, 26 pt at the default size) and the footer avatar scale with `@ScaledMetric(relativeTo: .body)`. At AX5 a fixed column let symbols overlap their titles and spill toward the rounded corner.
- Every target lies wholly inside the concentric panel shape.
- The page behind leaves `app.snapshot()` while the drawer is open.

Tests:
- `DrawerCornersAccessibilityTests` (hosted, `apple-ci`). It covers 7 iPhone and Duo geometries × default/AX5 × anonymous/player. It checks reading order, names, roles, selected state, the 12 pt inset, target size and clearance from the worst-case corner, plus the same tree under Reduce Transparency.
- `DrawerAccessibilityJourneyTests` (simulator, iPhone and `--device duo`). It runs a `performAccessibilityAudit` `.all` and an AX5 audit, using the measured-contrast, behind-modal and page-floor rules in [Apple accessibility audits](../../testing/apple/accessibility.md#drawer-journey-iphone-and-iphone-duo).

The open and close sequence (#362, tests #489) must not cost accessibility. After an animated open, sliding or with the Reduce Motion fade, the drawer reads as the static drawer does: same tree, same order, every control at its resting frame inside the panel. From the first frame of a close, the drawer is out of the accessibility tree and touches reach the page; reopening mid-close restores it whole. With Reduce Motion a control's frame never moves, so the VoiceOver cursor never travels with a slide. The panel is `.isModal` only while `isPresented`. On iOS, a closing panel that stayed modal kept Songs out of `app.snapshot()` until the slide-out ended, even though the panel was already hidden; the journeys below caught this (#489). Tests:
- `DrawerMotionAccessibilityTests` (hosted, `apple-ci`). It covers every iPhone and Duo geometry plus the iPad flyout, with slide and Reduce Motion, at the default size and AX5. It checks the animated open against the static drawer, closing (scrim click, then tree and click handed to a page button beside the panel, one `onDismissed`, reopen), reopening mid-close, and `DrawerPanelStage` stepped through the sequence.
- `DrawerAccessibilityJourneyTests` (simulator, in `apple-ci` against the large-catalogue fixture). `testReduceMotionDrawerPassesAccessibilityAudit` audits the Reduce Motion drawer. `testClosingDrawerHandsThePageBackAtOnce` and its `DuoFolded` form use `FST_DEBUG_DRAWER_SLOWMO=40`. They check that Songs is back in `app.snapshot()` with the drawer gone well before the 16 s close ends, then reopen the drawer from the menu button mid-close.
