# Notifications — iPhone notes

> **What:** iPhone implementation state and decisions for the notifications bell and sheet. **Read when:** changing this control on iPhone. Behavior: [spec.md](spec.md). Endpoint safety: [service-safety](../../platforms/service-safety.md).

Source: `FortniteFestivalWeb/src/components/notifications/MobileNotificationsModal.tsx`. Service: `FSTService/Api/ImprovementNotificationEndpoints.cs:10-31` (`/api/player/{accountId}/notifications`) — pure, keyless `GET` (single read-only `SELECT`, confirmed by reading `ImprovementNotificationService.GetPlayerNotifications`, `FSTService/Persistence/ImprovementNotificationService.cs:441-553`); never writes.

- Implemented: un-hid and wired the previously-reserved bell in `App/Shell/RootChrome.swift` (`NotificationsButton`), now showing the unread count (see "Bell badge" below) and opening `NotificationsSheet` (`Features/Notifications/NotificationsSheet.swift`) as a `festivalSheet(.large)`. `festivalRootChrome`'s `showsNotifications` default flipped from `false` to `true` (its only call site, `FestivalRootView.tabStack`, was unchanged). Row taps open their page in the main app (see "Row navigation" below); the sheet has no navigation path of its own.
- `NotificationsCenter` (`App/FestivalSession+Notifications.swift`) is a per-session `@Observable` store reached via `session.notificationsCenter`, using the same weakly-keyed-registry pattern as `FestivalSession+Artwork.swift`'s `backgroundCoordinator` — added without a new stored property on `FestivalSession.swift` (Lane P's file). Seen-state (`NotificationSeenStore`) is a small `UserDefaults`-backed, per-accountId GUID list, independently testable. `refresh` keeps rows already loaded for the same account visible while it revalidates (the bell refreshes on selection, the sheet again on open), so reopening the sheet or a cancelled revalidation never falls back to the spinner; a different account clears rows first (in-process only, no offline disclosure).
- `FestivalCore` additions: `PublicEndpoint.playerHistory`/`.playerNotifications` cases (`FestivalAPI.swift`; both opt out of the snapshot cache like `.player`, and `.playerHistory` was added to the HTTP-202 allowlist alongside `.player`), plus new files `PlayerHistory.swift`, `PlayerNotification.swift`, `FestivalAPI+History.swift`, `FestivalAPI+Notifications.swift`.
- Simplified vs. web this pass — see `spec.md`'s "Native client contract": player-only feed (no bands), tap/dismiss-based seen state instead of scroll-visibility tracking, and the badge only refreshes on profile-selection change or sheet close (no live WebSocket push).
- iPhone tab bar (owner, #632; [page-tools-and-nav-chrome R28](../../patterns/page-tools-and-nav-chrome.md)): the bell sits in the navigation bar in one glass pill with Profile (Profile trailing-most), on tab roots and pushed pages, label "Notifications, N unread" with its badge on the icon (`drawsBadgeOnIcon`); it never fades with the floating page tools and opens the sheet through the root's `openNotifications` action. From #92 to #632 it was the trailing item of the tab-bar accessory.
- IDs: `fst.shell.notifications` (bell, under the existing `fst.shell.*` → app-navigation family), `fst.notifications.row.<guid>`, `fst.notifications.empty`.
- Tests: `PlayerNotificationTests.swift` (Core) covers ranking-metric mapping, destination resolution and text formatting including the unknown-kind fallback. `NotificationSeenStoreTests.swift` (`FestivalUITests`) covers unread derivation, per-account isolation and idempotent marking against an isolated `UserDefaults` suite. `NotificationsCenterTests.swift` holds a fixture read open to cover first load, same-account revalidation, cancelled revalidation, failure and deselection. `PlayerHistoryNotificationsRenderTests.swift` hosts the real sheet against a keyless fixture feed (preloading the center, because an offscreen host under a loaded parallel CI run once sat on the spinner for the whole settle timeout) and writes a PNG when `FST_HISTORY_RENDER_OUT` is set.

## Operator batch 7 (Lane A3)

- Rows fade only during the first reveal (`FadeStagger` settle): List recycling while scrolling back up no longer re-fades them.
- "New" / "Older" headers are white (`FestivalText.primary`, no uppercase).
- Web trailing column: 20pt wide, chevron centred vertically (white 72%), 9pt yellow `#FACC15` unread dot with a 2pt ring, centred 24pt above the chevron.
- Built on the shared `FestivalModal` (with its `[AppRoute]` path): system Close top-right (`fst.notifications.close`).
- Header fade (issue #94, reopened 2026-10-03): like the web modal, rows never draw under the title and Close; once scrolled they fade out over the 40 pt below the header and are fully transparent at its edge, and the header has no glass band (top scroll-edge effect and bar background hidden; shared `ModalTopEdgeFadeModifier`). Platform default is content peeking through a glass scroll edge (HIG Materials: "Let content scroll and peek through while preserving control and navigation legibility"); the owner chose web parity, and with nothing behind the header HIG Scroll views applies: "Only use an edge effect when a scroll view is behind floating interface elements."

## Bell badge (issue #74)

- The bell shows the numeric unread count, capped at `9+` like web `HeaderActions.tsx:68` (`NotificationBadge` in `RootChrome.swift`; unit tests in `NotificationBadgeTests.swift`). The count is `NotificationsCenter.unreadCount`, the same set that fills the sheet's "New" section, so it clears when dismissal marks every row seen.
- iOS 26+ uses the system toolbar-item badge (`.badge(Text)` on the bell inside its `ToolbarItem`). The bar lays it out without clipping (HIG Notifications: "Avoid custom images or components that mimic a badge"). Before iOS 26 SwiftUI ignores `badge` on toolbar items, so a small numeric capsule overlay stands in.
- Finding (2026-10-02, iOS 26.5): a custom `.overlay` on a `Label` button inside a `ToolbarItem` is **dropped** because the bar hosts it as a system item. The old 9pt gold dot never drew, even with unread rows.
- The system badge also publishes its count as the bell's accessibility **value**, which stayed stale (`2`) after the badge cleared. The bell pins `accessibilityValue` to empty so VoiceOver reads only the label, "Notifications, N unread" (exact, uncapped count). `NotificationsJourneyTests` asserts the label and the empty value before and after dismissal.
- In the navigation bar (iPhone since #632, iPad, Duo) the system badge view is also its own accessibility element: a static text holding the capped digit on the bell's top-trailing corner (measured on iOS 26, live service: `Notifications, 6 unread` then `6`). SwiftUI has no handle to hide it, and a custom capsule would mimic a badge, so it stays; `NavButtonHitRegionJourneyTests` allows exactly that one sibling and nothing else.

## Row navigation (issue #75)

- A row with a destination marks itself seen, resolves its route (`NotificationRoute.resolve` in `NotificationsSheet.swift`: Song Detail; Full Rankings for a rank row with an instrument, else the Leaderboards hub), places it on the **presenting tab's** stack and dismisses the sheet (web `App.tsx` `handleNotificationOpen`: close, then `navigate`). Back returns to the page under the sheet. A row without a destination, or whose song is not in the catalogue, only marks seen and keeps the sheet open.
- Plumbing: `FestivalRootView` installs `\.pushRoute` (`PushRouteAction` in `RootChrome.swift`, appends to `paths[selected]`); `FestivalRootTrailingItems` hands it to `NotificationsButton`, which passes a plain `openRoute` closure into the sheet (a custom environment value does not reliably reach sheet content, same trap as `ProfileSelectionSheet`).
- The route is pushed without animation under the sheet, then `dismiss()` slides the sheet away to reveal it: one system transition, as `ProfileSelectionSheet.openPlayer` does. Earlier (until 2026-10-02) the sheet owned a `NavigationStack` and pushed full pages inside itself; HIG Modality ("Avoid an 'app within the app'") and Sheets ("Display only one sheet at a time from the main interface") rule that out, since Song Detail opens its own sheets.
- Tests: `NotificationRouteTests.swift` (route per destination kind, missing/failed song lookup); `NotificationsJourneyTests.testBellOpensSheetAndRowOpensSongDetailInMainApp` (sheet closes, Song Detail on the Songs tab, Back returns to Songs, badge cleared).

## Row formatting (issue #76)

- Until 2026-10-02 rows showed an instrument icon, one plain sentence per event (raw numbers such as `105593371`) and one upper-case purple badge; coalesced rows lost their Full Combo/gold-star events. `FestivalCore/NotificationPresentation.swift` now ports the web formatter (see `spec.md`'s "Native client contract") into `AppNotification` (`title`, `messageParts`, `flags`, `flagGroups`, `media`). Numbers use `Locale.current` grouping (web `toLocaleString()`).
- `NotificationRow` (`NotificationsSheet.swift`): 64pt decorative media rail (54pt `ArtworkTile`; 44pt art above 18pt instrument icons for multi-chart rows; else a 36pt `InstrumentIcon`), `.headline` marquee title, `.subheadline` message as an `AttributedString` whose emphasized runs are `.stronglyEmphasized` (bold keeps the Dynamic Type style), and `NotificationFlagChip`s (`.caption` semibold white on web `FLAG_COLORS`, 2pt 18%-white border, 8pt radius) in a wrapping `NotificationChipFlow`, one icon-led line per instrument for flag groups. Chips wrap rather than truncate at large text sizes. Kept the plain `List` row rather than web cards; chip gap 4pt (web 2px) for legibility.
- VoiceOver reads one element: "title. message" (web aria-label) then the flag names ("Lead: Full Combo. Drums: New High Score." for groups), so flag meaning is not colour-only (HIG Color: "Avoid relying solely on color to differentiate between objects"). The art, icons and trailing dot/chevron are hidden (HIG VoiceOver: exclude purely decorative images). The button trait conveys navigation, so there is no "Open notification." suffix.
- Every `FLAG_COLORS` fill keeps white text at 4.5:1 or better.
- Tests: `FestivalCoreTests/PlayerNotificationTests.swift` checks the port against `Fixtures/notification-text-web-parity.json`: 40 DTOs (13 live SFentonX feed rows plus edge cases) whose expected title, message, bold runs, flags and groups were generated by running the web `formatNotificationPresentation` itself. Regenerate it the same way when the web copy changes; never hand-edit expectations. `FestivalUITests/NotificationRowTests.swift` covers chip wrapping, bold runs and the spoken label; the hosted render fixture includes a coalesced multi-chart row.

## Pinned section headers (issue #301)

Applies to iPhone, iPhone Duo, iPad and Mac (shared `NotificationsSheet`). The sheet stays a native SwiftUI `List(.plain)` with pinned "New"/"Older" headers.

- **Cause:**
  - iOS's plain List adds a 22 pt top padding above each section header (UIKit's `sectionHeaderTopPadding`; not changeable from SwiftUI, and `listSectionSpacing(0)`, `contentMargins` and `defaultMinListHeaderHeight` leave it in place). The first header rested 22 pt low and slid up before pinning under the title bar.
  - The modal's 40 pt top ramp (#94) covers the whole List, so a pinned header was dimmed, and rows were only half faded while scrolling underneath it.
- **Fix** (`Design/PinnedHeaderEdgeFade.swift`, the one pinned-title fade shared with Songs; [scroll-edge](../../patterns/scroll-edge.md) R5, #308):
  - `pinnedHeaderEdgeFadeHeader(_:first:)` draws the first header lifted by the gap with `visualEffect`, so it sits where it pins from the start while the empty gap scrolls away (the gap now shows between the header and the first row at rest). Layout and accessibility frames are unchanged; the lift is 0 once the header is pinned or pushed.
  - `pinnedHeaderEdgeFadeList` sets the modal ramp to 0 through `ModalTopEdgeFadeRampKey`, giving a hard edge under the title.
  - Each row masks itself (`pinnedHeaderEdgeFadeRow`, drawing `PinnedHeaderFadeMask`): it is transparent above the pinned header's bottom edge and fades back in over the shared 40 pt linear ramp (`PinnedHeaderEdgeFade.height`, web `useScrollMask`), exactly like the Songs section bar. It is a hard edge under Reduce Transparency, Less Transparency or Increase Contrast (`ScrollEdgeHardEdge`). Headers are never masked, keep `.isHeader` and scale with Dynamic Type.
- **Row separators (issue #322):** the system List draws row separators outside SwiftUI masks (UIKit cells, AppKit table rows), so they kept passing under the pinned header while the rows faded. `pinnedHeaderEdgeFadeRow` hides the system separator (`.listRowSeparator(.hidden)`, as Songs and Search do) and draws the same 1 pt `separator` line in its masked `listRowBackground`. The line runs from the row's `.listRowSeparatorLeading` guide (the text) to its `.listRowSeparatorTrailing` guide on iOS/iPadOS, and on to the row's trailing edge on macOS (`PinnedHeaderEdgeFade.separatorSpan`), so it fades over the same 40 pt ramp and is a hard edge under R7. On macOS the table drops the full-width line under each section header once no row shows a system separator, so the header asks for it (`.listRowSeparator(.visible)`, macOS only). Never add a feature-level divider or a second mask for this.
- **Geometry:**
  - Measure rows and headers with `.frame(in: .global)`: inside an iOS List's cells `.scrollView` does not resolve to the List's scroll view.
  - The List's SwiftUI frame starts at the pin line (it is laid out in the safe area); its scroll view reaches up under the modal title by the top content inset. Positions are measured from that scroll-view top (`listTop − pinLine`).
  - The pinned band is the header's whole cell: the List centres the header content in it (+10 pt above and below on iOS 26; a 28 pt minimum on macOS 26). `listRowInsets` does not apply to headers.
  - A row's own frame starts below its cell by the row insets (15 pt here), so the first row's cell top is read from its `listRowBackground`, which fills the cell. At scroll offset 0, padding = row cell top − header content bottom, and gap = header content top − padding − pin line. Readings outside 0–24 pt padding or 0–48 pt gap are rejected.
  - The pin line and scroll offset come from `onScrollGeometryChange` on iOS 18 / macOS 15+. On iOS 17 / macOS 14 each row's `ListScrollViewLocator` hands the List's scroll view to `PlatformScrollObserver` (KVO on `contentOffset`/`contentSize`; `NSClipView` bounds notifications), the observer every Apple edge fade shares ([scroll-edge](../../patterns/scroll-edge.md)), so the ramp still grows from 0 to 40 pt there instead of staying a hard cut (#308 review).
- **Verified by:**

  - `ModalTopEdgeFadeTests` (zero ramp).
  - Accessibility of the sheet header (#94, backfilled by #447): hosted `notificationsRowsStayReadableUnderTheSheetHeader` (every realized row stays a named `AXButton` in visual order, with the Older heading between the sections, when scrolled under the header; macOS rows at least 28 pt) and iPhone journey `ModalHeaderAccessibilityJourneyTests/testNotificationsHeaderAtDefaultSize` / `…AtAX5` (title → Close → rows, Close hittable, 44 pt rows, rows under the header stay named, audit at rest and scrolled at AX5; at AX5 the title grows ≥ 1.15× and the first row, its message read back whole clear of the header, > 1.35× against a default-size launch).
  - `NotificationsPinnedHeaderRenderTests` (macOS hosted): scrolls the real `NSTableView` and asserts no row ink in the pinned header's row band, for New and for Older after the push. It fails without the row mask.
  - `notificationsRowSeparatorsDoNotDrawUnderThePinnedSectionHeader` (macOS hosted, #322): sweeps the scroll offset in 9 pt steps through New and Older and asserts no separator ink in the pinned header's band, while separators still draw lower down. It fails without the row's own separator. `pinnedHeaderRowSeparatorSpansTheSeparatorGuides` covers the span (iOS, macOS row edge, RTL, unreadable).
  - `PinnedHeaderLegacyScrollRenderTests` (macOS hosted): the same List on both scroll paths has no fade at rest, a 15 pt fade after 15 pt and the full 40 pt after that, with the same pin line and header band. The legacy case fails without the observer.

- **Accessibility (issue #459, backfilling #301):** a row wholly under the pinned title (its bottom between the List's top and the title's edge) is hidden from VoiceOver by its row mask (`PinnedHeaderEdgeFade.hiddenInCut`, [scroll-edge](../../patterns/scroll-edge.md) R7, as Android #417); a row partly under it stays readable. The masks use `accessibilityHidden(while:)` (`AccessibilityHiddenSourceTests`): a plain `accessibilityHidden(false)` would un-hide the rows' decorative artwork.
- **Known: the first title's focus frame at rest (#469).** XCUITest and VoiceOver read the title as its whole header cell (402 × 38 pt on iPhone 17 Pro). The lift above is a visual effect, so at rest that frame sits one gap (22 pt) below the drawn title until the header pins. A cell's frame cannot follow a visual effect without moving the layout that the lift exists to keep. The title still reads first, as a heading, and is not actionable. Journeys measure the pinned edge live from the pinned cell, never from the resting frame.
- **HIG:**
  - Lists and tables: "Choose a table or list style (`ListStyle`) that coordinates with your data and platform."
  - Materials: "Let content scroll and peek through while preserving control and navigation legibility."
  - Layout: "Prefer scroll-edge effects to solid/semi-opaque backgrounds beneath controls."
