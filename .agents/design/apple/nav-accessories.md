# Navigation accessories (iPhone, Duo, iPad)

> **What:** Decision record for where each page's controls go on iPhone, iPhone Duo and iPad: the iPhone floating page tools and account pill (#632), the top navigation bar, the tab bar's Search tab, an inline list filter, or the page content. **Read when:** adding a toolbar item, search field or persistent action to any Apple page.

**Current placement.** **Every horizontal tab bar** (`FloatingPageToolsHost.floatsPageTools(in:)`, `DeviceLayout.sectionChrome == .tabBar`: iPhone in either orientation, iPhone Duo's inner display in portrait and compact iPad windows; agent decision #633): each page tool is its own 44 pt Liquid Glass circle floating above the tab bar, and **Notifications and Profile share one glass pill trailing in the navigation bar, Profile rightmost** ([pattern R28](../../patterns/page-tools-and-nav-chrome.md); owner, #632: "No more accessory pill with notifications/quick links/filter/sort. Those buttons are now permanently floating individual glass chrome like the floating buttons on web. Notifications goes to header. Titles in header are now left-aligned next to hamburger button or back chevron."). The header holds the drawer or Back, the leading title, the player page's Select/Switch and the account pill. No page uses `tabViewBottomAccessory`. **iPhone Duo vertical bar (folded in every rotation, inner landscape, book pose) and the regular iPad sidebar shell:** the same items are rail or trailing navigation-bar items, with their 44 pt hit regions (pattern R27) and overflow priorities. macOS keeps its own window toolbar and search, with every toolbar item also a menu-bar command (`.agents/platforms/apple/macos.md`). Per-window table: [pattern agent decision #633](../../patterns/page-tools-and-nav-chrome.md#agent-decision-apple-page-tool-placement-per-chrome-633). The retired tab-bar accessory (#92, #300) is described only under [History](#history-the-iphone-tab-bar-accessory-92-300-retired-by-632).

## APIs (iOS 27.1 SDK; verified in the swiftinterface and on the iOS 26.5 simulator)

| API | Availability | Finding |
|---|---|---|
| `Tab(value:role: .search)` | 18 | Separate trailing round Search button beside the tab capsule on iOS 26 (iPhone), a separate item at the end of the folded Duo rail. **Counts toward the five-tab limit**: five sections + Search put Search under **More** (26.5, measured again for #92), so compact phone tabs drop one section (rule 3) |
| `tabViewSearchActivation(.searchTabSelection)` | 26.0 | Choosing the Search tab focuses its `.searchable` field: keyboard up at once. The system **Close** button beside the field dismisses search |
| `.searchable(text:isPresented:)` in the Search tab | 17+ | `isPresented` going false is the Close tap; the shell then returns to the previous tab. Close also clears the query (system) |
| `.searchable(placement: .navigationBarDrawer(displayMode: .always))` | 15+ | Pinned field under the large title; stays while the list scrolls |
| `tabBarMinimizeBehavior(.onScrollDown)` | 26.0 | Collapses the tab bar to the selected tab and Search on scroll; kept on the horizontal tab bar |
| `ToolbarSpacer(.fixed, placement:)` | 26.0 | Splits trailing items into separate Liquid Glass groups (Duo, iPad). The iPhone account pill uses none: the bell and Profile are adjacent `.topBarTrailing` items sharing one glass |
| `ToolbarItemVisibilityPriority`, `toolbarMinimizationBehavior` | **27.0** | Duo overflow priority (bell, profile, Quick Links `.high`). Not on the 26.5 iPhone |
| `tabViewBottomAccessory(isEnabled:)` | 26.1 | **Unused** since #632; its measurements and traps are under [History](#history-the-iphone-tab-bar-accessory-92-300-retired-by-632) |
| `searchToolbarBehavior(.minimize)` | 26.0 | Field becomes a top toolbar button after the avatar (breaks the avatar-rightmost rule): unused |
| `DefaultToolbarItem(kind: .search, placement: .bottomBar)` | 26.0 | Inside a `TabView` the bottom toolbar renders behind the floating tab bar: unusable |

## Rules (issue #92, 2026-10-04; issue #300, 2026-10-04; issue #632, 2026-10-13)

HIG sources: `apple-hig/references/hig/toolbars.md`, `search-fields.md`, `searching.md`, `tab-bars.md`, `materials.md`, `motion.md`, `accessibility.md`, `designing-for-iphone-duo` (via `duo.md`), `buttons.md`.

1. **Horizontal tab bars (iPhone, Duo inner portrait, compact iPad): floating page tools; Notifications and Profile in the header pill.** The front page's tools are individual floating Liquid Glass circles above the tab bar (`FloatingPageToolsBar` in each tab stack's bottom safe-area inset, `FloatingPageToolsInset`), trailing-aligned, reading left to right in page order: the page's own actions (Songs: Sort, then Filter), then **Quick Links** only on pages with Quick Links. Notifications is **never** a floating tool. Pages without tools show no circles and reserve no room for them (the row is empty and hidden from VoiceOver). The **account pill** is trailing in the navigation bar on every page: the bell (selected profile only; "Notifications, N unread", system badge, never fades) then **Profile**, trailing-most (tab roots: `FestivalRootTrailingItems`; pushed pages: `.pageTrailingItems()`; the player page's Select/Switch sits before the pill). Profile opens profile selection, or the selected player's Statistics (#290); the bell opens the root Notifications sheet (`openNotifications`). Pages register tools with `.festivalPageTool(token:order:isEnabled:)` (`PageToolOrder`; Quick Links via `QuickLinksPageTool`) behind their load gate, so tools appear with the content; `PageToolsRegistry` shows only the front page's (`pageToolsScope(inSelectedTab:)` on every tab root and pushed page in `FestivalTabStack`), so a push, pop or tab switch swaps them with a fade. Only a page on screen **in the selected tab** can be the front page (`PageToolsRegistry.pageVisibilityChanged`): SwiftUI calls `onAppear` on an unselected tab's root when the tab set changes, and a deselect (which drops the profile tabs) used to show Settings' Quick Links in place of Songs' Sort and Filter until the page was left (#487; HIG VoiceOver: "Update labels when UI changes."). Motion, cover and fallbacks follow [pattern R28](../../patterns/page-tools-and-nav-chrome.md) (web `MobileFloatingActionButton`). Where `\.pageToolsRegistry` is nil (Duo vertical bar, regular-width iPad and Duo windows) the same pages keep trailing navigation-bar items: reading right to left Profile, Notifications, Quick Links, page actions (`FestivalRootTrailingItems`, `.pageTrailingItems()`; HIG Toolbars: "Trailing: important always-available items"). **Supported deviation (owner-chosen, #632):** HIG Tab bars and Toolbars put current-view actions in a toolbar (should) and HIG Materials asks to "use Liquid Glass effects sparingly on custom controls" (should); the owner chose web-style floating buttons, so they use only public API, keep icon-only symbols with labels, 44 pt targets, safe areas and opaque Reduce Transparency/Increase Contrast fallbacks, and never add actions as tabs.
2. **Fixed slots, separate groups.** Every floating tool has a **fixed 44 pt circle** that is also its hit region (`FloatingPageToolsFit.slot`, `FloatingPageToolLabelStyle`; HIG Buttons: "the hit region is at least 44x44 pt"), 10 pt apart, 16 pt from the trailing edge. Circles never share out the width, so a push, pop or tab switch only swaps the tools, and the account pill in the header never moves. A page with floating tools ends its content at the row's top (`pageToolsScope`, `FloatingPageToolsFit.pageBottomReserve`, at most `FloatingPageToolsFit.reservedHeight`, 60 pt), so its last content row scrolls clear of the circles; a page without tools reserves nothing and keeps its room down to the tab bar (agent decision #678, superseding #632's universal reserve; rationale in [pattern R28](../../patterns/page-tools-and-nav-chrome.md)). Text in the circles stops at `FloatingPageToolsBar.maxTypeSize`; long-press shows the Large Content Viewer. VoiceOver reads the circles left to right after the page content (`fst.page-tools`). In navigation bars (Duo, iPad): page tools, then account, separated by `ToolbarSpacer(.fixed)` in horizontal bars (`RootChromeTrailingGroups.separatesAccount`; HIG Toolbars: "generally use no more than three groups"); the Duo vertical bar adds no fixed spacer (HIG iPhone Duo: "system spacing adapts, so don't add fixed spacing"). Page actions use `.festivalPageAction` (never `.primaryAction`, `PushedPageAvatarPlacementTests`).
3. **Global search is a Search tab.** A trailing `Tab(role: .search)` (`RootTab.search`) shows `GlobalSearchTab` with the keyboard up. HIG Search fields: a separate trailing tab "focuses the field and opens the keyboard immediately… choose it for fast, transient search that returns to the previous tab on exit"; HIG Tab bars: "A dedicated Search tab may be trailing." The section underneath stays selected: **Close** or tapping that section returns to it with its stack intact, and a chosen result is pushed on it (`RootTabTransition`, unit-tested). The query and scope survive while closed, but the system clears the text on Close. **No other global-search entry point** on iOS: no accessory, dock, toolbar button or floating capsule; ⌘F/⌘K select the Search tab. Five-tab limit: `FestivalTabPolicy.fittingSearchTab` drops **Statistics** first from compact phone tabs (player: Songs · Suggestions · Compete · Settings · Search); the drawer's Statistics row pushes it. Songs, Compete and Settings are never dropped (the drawer has no Compete row or pushable Settings). On folded Duo this also returns the rail's Profile slot (with six rail tabs only the bell fit beside `…`).
4. **iPad:** a regular-width window keeps the sidebar; a **Search** row heads it (`fst.nav.sidebar.search`) and shows the same search page in the detail column, field **unfocused** (HIG Search fields: "on iPad with only a virtual keyboard, leave it unfocused to avoid unexpected keyboard coverage"), with the account items in that column's bar. Compact iPad windows use the phone tabs, Search tab included. The column that owns a page shows its top-bar items.
5. **Inline list filter where the web has one.** Songs uses `.searchable(text:placement: .navigationBarDrawer(displayMode: .always), prompt: "Filter Songs")`: pinned above the list, filtering it with the current sort and filters (HIG Search fields: "Use an inline field when adjacency clarifies that it filters one view rather than searches globally… Put a top inline field above its list and consider pinning it"; "Use placeholder text to state what is searchable"; HIG Searching: Music "filters current songs/albums"). No second magnifier button. Only Songs has a list text filter on the web (`SongsToolbar.tsx`); Item Shop and the player page have none, so they get no field. **Owner-approved Duo variant (#333):** on iPhone Duo (any pose) the field is instead the shared `BottomSearchField` (`GlobalSearchField` on `festivalCardCapsule`) in the page's bottom safe-area inset, full width, on the trailing page only in book pose (`BottomSearchFieldPlacement.pageHinge(for:)`; agent decision #334, owner #349) ([pattern R2](../../patterns/page-tools-and-nav-chrome.md)); `SongsFilterFieldPlacement.resolve(pose:)` decides it, unit-tested.
6. **Overflow, decided from the window.** HIG Toolbars (iOS): "Put only essential actions in the main area; use More for the rest." The floating row folds Songs' Sort and Filter into one **Sort and Filter** control (`slider.horizontal.3`, not an ellipsis: HIG iPhone Duo "reserve ellipsis for overflow") only when the window cannot fit the circles (`FloatingPageToolsFit.folds(windowWidth:pageTools:)`); Quick Links stays visible. The circles do not grow with text size, so accessibility sizes do not fold. No animation is added to the swap (HIG Accessibility: "reduce automatic and repetitive animation"). In navigation bars `SongsToolbarFold.folds` does the same below 390 pt. The Duo vertical bar and the iPad sidebar keep system overflow, with Quick Links, bell and profile at `visibilityPriority(.high)` (`RootChromeRailItem`).
6a. **Menus in the floating row open as a sheet.** In the floating row `PageToolMenu` (Quick Links, Sort and Filter, Rank By, Band Size) is a button with the same label that lists the same choices in a compact sheet (`PageToolInlineMenuSheet`, presented from the root, title = menu name, current choice checked, Close `fst.page-tools.menu.close`); the row hides while the sheet covers it. A picked choice runs after the sheet has closed (`PageToolsRegistry.choose` → `inlineMenuDismissed`), so a sheet it opens (Filter…) never collides with it. `FloatingPageToolsBar` marks its content with `\.pageToolsFloating`, so the hosted `NavButtonAccessibilityTests` exercise the same button form on the Mac host. In navigation bars (Duo, iPad) it stays the ordinary menu.
7. **Tab bar minimizes on scroll** on the horizontal iPhone tab bar (`RootTabBarBehavior`); the floating row stays put (it sits in the stack's bottom safe area, which minimizing does not change); Duo rail and iPad keep `.automatic`. The row hides while the Search tab or a root sheet (Notifications, Profile, a tool's choices) covers the page. Pages' own bottom chrome (Full Rankings' and Song Leaderboard's pinned `RankingsPagerView`, Band Rankings' floating pager) lies inside the page, so it sits above the floating row.
8. **Player page Select / Switch / Deselect** is its own header button (text, prominent for Select/Switch; `ProfileIdentityToolbarItem`), `VerticalBarActionItem` in the Duo rail, prominent in the same `ProfileIdentityAction.prominentFill` (blue for Select/Switch, #351).
9. **Sheets apply immediately.** Songs Filter and Sort have no Cancel/Apply: every change applies, and a trailing **Done** closes the standard `festivalSheet` modal. Sheets open at the large detent.
10. **Header legibility:** every page gets `TopEdgeScrim` (`Common/Chrome/PageChrome.swift`): iOS 26 `scrollEdgeEffectStyle(.soft, for: .top)` plus a dark gradient behind the bar region over the artwork, at most 150 pt and ending 32 pt below the bar (`TopEdgeScrim.height(topInset:)`, issue #286), so it never dims a Quick Links landing under a short iPad, landscape or Duo bar. It ignores the top and horizontal safe areas (`TopEdgeScrim.extendedEdges`, #335), so under the Duo vertical bar the art is darkened exactly as beside it. Collapsed inline titles are 20 pt semibold, Dynamic Type scaled (`NavigationTitleStyle`).
11. **Monogram avatar** renders to a cached image (`MonogramLabel`/`MonogramImageCache` in `App/Shell/RootChrome.swift`) so it stays a standard bar button with the system hit expansion (issue #15); a custom-view item would not get it. **On iOS/iPadOS 26+ the avatar is the whole button:** its toolbar item hides the shared Liquid Glass (`sharedBackgroundVisibility(.hidden)` via `profileItemBackground`, only for `RootProfileButton.Presentation.monogram`) and the image is the 44 pt diameter of a bar item's glass circle with no rim (`RootProfileButton.MonogramMetrics`). A bar pads a background-less item by 10 pt on each side, so the image's alignment rect insets that much on both sides: the circle draws exactly where the glass circle was, 12 pt (the group gap) from the bell's glass on iPad. No glass ring shows around it on tab roots, pushed pages or Search (issue #311; [pattern R8](../../patterns/page-tools-and-nav-chrome.md)). The add-profile glyph, the Duo rail's symbol item, the bell and page tools keep their glass; iOS 17–25 and the Mac toolbar keep the 30 pt outlined avatar. **iPhone account pill (#632):** the monogram keeps the pill's shared glass and shrinks to `RootProfileButton.MonogramMetrics.pillDiameter` (30 pt) inside it (`sharedBackground(inAccountPill:)`). Visual evidence: `ProfileAvatarFillJourneyTests` (iPhone and iPad UI targets) screenshots Songs, Item Shop and Search (iPhone: the Search tab has no avatar, then the page again after closing it) and measures the disc with `ProfileAvatarPixels` (44 ± 2 pt round, 6–20 pt from the trailing edge when no page tool or toolbar search field follows it, band just outside no lighter than the bar); the pre-#311 30 pt disc in its glass ring fails it.

## Decisions per page

The iPhone column lists only the floating page tools, left to right (the same row floats on iPhone Duo's inner display in portrait and in compact iPad windows, #633). On every such page the navigation bar holds the drawer or Back, the leading title and the account pill (Notifications · Profile, Profile rightmost; the bell only with a selected profile); this column never contains the bell.

## Small widths

The floating circles (44 pt, 10 pt apart, 16 pt from the trailing edge; `FloatingPageToolsFit`) fold Sort and Filter only when the window cannot fit them; they do not fold at accessibility text sizes (the circles do not grow; long-press shows the Large Content Viewer). The widest page (three tools, 152 pt plus margins) fits from a 375 pt window up. UI journeys: `NavButtonHitRegionJourneyTests/testAccessibilityTextKeepsTheFloatingToolsWhileScrolled`, `SongsChromeJourneyTests/testToolsStayFloatingWhileScrolled`.

## Drawer

Matches the web sidebar (`Sidebar.tsx`): Songs, Suggestions*, Statistics*, Rivals*, Leaderboards, Item Shop (*player), the current destination highlighted; the profile row (name → profile, **Deselect**) or **Select Profile**, then **Settings** pinned at the bottom. Bands and Licenses are not listed (Bands: search and leaderboard links; Licenses: Settings).

Keep it on iPhone, Duo and iPad (agent decision #338, [page-tools-and-nav-chrome R13](../../patterns/page-tools-and-nav-chrome.md)). On phone shells it is the only route to Item Shop and, with a player, to the Leaderboards and Rivals overviews and Deselect. On iPad it is the window's whole navigation. Removing a row needs another visible route to it first.

## History: the iPhone tab-bar accessory (#92, #300; retired by #632)

**Not current rules.** This records why the accessory was retired, so it is not reintroduced. From #92 to #632 iPhone page tools and Notifications sat in the system tab-bar bottom accessory (`tabViewBottomAccessory`, `PageToolsAccessoryHost`, Music's mini-player slot): page tools in fixed 44 pt slots from the leading edge, a divider, then the bell pinned trailing (Songs: Sort · Filter · Quick Links | bell); Profile stayed trailing in the header (#300). Pages' pagers sat above the capsule. The capsule moved inline beside the minimized tab bar on scroll.

Measured on iOS 26.5: expanded = window − 54 pt, inline = window − 180 pt (348/222 pt on a 402 pt iPhone 17 Pro, 386/260 on a 440 pt Pro Max, 195 inline in a 375 pt canvas). The system animated the capsule's width between the two, so any layout decision read from the accessory's own width changed mid-morph. Traps: a `.sheet` attached inside the accessory never presented; a `Menu` there did not open while inline (known iOS 26 issue) and, expanded, answered only near its glyph (`NavButtonHitRegionJourneyTests` failed at 20 pt off-centre), which is why page-tool menus open as a sheet (rule 6a); a `TextField` there did not focus.

**Why it jittered (#300).** (1) The fold read the accessory's live width: during the expanded ↔ inline morph Songs' items stopped fitting partway, so Sort · Filter became Sort and Filter mid-animation and back; (2) items shared the width evenly, so any count change between pages moved every item. The #300 fix moved Profile to the header, used fixed 44 pt slots with the bell pinned trailing and decided the fold from the window width. Both lessons carry over to the floating row: fixed slots, a window-width fold, no animation hiding a swap (HIG Motion: "Add motion purposefully").
