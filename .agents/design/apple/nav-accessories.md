# Navigation accessories (iPhone, Duo, iPad)

> **What:** Decision record for where each page's controls go on iPhone, iPhone Duo and iPad: the iPhone tab-bar accessory, the top navigation bar, the tab bar's Search tab, an inline list filter, or the page content (issue #92 replaced the custom dock of #42/#84/#89). **Read when:** adding a toolbar item, search field or persistent action to any Apple page.

**iPhone (horizontal tab bar, iOS 26.1+):** page tools and Notifications sit in the system tab-bar bottom accessory (`tabViewBottomAccessory`, Music's mini-player slot), **not** in the navigation bar (owner, #92 follow-up: "should be in an *accessory* to the bottom tab bar… *Not* as part of the top header bar"). **Profile** is the navigation bar's trailing-most button on every page (issue #300, owner: "profile button can go back to permanent right side residence in header"). The header keeps the drawer or Back, the title, the player page's Select/Switch and Profile. **Duo vertical bar, iPad and older iOS:** the same items stay trailing navigation-bar items. macOS keeps its own window toolbar and search (`.agents/platforms/apple/macos.md`).

## APIs (iOS 27.1 SDK; verified in the swiftinterface and on the iOS 26.5 simulator)

| API | Availability | Finding |
|---|---|---|
| `Tab(value:role: .search)` | 18 | Separate trailing round Search button beside the tab capsule on iOS 26 (iPhone), a separate item at the end of the folded Duo rail. **Counts toward the five-tab limit**: five sections + Search put Search under **More** (26.5, measured again for #92), so compact phone tabs drop one section (rule 3) |
| `tabViewSearchActivation(.searchTabSelection)` | 26.0 | Choosing the Search tab focuses its `.searchable` field: keyboard up at once. The system **Close** button beside the field dismisses search |
| `.searchable(text:isPresented:)` in the Search tab | 17+ | `isPresented` going false is the Close tap; the shell then returns to the previous tab. Close also clears the query (system) |

| `tabBarMinimizeBehavior(.onScrollDown)` | 26.0 | Collapses the tab bar to the selected tab and Search on scroll; kept on the horizontal tab bar |
| `ToolbarSpacer(.fixed, placement:)` | 26.0 | Splits trailing items into separate Liquid Glass groups (Duo, iPad, iOS < 26.1) |
| `ToolbarItemVisibilityPriority`, `toolbarMinimizationBehavior` | **27.0** | Duo overflow priority (bell, profile, Quick Links `.high`). Not on the 26.5 iPhone |
| `tabViewBottomAccessory(isEnabled:)` | 26.1 | iPhone page tools (`PageToolsAccessoryHost`). One glass capsule above the tab bar; moves **inline** beside the minimized bar on scroll (`\.tabViewBottomAccessoryPlacement == .inline`). Measured on 26.5: expanded = window − 54 pt, inline = window − 180 pt (348/222 pt on a 402 pt iPhone 17 Pro, 386/260 on a 440 pt Pro Max, 195 inline in a 375 pt canvas). The system animates the capsule's width between the two, so any layout decision read from the accessory's own width changes mid-morph (issue #300). Traps: a `.sheet` attached **inside** the accessory never presents (the root presents Notifications/Profile via `openNotifications`/`openProfile`); a `Menu` there **does not open while inline** (known iOS 26 issue) and, expanded, answers only near its glyph (a full-slot label or `contentShape` does not widen it; `NavButtonHitRegionJourneyTests` failed at 20 pt off-centre); a `TextField` there did not focus |
| `searchToolbarBehavior(.minimize)` | 26.0 | Field becomes a top toolbar button after the avatar (breaks the avatar-rightmost rule): unused |
| `DefaultToolbarItem(kind: .search, placement: .bottomBar)` | 26.0 | Inside a `TabView` the bottom toolbar renders behind the floating tab bar: unusable |

## Rules (issue #92, 2026-10-04; issue #300, 2026-10-04)

HIG sources: `apple-hig/references/hig/toolbars.md`, `search-fields.md`, `searching.md`, `tab-bars.md`, `motion.md`, `accessibility.md`, `designing-for-iphone-duo` (via `duo.md`), `buttons.md`.

1. **iPhone: page tools in the tab-bar accessory, on every page; Profile in the header.** The accessory reads left to right: the page's own actions in page order (Songs: Sort, then Filter), **Quick Links** only on pages with Quick Links, then (selected profile only) a divider and **Notifications**, pinned to the trailing edge. Songs reads Sort · Filter · Quick Links | Notifications; pages without tools show only Notifications. **Profile** is the navigation bar's trailing-most item on every page, its own glass group after a `ToolbarSpacer(.fixed)` (tab roots: `FestivalRootTrailingItems.accessoryProfileItem`; pushed pages: `.pageTrailingItems()`; the player page's Select/Switch sits before it). It still opens profile selection, or the selected player's Statistics (#290). With no profile and no tools (Compete, Settings before Quick Links register) the accessory has nothing to show and is disabled (`PageToolsRegistry.hasContent`) rather than drawn as an empty capsule; the system then hides it. Pages register tools with `.festivalPageTool(token:order:isEnabled:)` (`PageToolOrder`; Quick Links via `QuickLinksPageTool`); `PageToolsRegistry` shows only the front page's (`pageToolsScope()` on every tab root and pushed page in `FestivalTabStack`), so a push, pop or tab switch swaps them. Where `\.pageToolsRegistry` is nil (Duo vertical bar, iPad, iOS < 26.1) the same pages keep trailing navigation-bar items: reading right to left Profile, Notifications, Quick Links, page actions (`FestivalRootTrailingItems`, `.pageTrailingItems()`; HIG Toolbars: "Trailing: important always-available items"). **Supported deviation:** HIG Tab bars treats the accessory as a slot for a persistent item such as Music's MiniPlayer and toolbars as the place for view actions; the owner chose the accessory, so it uses only the public API, keeps icon-only symbols with labels, 44 pt targets, Liquid Glass and safe areas, and never adds actions as tabs.
2. **Two groups, fixed slots.** In the accessory a 1 pt divider (hidden from VoiceOver) separates page tools from Notifications. Every item has a **fixed 44 pt slot** (`PageToolsAccessoryFit.slot`; the label fills it, `PageToolsAccessoryLabelStyle`, so the hit region is 44 × 48 pt; HIG Buttons: "the hit region is at least 44x44 pt"): page tools from the leading edge, then a flexible space, then the divider and Notifications at the trailing edge. Items never share out the width, so a push, pop or tab switch only swaps the page tools and Notifications never moves (issue #300; before, five evenly shared slots moved every item whenever the count changed). Text in the fixed-height capsule stops at `xxxLarge`; long-press shows the Large Content Viewer. VoiceOver reads the container "Page Tools" (`fst.page-tools`) left to right. In navigation bars: page tools, then account, separated by `ToolbarSpacer(.fixed)` in horizontal bars (`RootChromeTrailingGroups.separatesAccount`; HIG Toolbars: "generally use no more than three groups"); the Duo vertical bar adds no fixed spacer (HIG iPhone Duo: "system spacing adapts, so don't add fixed spacing"). Page actions use `.festivalPageAction` (never `.primaryAction`, `PushedPageAvatarPlacementTests`).
3. **Global search is a Search tab.** A trailing `Tab(role: .search)` (`RootTab.search`) shows `GlobalSearchTab` with the keyboard up. HIG Search fields: a separate trailing tab "focuses the field and opens the keyboard immediately… choose it for fast, transient search that returns to the previous tab on exit"; HIG Tab bars: "A dedicated Search tab may be trailing." The section underneath stays selected: **Close** or tapping that section returns to it with its stack intact, and a chosen result is pushed on it (`RootTabTransition`, unit-tested). The query and scope survive while closed, but the system clears the text on Close. **No other global-search entry point** on iOS: no accessory, dock, toolbar button or floating capsule; ⌘F/⌘K select the Search tab. Five-tab limit: `FestivalTabPolicy.fittingSearchTab` drops **Statistics** first from compact phone tabs (player: Songs · Suggestions · Compete · Settings · Search); the drawer's Statistics row pushes it. Songs, Compete and Settings are never dropped (the drawer has no Compete row or pushable Settings). On folded Duo this also returns the rail's Profile slot (with six rail tabs only the bell fit beside `…`).
4. **iPad:** a regular-width window keeps the sidebar; a **Search** row heads it (`fst.nav.sidebar.search`) and shows the same search page in the detail column, field **unfocused** (HIG Search fields: "on iPad with only a virtual keyboard, leave it unfocused to avoid unexpected keyboard coverage"), with the account items in that column's bar. Compact iPad windows use the phone tabs, Search tab included. The column that owns a page shows its top-bar items.
5. **Inline list filter where the web has one.** Songs uses `.searchable(text:placement: .navigationBarDrawer(displayMode: .always), prompt: "Filter Songs")`: pinned above the list, filtering it with the current sort and filters (HIG Search fields: "Use an inline field when adjacency clarifies that it filters one view rather than searches globally… Put a top inline field above its list and consider pinning it"; "Use placeholder text to state what is searchable"; HIG Searching: Music "filters current songs/albums"). No second magnifier button. Only Songs has a list text filter on the web (`SongsToolbar.tsx`); Item Shop and the player page have none, so they get no field. **Owner-approved Duo variant (#333):** on iPhone Duo (any pose) the field is instead the shared `BottomSearchField` (`GlobalSearchField` on `festivalCardCapsule`) in the page's bottom safe-area inset, full width, on the trailing page only in book pose (`BottomSearchFieldPlacement.pageHinge(for:)`; agent decision #334, owner #349) ([pattern R2](../../patterns/page-tools-and-nav-chrome.md)); `SongsFilterFieldPlacement.resolve(pose:)` decides it, unit-tested.
6. **Overflow, decided once for both placements.** HIG Toolbars (iOS): "Put only essential actions in the main area; use More for the rest." In the accessory, `PageToolsAccessoryFit.folds` folds Songs' Sort and Filter into one **Sort and Filter** control (`slider.horizontal.3`, not an ellipsis: HIG iPhone Duo "reserve ellipsis for overflow") only when the **inline** accessory for this window (`PageToolsRegistry.windowWidth` − 180 pt − 12 pt padding) is narrower than the items' slots, or text is at an accessibility size; Quick Links and Notifications stay visible. The tab view's width does not change while the system morphs the accessory, so the expanded and inline accessory always show the same items: it never reads the accessory's own width (issue #300: folding from the live width swapped Sort · Filter for Sort and Filter halfway through every minimize and back on every expand, the reported jitter). The widest page (3 tools + Notifications = 177 pt) fits inline from a 375 pt window up, so only accessibility text sizes or Display Zoom-narrow windows fold. No animation is added to the swap (HIG Accessibility: "reduce automatic and repetitive animation"). In navigation bars `SongsToolbarFold.folds` does the same below 390 pt. The Duo vertical bar and the iPad sidebar keep system overflow, with Quick Links, bell and profile at `visibilityPriority(.high)` (`RootChromeRailItem`).
6a. **Menus in the accessory open as a sheet.** iOS 26 does not open a `Menu` in the accessory while it sits inline, and expanded its hit region is only the glyph, so in the accessory `PageToolMenu` (Quick Links, Sort and Filter, Rank By, Band Size) renders a button with the same label that lists the same choices in a compact sheet (`PageToolInlineMenuSheet`, presented from the root, title = menu name, current choice checked, Close `fst.page-tools.menu.close`), the same whether or not the tab bar is minimized. A picked choice runs after the sheet has closed (`PageToolsRegistry.choose` → `inlineMenuDismissed`), so a sheet it opens (Filter…) never collides with it. In navigation bars (Duo, iPad) it stays the ordinary menu.
7. **Tab bar minimizes on scroll** on the horizontal iPhone tab bar (`RootTabBarBehavior`), moving the accessory inline (HIG Tab bars: "With an attached accessory such as Music's MiniPlayer, scrolling down can minimize the bar and move the accessory inline"); Duo rail and iPad keep `.automatic`. The accessory hides while the Search tab is open, and while it has nothing to show (rule 1). Pages' own pagers (Full Rankings' pinned pager, Band Rankings' floating pager) sit above it.
8. **Player page Select / Switch / Deselect** is its own header button (text, prominent for Select/Switch; `ProfileIdentityToolbarItem`), `VerticalBarActionItem` in the Duo rail.
9. **Sheets apply immediately.** Songs Filter and Sort have no Cancel/Apply: every change applies, and a trailing **Done** closes the standard `festivalSheet` modal. Sheets open at the large detent.
10. **Header legibility:** every page gets `TopEdgeScrim` (`Common/Chrome/PageChrome.swift`): iOS 26 `scrollEdgeEffectStyle(.soft, for: .top)` plus a dark gradient behind the bar region over the artwork, at most 150 pt and ending 32 pt below the bar (`TopEdgeScrim.height(topInset:)`, issue #286), so it never dims a Quick Links landing under a short iPad, landscape or Duo bar. It ignores the top and horizontal safe areas (`TopEdgeScrim.extendedEdges`, #335), so under the Duo vertical bar the art is darkened exactly as beside it. Collapsed inline titles are 20 pt semibold, Dynamic Type scaled (`NavigationTitleStyle`).
11. **Monogram avatar** renders to a cached image (`MonogramLabel`/`MonogramImageCache` in `App/Shell/RootChrome.swift`) so it stays a standard bar button with the system hit expansion (issue #15); a custom-view item would not get it. **On iOS/iPadOS 26+ the avatar is the whole button:** its toolbar item hides the shared Liquid Glass (`sharedBackgroundVisibility(.hidden)` via `profileItemBackground`, only for `RootProfileButton.Presentation.monogram`) and the image is the 44 pt diameter of a bar item's glass circle with no rim (`RootProfileButton.MonogramMetrics`). A bar pads a background-less item by 10 pt on each side, so the image's alignment rect insets that much on both sides: the circle draws exactly where the glass circle was, 12 pt (the group gap) from the bell's glass on iPad. No glass ring shows around it on tab roots, pushed pages or Search (issue #311; [pattern R8](../../patterns/page-tools-and-nav-chrome.md)). The add-profile glyph, the Duo rail's symbol item, the bell and page tools keep their glass; iOS 17–25 and the Mac toolbar keep the 30 pt outlined avatar. Visual evidence: `ProfileAvatarFillJourneyTests` (iPhone and iPad UI targets) screenshots Songs, Item Shop and Search (iPhone: the Search tab has no avatar, then the page again after closing it) and measures the disc with `ProfileAvatarPixels` (44 ± 2 pt round, 6–20 pt from the trailing edge when no page tool or toolbar search field follows it, band just outside no lighter than the bar); the pre-#311 30 pt disc in its glass ring fails it.

## Small widths

`FST_DEBUG_CANVAS_WIDTH=375` (Debug) lays the app out in a 375 pt canvas on the 402 pt iPhone 17 Pro. Accessory (issue #300, 2026-10-04): 44 pt slots everywhere. 402 pt: Songs and Song Detail keep all four items expanded (348 pt) and inline (222 pt). 375 pt canvas: Song Detail inline (195 pt) shows Item Shop · Paths · Quick Links | bell with the bell's slot ending at the capsule edge. `AccessibilityXL` at 375 pt: Sort and Filter | bell, the same expanded and inline. Nothing clipped; UI journeys `NavButtonHitRegionJourneyTests` (including `testAccessibilityTextFoldIsTheSameExpandedAndInline`) and `SongsChromeJourneyTests/testToolsStayInTheTabBarAccessoryWhileScrolled`.

## Why the accessory jittered (issue #300)

Two layout choices, not the system, caused it. (1) The fold read the accessory's live width: during the system's expanded ↔ inline morph Songs' five items (Sort, Filter, Quick Links | bell, avatar = 253 pt) stopped fitting partway down to 222 pt, so Sort · Filter became Sort and Filter mid-animation and back on the way out; Song Detail's fixed four items morphed cleanly, which isolated the cause. (2) Items shared the width evenly, so any count change between pages (or a late Quick Links registration) moved every item. Fix: Profile back to the header (HIG Toolbars: "Trailing: important always-available items… Trailing items remain visible at every window size"), fixed 44 pt slots with the bell pinned trailing, and a fold decided from the window width so both placements agree. HIG sets **no numeric maximum** for the accessory: HIG Tab bars shows it holding one persistent item (Music's MiniPlayer) and HIG Toolbars asks for "only essential actions in the main area". No animation was added to hide the swap (HIG Motion: "Add motion purposefully").

## Drawer

Matches the web sidebar (`Sidebar.tsx`): Songs, Suggestions*, Statistics*, Rivals*, Leaderboards, Item Shop (*player), the current destination highlighted; the profile row (name → profile, **Deselect**) or **Select Profile**, then **Settings** pinned at the bottom. Bands and Licenses are not listed (Bands: search and leaderboard links; Licenses: Settings).
