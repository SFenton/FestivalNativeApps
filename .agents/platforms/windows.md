# Windows architecture and performance

> **What:** WinUI 3 stack, the C#-vs-C++/WinRT decision and its evidence, build/perf tooling, host tooling and `tools/windows/uiwin.py`. **Read when:** working on or driving the Windows app (host `sfenton-music`, reached via [windows-relay](../workflow/windows-relay.md)). Design: [design/windows.md](../design/windows.md); tests: [testing/windows.md](../testing/windows.md).

## Stack

- **C# / .NET 9 + WinUI 3, Windows App SDK 2.5.1**, unpackaged, self-contained, x64, min Windows 10 19041. The Store build adds `-p:FstMsix=true` (unsigned MSIX via `tools/windows/package_msix.ps1`; see [release machine](../workflow/release-machine.md#windows-microsoft-store)). C#/WinRT projection pinned to `10.0.26100.87` (trim/AOT-annotated).
- MVVM with CommunityToolkit.Mvvm. `Festival.Core` (UI-free, `net9.0`) holds `Data/` (request gate, client, wire models, caches, settings store), `Domain/` (instruments, songs pipeline, routes, settings, launch options, artwork policy) and `ViewModels/`. `Festival.App` holds XAML, controls and thin code-behind.
- System.Text.Json source generation everywhere (no reflection), so Release can be trimmed or NativeAOT-published.
- Service access: [service-safety.md](service-safety.md). The single gate is `RequestGate` (GET-only, rejects `X-API-Key`/`x-fst-selected-*`, 30 s deadline, maps 202/304/404/503 + `Retry-After` + freeze reason to `ServiceIssue`). `FestivalApiClient` bootstraps `/api/publication`, pins only when `readyForPinning && pinningEnabled`, reuses ETags within one publication, retries one `publication_changed` 409. The one exception to `RequestGate` is the live socket (`Data/PublicationLiveUpdates.cs`, #616): `ClientWebSocketPublicationLiveSocket` opens `/api/ws?publicationId=N` (wss only; ws only on loopback, and only with `FST_LIVE_PUBLICATION_UPDATES=1` in Debug or automation launches) with no headers, cookies or credentials, sends nothing but Close and only re-reads `/api/publication` on a message; `PublicationLiveConnection` runs it while the window is visible and not minimized, with web `useAppWebSocket` backoff (1 s doubling to 30 s, reset on open). `SocketsHttpHandler` has no disk cache; art never goes through `BitmapImage.UriSource` (which would use the WinINet cache).
- Routes: `AppRoute` records for every web route except the deprecated Manual; `AppRouteParser` parses web paths (deep links, `--route`). Routes carry IDs, not objects.
- Settings: `settings.json` in the app data folder (atomic temp-file replace, re-validated on load; corrupt → defaults). The selected player survives restarts. Online-only: no offline UX.
- App data folder (`Data/AppDataPaths.cs`): Release always `%LOCALAPPDATA%\FestivalScoreTracker`. **Debug** uses `FST_DEBUG_DATA_DIR` when set, else `%LOCALAPPDATA%\FestivalScoreTracker.Debug\<worktree>-<hash8>` derived from the build's git worktree, so parallel lanes never share settings, the selected profile, seen-state or `diagnostics.log`. `App.OnLaunched` configures it before any store resolves a path. `FST_SETTINGS_PATH` still overrides just the settings file.
- State-file registry (`Data/AppStateFiles.cs`): every persisted file (settings, first-run, notifications-seen, suggestions-filter, diagnostics log) is listed with its Settings-Reset behaviour; a feature that persists anything adds its file there and reads `AppStateFile.DefaultPath`. Reset rewrites `settings.json` in place (profile and song filters stay) and deletes `Delete`-scoped files (today `suggestions-filter.json`); the shell then drops the owning section's cached frame (`AppStateFile.Owner`) so it reloads from defaults.
- Don't disable background visuals just because focus moves to a game (the app may stay visible beside it); use data-saving/reduced-motion and measured occlusion policies. Don't adopt invented startup/memory limits or assume a notification-state API recognizes every game.

## Language decision: stay on C# (decided 2026-09-28)

Guidance: Microsoft recommends WinUI 3 for new desktop apps and supports both C# and C++/WinRT ([WinUI 3](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/), [FAQ](https://learn.microsoft.com/en-us/windows/apps/get-started/windows-developer-faq)); the WinUI team's position is that C# with NativeAOT approaches C++ ([discussion #10328](https://github.com/microsoft/microsoft-ui-xaml/discussions/10328)). Rendering (XAML, DirectComposition, DWM) is native in both, so language only changes the managed-runtime floor.

Twin benchmark (`tools/windows/bench.ps1`: same window, label and full-window image with the same stepped composition zoom; medians of 5 runs, Release, Ryzen 7 9800X3D (16 threads), RTX 5090, 3840×2160 at 240 Hz):

| Variant | First frame | Private MB | Working set MB | CPU animated / static (one core) |
|---|---|---|---|---|
| C++/WinRT | 173 ms | 146.9 | 87.5 | ≤1% / 0.1% |
| C# NativeAOT | 182 ms | 150.9 | 92.4 | ≤1% / 0% |
| C# ReadyToRun | 214 ms | 153.7 | 104.4 | ≤1% / 0% |

Animated CPU for all three is at the resolution limit of `TotalProcessorTime` sampling (the C++ twin read 0% while visibly animating). Caveat: another app instance was idling on the host during this run.

Full app (Release, 1280×820 at 150%, live API, 30 s per scenario, `tools/windows/perf.ps1`):

| Scenario | Shell loaded (JIT / AOT) | App CPU, one core (JIT / AOT) | GPU 3D | Private / working set MB (JIT / AOT) |
|---|---|---|---|---|
| Songs, animated background | 717 / 333 ms | 4.2% / 2.7% | 1.0% | 243 / 235 · 223 / 192 |
| Songs, animated + list auto-scroll | 736 / 331 ms | 16.5% / 13.2% | 1.8% | 267 / 270 · 252 / 230 |
| Songs, static (reduced motion) | 357 / 294 ms | 0.0% / 0.0% | 0% | 238 / 238 · 216 / 193 |
| Song Detail (static cover) | 338 / 281 ms | 0.0% / 0.1% | 0% | 224 / 215 · 190 / 163 |
| Minimized | 342 / 287 ms | 0.1% / 0.0% | 0% | 241 / 238 · 215 / 193 |

Scroll frame delivery (UI thread, `--frame-stats`, which itself forces per-frame rendering): 240 fps, p50 4.2 ms, p95 4.6–4.7 ms, p99 5.0 (JIT) / 8.3 (AOT) ms, no frame over 33 ms. The songs list is ready 0.8–2.1 s after launch, dominated by the live catalogue fetch. Managed heap is only ~42 MB committed; the rest of the working set is native XAML, composition and image surfaces, which C++ pays too. Whole-app CPU stays under 0.3% of the 16-thread machine except while scrolling.

**Decision:** keep C#. C++/WinRT's advantage is ~10 MB private memory and a slightly lower working set; NativeAOT closes the startup gap (first frame within ~10 ms of C++), and animation cost is set by the compositor, not the language. Background motion costs were dominated by redrawing at display refresh, fixed by stepped keyframes (see [artwork-background](../controls/artwork-background/windows.md)). Re-open only if a measured scenario beside a game shows managed GC or JIT on the critical path.

**Ship configuration:** NativeAOT Release (`build.ps1 -Configuration Release -Aot`). Constraints: collections bound to XAML must have concrete `List<T>`/`ObservableCollection<T>` static types (CsWinRT generates vtables only for types it sees; an `IReadOnlyList<T>` backed by a collection expression threw `E_INVALIDARG` in `ItemsSource`), use `x:Bind` rather than `{Binding}`, and keep `CsWinRTAotOptimizerEnabled`.

**Automation mode** (`Domain/AutomationLaunch.cs`): `--automation` or `FST_AUTOMATION=1` makes a launch honour every `FST_*` environment hook (deep links, loopback base URL, `FST_SETTINGS_PATH`, `FST_DEBUG_PROFILE`/`ANONYMOUS`, a per-worktree data folder), defaults first-run carousels to off (an explicit `--first-run` still wins) and presents no other UI unasked. Debug honours the request alone; **Release/NativeAOT honours it only when `fst-automation.marker` sits next to the executable**, which `uiwin.py launch` writes into publishes under `windows/.artifacts` (never elsewhere), so an installed build can't be switched by an environment variable. `build.ps1` republishes into a clean folder, so a fresh publish carries no marker. `uiwin.py launch` sets `FST_AUTOMATION=1` for every launch (`--no-automation` for user-default runs). Diagnostics (unhandled exceptions, binding and resource failures) go to `diagnostics.log` in the app data folder.

## Gotchas

- `TreatWarningsAsErrors` is on for all projects; trim-analysis warnings from framework assemblies are kept non-fatal (`ILLinkTreatWarningsAsErrors=false`).
- `dotnet publish -p:PublishAot=true` needs `vswhere` on `PATH` (`build.ps1` adds it).
- XAML compiler crash `WMC9999` ("Could not find any resources appropriate for the specified culture…") hides the real error. One cause: an `x:Name` inside an `x:DataType` template equal to a bound property of that type (e.g. `x:Name="BadgeText"` + `{x:Bind BadgeText}`). Bisect by stripping templates.
- Each feature's `[JsonSerializable]` types need their **own** `JsonSerializerContext` class (e.g. `SongsJsonContext`); attributed partials of one context collide in the source generator.
- `coverage.runsettings` excludes only `GeneratedCode`/`ExcludeFromCodeCoverage` attributes and `*.g.cs` files. Do **not** exclude `CompilerGeneratedAttribute`: that also drops every `async` state machine and lambda body (until 2026-09-28 ~2,200 lines, e.g. all of `FestivalApiClient`'s async reads, were silently unmeasured and async-only partials failed as "missing coverage").
- WinUI content is presented by DWM through DirectComposition: PresentMon attributes no presents to the app process, only to `dwm.exe`. Use app CPU, DWM CPU and GPU 3D engine counters; treat DWM present intervals as a system-wide signal.
- Handling `ContainerContentChanging` with `args.Handled = true` suppresses x:Bind template updates.
- **A collapsed element's tooltip stays open** (issue #571): WinUI raises no PointerExited or LostFocus when a breakpoint sets an element `Collapsed` under the pointer or keyboard focus, so its tooltip floats where it was and its windowed `PopupHost` stays in the UIA tree (Axe open item 8 in [windows-accessibility.md](../testing/windows-accessibility.md#open-issues)). Clearing or replacing a plain-string `ToolTipService.ToolTip` does not close an open one either. Every element that a width breakpoint (or a responsive control's own layout swap) collapses is registered with `Controls/CollapsedToolTip.CloseWhenCollapsed(element)`: on `Collapsed` it closes every open tooltip **in the element's subtree** (`CloseWithin`), so a consumer that hides a whole panel covers the controls inside it. Give a tooltip the helper can close: set it with `CollapsedToolTip.Set(element, content)` (an app-owned `ToolTip`; update its `Content`, never re-set the service value) or declare `<ToolTipService.ToolTip><ToolTip …/></ToolTipService.ToolTip>`; a plain string realized later (an item template) is closed by matching the window's open tooltip popups against it. A swap that rebuilds children calls `CloseWithin` before clearing them. When the collapsed side held focus (`CollapsedToolTip.HasFocusWithin`, checked *before* the swap), hand focus to its replacement with `HandFocus(anchor, () => control)` or `HandFocusWith(anchor, focus)`: both use `FocusState.Programmatic` (the user resized, so the newcomer opens no keyboard tooltip; never pass the old `FocusState` on) and retry once after layout; otherwise WinUI moves focus to the next control and opens *its* tooltip. Consumers: the title-bar search box ↔ compact button (`MainWindow.Search.cs` `ApplySearchWidth`), `QuickLinksMenuButton` and `QuickLinksHost` (menu ↔ pane, focus to the pane's current item or back to the button), the Settings menu ↔ pane and list/detail switch (`SettingsPage.OnRootSizeChanged`: focus stays on a moved card or goes to its chevron row/body, then the replacement is brought into view after the new layout settles, since programmatic focus scrolls against the old one), `InstrumentSelector` (full row ↔ compact arrows, arrows/circles/centre via `Set`; focus to `FocusCurrent`'s button) and `SongPathsView` (wide selectors ↔ compact boxes; the sheet fixes its width when it opens, so this swap is defensive today). Tests: `a11y-search.json` `search-swap-*`, `a11y-instrument-selector.json` `instrument-selector-swap-*`, `a11y-settings-swap.json` `settings-split-swap-*`.
- **A search box's hint tooltip opens over its suggestions** (issue #571): keyboard focus (Ctrl+E) opens an `AutoSuggestBox`'s hint after WinUI's show delay, and typing that starts within the delay does not cancel it under `SendInput`, so the hint opened over the suggestion list and its windowed `PopupHost` failed Axe. Every `AutoSuggestBox` with a `ToolTipService.ToolTip` calls `Controls/TypingToolTip.SuspendWhileTyping(box)`: from the first typed character (or the suggestion list opening) until focus leaves the box, the hint is closed and removed (`CollapsedToolTip.Set(box, null)`), then restored for the next focus. Consumers: the title-bar search box (`MainWindow.Search.cs`) and the Search page field (`SearchPage`). Tests: `PopupHostingMarkupTests.AutoSuggestBoxHints_SuspendWhileTyping`, `search.json` `wide-hint-suspends-while-typing`, `a11y-search.json` `search-suggestions` (no `ToolTip` 1.5 s after typing, Axe 0).
- An `ItemsRepeater` with a virtualizing `StackLayout` inside a page `ScrollViewer` estimates its unrealized items' heights from the realized ones. When the items differ widely in height (scored vs. unplayed profile sections, card rows), the extent changes as you scroll. The page jumps after Back (#276) or snaps back from its end (#533: the scrollbar to 100% landed at 76%, PageDown went backwards, and the last groups were unreachable), and unrealized items are missing from the Tab and Narrator order. For a bounded list in a page, use `LeaderboardsCardGridLayout` (`MaxColumns="1" MinColumnWidth="0"` for a stack). Keep per-item reads lazy with the element's `EffectiveViewportChanged` (Player Profile, `LazySectionReach`), not `ElementPrepared`. An x:Bind template root has no `DataContext`, so resolve the item with `GetElementIndex`.
- The default `ListViewItem` template binds `Background` and `Padding` (as `ContentMargin`) to its `ListViewItemPresenter`, but not `BorderBrush`, `BorderThickness` or `CornerRadius`. The radius is the `ListViewItemCornerRadius` theme resource, and the rounded fill is inset 4,2 epx from the item bounds. So override the radius in the `ListView.Resources`, and draw a card stroke in the item template's root `Border` with `Margin="4,2"` (issue #272, notification rows).
- Native `PackageReference` in a `.vcxproj` needs `ResolveNuGetPackages=false`.
- **Per-scroll-frame WinRT objects stall scrolling** (#642): every C#/WinRT wrapper adds 1000 bytes of `GC.AddMemoryPressure` (`IObjectReference`), so about 4,000 new native objects induce a blocking gen2 collection however small the managed heap is (12–23 ms on this host, once or twice per 2 s of scrolling). New objects are what count: each `TransformToVisual` (a new `GeneralTransform`), each event's args (`ViewChanged`, `ViewChanging` and its `NextView`, `EffectiveViewportChanged`, `CompositionTarget.Rendering`), each brush or geometry. Wrappers of live elements (`ContainerFromIndex`, `GetParent`) come from the cache. In code that runs while a scroll moves: transform one element that scrolls with the content (a list's panel, the scroller's `Content`) once per update and place the rest by `UIElement.ActualOffset` (`Controls/LayoutGeometry.TopWithin`; it ignores render transforms and composition translations, as `TransformToVisual` ignores the latter); cache positions that don't change with the scroll (`SongsPage.ShowIncoming`'s push origin, `BoardFooterFade`'s footer top on intermediate changes); throttle reports that only update a highlight (Quick Links, `QuickLinks.IntermediateReportInterval`); and unsubscribe from per-frame events once their work is done (`PlayerProfileView` after a section loads, FadeIn's `ScrollTracker` once `StaggerArm.WatchesScroll` is false). Measure with `tools/windows/scroll_probe.py` (below) and check its `gc` line's `gc2=` per pass. Upstream: [microsoft-ui-xaml#12112](https://github.com/microsoft/microsoft-ui-xaml/issues/12112).
- **A final `ViewChanged` fires every frame of a scrollbar-thumb drag** (#668): a non-animated `ChangeView` (thumb drag, keyboard, UI Automation `SetScrollPercent`) raises `ViewChanged` with `IsIntermediate=false` on every frame, so work kept for "the scroll settled" runs 120 times a second. Quick Links treated each one as settled and walked its anchors (3–4 ms a frame: Song Detail drag handlers 310–335 ms per 1.5 s pass, p95 16 ms). A final change within `QuickLinks.IntermediateReportInterval` of the previous one is part of a stream (`QuickLinks.ContinuesFinalStream`): report it like an intermediate one and do the settled work once, 100 ms after the stream stops (`QuickLinksBinder.SettleStream`). Apply the same to any new final-change handler.
- **A virtualizing `StackLayout` in a nested `ItemsRepeater` stalls scrolling** (#668): each repeater with a virtualizing layout follows its effective viewport, so a page of cards or rows whose templates nest small repeaters (a band's members, a member's instrument icons) re-measures them all on every scroll frame. Player Bands (25 cards, about a hundred nested repeaters) scrolled with p95 99–141 ms and 480 ms stalls; the Song band board's rows with p95 33–41 ms. A short bounded list inside a scrolled card or row stacks with `LeaderboardsCardGridLayout` (`MaxColumns="1" MinColumnWidth="0"`, below) or, for a horizontal row such as instrument icons, `Controls/NonVirtualizingRowLayout` (afterwards p95 8.8 and 9.0 ms); only a page-length list keeps a virtualizing layout.
- **A dimmed or switched-off display throttles frames to ~31 ms** (#668): DWM paces a window on a display in power-saving state like a covered one, so frame timings taken then measure the timer, not the app (the earlier "31 ms Song Detail frames" were this). `scroll_probe.py` wakes the display by nudging the mouse one pixel and back before each entry, the probe holds it on with `SetThreadExecutionState`, and each pass records `hidden=display-off` from `OcclusionTracker` when it happened anyway.
- Expander (#561): `DefaultExpanderStyle` is not a resolvable `StaticResource` in this app, so an implicit `Expander` style must not use `BasedOn` (the page fails to load); the default template still applies under it. Never assign `VisualState.Storyboard` on a templated control at run time: the next `GoToState` hangs and UIA `Expand` times out. To replace a state's motion, `Stop()` its storyboard and `Children.Clear()` it in place (`Controls/Accordion.cs`).
- Storyboards over newly shown content (#561): begin them after the content's first rendered frame (`CompositionTarget.Rendering`), not in the handler that makes it visible. The first layout of new content can stall the UI thread ~50 ms, and a storyboard's clock runs through the stall, so its first visible frame skips most of a short animation (`AccordionMover.OnStartFrame`).
- UIA automation in a locked session: the driver's `invoke:` falls back to a real mouse click on controls without the Invoke pattern (a `ToggleButton` such as the Instrument Selector's circles), which does nothing while the desktop is locked. Use `toggle:` for toggle buttons. Content inside a named Expander is not in the `assertorder` walk (the Expander reads as a whole button), so check revealed content with `assertread`.

## Desktop sessions

Lanes run over SSH in non-interactive **session 0**, where no windows, UIA tree or screenshots exist. The operator `sfent` is logged on at the console (session 1). `uiwin.py` runs each driver request in session 1 through a one-shot `schtasks /Create … /IT` task named `FST_UiWin_<token>`, deleting the task immediately afterwards. It configures no autologon and no persistent task. If nobody is logged on at the console, GUI commands fail with "no interactive console session".

Targets: `--pid`, `--process <name>`, or the pid last launched from this worktree. Other lanes' app windows often sit exactly on top of yours (every launch is centred), so the driver foregrounds the target before every real-input step (`click`, `rightclick`, `type`, `key`, `scroll`) and `shot --mode screen`: a topmost/not-topmost bounce, then `SetForegroundWindow` with the foreground thread's input attached and a zero-length mouse move to lift the foreground lock, waiting until it is foreground. If it still isn't and something overlaps it, the step fails naming the covering windows instead of clicking into another lane's app. `--isolate` also minimizes overlapping windows of other same-named processes for the request and restores them (without activating) when it ends. UIA-pattern steps (`invoke`, `toggle`, `select`, `waitfor`) and `print` screenshots work while covered. Step paths in MSYS form (`shot:/c/...`) are translated to `C:/...` (Python alone resolved them to `C:\c\...`).

Tablet posture: Windows 11 has no tablet mode. The touch-optimized taskbar only appears on real 2-in-1 hardware when the keyboard detaches, so it can't be emulated here. Approximate a tablet with `portrait-tablet`, `full-screen` or `maximized` plus touch-sized targets; a true tablet pass needs real touch hardware (TODO(orchestrator)).

Layout: `assertinset:<sel>|<container-sel>|<epx>` waits up to 3 s until the element's UIA top edge is `epx` effective pixels (window DPI) below the container's top, within 1 epx (Quick Links landing, `journeys/quick-links-landing.json`); UIA rects of panels such as `AccessibleGroup` start at their first visible content, not at a child's top margin. `scrollinset:<sel>|<scroller-sel>|<epx>` (epx > 0) scrolls the scroller through the UIA Scroll pattern until the element's top sits `epx` below the scroller's top, within 1 epx: a fixed list position for Axe scans (issue #259; see [testing/windows](../testing/windows.md) "Scrolled matrix pages end on a deterministic edge"). A trailing `|end` also accepts the scroller's end (100%) when a target near the bottom cannot rise that far but its top is on screen (#571). `pagedown:<scroller-sel>[@seconds]` waits (default 5 s) until the scroller has content below its viewport (vertical scroll < 99%), then pages it down one viewport with the UIA Scroll pattern's LargeIncrement: it brings an appended batch's first rows on screen without a fixed settle (#664). Tree lines also carry `heading=`, `landmark=`, `live=`, `accel=`, `access=`, `status=` and `desc=` when set (each read independently, so a property a WinUI peer rejects doesn't drop the rest), and a `selected` flag on selected SelectionItem elements such as the current `fst.nav.*` pane item. Narrator model (issue #271; no input, locked-console safe): `narrate:<sel>` records the reading order and phrase under an element, `assertread:<sel>[@secs]|<phrase>` (exact, or `~<regex>`) checks one element's phrase and `assertorder:<sel>|<sel>[|…]` checks that the elements are read in that order (results `narration`, `read`, `orders`; see [testing/windows](../testing/windows.md) "Narrator model"). Real presses at an offset (issue #271 retry; unlocked console only): `tapat:<sel>|<dx>,<dy>` sends an injected touch tap and `clickat:<sel>|<dx>,<dy>` a left mouse click at the point `<dx>,<dy>` epx from the element's centre. The driver refuses a locked session, and a point covered by another process's window, rather than sending input elsewhere (results in `presses`, with `nonclient` when the point reads as caption).

While the Windows session is locked, `shot:` returns a black frame (title-bar glyphs only) and `shot:@screen` captures the lock screen; neither is evidence. UIA still works, so `tree` reads control text (e.g. `fst.settings.app-version`) even for offscreen rows; capture pixels only once the desktop is unlocked.

The driver's `sysset` request (used only by `a11y_matrix.py`, inside its lock hold) switches contrast themes (`aquatic`, `desert`, `dusk`, `night-sky` via `SPI_SETHIGHCONTRAST` with the legacy scheme display names; the registry's `@themeui.dll,-85x` names are ignored), Animation effects (`SPI_SETCLIENTAREAANIMATION`), transparency (`EnableTransparency` + `ImmersiveColorSet` broadcast), app light/dark theme (`AppsUseLightTheme` + broadcast), primary-display scale (`FstUia/DisplayScale.cs`, `DisplayConfig` relative DPI steps) and text size (`HKCU\Software\Microsoft\Accessibility\TextScaleFactor`, read by apps at launch), and returns the previous values so the runner restores them before releasing the lock. The `SystemParametersInfo` import must be the `W` entry point: the ANSI one silently garbles the scheme name and Windows applies the last-used contrast theme instead.
## Desktop lock

- A single `desktop` host lock (`tools/android/hostlock.py`, shared with the emulator lock design: an OS lock plus a FIFO ticket queue in `~/.fst-locks/`) serializes every GUI command across lanes. A hold lasts at most **300 s**; each driver request also has its own budget (120 s, or the rest of the hold for `drive`).
- The driver is rebuilt automatically when its sources change (cached by hash under `~/.fst-tools/fstuia/`). Request/response files live in `~/.fst-locks/uiwin/`.
- A driver crash is reported immediately (the task ended without a response); details are in the Application event log under `FstUia.exe`.
