# Scroll edge: content under pinned chrome

> **What:** how scrolling content meets anything pinned above or below it: page headers, sheet headers, pinned section titles and bottom chrome (pagers, footers). **Read when:** you touch a fade, mask, scrim, scroll-edge effect or sticky header on any platform, or a bug says content "shows under", "is faded under" or "is cut off at" a header.

Status: **current**, 2026-10-05. Provenance: #10, #49, #93, #94, #286, #288, #297, #298, #301, #305, #306, #322 (audit 2026-10-05: six parallel mechanisms grew up for this one behavior), #308 (Apple consolidated to one component per edge kind; all three Apple edge fades read the scroll position on every supported system; Android and Windows moved to one shared linear ramp per edge kind; #305 merged into Windows #308's board ramp, which the #305 design review moved to the web board pages' 40 epx), #329 (Apple board footer ramp moved to 40 pt), #335 (`TopEdgeScrim` spans under the Duo vertical bar), #393 (Apple page header goes hard with the app's own R7 settings), #462 (Android footer band covers rows beneath it in the accessibility tree).

## Intent

Chrome never sits on half-visible content. Content scrolling toward a pinned edge is completely gone **at** that edge and fades back in over a short ramp **away from** it. Nothing is drawn behind header text. At rest nothing is dimmed. The web defines the behavior; platforms only choose how to draw it.

## Web source (behavior reference)

| Web | Behavior |
|---|---|
| `FortniteFestivalWeb/src/hooks/ui/useScrollMask.ts` (`DEFAULT_SIZE = 40`) | Linear CSS mask: transparent at the viewport/header edge, opaque 40 px inside it. No top mask while at the top (`atTop`), no bottom mask at the bottom. Used by `pages/Page.tsx` (unconditionally, on every page; no page passes `scrollMaskOptions`, so every board ramps 40 px). On the boards (Song, band song, Full Rankings, Band Rankings, Player Bands) `components/leaderboard/LeaderboardPaginationFooter.tsx` `useLeaderboardFooterScrollMargin` ends the scroll viewport at the floating footer, so this 40 px linear mask is the board-footer fade, with or without the player row. Also used by `components/modals/Modal.tsx` (`selfScroll`), `ChangelogModal.tsx`, `search/SearchModal.tsx`, `page/PageQuickLinks.tsx`, `settings/LicensesPage.tsx` |
| `FortniteFestivalWeb/src/hooks/ui/useScrollFade.ts` (`DEFAULT_DISTANCE = 36`) | Per-child mask at both viewport edges over 36 px with exponential `DEFAULT_STOPS` (0.01 at 15%, 0.40 at 75%), not linear. Used only by the Suggestions list, `SearchModal` and the player statistics content (`PlayerContent`); **no leaderboard uses it**, so it is not the board-footer rule |
| `components/common/PageHeader.tsx` | Header is rendered above the scroll container (portal); content never scrolls *behind* visible header text |

The web has **no sticky section headers**. Native pinned section titles are a native addition and follow R5.

## Rules

- **R1. One mechanism per edge kind per platform.** Every top or bottom edge treatment goes through the platform's canonical component (table below). Feature folders never build their own scroll mask, gradient mask or scroll-edge effect; extend the canonical component instead.
- **R2. Clear at the edge, opaque after the ramp.** Content is fully transparent at the obscuring edge (header bottom, pinned title bottom, chrome top) and fully opaque `ramp` units away from it. Nothing scrolls visibly behind header or title text.
- **R3. Ramp lengths come from the web.** The target is 40 pt/dp/epx linear for top edges and for a board's floating footer (pager, pinned player/band row): both are the web `Page.tsx` `useScrollMask` (`DEFAULT_SIZE = 40`, linear), the board footer because `useLeaderboardFooterScrollMargin` ends the viewport at the footer (#305 review). `useScrollFade`'s 36 px exponential per-row fade belongs to the Suggestions, Search and player-statistics lists, not to boards. Each constant lives in exactly one place per platform. Apple, Android and Windows board footers all ramp 40 (#305, #329); a 36-unit board ramp or a 28-unit smoothstep ramp is known debt, not precedent.
- **R4. At rest, nothing is dimmed.** At the top of a list there is no top ramp; it grows with the scroll offset (web `atTop`). At the bottom there is no bottom ramp.
- **R5. Pinned section titles behave like native sticky headers.** The title sits opaque on the page background and is never dimmed by a ramp. Rows, not titles, fade under it (R2). An incoming title pushes the pinned one out 1:1 with the scroll. Never swap text or snap. A container-level modal or page mask must not cover a pinned title; the list's own row fade takes over (`ModalTopEdgeFadeRampKey` = 0 on Apple). Everything a row draws fades with it, its separator included: a system-drawn list separator escapes the row's mask, so the pinned-title row hides it and draws the same line inside its own masked background (Apple `pinnedHeaderEdgeFadeRow`, #322). A screen reader reads the pinned title before the rows beneath it, then its section's rows, then the incoming title: a row partly hidden under the title must not be read first just because its clipped bounds start at the same edge (Android `rememberPinnedHeaderReadOrder`, #462).
- **R6. No decorative bands.** A header gets a glass or material band only when content actually scrolls behind floating chrome. HIG Scroll views: "Only use an edge effect when a scroll view is behind floating interface elements. It isn't decorative." Sheets hide the system edge effect (#94). **Approved variant (Apple pages):** the system soft top scroll-edge effect plus `TopEdgeScrim`, a dark legibility gradient over bright artwork that ends no lower than bar + 32 pt (max 150). It is a scrim, not a content mask, and must never dim a section-jump landing ([section-jump-landing](section-jump-landing.md)). The scrim spans the full screen width, under horizontal safe areas such as the Duo vertical bar (`TopEdgeScrim.extendedEdges`, #335), so the darkening is equal either side of the bar edge. HIG Layout: "Extend full-screen backgrounds beneath sidebars, toolbars, and tab bars to window/screen edges."
- **R7. Accessibility gives a hard edge, never a leak.** With Reduce Transparency, Increase Contrast or the in-app Less Transparency on (Android: the app's Increase Contrast, Reduce Transparency or Reduce Motion, or the system contrast level, High contrast text or Remove animations, all read by `ui/common/ScrollEdgeFade.kt` `rememberScrollEdgeHardEdge`; Windows: transparency effects off, high contrast and the in-app settings), the ramp becomes a hard cut at the edge. Content still never shows behind the header. Apple pages: `TopEdgeScrim` asks for the system **hard** top scroll-edge style whenever `ScrollEdgeHardEdge` is on (`PageTopScrollEdge`), because the app's own settings never reach the system's edge (#393: with only the in-app Reduce Transparency on, rows stayed readable behind the Settings title after a Quick Links jump). Bottom chrome too: only the ramp goes, never the cut, so rows covered by a pinned footer or pager stay hidden and out of touch and the screen reader in every mode, including the gaps between pager buttons (Android `RankingsBoardLayout` keeps `clipAboveFooter` whenever `fadeAboveFooter` is set; #306). A row peeking less than 48 dp above a clip gets Compose touch/TalkBack bounds up to 24 dp below it (the clip widens by half the minimum touch target), so Android's `AnchoredFooter` marks its full width as covering the rows (`coversRowsForAccessibility`); beside a narrow pager with no pinned row, a hidden row's TalkBack focus otherwise reached under the footer (#473; the #462 journeys found the same leak). Windows boards: contrast themes, transparency effects off, Less Transparency and Increase Contrast draw the footer ramp at depth 0 (a hard cut at the footer's top); contrast themes also show the window-colour `FooterPlate` behind the footer on every board (#305).
- **R8. Jumps land clear of the ramp.** After a Quick Links or A–Z jump the target's first row is fully opaque and the pinned title names the target ([section-jump-landing](section-jump-landing.md)).
- **R9. Every board's bottom chrome fades the same way (#305).** Each board with a floating pager or footer (Song, Full Rankings, Band Rankings, band song leaderboard, Player Bands) fades its rows above that chrome. The fade is the same with or without the selected player's pinned row: it depends only on the chrome being on screen and on the R7 settings. Windows pages call `BoardFooterFade.Attach(source, host, list, footer, plate)` and never wire the fade themselves (#308). The fade also re-evaluates when rows arrive (the scroller's `ScrollableHeight`), not only on scroll, so a board that loads long already shows the ramp. `tools/windows/journeys/a11y-board-footer-fade-no-player.json` asserts the `fst.<board>.footer-fade` status on all five boards with no selected player (mid-scroll, list end, each R7 mode); `a11y-board-footer-fade.json` covers the same boards with one.

Apple's edge fades read the scroll position the same way on every supported system: `FestivalUI/Common/ScrollEdgeReader.swift` `onScrollEdgeReading` (sheet header, bottom chrome) uses `onScrollGeometryChange` on iOS 18 / macOS 15+; on iOS 17 / macOS 14 (`ScrollEdgeTracking.usesLegacyPath`) its `EnclosedScrollViewLocator` finds the wrapped content's own `UIScrollView` / `NSScrollView` (the one covering most of the content, searched no higher than the hosting view controller's view, so never the page behind a sheet) and hands it to `PlatformScrollObserver`, which reports the same top inset, offset and remaining overflow. Pinned-title sheet lists reach the same observer through their rows' `ListScrollViewLocator`. `onScrollGeometryChange` can record a changed value without calling its action (a scroll view that outlives a reload gate's content swap kept a 0 pt bottom fade over its taller rows, #317), so the reader re-delivers a value its action missed on the next main-actor turn (`ScrollEdgeReadingRelay.reconcile`); never rely on the action alone. Never fall back to a permanent hard cut or a permanent full ramp (#308 review). Tests: `PinnedHeaderLegacyScrollRenderTests` and `ScrollEdgeLegacyRenderTests` (sheet-header 40 pt ramp while scrolling, zero bottom ramp at the end of a `List` and a `ScrollView`, reader parity) run both paths; `FST_DEBUG_LEGACY_SCROLL_GEOMETRY=1` (Debug) forces the legacy path on a newer simulator.

**Approved variant (Apple Songs before iOS 26 / macOS 26):** Songs keeps native pinned List headers on an opaque backing with a hairline and no row ramp. The owner chose "sticky section titles … pinned at the top on a fully opaque backing, so no row shows through beneath them" ([songs spec](../pages/songs/spec.md), 2026-09-28); the floating section bar and its ramp need iOS 26's scroll-edge chrome.

Apple ramp constants live only in `FestivalCore/ScrollEdgeFade.swift` (`topDistance` 40 for top edges, `distance` 40 for board footers, the web board pages' `useScrollMask`, #329; applied through `ScrollEdgeFade.ramp`). Apple has no `useScrollFade`-style list fade (Suggestions, Search, player statistics), so no 36 pt list constant exists there; one added for those lists must stay apart from the board's `distance`. The First Run infinite-scroll demo (#380) is not a scroll view: it is an inert auto-scrolling viewport with the web demo's own 36 pt `fadeTop`/`fadeBottom` (`FestivalCore/FirstRunMotion.swift` `FirstRunAutoScroll.edgeFade`, shown only on edges hiding cards), drawn with `ScrollEdgeFade.ramp` and hard-cut by `ScrollEdgeHardEdge`; and `Design/ScrollEdgeFadeModifiers.swift` `ScrollEdgeHardEdge` is the one R7 switch (system Reduce Transparency or Increase Contrast, or the in-app Less Transparency or Increase Contrast) read by every Apple edge component, `bottomChromeFade` included. Apple Search shows no section titles (#299), so it has no pinned-title fade.

**Apple mask stability (#383).** Every pinned-title consumer (Songs rows, Notifications rows) draws through `PinnedHeaderFadeMask` **per row**. An alpha mask around a whole `List` makes SwiftUI drive the List's insets from its lagging safe area on iOS 26/27, so under a large title the title snaps closed when the tab bar expands near the top and rests part-way collapsed; never mask a List under a large title (Duo's `bottomChromeFade` List mask sits under a fixed in-content title, so it is unaffected). The ramp band always keeps at least 1 pt of layout (`PinnedHeaderFadeMask.bandHeight`); the opaque shape starts at `cut + depth`, so a 0 depth still draws a hard edge, and a band that falls to or grows from 0 pt rebuilds the mask layer. A mask under a large title also must not observe geometry that moves with the title while nothing is faded (Songs `SongsScrollChrome.rowFade(enabled:)`), and only rows near the title (`PinnedHeaderEdgeFade.rowLimit`) report their position. Regression: `SongsChromeJourneyTests/testSlowDragsNearTheTopKeepTheLargeTitleSteady`. Only rows near the edge read the depth limit, which moves every frame while a section title passes (`PinnedHeaderEdgeFade.RowMaskDepth`, #553). The row mask is decoration: it adds no accessibility element and leaves the row's label, role, full frame and hit testing unchanged, with the pinned title above it. iPhone journey `SongsChromeJourneyTests/testRowUnderTheSectionBarFadeKeepsItsAccessibility` (apple-ci) compares one row clear of the fade, in the band and cut by the edge, checks the layout order (XCUITest lists overlays after rows) and audits the cut state; the hosted `SongsSectionBarAccessibilityTests` prove the tree order.

**Android (#308).** The ramp constants (`TOP_DP = 40`; `BOTTOM_DP = 40`, the board footer, #329), the depth rule (`depth(scrolled, full)`, the web's `min(scrollTop, distance)`) and the R7 decision (`isHardEdge`) live only in `core/scrolledge/ScrollEdgeFade.kt`. The only `BlendMode.DstIn` ramp is `ui/common/ScrollEdgeFade.kt` `drawScrollEdgeRamp`, shared by the pinned-title fade and `bottomChromeEdgeFade`; `rememberScrollEdgeHardEdge` is the one R7 switch for both. The pinned-title ramp is the distance scrolled under the pinned title, capped by the room left above the incoming title (so it reaches 0 during a push, R5) and by 40 dp; a title that has just pinned (Quick Links landing) shows its first row opaque (R8). Tests: `ScrollEdgeFadeTest`, `SongHeaderEdgeFadeTest`, `BoardFooterEdgeFadeTest`, Robolectric `PinnedHeaderEdgeFadeDrawUiTest` / `BoardFooterFadeDrawUiTest` (incl. the pager-only footer's TalkBack bounds, #473), device `PinnedHeaderEdgeFadeDeviceTest`, and device ATF journeys: `BoardFooterFadeAccessibilityJourneyTest` (all four fading boards with a selected player at device text and 200 %, at rest and with a row peeking 8 dp above the footer: dimmed rows stay TalkBack stops, labelled wherever the list shows their content, read before the pager, no row node reaches under the footer, ATF; the drawn 40 dp ramp and the live system High contrast text / Remove animations hard cut, #473), `BoardFooterFadeNoPlayerAccessibilityJourneyTest` (Full Rankings, Band Rankings and the band song board with no selected player, R9: no row under the pager in the accessibility tree mid-scroll and at the end, last row whole, rows read before the pager, 48 dp labelled pager buttons, a polite "Page 1 of n", each in-app R7 setting and 200 % text, #462), `SongLeaderboardJourneyTest` (with a pinned player row, #443) and `SongsBucketHeaderAccessibilityJourneyTest` (Songs pinned titles, each in-app R7 setting; TalkBack's published order puts the pinned title before the partly hidden row under it, R5, #462). It also covers the section push (R5, #288; #452) with the fade, at 200 % text and with the R7 hard cut forced separately by the app's Reduce Transparency, the app's Reduce Motion and the system's Remove animations, each proven hard by switching it off and on live. The journeys call `JourneyHarness.publishTalkBackTree()` after launch, so `readingOrder` follows Compose's traversal links rather than raw tree order. The pinned title's order is `ui/songs/PinnedHeaderEdgeFade.kt` `rememberPinnedHeaderReadOrder` (`traversalIndex` -1 while `SongHeaderEdgeFade.pinned`; Robolectric `SongsBucketHeaderDrawUiTest.onlyThePinnedHeaderIsReadBeforeTheRowsBeneathIt`).

**Agent decision (Android, #308; the owner may override with `/choose`).** Android's Notifications sheet ("New" / "Older") and Search sheet keep their section titles as ordinary in-flow list items, not pinned titles, so they need no pinned-title fade: the web has no sticky headers, `section-headers` R7 and the `android-sticky-header` guard allow `stickyHeader` only on Songs, and Windows made the same call. Songs is the only Android list with pinned section titles.

**Agent decision (Apple, #393 design review; the owner may override with `/choose`).** With the app's own Reduce Transparency or Increase Contrast on, Apple pages kept the system *soft* top edge, so rows read through behind the title (system Reduce Transparency was already opaque: iOS adapts its own edge). Options weighed: (a) test only and leave the soft edge (rejected: breaks R7 "content still never shows behind the header" and liquid-glass rule 6 "accessibility overrides win"); (b) hide the system edge and draw an opaque band (rejected: a second mechanism for the page header, R1, and hand-built chrome, liquid-glass rule 1); (c) ask the system for its `.hard` style in R7 modes (chosen: still the native edge effect; HIG Scroll views: hard is an "opaque blur, defined edge", and "Prefer the automatic style … If you use soft … thoroughly test control legibility", a *should*). The system tab bar and bottom accessory stay system glass.

## Known debt

#308 consolidated every platform to one component per edge kind. No ramp length remains off the web: Apple and Android board footers moved from 36 to 40 in #329, matching Windows (#305) and the web board pages' `useScrollMask`.

**Agent decision (Windows, #305 design review; the owner may override with `/choose`).** #308 had moved the Windows board ramp from 40 to 36 epx citing `useScrollFade`. The web source shows no board uses `useScrollFade`: `Page.tsx` calls `useScrollMask` on every page with no size override, and the board's footer scroll margin ends the viewport at the pager, so the web board fade is 40 px linear. Windows `BoardFooterEdgeFade.Depth` is 40 and the UIA journeys assert `fading:40`. Options weighed: keep 36 to match Apple/Android (rejected: copies a native divergence over the web, which ranks higher on the design ladder) or 40 on Windows now with Apple/Android as listed debt (chosen). Apple (`ScrollEdgeFade.distance = 40`) and Android (`BOTTOM_DP = 40`) followed in #329.
