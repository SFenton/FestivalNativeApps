# Page tools and navigation chrome

> **What:** where navigation, global search, page actions, Quick Links, notifications and Profile belong. **Read when:** adding, moving or styling a shell or page action.

Status: **current**, 2026-10-05. Provenance: #52, #72, #84, #92, #160, #271, #300, #309, #311.

## Intent

Navigation preserves location; page tools act on the current content. The web is the behavior reference, while each native shell uses its platform's navigation and command placement rather than reproducing web pixels.

## Rules

- **R1. Separate destinations from page actions.** Navigation remains in the platform shell; Sort, Filter, Quick Links and similar tools are supplied by the current page through its canonical shell hook.
- **R2. Follow the Apple placement ADR, not a copied toolbar.** [Navigation accessories](../design/apple/nav-accessories.md) is the detailed, owner-approved Apple ADR (#92, #300): iPhone page tools register with `PageToolsRegistry` for the system tab-bar accessory; Profile remains the trailing header action; global Search is a Search tab; Songs has the inline `Filter Songs` field; Duo and iPad keep tools as trailing bar items. This is an approved deviation from HIG Tab bars, which says to use tabs for navigation and a toolbar for current-view actions; HIG Toolbars says, “Trailing: important always-available items.” **Owner-approved variant (#333, iPhone Duo only):** on iPhone Duo, folded or unfolded, Songs' `Filter Songs` field sits at the bottom of the page in thumb reach (owner: "Filter Songs should be at bottom of screen on Duo for ease of use"; HIG Search fields: "Place search at the bottom if there's room; this keeps priority search easy to reach"), not in the navigation-bar drawer. It is the shared `GlobalSearchField` on the floating-control surface (`festivalCardCapsule`) in the page's bottom safe-area inset (`SongsBottomFilterField`, `SongsFilterFieldPlacement`), so the list's last rows and the A–Z scrubber end above it and it rises with the keyboard (plus the measured `keyboardLift` the Duo outer display's inset keyboard otherwise leaves it short); the list fades above it with `bottomChromeFade` (scroll-edge R1). **Agent decision (#334, 2026-10-07; supersedes #333's flat-landscape choice): only a book-pose fold (`DeviceLayout.pose == .partiallyFolded`, `SongsFilterFieldPlacement.fold(in:)`) moves the field to the trailing page, a 16 pt margin clear of the fold; folded, flat (portrait or landscape, even with the inactive hinge reported) and inner portrait it spans the full width; owner may override with `/choose`** (owner, #332: "When partially folded landscape, align filter songs on right page" and the bottom search bar "unfolded should take full bottom width. Can stay on right side if hinge is unfolded but device is not completely unfolded"; HIG Designing for iPhone Duo: "Folding region | Present when partially open"; "Expand the existing layout with space"). Do not pass `DeviceLayout.splitHinge` (it also returns the inactive hinge and the midline flat) to a bottom field: Duo Search (#349) reuses `fold(in:)`. iPhone, iPad and Mac keep the top inline field; do not move them.
- **R3. Keep the accessory stable.** Apple accessory slots are fixed at 44 pt, page tools remain in page order, the bell stays trailing, and a width/type-size fold is decided from window width rather than the accessory’s live morphing width (#300). HIG Buttons: “the hit region is at least 44x44 pt.”
- **R4. Use the current Android placement.** Global search is a top app bar action (`GlobalSearchEntry`, a full-screen search view on compact windows) on every window size, before notifications then Profile at the trailing end. Compact windows put page tools (Sort, Filter, Quick Links) in the shell’s `FloatingToolbar`; regular windows put them in the top app bar. A page's own list filter (Songs) is a search field pinned inline above the list at every size, never a toolbar item. Material 3’s top-app-bar rule is “Use when: Every screen needs a title and optional actions”; search is “Compact: Full-screen search view”; toolbars display “frequently used actions relevant to current page context”. **Agent decision (#309, 2026-10-05): option C, top app bar search + inline Songs filter + floating toolbar for Sort/Filter/Quick Links (replaces #84's toolbar search pill); owner may override.** It matches Apple's inline filter and bottom page-tools grouping and the web's `SongsToolbar`/`HeaderActions` split, and keeps five bottom destinations. It departs from Apple only by not adding a Search tab, which would push Statistics out of M3's 3–5 destination limit.
- **R5. Use the current Windows placement.** `TitleBar.Content` owns the global `AutoSuggestBox`; page-local Songs search, Sort, Filter and Jump remain in the page actions row. `NavigationView` owns destinations; it has no minimizing bottom-tab accessory (#84).
- **R6. Do not add a parallel command surface.** Pages register Apple tools, register Android shell actions, or use the Windows page-header convention; they do not create a second dock, floating capsule, global-search entry point or custom navigation bar.
- **R7. Android page tools stay reachable while the content scrolls (#52, #160).** Songs and Suggestions pass `FestivalScreen(pinActions = true)`: the compact floating toolbar never hides or minimizes on scroll, Songs' inline filter stays pinned above the list, the top app bar never scrolls, and scrolling back to the top restores the same bounds. Long or endless lists also pass `actionsReadFirst = true`, so TalkBack reads top bar → toolbar → content. On a list pane too narrow for the title, `AdaptiveTopBarActions` moves the page tools behind ⋮; its menu closes once the sheet or menu one of its tools opened has closed (window refocus). Material 3 toolbars: “Displays frequently used actions relevant to current page context”; keeping them pinned instead of hide-on-scroll is the owner's #52 choice. Device evidence: `journeys/PinnedPageControlsDeviceTest` on `FST_Phone` (toolbar) and `FST_Book_Fold --posture half` (⋮).
- **R8. The selected player's avatar is the whole Profile button, with no container ring.** Web `HeaderActions` `profileButton` (`background: 'none'`, `border: 'none'`), Android `ProfileAvatarButton` (containerless `IconButton`, filled circle) and Windows `ProfileButton` (transparent, `BorderThickness="0"`) draw nothing around it. Apple iOS/iPadOS 26+: the monogram toolbar item hides its shared Liquid Glass (`ToolbarContent.profileItemBackground` → `sharedBackgroundVisibility(.hidden)`, in `RootChrome.swift` only) and fills the 44 pt glass-item diameter with no rim, overhanging its layout rect by the 10 pt padding a bar puts on each side of a background-less item, so the circle lands exactly where the glass circle was and sits the standard 12 pt group gap from the bell (`RootProfileButton.MonogramMetrics`, `UIImage` alignment-rect insets); the add-profile glyph, the Duo rail symbol, the bell and page tools keep system glass. **Agent decision (#311, 2026-10-05): option C, hide the item's glass and overhang the 44 pt avatar to the glass circle's position (B plus alignment), rather than enlarge the image inside the glass (A) or hide it without realigning (B); owner may override with `/choose`.** HIG Toolbars: "Reduce backgrounds/tints that interfere with system effects" (should); HIG Materials: "Use Liquid Glass effects sparingly on custom controls" (should); HIG Buttons: "the hit region is at least 44x44 pt" (kept: it is still a standard image bar button, issue #15). Prototyped on iOS 26.5: option A (44 pt image inside the glass) grew the glass into a wider capsule, kept the ring and clipped the avatar; plain option B moved the avatar 10 pt in from the trailing edge and left 22 pt (not 12 pt) beside the iPad bell, which the overhang corrects. Evidence: `ProfileAvatarFillJourneyTests` on iPhone and iPad (screenshot-measured disc size, rim and position on a tab root, Item Shop and Search; the phone Search tab has no account items).
- **R9. Android bar and toolbar buttons keep forgiving, separate hit regions (#72, #179).** Quick Links, Sort, Filter, global Search, the bell, Profile and ⋮ are Material 3 `IconButton`s: a 40 dp container inside `minimumInteractiveComponentSize()`'s 48×48 dp touch target, at every window size and font scale, in every placement (floating toolbar, top app bar, ⋮ menu). Neighbouring targets never overlap, and a touch just off the glyph activates the button. Never shrink a bar action below the target with a fixed `Modifier.size` or wrap a bare icon in `clickable`. The bell's unread badge is decorative (`clearAndSetSemantics`) and passes touches to the button. Material 3: “Minimum touch target 48x48dp”; “Touch targets remain 48dp minimum even on large screens”. Tests: the shared `testing/ShellHitTargets` probe, run by `ui/ShellHitTargetUiTest` (Robolectric phone, 200 % text, medium, expanded and ⋮ pane) and `journeys/ShellHitTargetDeviceTest` (every FST AVD and posture), touches each button 22 dp off-centre in four directions.
- **R10. Windows nav-bar and page-tool targets are at least 40x40 epx, and the whole target is clickable (#72, #271).** Each title-bar button (Search, bell, profile) and each page tool (Sort, Filter, Jump, Quick Links, Rank By, the Full/Band Rankings pickers, Song Detail Paths/Item Shop and the pinned Paths) uses `Themes/Styles.xaml` `FSTMinTargetSize`. Icon-only buttons also use it as `MinWidth`. Every new `DropDownButton` uses it too (`HitTargetMarkupTests.EveryDropDownButton_UsesMinTarget`). After any dynamic title-bar change, the shell queues `TitleBar.RecomputeDragRegions()` (`MainWindow.TitleBar.cs` `QueueDragRegionRefresh`). Those changes are: window width, the right header's size (the bell appears), the search box/button swap, and the title cleared at large text. Without the recompute, the stale passthrough rectangles make taps on the new Search control drag the window. Do not use `AutoRefreshDragRegions`: the WinUI spec says it "triggers a visual tree walk on every layout pass". Fluent targeting: "a minimum target size of 40x40 epx". Evidence: `journeys/a11y-hit-targets.json` (geometry, no input) and `journeys/a11y-hit-targets-press.json` (a real touch tap, and a mouse click on the title bar, at every off-glyph probe, each asserting that control's own result, so a press that lands in the drag region fails; unlocked console only); Narrator reading order and phrases of the same targets: `journeys/a11y-narration.json` (the 40 epx targets don't change what is read or its order).
- **R11. Windows page-header button rows wrap instead of clipping (#285).** A row of page-header buttons whose labels grow with text size goes in the shared `Controls/WrapPanel` (8 epx both ways), never a horizontal `StackPanel`. At 225% text in a compact window, the profile's "Switch to This Profile" + Quick Links row ran Quick Links off the window edge. Consumers: Rivals `Commands`, Player profile/Statistics `TitleActions`. Songs' `Actions` is its own adaptive `Grid`. winui-design: "Clipped content is a worse failure than a slightly-wide window"; Reflow: "Sequence can wrap or change columns". Evidence: `journeys/a11y-profile-title.json` `pt-actions-wrap` (Quick Links below Switch at `text-225`) and `pt-actions-row` (one row at normal text).
- **R12. A page's primary action looks the same in every bar (#351).** Where a page's key action (Player Select / Switch to This Profile) is a prominent accent button in a horizontal bar (`ProfileIdentityToolbarItem`, `.borderedProminent` tinted `ProfileIdentityAction.prominentFill`), the iPhone Duo vertical bar draws it with the canonical `VerticalBarActionItem` passing the same `prominentFill`, and ranks it `RootChromeRailItem.primaryPageAction` (`.high`) so it stays visible right after Back instead of overflowing into `…`. Select and Switch share the accent fill; destructive Deselect (drawer only) stays red. Plain page actions keep the monochrome symbol and default priority; do not tint a rail symbol by hand. HIG Toolbars: "Use `.prominent` for a key action such as Done/Submit"; HIG Color: "For a primary action, color the background, not symbols or text"; HIG Designing for iPhone Duo: "Place primary navigation (Back/Close) at the top, then prominent actions (Done)". Tests: `ProfileIdentityActionTests`, `RootChromeRailPriorityTests`.
