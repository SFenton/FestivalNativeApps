# Page tools and navigation chrome

> **What:** where navigation, global search, page actions, Quick Links, notifications and Profile belong. **Read when:** adding, moving or styling a shell or page action.

Status: **current**, 2026-10-14. Provenance: #52, #72, #84, #92, #160, #271, #300, #309, #311, #337, #338, #341, #363, #375, #394, #557, #576, #590, #601, #611, #625, #632, #633.

## Intent

Navigation preserves location; page tools act on the current content. The web is the behavior reference, while each native shell uses its platform's navigation and command placement rather than reproducing web pixels.

## Web source (behavior reference)

| Web | Behavior |
|---|---|
| `FortniteFestivalWeb/src/components/shell/mobile/BottomNav.tsx` (`BottomNav`, `BOTTOM_NAV_TAB_MIN_HEIGHT`, `SPACIOUS_BOTTOM_NAV_QUERY`) | Top-level destinations retain their selected state and adapt the compact destination set. |
| `FortniteFestivalWeb/src/components/shell/HeaderActions.tsx` (`HeaderActions`) | Search, notifications and profile are separately labelled shell actions. |
| `FortniteFestivalWeb/src/pages/songs/components/SongsToolbar.tsx` (`SongsToolbar`) | Songs has a local query plus distinct Sort and Filter controls. |
| `FortniteFestivalWeb/src/components/shell/desktop/Sidebar.tsx` (`Sidebar`), opened by `HamburgerButton` in `mobile/MobileHeader.tsx` | Mobile keeps a hamburger sidebar beside the bottom tabs: Songs, Suggestions, Statistics, Rivals, Leaderboards, Shop, the player link with Deselect, then Settings. |

## Rules

- **R1. Separate destinations from page actions.** Navigation remains in the platform shell; Sort, Filter, Quick Links and similar tools are supplied by the current page through its canonical shell hook.
- **R2. Follow the Apple placement ADR, not a copied toolbar.** [Navigation accessories](../design/apple/nav-accessories.md) is the detailed, owner-approved Apple ADR (#92, #300): iPhone page tools register with `PageToolsRegistry`, which since #632 draws them as individual floating Liquid Glass buttons above the tab bar, not the system tab-bar accessory (R28); Profile remains the trailing header action, sharing one glass pill with the bell on iPhone (R28); global Search is a Search tab; Songs has the inline `Filter Songs` field; tools float wherever the section chrome is a horizontal tab bar, and the iPhone Duo vertical bar, the iPad sidebar shell and the Mac keep them as rail, bar or window-toolbar items (agent decision #633, R28). This is an approved deviation from HIG Tab bars, which says to use tabs for navigation and a toolbar for current-view actions; HIG Toolbars says, “Trailing: important always-available items.” **Owner-approved variant (#333, iPhone Duo only):** on iPhone Duo, folded or unfolded, Songs' `Filter Songs` field sits at the bottom of the page in thumb reach (owner: "Filter Songs should be at bottom of screen on Duo for ease of use"; HIG Search fields: "Place search at the bottom if there's room; this keeps priority search easy to reach"), not in the navigation-bar drawer. It is the shared `GlobalSearchField` on Liquid Glass (**owner-approved, #358**: [surface-materials](surface-materials.md) R2 variant; opaque and bordered under Reduce Transparency or Increase Contrast) in the page's bottom safe-area inset (the shared `BottomSearchField`, `BottomSearchFieldPlacement`; `SongsFilterFieldPlacement` picks it), so the list's last rows and the A–Z scrubber end above it and it rises with the keyboard (plus the measured `keyboardLift` the Duo outer display's inset keyboard otherwise leaves it short); the list fades above it with `bottomChromeFade` (scroll-edge R1). **Owner-approved (#358): it matches the system Search button's height and, with the keyboard hidden, its vertical centre** (owner: "Filter Songs on Duo should align with Search button vertically (in height too)"). Beside the vertical bar (folded in every rotation, inner landscape) the field is 48 pt and centred 48 pt above the window's bottom edge, where the bar's 48 pt Search button sits 24 pt above it; the row ends at the page's bottom safe area (10–34 pt higher), so the field reaches below it (`BottomSearchFieldPlacement.bottomPadding(chrome:rowBottom:windowBottom:fieldHeight:keyboardTop:floatingRowTop:)`). SwiftUI's hierarchy on Duo ends at that safe area (`DeviceLayout.size` is 644 pt of a 678 pt folded window), so the window's bottom comes from the hosting `UIWindow` (`WindowBottomProbe`). Larger Dynamic Type grows the field around the same centre. With the software keyboard up it sits 8 pt above the keyboard as before. In inner portrait the Search button is in the tab bar, which the field must not cover: the field keeps the tab bar Search button's 62 pt height and, since page tools float there (#633), stacks 8 pt above the floating row that sits above the bar. On iOS the page's own bottom safe area ends at the tab bar, not above the tab stack's floating-row inset, so the field measures the selected row's top (`PageToolsRegistry.floatingRowTop`, reported by `FloatingPageToolsBar` and cleared only by the row that reported it) and adds `BottomSearchFieldPlacement.floatingRowClearance(rowBottom:floatingRowTop:)`; with the keyboard up the larger of that and `keyboardLift` applies. Known gap: in the outer landscape with the camera at the bar's bottom the system lifts its Search button clear of the camera (y 336–384 of 466 in a 2026-10-04 capture); the field keeps the 24 pt model there until the pose can be captured again. **Agent decision (#334, 2026-10-07; supersedes #333's flat-landscape choice) and owner rule (#349): only a book-pose fold (`DeviceLayout.pose == .partiallyFolded`, `BottomSearchFieldPlacement.pageHinge(for:)`) moves the field to the trailing page, a 16 pt margin clear of the fold; folded, flat (portrait or landscape, even with the inactive hinge reported) and inner portrait it spans the full bottom width (16 pt margins); owner may override with `/choose`** (owner, #332/#349: "When partially folded landscape, align filter songs on right page" and "search bar when keyboard is closed and unfolded should take full bottom width. Can stay on right side if hinge is unfolded but device is not completely unfolded"; HIG Designing for iPhone Duo: "Folding region | Present when partially open"; "use reserved-region APIs to keep important elements clear of the center"). `pageHinge(for:)` is `DeviceLayout.splitHinge`, which is nil unless partially folded (#361); never pass `DeviceLayout.screenDivide` (it returns the flat free-space midline) to a bottom field. iPhone, iPad and Mac keep the top inline field; do not move them. **Search on the Duo inner display (#349):** the Search tab's system `.searchable` field sat in the bottom trailing ~370 pt beside the vertical bar and rose centred over the keyboard, out of line with the full-width scope bar, and no system API sets its width; so on the inner display (flat or book-folded; `GlobalSearchFieldPlacement`) the tab shows the same `BottomSearchField`, focused when the tab appears. **Agent decision (#349, 2026-10-07; owner may override with `/choose`): the scope bar and the field share one column** (`bottomSearchFieldColumn(hinge:)`): full width when flat, the trailing page in book pose, with the scope bar kept at the top of the results (HIG Search fields: "Consider a scope bar in the results area"; web `SearchModal` keeps its search bar and target tabs in one column). Rejected: scope bar on the left page with the field on the right (splits two controls that work together), scope in a menu or tokens (hides the current scope; HIG Searching: "Show current scope with descriptive placeholder, scope bar, or title"). The folded outer display keeps the system Search field, which already spans its bottom. **Targets (#474 for #333, tested in every Duo pose by #475 for #334):** the shared `GlobalSearchField` keeps both of its parts at HIG Buttons' "hit region is at least 44x44 pt" (R25): on iOS a tap anywhere on the capsule (above or below the ~22 pt text line, or on the magnifier) focuses the field through a hidden layer behind its content, and Clear Search is a 44 × 44 pt button (`GlobalSearchField.clearTarget`; the capsule's trailing padding narrows to 4 pt so the glyph stays near the end); neither changes the field's or Clear Search's accessibility frame, so VoiceOver reads the same elements in the same order.
- **R3. Keep the floating tools stable.** (Until #632 this was the tab-bar accessory; see R28 for the iPhone floating row, which keeps every rule here except the bell, which moved to the header.) Apple tool slots are fixed at 44 pt, page tools remain in page order, and a fold is decided from window width alone (#300; since #632 the row never morphs and the bell is in the header). HIG Buttons: “the hit region is at least 44x44 pt.” Accessibility (#395, for #15): the hosted `NavButtonAccessibilityTests` (`apple-ci`) render the real `PageToolsAccessoryBar` and require Sort, Filter Songs, Quick Links, Notifications as named buttons (with Sort's and Quick Links' values) read left to right, each a 44 pt slot that no neighbour overlaps, the bell trailing, unchanged at AX5 (the bar caps text at `maxTypeSize`), and a press on Quick Links opening its choices; the header's Open Navigation and Profile buttons stay single named buttons with hints and a decorative monogram (R8). Accessibility (#442, for #89): the tools never join the search field. The hosted `quickLinksAloneIsOneIconSlot` requires a Quick-Links-only row (Leaderboards) to read as one 44 pt icon circle (no title text) on the trailing edge, at default size and AX5. The simulator `PageToolsSearchFieldJourneyTests` (`apple-ci`: iPhone; simulated Duo folded, Songs and Leaderboards at default size and AX5; iPad) requires each tool to be one named button, not inside or overlapping the Filter Songs field (drawer or `BottomSearchField`), read in drawn order and never split by the field; Quick Links is no wider than one icon button and reads its section; the `.hitRegion`/description/Dynamic Type/clipping audit reports nothing on them. Navigation-bar items (Duo, iPad) are 36 pt system elements whose 44 pt region comes from the bar, so the audit, not the frame, proves their target. Keyboard (iPad, its own `--a11y full-keyboard-access` run): hardware-keyboard focus rests in the tools' navigation bar, Sort, Filter Songs and Quick Links sit in its focus group in drawn order before the field, and Go › Next / Previous Section (⌥⌘↓ / ⌥⌘↑) operates Quick Links. Agent decision (#442, 2026-10-11): Tab traversal to each tool is not automatable on the simulator, so the journey proves focus-group placement and keyboard operation and FKA traversal stays an operator check; owner may override ([ipados.md](../design/apple/ipados.md#keyboard-only-and-full-keyboard-access-2026-10-03)).
- **R4. Use the current Android placement.** Global search is a top app bar action (`GlobalSearchEntry`, a full-screen search view on compact windows) on every window size, before notifications then Profile at the trailing end. Page tools (Sort, Filter, Quick Links and every other page's tools) float in the shell’s `FloatingToolbar` at **every** window size, posture and orientation; they never move into the top app bar or behind ⋮. A page's own list filter (Songs) is a search field pinned inline above the list at every size, never a toolbar item. Material 3’s top-app-bar rule is “Use when: Every screen needs a title and optional actions”; search is “Compact: Full-screen search view”; toolbars display “frequently used actions relevant to current page context”. **Agent decision (#309, 2026-10-05): option C, top app bar search + inline Songs filter + floating toolbar for Sort/Filter/Quick Links (replaces #84's toolbar search pill); owner may override.** It matches Apple's inline filter and bottom page-tools grouping and the web's `SongsToolbar`/`HeaderActions` split, and keeps five bottom destinations. It departs from Apple only by not adding a Search tab, which would push a destination (Item Shop since #601, R22) out of M3's 3–5 destination limit. **Owner-approved variant (#576, Android only; supersedes #309's regular-window placement):** owner: "Settings: When in landscape (and in general on all pages for this), Quick Links, filter, etc. should still be floating buttons and not be in Android header". #309 had moved the tools into the top app bar on windows 600 dp and wider (landscape phones, tablets, foldables) and behind ⋮ on a narrow list pane; the shell (`FestivalApp`) now hosts the one `FloatingToolbar` on every layout. Global search, the bell and Profile stay in the top app bar. Placement (`core/shell/FloatingToolbarPlacement`): the toolbar sits at the bottom end of the page that registered the tools, bounded by that page's pane (`FestivalScreen` reports it, so a two-pane page keeps the tools over the pane that registered them; Songs has no split since #581), the horizontal `safeDrawing` insets (cutouts, side navigation bar) and one side of a separating vertical hinge (the far side of the fold; Material 3 foldables: "Never place interactive content or critical information across the hinge area"). On rail and drawer layouts it also lifts by the system navigation bar's height, and every layout pads the scrolling content by the toolbar's height plus both margins (and that lift), so the last row scrolls clear of it. Material 3 toolbars: "Displays frequently used actions relevant to current page context" (a floating toolbar is a supported placement at any width; the bar keeping only global actions is the trade-off). **On-demand split pane (#583, [split-panes](split-panes.md) R7):** the trailing pane is the only other place that renders the shared `FloatingToolbar`, with its own `FloatingToolbarHost`, for the page inside it (`ui/common/OnDemandSplit.kt`, allowed by the guard); it sits at the pane's bottom end, so the list page's and the pane page's tools each stay over the pane that registered them. It is the same component, never a second kind of toolbar. Never reintroduce a width test for the toolbar; siblings (Apple R2/R3, Windows R5) keep their own rules. `AdaptiveTopBarActions` (⋮) remains only the fallback for a `FestivalScreen` composed outside the shell (previews, isolated tests).
- **R5. Use the current Windows placement.** `TitleBar.Content` owns the global `AutoSuggestBox`; page-local Songs search, Sort, Filter and Jump remain in the page actions row. `NavigationView` owns destinations; it has no minimizing bottom-tab accessory (#84).
- **R6. Do not add a parallel command surface.** Pages register Apple tools, register Android shell actions, or use the Windows page-header convention; they do not create a second dock, floating capsule, global-search entry point or custom navigation bar. **Owner-approved variant (#632; every horizontal tab bar since agent decision #633):** the registry's own floating row (`FloatingPageToolsBar`, R28) is the one floating page-tool surface; pages never draw their own floating buttons, and no Apple chrome has a second floating implementation. **Owner-approved variant (#590, Android player page and Statistics only):** Select/Switch/Deselect Profile is its own pill beside the floating toolbar, through the toolbar's `companion` slot, never a page-drawn capsule (R24).
- **R7. Android page tools stay reachable while the content scrolls (#52, #160, #577).** The shell's floating toolbar never hides or minimizes on scroll, on **every** page: `FloatingToolbar` has no scroll behaviour (no M3 "exit always", no `pinActions` opt-in), so Quick Links and every page tool keep their bounds while the page scrolls. **Every page ends one standard gap above the chrome actually shown (#578):** the shell's `shell.bottomPadding` is only the rail/drawer lift; `FestivalScreen` adds the toolbar's drawn height and its 16 dp margin only while the toolbar shows tools, then one 16 dp gap (`core/shell/BottomChromeSpacing.contentBottomDp`, Material 3's compact margin), so a page with no tools (song boards, All Rivals, Player Bands, Licenses) ends 16 dp above the bottom bar instead of above an absent 64 dp toolbar, and a page with tools ends 16 dp above the toolbar (no dead band, no overlap at the end). The toolbar reports its drawn row height per owner (`FloatingToolbarHost.Registration.heightDp`, 0 with no tools and no companion pill, taller at large text; the #590 companion pill counts, so the player page ends above it even with no tools); a page starts from its last height (`rememberSaveable`, so Back keeps place) or, before it is drawn, 0 for `NoPageActions` and 64 dp otherwise. Pages and boards add no bottom margin of their own: the former +24 dp page and +12 dp board-pager margins are gone. Device evidence: `journeys/BottomChromeSpacingAccessibilityJourneyTest` (song board without a profile, Full Rankings, Leaderboards, All Rivals, Rival Detail, Rivalry at 100 % and 200 % text); unit `core/BottomChromeSpacingTest`. **Agent decision (#577, 2026-10-10; owner may override with `/choose`):** of (A) hide on scroll and slide back when scrolling stops, (B) pin on every page and (C) keep hiding until the user scrolls back (the reported bug), B was chosen: it extends the owner's #52 choice ("nothing leaves the screen") from Songs and Suggestions to every page; the web's mobile FAB dock, the Windows page-actions row and Apple's tab-bar accessory all stay visible while scrolling; M3 makes hiding optional (MDC FloatingToolbar: "Floating toolbars **can** hide on scroll", consider); and TalkBack, switch and keyboard users get the same toolbar as touch users, where A would bounce the pill in and out after every fling and need dynamic padding. Until #577 every other page hid it (`FloatingToolbarScrollState`, removed). Songs' inline filter stays pinned above the list, the top app bar never scrolls, and scrolling back to the top restores the same bounds. Long or endless lists also pass `actionsReadFirst = true`, so TalkBack reads top bar → toolbar → content. Since #576 the tools float on every window, so in the app no page tool sits in the top app bar or behind ⋮ (outside the shell, `AdaptiveTopBarActions`' ⋮ menu still closes once the sheet or menu one of its tools opened has closed). Material 3 toolbars: “Displays frequently used actions relevant to current page context”; keeping them pinned instead of hide-on-scroll is the owner's #52 choice. Device evidence: `journeys/FloatingToolbarStaysOnScreenAccessibilityJourneyTest` (#577, `android-device` CI) scrolls Statistics (100 % and 200 % text), Song Details, Leaderboards, Compete and Settings by touch and asserts the toolbar keeps its bounds above the bottom bar, Quick Links stays a named 48 dp button in TalkBack's order, and the last row ends above the toolbar (Robolectric twin `ui/FloatingToolbarStaysOnScreenUiTest`, PR CI); `journeys/PinnedPageControlsDeviceTest` (in the `android-device` CI check) runs Songs and Suggestions in portrait and landscape on the phone (floating toolbar in both since #576, wholly on screen), at 100 % and 200 % text. At the top, while scrolled and back at the top it asserts TalkBack's linear order (`JourneyHarness.publishTalkBackTree`): shell actions → toolbar tools → inline filter → list. It also asserts each pinned control's name, role, state and 48 dp target (#418). A page tool with filters says its state in `stateDescription`, never in its name: "No filters" or "Filters on: …" (Songs #181, Item Shop #145, Suggestions #418, which had folded "filters on" into its name).

The selected player's avatar is the whole Profile button, with no container ring.** Web `HeaderActions` `profileButton` (`background: 'none'`, `border: 'none'`), Android `ProfileAvatarButton` (containerless `IconButton`, filled circle) and Windows `ProfileButton` (transparent, `BorderThickness="0"`) draw nothing around it. Prototyped on iOS 26.5: option A (44 pt image inside the glass) grew the glass into a wider capsule, kept the ring and clipped the avatar; plain option B moved the avatar 10 pt in from the trailing edge and left 22 pt (not 12 pt) beside the iPad bell, which the overhang corrects. Evidence: `ProfileAvatarFillJourneyTests` on iPhone and iPad (screenshot-measured disc size, rim and position on a tab root, Item Shop and Search; the phone Search tab has no account items).
- **R9. Android bar and toolbar buttons keep forgiving, separate hit regions (#72, #179).** Quick Links, Sort, Filter, global Search, the bell, Profile and ⋮ are Material 3 `IconButton`s: a 40 dp container inside `minimumInteractiveComponentSize()`'s 48×48 dp touch target, at every window size and font scale, in every placement (floating toolbar, top app bar, and ⋮ menu outside the shell). Neighbouring targets never overlap, and a touch just off the glyph activates the button. Never shrink a bar action below the target with a fixed `Modifier.size` or wrap a bare icon in `clickable`. The bell's unread badge is decorative (`clearAndSetSemantics`) and passes touches to the button. Material 3: “Minimum touch target 48x48dp”; “Touch targets remain 48dp minimum even on large screens”. Tests: the shared `testing/ShellHitTargets` probe, run by `ui/ShellHitTargetUiTest` (Robolectric phone, 200 % text, medium, expanded and landscape phone, all with the tools in the floating toolbar since #576) and `journeys/ShellHitTargetDeviceTest` (every FST AVD and posture; the toolbar on screen and off any hinge), touches each button 22 dp off-centre in four directions.
- **R10. Windows nav-bar and page-tool targets are at least 40x40 epx, and the whole target is clickable (#72, #271).** Each title-bar button (Search, bell, profile) and each page tool (Sort, Filter, Jump, Quick Links, Rank By, the Full/Band Rankings pickers, Song Detail Paths/Item Shop and the pinned Paths) uses `Themes/Styles.xaml` `FSTMinTargetSize`. Icon-only buttons also use it as `MinWidth`. Every new `DropDownButton` uses it too (`HitTargetMarkupTests.EveryDropDownButton_UsesMinTarget`). **Their menu items are targets too (#416):** WinUI's keyboard and mouse padding (`MenuFlyoutItemThemePaddingNarrow`) draws a `MenuFlyout` item's hit-testable pill 27 epx tall, so `Styles.xaml` gives `MenuFlyoutItem`, `ToggleMenuFlyoutItem` and `RadioMenuFlyoutItem` implicit styles with `MinHeight` `FSTMenuItemMinHeight` (44 = `FSTMinTargetSize` plus the template's 2 + 2 epx `MenuFlyoutItemMargin`), so every menu's pill (the UIA bounds) is at least 40 epx tall: Quick Links, Rank By, the Full/Band Rankings pickers, Player History Sort and the Shop tile menu. Items set no height or style of their own (`HitTargetMarkupTests.MenuItems_UseMinTarget`). Agent decision (#416, 2026-10-08): one implicit style for every app menu (A), not Quick Links items only (B: the same 27 epx defect would stay in the other page-tool menus beside it) or WinUI's pointer density (C: fails the Fluent minimum the page tools already meet); owner may override with `/choose`. **Radio choices are targets too (#430):** WinUI's `RadioButton` template draws each choice in a fixed 32 epx row (no `MinHeight`) with an 8 epx `RadioButtonsRowSpacing` between choices, so the Paths wide Difficulty and Display choices, the Sort flyout's Sort By (Songs, Item Shop) and Settings' CHOpt Path Default View were 120 × 32 epx targets. `Styles.xaml` gives `RadioButton` an implicit style (`BasedOn` `DefaultRadioButtonStyle`) with `MinHeight` `FSTMinTargetSize` and `Padding` `8,6,0,6` (6 epx under the label, as the template has above it), and sets `RadioButtonsRowSpacing` to 0, so the target absorbs the old row gap: a one-line list keeps its 40 epx row pitch, and only a group's last choice adds 8 epx below it. Radios and groups set no height, padding, style or spacing of their own (`HitTargetMarkupTests.RadioButtons_UseMinTarget`). Agent decision (#430 design review, 2026-10-10): one app-wide implicit style that turns the row gap into target (A), not a Paths-only style (B: Sort By and Settings would keep the same 32 epx defect) or `MinHeight` with the 8 epx gap kept (C: every Sort By row moves 8 epx and the flyout grows by about 100 epx); owner may override with `/choose`. Evidence: `a11y-paths-swap.json` `paths-swap-keyboard-wide` (CI, normal and 225% text: instrument circles and every Difficulty/Display choice at least 40 × 40, mid-swap and settled), `a11y-keyboard.json` `kb-songs-sort-groups`/`kb-shop-sort` and `a11y-settings-path-view.json` (host). **Drop-down options are targets too (#439):** WinUI's keyboard and mouse `ComboBoxItemThemePadding` (5 epx above, 7 below) draws each `ComboBox` option 38 epx tall, inside a template that insets its pill (`LayoutRoot`) by 2 epx top and bottom like a menu item. `Styles.xaml` gives `ComboBoxItem` an implicit style (`BasedOn` `DefaultComboBoxItemStyle`) with `MinHeight` `FSTMenuItemMinHeight`, so every option (UIA bounds) is at least 40 epx tall, its label still centred: the Paths compact Instrument, Difficulty and Display pickers, Band Detail Rank By, Rivals Rank By and Rivalry Sort By. No `ComboBox` sets an `ItemContainerStyle`, and no option sets its own height or style (`HitTargetMarkupTests.ComboBoxItems_UseMinTarget`). Agent decision (#439, 2026-10-10): one app-wide implicit style, as for menu items and radios (A), not the Paths Instrument picker only (B: the other pickers would keep the same 38 epx defect) or WinUI's pointer density (C: fails the Fluent minimum); owner may override with `/choose`. Evidence: `a11y-paths-swap.json` `paths-instrument-picker` (CI, normal, 225% text and Animation effects off: Lead, Bass, Drums, Tap Vocals each at least 40 epx) and `a11y-experimental-ranks.json` `xr-band-detail-on` (CI: the four Rank By options). Quick Links R6 already sets 48 dp Android and 44 pt Apple menu rows. After any dynamic title-bar change, the shell queues `TitleBar.RecomputeDragRegions()` (`MainWindow.TitleBar.cs` `QueueDragRegionRefresh`). Those changes are: window width, the right header's size (the bell appears), the search box/button swap, and the title cleared at large text. Without the recompute, the stale passthrough rectangles make taps on the new Search control drag the window. Do not use `AutoRefreshDragRegions`: the WinUI spec says it "triggers a visual tree walk on every layout pass". **Passthrough strips span the full title-bar height (#536).** TitleBar truncates each passthrough rect to whole device pixels, so a centred control's rect could stop one pixel short: at 100% scale the bottom pixel row of the search box, Search, the bell and Profile dragged the window (CI `windows-ui`; locally hidden by the locked-console bounds fallback). `MainWindow.xaml` overrides `TitleBarContentVerticalAlignment` and `TitleBarRightHeaderVerticalAlignment` to `Stretch` in `AppTitleBar.Resources` (lightweight styling), and the box sits in `GlobalSearchBoxHost` (`TitleBar.IsDragRegion="False"`, the box's width, collapsed with the box), so each passthrough rect is the full title-bar row around the centred 32 epx box and 40 epx buttons. The search fills the width the tools leave (web `SongsToolbar` `searchWrap` `flex: 1`, the same height as its pills), with no `MaxWidth` or spacer. A new search box in a tools row uses this style (`HitTargetMarkupTests.SongsSearch_MatchesToolHeightAndFillsTheRow`; `journeys/a11y-songs-toolbar.json`: `assertheight` across the four, `assertright` with the rows' right edge, 40x40 buttons, reading order, at compact/medium/wide and 225% text). Fluent targeting: "a minimum target size of 40x40 epx". Evidence: `journeys/a11y-hit-targets.json` (geometry, no input) and `journeys/a11y-hit-targets-press.json` (a real touch tap, and a mouse click on the title bar, at every off-glyph probe, each asserting that control's own result, so a press that lands in the drag region fails; unlocked console only); Narrator reading order and phrases of the same targets: `journeys/a11y-narration.json` (the 40 epx targets don't change what is read or its order).

### Agent decision: Apple page-tool placement per chrome (#633)

Agent decision (#633, 2026-10-14; owner may override with `/choose`). Owner: "Design agent and duo skill can decide what should be floating buttons on Duo and what should go in vertical rail, as well as best iPad and MacOS practices." The rule is **float wherever the section chrome is a horizontal tab bar** (`FloatingPageToolsHost.floatsPageTools(in:)`):
