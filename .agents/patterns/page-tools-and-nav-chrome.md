# Page tools and navigation chrome

> **What:** where navigation, global search, page actions, Quick Links, notifications and Profile belong. **Read when:** adding, moving or styling a shell or page action.

Status: **current**, 2026-10-07. Provenance: #52, #72, #84, #92, #160, #271, #300, #309, #311, #337, #338, #341, #363, #375, #394, #557.

## Intent

Navigation preserves location; page tools act on the current content. The web is the behavior reference, while each native shell uses its platform's navigation and command placement rather than reproducing web pixels.

## Web source (behavior reference)

| Web | Behavior |
|---|---|
| `FortniteFestivalWeb/src/components/shell/mobile/BottomNav.tsx` (`BottomNav`, `BOTTOM_NAV_TAB_MIN_HEIGHT`, `SPACIOUS_BOTTOM_NAV_QUERY`) | Top-level destinations retain their selected state and adapt the compact destination set. |
| `FortniteFestivalWeb/src/components/shell/HeaderActions.tsx` (`HeaderActions`) | Search, notifications and profile are separately labelled shell actions. |
| `FortniteFestivalWeb/src/pages/songs/components/SongsToolbar.tsx` (`SongsToolbar`) | Songs has a local query plus distinct Sort and Filter controls. |
| `FortniteFestivalWeb/src/components/shell/desktop/Sidebar.tsx` (`Sidebar`), opened by `HamburgerButton` in `mobile/MobileHeader.tsx` | Mobile keeps a hamburger sidebar beside the bottom tabs: Songs, Suggestions, Statistics, Rivals, Leaderboards, Shop, the player link with Deselect, then Settings. |

## Rules

- **R1. Separate destinations from page actions.** Navigation remains in the platform shell; Sort, Filter, Quick Links and similar tools are supplied by the current page through its canonical shell hook.
- **R2. Follow the Apple placement ADR, not a copied toolbar.** [Navigation accessories](../design/apple/nav-accessories.md) is the detailed, owner-approved Apple ADR (#92, #300): iPhone page tools register with `PageToolsRegistry` for the system tab-bar accessory; Profile remains the trailing header action; global Search is a Search tab; Songs has the inline `Filter Songs` field; Duo and iPad keep tools as trailing bar items. This is an approved deviation from HIG Tab bars, which says to use tabs for navigation and a toolbar for current-view actions; HIG Toolbars says, “Trailing: important always-available items.” **Owner-approved variant (#333, iPhone Duo only):** on iPhone Duo, folded or unfolded, Songs' `Filter Songs` field sits at the bottom of the page in thumb reach (owner: "Filter Songs should be at bottom of screen on Duo for ease of use"; HIG Search fields: "Place search at the bottom if there's room; this keeps priority search easy to reach"), not in the navigation-bar drawer. It is the shared `GlobalSearchField` on Liquid Glass (**owner-approved, #358**: [surface-materials](surface-materials.md) R2 variant; opaque and bordered under Reduce Transparency or Increase Contrast) in the page's bottom safe-area inset (the shared `BottomSearchField`, `BottomSearchFieldPlacement`; `SongsFilterFieldPlacement` picks it), so the list's last rows and the A–Z scrubber end above it and it rises with the keyboard (plus the measured `keyboardLift` the Duo outer display's inset keyboard otherwise leaves it short); the list fades above it with `bottomChromeFade` (scroll-edge R1). **Owner-approved (#358): it matches the system Search button's height and, with the keyboard hidden, its vertical centre** (owner: "Filter Songs on Duo should align with Search button vertically (in height too)"). Beside the vertical bar (folded in every rotation, inner landscape) the field is 48 pt and centred 48 pt above the window's bottom edge, where the bar's 48 pt Search button sits 24 pt above it; the row ends at the page's bottom safe area (10–34 pt higher), so the field reaches below it (`BottomSearchFieldPlacement.bottomPadding(chrome:rowBottom:windowBottom:fieldHeight:keyboardTop:)`). SwiftUI's hierarchy on Duo ends at that safe area (`DeviceLayout.size` is 644 pt of a 678 pt folded window), so the window's bottom comes from the hosting `UIWindow` (`WindowBottomProbe`). Larger Dynamic Type grows the field around the same centre. With the software keyboard up it sits 8 pt above the keyboard as before. In inner portrait the Search button is in the tab bar, which the field must not cover: the field stays 8 pt above the bar at the tab bar Search button's 62 pt height. Known gap: in the outer landscape with the camera at the bar's bottom the system lifts its Search button clear of the camera (y 336–384 of 466 in a 2026-10-04 capture); the field keeps the 24 pt model there until the pose can be captured again. **Agent decision (#334, 2026-10-07; supersedes #333's flat-landscape choice) and owner rule (#349): only a book-pose fold (`DeviceLayout.pose == .partiallyFolded`, `BottomSearchFieldPlacement.pageHinge(for:)`) moves the field to the trailing page, a 16 pt margin clear of the fold; folded, flat (portrait or landscape, even with the inactive hinge reported) and inner portrait it spans the full bottom width (16 pt margins); owner may override with `/choose`** (owner, #332/#349: "When partially folded landscape, align filter songs on right page" and "search bar when keyboard is closed and unfolded should take full bottom width. Can stay on right side if hinge is unfolded but device is not completely unfolded"; HIG Designing for iPhone Duo: "Folding region | Present when partially open"; "use reserved-region APIs to keep important elements clear of the center"). `pageHinge(for:)` is `DeviceLayout.splitHinge`, which is nil unless partially folded (#361); never pass `DeviceLayout.screenDivide` (it returns the flat free-space midline) to a bottom field. iPhone, iPad and Mac keep the top inline field; do not move them. **Search on the Duo inner display (#349):** the Search tab's system `.searchable` field sat in the bottom trailing ~370 pt beside the vertical bar and rose centred over the keyboard, out of line with the full-width scope bar, and no system API sets its width; so on the inner display (flat or book-folded; `GlobalSearchFieldPlacement`) the tab shows the same `BottomSearchField`, focused when the tab appears. **Agent decision (#349, 2026-10-07; owner may override with `/choose`): the scope bar and the field share one column** (`bottomSearchFieldColumn(hinge:)`): full width when flat, the trailing page in book pose, with the scope bar kept at the top of the results (HIG Search fields: "Consider a scope bar in the results area"; web `SearchModal` keeps its search bar and target tabs in one column). Rejected: scope bar on the left page with the field on the right (splits two controls that work together), scope in a menu or tokens (hides the current scope; HIG Searching: "Show current scope with descriptive placeholder, scope bar, or title"). The folded outer display keeps the system Search field, which already spans its bottom.
- **R3. Keep the accessory stable.** Apple accessory slots are fixed at 44 pt, page tools remain in page order, the bell stays trailing, and a width/type-size fold is decided from window width rather than the accessory’s live morphing width (#300). HIG Buttons: “the hit region is at least 44x44 pt.” Accessibility (#395, for #15): the hosted `NavButtonAccessibilityTests` (`apple-ci`) render the real `PageToolsAccessoryBar` and require Sort, Filter Songs, Quick Links, Notifications as named buttons (with Sort's and Quick Links' values) read left to right, each a 44 pt slot that no neighbour overlaps, the bell trailing, unchanged at AX5 (the bar caps text at `maxTypeSize`), and a press on Quick Links opening its choices; the header's Open Navigation and Profile buttons stay single named buttons with hints and a decorative monogram (R8).
- **R4. Use the current Android placement.** Global search is a top app bar action (`GlobalSearchEntry`, a full-screen search view on compact windows) on every window size, before notifications then Profile at the trailing end. Compact windows put page tools (Sort, Filter, Quick Links) in the shell’s `FloatingToolbar`; regular windows put them in the top app bar. A page's own list filter (Songs) is a search field pinned inline above the list at every size, never a toolbar item. Material 3’s top-app-bar rule is “Use when: Every screen needs a title and optional actions”; search is “Compact: Full-screen search view”; toolbars display “frequently used actions relevant to current page context”. **Agent decision (#309, 2026-10-05): option C, top app bar search + inline Songs filter + floating toolbar for Sort/Filter/Quick Links (replaces #84's toolbar search pill); owner may override.** It matches Apple's inline filter and bottom page-tools grouping and the web's `SongsToolbar`/`HeaderActions` split, and keeps five bottom destinations. It departs from Apple only by not adding a Search tab, which would push Statistics out of M3's 3–5 destination limit.
- **R5. Use the current Windows placement.** `TitleBar.Content` owns the global `AutoSuggestBox`; page-local Songs search, Sort, Filter and Jump remain in the page actions row. `NavigationView` owns destinations; it has no minimizing bottom-tab accessory (#84).
- **R6. Do not add a parallel command surface.** Pages register Apple tools, register Android shell actions, or use the Windows page-header convention; they do not create a second dock, floating capsule, global-search entry point or custom navigation bar.
- **R7. Android page tools stay reachable while the content scrolls (#52, #160).** Songs and Suggestions pass `FestivalScreen(pinActions = true)`: the compact floating toolbar never hides or minimizes on scroll, Songs' inline filter stays pinned above the list, the top app bar never scrolls, and scrolling back to the top restores the same bounds. Long or endless lists also pass `actionsReadFirst = true`, so TalkBack reads top bar → toolbar → content. On a list pane too narrow for the title, `AdaptiveTopBarActions` moves the page tools behind ⋮; its menu closes once the sheet or menu one of its tools opened has closed (window refocus). Material 3 toolbars: “Displays frequently used actions relevant to current page context”; keeping them pinned instead of hide-on-scroll is the owner's #52 choice. Device evidence: `journeys/PinnedPageControlsDeviceTest` (in the `android-device` CI check) runs Songs and Suggestions in portrait (floating toolbar) and landscape (Suggestions: top app bar; Songs: ⋮) on the phone, at 100 % and 200 % text. At the top, while scrolled and back at the top it asserts TalkBack's linear order (`JourneyHarness.publishTalkBackTree`): shell actions → toolbar tools → inline filter → list on the toolbar; page tools → Search → Profile → list in the top app bar; ⋮ → Search → Profile → list with ⋮, whose menu reads Quick Links → Sort → Filter. It also asserts each pinned control's name, role, state and 48 dp target (#418). A page tool with filters says its state in `stateDescription`, never in its name: "No filters" or "Filters on: …" (Songs #181, Item Shop #145, Suggestions #418, which had folded "filters on" into its name).
- **R8. The selected player's avatar is the whole Profile button, with no container ring.** Web `HeaderActions` `profileButton` (`background: 'none'`, `border: 'none'`), Android `ProfileAvatarButton` (containerless `IconButton`, filled circle) and Windows `ProfileButton` (transparent, `BorderThickness="0"`) draw nothing around it. Apple iOS/iPadOS 26+: the monogram toolbar item hides its shared Liquid Glass (`ToolbarContent.profileItemBackground` → `sharedBackgroundVisibility(.hidden)`, in `RootChrome.swift` only) and fills the 44 pt glass-item diameter with no rim, overhanging its layout rect by the 10 pt padding a bar puts on each side of a background-less item, so the circle lands exactly where the glass circle was and sits the standard 12 pt group gap from the bell (`RootProfileButton.MonogramMetrics`, `UIImage` alignment-rect insets); the add-profile glyph, the Duo rail symbol, the bell and page tools keep system glass. **Agent decision (#311, 2026-10-05): option C, hide the item's glass and overhang the 44 pt avatar to the glass circle's position (B plus alignment), rather than enlarge the image inside the glass (A) or hide it without realigning (B); owner may override with `/choose`.** HIG Toolbars: "Reduce backgrounds/tints that interfere with system effects" (should); HIG Materials: "Use Liquid Glass effects sparingly on custom controls" (should); HIG Buttons: "the hit region is at least 44x44 pt" (kept: it is still a standard image bar button, issue #15). Prototyped on iOS 26.5: option A (44 pt image inside the glass) grew the glass into a wider capsule, kept the ring and clipped the avatar; plain option B moved the avatar 10 pt in from the trailing edge and left 22 pt (not 12 pt) beside the iPad bell, which the overhang corrects. Evidence: `ProfileAvatarFillJourneyTests` on iPhone and iPad (screenshot-measured disc size, rim and position on a tab root, Item Shop and Search; the phone Search tab has no account items).
- **R9. Android bar and toolbar buttons keep forgiving, separate hit regions (#72, #179).** Quick Links, Sort, Filter, global Search, the bell, Profile and ⋮ are Material 3 `IconButton`s: a 40 dp container inside `minimumInteractiveComponentSize()`'s 48×48 dp touch target, at every window size and font scale, in every placement (floating toolbar, top app bar, ⋮ menu). Neighbouring targets never overlap, and a touch just off the glyph activates the button. Never shrink a bar action below the target with a fixed `Modifier.size` or wrap a bare icon in `clickable`. The bell's unread badge is decorative (`clearAndSetSemantics`) and passes touches to the button. Material 3: “Minimum touch target 48x48dp”; “Touch targets remain 48dp minimum even on large screens”. Tests: the shared `testing/ShellHitTargets` probe, run by `ui/ShellHitTargetUiTest` (Robolectric phone, 200 % text, medium, expanded and ⋮ pane) and `journeys/ShellHitTargetDeviceTest` (every FST AVD and posture), touches each button 22 dp off-centre in four directions.
- **R10. Windows nav-bar and page-tool targets are at least 40x40 epx, and the whole target is clickable (#72, #271).** Each title-bar button (Search, bell, profile) and each page tool (Sort, Filter, Jump, Quick Links, Rank By, the Full/Band Rankings pickers, Song Detail Paths/Item Shop and the pinned Paths) uses `Themes/Styles.xaml` `FSTMinTargetSize`. Icon-only buttons also use it as `MinWidth`. Every new `DropDownButton` uses it too (`HitTargetMarkupTests.EveryDropDownButton_UsesMinTarget`). **Their menu items are targets too (#416):** WinUI's keyboard and mouse padding (`MenuFlyoutItemThemePaddingNarrow`) draws a `MenuFlyout` item's hit-testable pill 27 epx tall, so `Styles.xaml` gives `MenuFlyoutItem`, `ToggleMenuFlyoutItem` and `RadioMenuFlyoutItem` implicit styles with `MinHeight` `FSTMenuItemMinHeight` (44 = `FSTMinTargetSize` plus the template's 2 + 2 epx `MenuFlyoutItemMargin`), so every menu's pill (the UIA bounds) is at least 40 epx tall: Quick Links, Rank By, the Full/Band Rankings pickers, Player History Sort and the Shop tile menu. Items set no height or style of their own (`HitTargetMarkupTests.MenuItems_UseMinTarget`). Agent decision (#416, 2026-10-08): one implicit style for every app menu (A), not Quick Links items only (B: the same 27 epx defect would stay in the other page-tool menus beside it) or WinUI's pointer density (C: fails the Fluent minimum the page tools already meet); owner may override with `/choose`. Quick Links R6 already sets 48 dp Android and 44 pt Apple menu rows. After any dynamic title-bar change, the shell queues `TitleBar.RecomputeDragRegions()` (`MainWindow.TitleBar.cs` `QueueDragRegionRefresh`). Those changes are: window width, the right header's size (the bell appears), the search box/button swap, and the title cleared at large text. Without the recompute, the stale passthrough rectangles make taps on the new Search control drag the window. Do not use `AutoRefreshDragRegions`: the WinUI spec says it "triggers a visual tree walk on every layout pass". **Passthrough strips span the full title-bar height (#536).** TitleBar truncates each passthrough rect to whole device pixels, so a centred control's rect could stop one pixel short: at 100% scale the bottom pixel row of the search box, Search, the bell and Profile dragged the window (CI `windows-ui`; locally hidden by the locked-console bounds fallback). `MainWindow.xaml` overrides `TitleBarContentVerticalAlignment` and `TitleBarRightHeaderVerticalAlignment` to `Stretch` in `AppTitleBar.Resources` (lightweight styling), and the box sits in `GlobalSearchBoxHost` (`TitleBar.IsDragRegion="False"`, the box's width, collapsed with the box), so each passthrough rect is the full title-bar row around the centred 32 epx box and 40 epx buttons. New title-bar controls go inside these hosts, never as a bare centred control (`HitTargetMarkupTests.TitleBar_PassthroughSpansTitleBarHeight`; `hit-titlebar-box` probes the box 14.5 epx above and below its centre). Fluent targeting: "a minimum target size of 40x40 epx". Evidence: `journeys/a11y-hit-targets.json` (geometry, no input) and `journeys/a11y-hit-targets-press.json` (a real touch tap, and a mouse click on the title bar, at every off-glyph probe, each asserting that control's own result, so a press that lands in the drag region fails; unlocked console only); Narrator reading order and phrases of the same targets: `journeys/a11y-narration.json` (the 40 epx targets don't change what is read or its order).
- **R11. Windows page-header button rows wrap instead of clipping (#285).** A row of page-header buttons whose labels grow with text size goes in the shared `Controls/WrapPanel` (8 epx both ways), never a horizontal `StackPanel`. At 225% text in a compact window, the profile's "Switch to This Profile" + Quick Links row ran Quick Links off the window edge. Consumers: Rivals `Commands`, Player profile/Statistics `TitleActions`, Item Shop `HeaderActions` (Sort, Filter, List/Grid; #379, in a `*` column because a `WrapPanel` in an `Auto` column gets infinite width and never wraps). Songs' `Actions` is its own adaptive `Grid`. winui-design: "Clipped content is a worse failure than a slightly-wide window"; Reflow: "Sequence can wrap or change columns". Evidence: `journeys/a11y-profile-title.json` `pt-actions-wrap` (Quick Links below Switch at `text-225`) and `pt-actions-row` (one row at normal text).
- **R12. Apple phone tab bars show one section set in every pose (#92, #337).** `FestivalTabPolicy` decides the sections; `ShellPresentation.sections` fits phone tabs beside the Search tab (`fittingSearchTab`). Every phone, iPhone Duo folded and unfolded (landscape vertical bar and portrait tab bar) included, shows Songs · Leaderboards · Settings without a player and Songs · Suggestions · Compete · Settings with one: Compete covers Leaderboards and Rivals, which the drawer pushes, and Statistics opens from the Profile button (`ProfileButtonAction`) and the drawer. Only the wide shells (iPad flyout, Mac sidebar) list Leaderboards, Rivals and Statistics as separate destinations (`DeviceLayout.usesRegularSectionSet` is the sidebar shell only). A fold or unfold therefore never rebuilds the tabs or moves the selection. Owner (#337): "On Duo, keep Compete button in unfolded nav bar vertical; remove Rivals/Leaderboards. In unfolded portrait, make that consistent." HIG Designing for iPhone Duo: "Preserve functionality, element state, hierarchy, and access across displays/poses" (should); HIG Tab bars: "use as few tabs as the hierarchy needs" (should). Tests: `ShellPresentationTests` (policy) and the iOS journey `DuoShellJourneyTests` (fold → unfolded landscape → unfolded portrait → fold through real UIKit size-class changes with the Debug `FST_DEBUG_DUO_WINDOW_REMOTE` switch: phone tabs, Compete selected, pushed Rivals and Profile → Statistics kept, no tab-rebuild crash).
- **R13. Apple keeps the hamburger drawer on iPhone, iPhone Duo and iPad (#338).** On phone shells (iPhone, Duo folded and unfolded) the drawer (`DrawerMenu`, `FestivalDrawer`) is the only route to Item Shop and, with a player, to the Leaderboards overview (Band Rankings included) and the Rivals overview. It is also the only touch route to Deselect. Every other destination is a tab (Songs, Suggestions, Compete, Leaderboards without a player, Settings) or the Profile button (Statistics, Select Profile). On iPad the flyout is the window's whole navigation: Search plus every `SidebarMenu` section, the profile footer with Deselect, then Settings; the menu-bar Go/Profile commands are a keyboard-only second path. Do not remove the drawer, or move one of its rows elsewhere, unless the same change gives that destination another visible route; `ShellPresentationTests.phoneDrawerIsTheOnlyRouteToItsDestinations` and `iPadFlyoutReachesEverySection` pin the set. **Agent decision (#338, 2026-10-07; owner may override with `/choose`): option A, keep the drawer on every Apple touch shell** over B (remove it on iPhone/Duo, moving Deselect to the Profile sheet) and C (remove it everywhere). B needed three new entry points: Item Shop as a tab breaks the five-slot bar with Search (HIG Tab bars: "Avoid overflow… insufficient width turns the trailing item into More, hiding the remaining items in a separate list", should); overview links on Compete reverse web #36; Deselect on the player page reverses operator batch 7.10. C fails "iPad keeps a way to reach every section" and the 2026-10-04 flyout decision. The web keeps the same hamburger on mobile (`MobileHeader` → `Sidebar`, with Shop, Rivals, Leaderboards and Deselect). HIG Sidebars: "When more areas are needed than fit in a tab bar, its convertible sidebar-style appearance can expose less-frequent areas" (should); HIG Designing for iPhone Duo: "Preserve functionality, element state, hierarchy, and access across displays/poses" (should).
- **R14. Every Apple page shows its standard navigation title, in every iPhone Duo pose (#341).** Each page sets its title with `festivalNavigationTitle(_:)` (`Common/PageTitle.swift`; the Songs, Settings and Search roots use `navigationTitle`), in every state: Statistics' brief no-profile state is titled "Statistics". Keep the system display mode: roots get the large title, which collapses into the bar while scrolling wherever the bar is horizontal (iPhone, Duo inner portrait, iPad), and pages that chose inline (Song Detail, leaderboards) stay inline. Under the Duo vertical bar (folded in every rotation, inner landscape) the system has no horizontal bar for the collapsed title, so it shows the title at the top of the page and, by minimizing the navigation bar on scroll (iOS 27 `toolbarMinimizationBehavior`), scrolls it away with the content in **both** modes (inline too); the selected rail tab (roots) or Back (pushed pages) keeps the location, and the title returns at the top. Never hide the navigation bar, force a display mode per pose, or add a pinned custom title: a custom-view title item stays horizontal and is drawn in a top bar beside the rail, which minimizes away on scroll ([duo.md](../design/apple/duo.md#toolbar-rules-all-duo-poses)). Song pages' principal bar titles are owned by [song-header](song-header.md) R4 and [song-leaderboard-header](song-leaderboard-header.md); the instrument title beside Song Detail (`InstrumentPageTitleToolbarItem`, #342) is added only under a horizontal bar, so the Duo rail keeps the system title. **Song-page exception (owner-approved, #363; overrides #341 for these pages only):** Song Details, Song Leaderboard, Band Song Leaderboard and Player History with their song header show **no** title at the top under the Duo vertical bar while the header is on screen, then the pinned song title once it scrolls away, and none again when it returns, as on iPhone (song-header R4). They keep their system title (`festivalNavigationTitle(song.title)`, for Back menus and the app switcher), hide it behind the `SongBarTitleToolbarItem` placeholder, and keep the bar from minimizing with `View.songBarTitleKeepsBarVisible(_:)`. The title is read once: the hero or header names the song while it is visible, the bar title only after. Owner: "Song page title doesn't need to appear until scroll begins and header is out of view (similar to how it works on iPhone, where we scroll then the page header appears)". Every other Duo page, a song board titled by its board beside Song Detail included, keeps the base rule. **Agent decision (#341, 2026-10-07): option A, the system navigation title in every pose, folded and unfolded (not B, no titles on Duo; not C, titles only unfolded); owner may override with `/choose`.** HIG Toolbars: "Give each window a useful title to confirm location" (should) and, on iOS, "Use a large title to help people stay oriented" (should); Designing for iPhone Duo: "Preserve functionality, element state, hierarchy, and access across displays/poses" and "in general, don't override the default bar placement" (should). Prototyped and dropped: forcing `.inline` under the vertical bar only shrank the folded title (large → 17 pt); Settings and Songs still lost it on scroll (iOS 27.1 Duo simulator). The web's `PageHeader` pins its title above the scroll container, but native chrome beats web chrome here. The old "S…" list-column truncation (duo-notes S5) belonged to the superseded always-on inner-portrait split: inner portrait now pushes full-width pages under a horizontal bar, and every root title is under 15 characters. **Band Detail shows the large title (#555):** it sets `.navigationBarTitleDisplayMode(.large)` so it never inherits Band Rankings' or a song board's inline mode, and its "{type} • {N} appearances" subtitle is the first content row (web `PageHeader` subtitle; the Band Rankings `RankingsCountHeader` precedent), never `navigationSubtitle` or a custom pinned title. **Item Shop is a root-level page (#375):** phones push it from Songs (the iPad sidebar shows it as a root), and it keeps the same system large title as the roots, never a page-specific mode or font. Measured on the Duo (iOS 27.1, live service): Songs, Leaderboards, Settings, Suggestions, Compete, Statistics and Item Shop titles are the same 34 pt glyphs folded and in the simulated unfolded windows. A title that *looks* bigger is the context, not the page: inline pages (Song Detail, leaderboards) are 17 pt, a root's title collapses to 17 pt once scrolled under a horizontal bar (inner portrait), and the same 34 pt reads larger on the 466 pt outer display than on the 951 pt inner one.
- **R15. A page's primary action looks the same in every bar (#351).** Where a page's key action (Player Select / Switch to This Profile) is a prominent accent button in a horizontal bar (`ProfileIdentityToolbarItem`, `.borderedProminent` tinted `ProfileIdentityAction.prominentFill`), the iPhone Duo vertical bar draws it with the canonical `VerticalBarActionItem` passing the same `prominentFill`, and ranks it `RootChromeRailItem.primaryPageAction` (`.high`) so it stays visible right after Back instead of overflowing into `…`. Select and Switch share the accent fill; destructive Deselect (drawer only) stays red. Plain page actions keep the monochrome symbol and default priority; do not tint a rail symbol by hand. HIG Toolbars: "Use `.prominent` for a key action such as Done/Submit"; HIG Color: "For a primary action, color the background, not symbols or text"; HIG Designing for iPhone Duo: "Place primary navigation (Back/Close) at the top, then prominent actions (Done)". Tests: `ProfileIdentityActionTests`, `RootChromeRailPriorityTests` (shared fill and rail rank) and the fixture-backed `PlayerIdentityRailJourneyTests` (screenshot-measured: Select and Switch must fill at least half their frame with the accent blue, in the Duo rail when the sections are a vertical bar and in the header button otherwise, and stay hittable rather than overflow; the drawer Deselect must read red, not blue). Run it with `ios_sim.py uitest --device duo --pose folded` for the rail and on the default iPhone for the horizontal bar.
- **R16. One drawer placement on every Apple touch shell (#339).** `DrawerPlacement` (`FestivalDrawer.swift`) owns the geometry. The scrim always dims the **whole window**, the iPhone Duo vertical bar and the artwork behind it included, and a tap anywhere on it (over the bar too) closes the drawer; the bar's items are not tappable while the drawer is open, as the iPhone tab bar is not. The panel floats 8 pt (`DrawerPlacement.margin`) from the window's top and bottom edges and pads its rows clear of the status bar and home indicator (`contentTop`, `contentBottom`) rather than shrinking. On iPhone Duo it also starts after a leading vertical bar and moves off an edge only for the camera occlusion beyond the safe area (`DeviceLayout.cutoutInsets`), in every pose: folded (four rotations), flat landscape, book and inner portrait. Owner (#339): "nav bar flyout does not darken animated image behind system rail"; "hamburger flyout does not extend to bottom of screen". Precedent: the iPhone drawer and the iPad flyout (full-window scrim, full-height panel). HIG Layout: "Extend full-screen backgrounds beneath sidebars, toolbars, and tab bars to window/screen edges"; HIG Designing for iPhone Duo: "Keep controls' relative positions as similar as possible across poses" (should). Tests: `ShellPresentationTests.iPhoneDrawerPlacementUnchanged`, `duoDrawerAvoidsBarAndCamera`, `duoUnfoldedDrawerReachesTheBottom`, `drawerCutoutSitsOnThePanel` (geometry), and the rendered iOS journey `DuoDrawerJourneyTests` (real drawer on the folded Duo and on the simulated unfolded window; it compares bar luminance in screenshots before and after opening, at most 75 % kept against a 45 % scrim, checks that the panel's frame reaches the window bottom less the margin, and checks the modal panel (`.isModal`, an XCUI `Alert`) with its rows in reading order, then taps the bar's spot and asserts the drawer closes with Songs still selected. On the pre-#339 code it fails all three checks.) **Owner-approved variant (#362, Apple touch drawer: iPhone, iPad flyout, iPhone Duo folded and unfolded): the drawer opens and closes in two stages.** Owner: "“Shadow” flies out with hamburger menu flout. Can screen darken and *then* hamburger menu opens? (And reverse for closing as well)". Opening, the whole-window scrim fades in place (`DrawerMotion.scrimDuration` 0.15 s, to 45 % black) and then the panel slides in from the leading edge (`panelDuration` 0.25 s, ease-out, the web `SIDEBAR_DURATION`). Closing (scrim tap, swipe, Escape, close button, choosing a row) runs the same timeline backwards: the panel slides out, then the scrim fades. Never put a `.move` transition on the whole `FestivalDrawer` again: the scrim must not travel with the panel. `FestivalDrawer` animates one linear `presence` (0–1) that `DrawerMotion` maps to the two stages; `DrawerScrimStage` and `DrawerPanelStage` are `Animatable` modifiers placed directly on the scrim, the scrim's cut-out and the panel (a transition modifier that writes an environment value does not re-render the children each frame). The root keeps the drawer mounted (`drawerMounted`) until the close sequence completes (`onDismissed`), and the closing drawer ignores touches and leaves the accessibility tree at once. Reduce Motion (system or the in-app override): the same two stages fade only, with no slide (HIG Accessibility: "When Reduce Motion is on … replacing axis transitions with fades"). Dragging the panel still ties scrim opacity to its position (`dragProgress`), and a released drag that does not dismiss snaps back. The web overlay fades while the panel translates at the same time; this sequential order is the owner's choice for Apple and does not apply to Android, Windows or the web unless the owner asks there. HIG Motion: "Keep feedback animations brief and precise" (0.4 s in total). It measures the scrim as the brightness kept beside the panel and the panel as the share of changed pixels in six strips across its header and first rows (the glass edge is found in pixels, because the Duo and iPad flyout drawer elements are wider than the glass; the status bar, which the scrim never dims, is left out of every measured region; on iPad the test fills the window first, since iPadOS remembers resized windows). - **R17. - **R19. The iPhone search drawer keeps its capsule through push and pop (#544).** A page's system `.searchable` navigation-bar drawer (Songs Filter Songs on iPhone and narrow iPad windows) goes through `SongsSystemFilterField`, which applies `SearchDrawerTransitionFill` (`Common/Chrome`). Why: while a page pushes or pops, iOS 26/27 hides the real search bar and slides a `_UIPortalView` copy with the page. Once content is scrolled under the bar, the field's resting look is Liquid Glass, which the portal cannot draw, so only the magnifier and prompt moved and the capsule popped in about 0.5 s after the transition. A bare SwiftUI `List` with the same drawer does the same, so this is system behavior, not a page modifier. Rule: for an animated push or pop in the field's own `UINavigationController` (not a tab switch or modal), and only when `isContentUnderBar` (content scrolled past 0.5 pt), the search text field gets `UIColor.tertiarySystemFill` (UIKit: the fill for "input fields, search bars"), which the portal draws. The fill is cleared when the last overlapping transition completes or is cancelled. The resting field keeps its system glass, its flat at-top fill, and its Reduce Transparency and Increase Contrast looks. Never replace the drawer with a custom glass field and never keep a constant fill (it lightens the at-top field). A new pushing page with a drawer reuses `SongsSystemFilterField`'s modifier; guard `apple-search-drawer-fill`. HIG Search fields: "Put a top inline field above its list and consider pinning it to the top toolbar while scrolling" (consider); HIG Materials: "system components provide the appearance and behavior automatically". Back still moves and rebuilds nothing ([back-keeps-place](back-keeps-place.md) R2/R3).
- **R20. Windows page-tool and title-bar popups open inside the window (#534).** Every app `Flyout`/`MenuFlyout` (Sort, Filter, Quick Links, Rank By, the Full/Band Rankings pickers, Player History Sort, the Shop tile menu, the profile and Notifications flyouts) sets `ShouldConstrainToRootBounds="True"` in XAML or its code initializer, and every `AutoSuggestBox` (title-bar search, profile search, Songs search, the Search page, Find Rival) sets `controls:PopupHosting.InWindow="True"`, which constrains the template's `SuggestionsPopup` (the template sets it `False`) before its first open. A WinUI 3 desktop popup is otherwise windowed: its `PopupHost` bridge's input site exactly covers the bridge, which Axe.Windows reports as `BoundingRectangleCompletelyObscuresContainer` (an error for Narrator users' scan tools), and the bridge lingers after the popup closes. An in-window menu taller than the window scrolls inside it rather than extending past the window edge. Tooltips have no public opt-out (WinUI always windows them), so journeys move keyboard focus off a button with a tooltip before a final scan. **Agent decision (#534, 2026-10-09): constrain every app popup (A), rather than allow the finding per page (B: hides real flyout regressions) or only the two reported menus (C: leaves the same finding in every other flyout); owner may override with `/choose`.** winui-design keeps the Fluent idiom ("contextual action → `Flyout` / `MenuFlyout`"); `winapp find-api` documents the public property: `FlyoutBase.ShouldConstrainToRootBounds` "indicates whether the flyout should be shown within the bounds of the XAML root." Guards: `PopupHostingMarkupTests` (Core tests) and the `popups`/`popups-text-225` runs in `tools/windows/ui_ci.py` (Rank By, Quick Links, profile and Notifications flyouts open, scanned with no Axe allowance).
