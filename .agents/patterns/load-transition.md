# Load transition

> **What:** first-load gates, reload swaps, graph card list swaps and row entrances for pages, boards and data-backed modal content. **Read when:** a load, refresh, selector, page or modal switch changes visible data.

Status: **current**, 2026-10-07. Provenance: #30, #60, #61, #70, #71, #149, #169, #177, #260, #261, #270, #304, #316, #323, #325.

## Intent

Loading must communicate a deliberate state change rather than a hard cut: first loads gate incomplete content, reloads replace stale content through a spinner, and row entrances run once per reveal rather than while the reader scrolls.

## Rules

- **R1. Separate first load from reload.** A first-load gate shows one spinner until the initial content is ready; a selector, page or retry reload uses the shared swap rather than a local Boolean or skeleton implementation. Nothing comes before that spinner: a page that must read settings before it can build its content (Android Leaderboards overview, #178) counts unread settings as not ready in its swap, so the first load shows the spinner, keeps it while its first data loads, and reveals with the swap's entrance. It never shows an empty body.
- **R2. Reloads are latest-wins.** Hide or fade the old result, show the spinner while the newest request settles, fade the spinner, then reveal the committed result and its row stagger. Apple’s immediate old-content removal is the approved #71 variant that prevents new labels on stale rows. Stale content never shows under the spinner: content that keeps its slot beside the spinner (a pinned "your score" row whose slot holds the pager in place, #93) is invisible, absent from the accessibility tree and ignores touches until the new result commits, with or without reduced motion (Android `LoadSwap.pinnedContentModifier` with `pinnedStaggered`, opt-in for content kept composed under the spinner only: the song and song band leaderboards' pinned rows, #149, keyed by `rememberLoadSwap(pinnedKey = …)` since #190, and the Leaderboards overview list that keeps loading its cards there, #178, which hides on every reload; Windows `LoadSwapGate` + `PinnedRowGate` + `PinnedRowReveal` on the song leaderboard, #295, the song band leaderboard, #306 and #307, and Full Rankings, #270). A pinned row is stale only when the pending request can change it: like the web footer (`PaginatedLeaderboard` re-animates only when `footerAnimKey` changes; Full Rankings passes its instrument + Rank By `cacheKey`, never the page), a page-only, retry or refresh reload keeps it visible and usable beside the spinner, without a fade or re-entrance; it still fades in with the first rows on the first load (#295) (Windows agent decision below; Android owner decision, #190). The spinner is one element: the system busy indicator, named for what is loading ("Loading Item Shop"); never wrap it in a role-less element. Assistive technology reads whatever the gate keeps (a retained header) before the spinner, and the gate never reorders the controls around it (Apple `FestivalLoadingView` labels the `ProgressView` itself; `FestivalReloadGate` sorts its retained frame first inside its own container, #431; only the retained-frame gate adds that container, because macOS reads a container's children back to front and a whole-content gate's container put Songs' floating section title after its rows, #391). HIG VoiceOver: "be sure to keep labels current as interface and content change".
- **R3. Use the shared timings.** Board/page swaps use 300 ms content-out and 500 ms spinner-out; Apple gates retain the web 150 ms spinner-in and 400 ms minimum spinner. Paths uses 300 ms fades (web `opacity 300ms ease`) with a 400 ms image or 500 ms text minimum. The Paths table then reveals by its row stagger rather than a container fade (web `PathDataTable` `textStagger`: each row's 400 ms `fadeInUp` starts 60 ms after the previous one, `STAGGER_ROW_MS`, uncapped). It still fades out as a whole (Android #177 and Windows `FadeIn.Stagger`). Agent decision (#177, 2026-10-06): the Paths content, message and spinner fades use the web CSS `ease` curve (`cubic-bezier(0.25, 0.1, 0.25, 1)`, Compose `Ease`), not the M3 Standard curve (`cubic-bezier(0.2, 0, 0, 1)`) nor the earlier Android linear fade. Material 3's transition table ("Standard | 300ms | Begin and end on screen (utility)") is a recommendation, not a requirement, and the duration is already met; web `PathsModal` sets `opacity 300ms ease`, and web semantics beat undocumented native copies (Android's linear fade, Apple's `.easeInOut`), so this keeps what the web reader sees: about 80% faded in halfway through, where Standard is about 88% and linear 50%. The `SongPathsSheetUiTest` image fade test fails if the curve goes back to linear. Owner may override. The publication refresh (R9) runs all four phases: content out 300 ms → spinner in 150 ms, held ≥400 ms and until the page has prepared for the new generation → spinner out 500 ms → rebuilt content in.
- **R4. Keep controls usable.** Pickers, pagers and modal selectors live outside the gated result area; a new selection supersedes pending work instead of waiting for it. A pager stays visible and tappable while the next page loads, showing the last loaded page count until the new one commits (web `placeholderData: (previous) => previous`); it hides only for the first load and on failure. The stale-content hiding of R2 never applies to controls (Android band pagers, #149). A page header naming what is loaded (the song leaderboard header, [song-leaderboard-header](song-leaderboard-header.md) R5) also stays outside the gate: it appears with the first load and stays still while pages change, and only the rows swap (web `LeaderboardPage` keeps `SongInfoHeader` outside its LoadGate and skips its stagger on `'paginate'`, #316). Apple keeps a header that shares the rows' scroll view through `FestivalReloadGate`'s retained-frame form; Android and Windows hold it outside their swap. A failed reload keeps that header too: the error and Retry replace only the rows beneath it (web renders `EmptyState` in the result area under `SongInfoHeader`); only a failed first load, with no header yet, fills the page. A reload must not shrink the scroll content enough to clamp a header that has scrolled under the bar back into view ([song-leaderboard-header](song-leaderboard-header.md) R3).
- **R5. A scroll rushes the first-load stagger and never replays it.** Every page has one fade window for its first-load entrance. Like the web `useStaggerRush` (installed for every page by `Page.tsx`, and by `SearchModal`), any scroll while the entrance is running starts every fade that hasn't begun yet. That includes a drag, a fling, a Quick Links or section jump, and the programmatic jump to a selected row. The remaining content then fades in together (one 400 ms `fadeInUp`) instead of finishing its stagger. Content that the scroll realizes while the entrance runs joins it rather than appearing opaque (#323). Fades that have already started keep running. Once the entrance has finished, lazily realized content appears immediately, so scrolling never replays an entrance. A list window that limits fades to its load (sections that start loading when scrolled to) also shows content loaded after the scroll in place. Suggestions alone fades newly generated batches: only its first batch is rushed, because web `SuggestionsPage` doesn't install the rush. A selected-row reveal (web `navToPlayer`/`navToBand`: the song leaderboard, the song band leaderboard and Full Rankings) scrolls only after that row's own entrance, and doesn't scroll if the reader has already scrolled. Apple re-arms the Suggestions window for each new batch, so a scroll rushes only that batch's entrances. The rows a selected-row reveal reaches fade in with its rush even when it starts as the stagger ends, and a row a lazy list builds below the viewport ahead of time never spends its entrance unseen (#351 review).
- **R6. Honor reduced motion.** Motion-disabled platforms swap without fades or stagger; retain only the minimum spinner hold needed to avoid a blink. An automatic scroll to a selected row is instant and does not wait for an entrance. HIG Motion: "Add motion purposefully; gratuitous or excessive animation distracts and can cause physical discomfort." MD3: the easing/duration system is used for "transitions (entering, exiting, shared-axis)."
- **R7. Graph card lists follow the web list sequence.** When a graph card's selector changes already-loaded data, its list under the card (Score History's best scores) is not a reload and shows no spinner. The old rows fade out and drift up 8 units (150 ms ease-in, 40 ms stagger; the phase lasts 200 + 40 × (rows − 1) ms). Then the list eases to its new height over 300 ms (`ease`) with no rows visible, and the new rows fade in from 12 units below (300 ms ease-out, 60 ms stagger). A newer change cancels the running one, and the same rows update in place. The list follows the selection at once rather than a graph fade, and the card's View All button sits outside the list, toggling with the selection as in the web `GraphCard`. Reduced motion swaps at once (R6).
- **R8. Graph card chart swaps keep the card's size.** When a graph card's selector switches charts, the graph fades out (150 ms), swaps and fades in (250 ms) while the card keeps its width and height, so nothing below it moves (owner, #61). Rows only some charts need stay reserved on every chart (the pager row while any selectable chart pages). The new chart opens with no bar selected (web `useChartPagination`), and a detail row the switch closes keeps its space, empty, until the reader picks or clears a bar or the data reloads. Agent decision (#261, 2026-10-05): reserve rather than ease to the shorter height (the web detail-card shrink moved the content below) or carry the selection over (no web precedent; a screen reader would announce a bar the reader never picked); owner may override. Reduced motion swaps at once and keeps the same reserved rows (R6).
- **R9. A publication refresh keeps the reader on the page.** A new publication refreshes every open page and route in place through the shared publication boundary: no pop to a root, no explanatory card. While old content is hidden behind the spinner, VoiceOver keeps a stable page anchor (an invisible heading named with the page title, value "Loading new scores"); focus moves there only if it was established to be inside the page (on screen, uncovered, in the page's hierarchy and frame), and returns there after the rebuild unless the reader moved elsewhere during the spinner. Focus elsewhere (tab bar, navigation bar, a sheet, another column) is never moved; one on-screen page announces "Loading new scores" per publication instead. Where the platform cannot report the VoiceOver cursor (macOS), always announce and never move focus. Pages inside the boundary therefore set their title with `festivalNavigationTitle`. A root whose search field and page tools must stay usable (Apple Songs, #304 review) wraps only its result area, names the anchor with the boundary's `title`, reads the new generation in `prepare` (never from a revision-keyed task, so the fading list never draws new rows) and reveals through `onReveal`; its own reload gate is rebuilt already loaded, so the refresh shows one spinner, not two. When those results are a UIKit-backed `List`, it also passes `retainsHiddenContent: false`: `accessibilityHidden` does not reach `List` rows, so the faded-out list unmounts under the spinner rather than leaving old rows readable. The boundary never re-runs its page for its own focus bookkeeping: Apple keeps the `@AccessibilityFocusState`, spinner and page anchor in the `PublicationRefreshFocusLayer` overlay, because the accessibility focus store invalidates the view that owns that state while a list scrolls, and on the boundary each pass rebuilt the whole page mid-gesture (Songs title and rows jumped, #325). HIG Focus and selection: "Avoid changing focus without people's interaction", with the exception "if the focused item disappears during discrete, directional input (keyboard, remote, game controller), moving focus to an item one step away keeps it findable" (VoiceOver swipes are discrete, directional input; the anchor is the nearest surviving item); HIG VoiceOver: "Announce visible content and layout changes."

**Chose B:** web behavior beats an undocumented native copy (precedence table), it matches R2's intent (the row on a page change is not stale: its rank and value don't depend on the page) and it keeps context beside the spinner, which the Fluent guidance asks for; A and C remove a still-valid control for no gain. Key per board: Full Rankings (instrument, Rank By); song leaderboard the invalid-score leeway (the instrument and song are the route, so a change is a new page); song band leaderboard (band size, selected account), since its pinned band (#306) follows both. The first load and any row that newly appears while the rows are hidden are gated too (`PinnedRowGate.Arrived`). Mechanics: `Festival.Core/Domain/LoadSwap.cs` `PinnedRowGate` decides (`Begin(key, phase)` before the request, `Commit(key)` with the result); the row sits in `Controls/LoadSwapGate` bound with `LoadSwapVisual.IsGated`, which shares the rows' `LoadSwap` opacity and hit testing while gated, disables it only while fully transparent (no Tab stop on an invisible button, no disabled flicker while fading) and removes its UIA subtree from the control and content views. `AccessibilityView="Raw"` on a panel does **not** hide its descendants from UIA (#270: Narrator still read the old row and Your Page under the spinner), so a gated element must be a `LoadSwapGate`, whose peer reports no children while hidden and raises `ChildrenInvalidated`. The entrance `FadeIn` plays on the inner row only when gated, never on the gate itself (0xc000027b); the row fades in with the first row (`PinnedRowReveal.RevealDelay`) or on its own when it arrives later (`PinnedRowReveal.FadesOnArrival`), and the view model replaces it only when the new board commits. The pager stays outside the gate (R4). Evidence: `tools/windows/journeys/full-rankings-swap.json` (fixture `--rankings-delay`), normal and Reduce Motion.

- The first scroll movement (≥ 1 DIP) while the entrance runs (`StaggerArm.IsRunning`: the window, a scheduled fade, or a held tail) returns `ArmScroll.Rushed`. `FadeIn` then restarts every pending fade of that arm at delay 0 (`RushPending`). - `SelectedRowReveal.Start` waits `FadeInTiming.RevealWait` = the row's stagger (or the tail's) + 400 ms, so the row's own entrance has finished (web waits + 300 ms). It holds the tail for the jump (`ExpectAutomaticScroll`), then rushes it (`RushForAutomaticScroll`, 500 ms of realization) and centres the row (`StartBringIntoView`, ratio 0.5, instant; see the selected-row reveal below). It doesn't scroll if the reader scrolled, the board reloaded or the page left. With animations off it scrolls at once (R6).
- Song leaderboard: the reveal runs on a fresh visit from Song Details' player score (route `?page=N&navToPlayer=true`, web `leaderboardAtSelectedPlayer`) and after a page change. Song band leaderboard: a page change scrolls to the top and then reveals the selected band on the new page. Full Rankings: the pinned row's jump (#318) waits the same way, whatever invoked it.
- Every delayed fade belongs to an entrance (PR #358 review): `FadeIn.Play` is immediate-only, and a delayed fade is `FadeIn.Enter(owner, element, natural)`, scheduled on its owner's arm. - `SelectedRowReveal` calls `expectAutomaticScroll()` on the page scope before it waits. While that expectation is open, a `.pastFirstScreen` entrance whose time comes is held (`holds(_:)`, `waitToStart(after:start:)`).
- As it scrolls, it calls `prepareForAutomaticScroll(lasting: 0.35)`. With fades held, or none waiting, this rushes at once; otherwise the scroll's movement rushes them. The rush window becomes the scroll plus one fade, so rows the scroll realizes fade at delay 0.
- A cancelled reveal (`endAutomaticScrollExpectation(_:)`, by token, so a stale reveal can't end a newer one) or a reset releases held rows.
