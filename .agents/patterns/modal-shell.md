# Modal shell

> **What:** the shared sheet, dialog and alert container with its title, dismissal and standard Close affordance. **Read when:** presenting a scoped task, confirmation or notice.

Status: **current**, 2026-10-05. Provenance: #23, #24, #25, #94, #96, #125, #139, #140, #183, #360, #373, #400.

## Intent

A modal identifies one short, scoped task, exposes its platform-standard dismissal and closes before another modal opens. Features own body content and actions; the shared shell owns chrome, focus/dismissal behavior and the header.

## Rules

- **R1. Use only the shared shell.** Every feature modal uses its platform canonical component; never construct an unowned sheet, dialog or `ContentDialog`.
- **R2. Name the task.** The common header/dialog title is concise and announced before body content. Apple HIG Modality: “Identify the task with a title or explanatory/guidance text so people can regain their place after switching context.” **Owner-approved variant (#360, Paths sheet on folded iPhone Duo only):** where `DeviceLayout.pose == .folded`, the Paths title names the selected instrument, "Paths · <instrument>" (updating as it changes), and its instrument selector shows only the instrument icon (owner: "On Duo folded, don’t show instrument name in paths modal selector- icon is fine. Title can say Paths {dot} {instrument name}"; HIG Designing for iPhone Duo: "prefer a symbol wherever one works"). The selector keeps its VoiceOver label and value ("Instrument, <name>") and its icon scales with Dynamic Type. Every other pose and platform (unfolded/book Duo, iPhone, iPad, Mac) and every other modal keep the plain task title; do not revert or spread it without an owner ask. `SongPathsSheet.title(for:pose:)` / `showsInstrumentName(pose:)` own it. Evidence: `SongPathsSelectorTests` (rule) and `DuoPathsSelectorJourneyTests` (rendered: folded icon-only selector measured in pixels, title following an instrument switch, "Instrument, <name>" kept, unfold/refold, standard iPhone).
- **R3. Offer the native dismissal.** Apple sheets use the system Close and permit vertical dismissal where no input is at risk; Android uses the Material Close button plus back/scrim/swipe; Windows uses the standard `ContentDialog` Close command and Esc/light dismiss. Apple HIG Modality: “Always provide an obvious, platform-conventional dismissal.” Windows evidence (#400): `tools/windows/journeys/a11y-modals.json` has one `a11y_matrix` page per `FestivalDialog` caller. Each page asserts the title is read first, then the body, then the commands with Close last (R2). It first waits for the title and body text to be on screen, then checks Close's Narrator phrase, asserts every Close and alert command is at least 40×40 epx with hit-test probes 18.5 epx from its centre on each side, checks that Tab reaches Close, and checks that Esc closes and restores focus. Every dialog command is 40 epx tall: `DialogChrome.CommandTargets` raises the template's Primary/Secondary/Close buttons to `FSTMinTargetSize` (see the agent decision below). The `windows-ui` workflow (`.github/workflows/windows-ui.yml` → `tools/windows/ui_ci.py`) builds the app and runs the journey with `--scan --tabs 30` at default text (compact and medium) and at 225% text (compact). `tools/windows/tests/test_modal_journeys.py` fails when a new caller has no page or the journey leaves the `windows-ui` runs.
- **R4. Keep Close out of feature bodies.** Do not draw a custom xmark, footer Close or live-apply Done control. Apple’s system `FestivalSheetCloseItem`, Android’s 48 dp `FestivalModalCloseButton` and Windows’ command row are the only shared close affordances.
- **R5. Keep the body below the header.** The Apple shell applies the shared top fade (#94); Android and Windows retain a hard content edge. Modal presentation never covers its own title or Close control.
- **R6. Preserve the feedback-form exception.** It has potentially lossy text input, so it uses Cancel and Submit with discard confirmation rather than the ordinary Close-only task shell. Apple HIG Sheets: “Single-view sheets: Cancel on the top toolbar's leading edge; Done, when present, trailing.”
- **R11. Take feedback media beside the form, not over it (Apple, #373).** Photos, videos and image/movie files dropped anywhere on the feedback form attach to it on every Apple surface (iPhone, iPad, Duo, Mac), through the same limits and location removal as a picked file, with an accent outline and "Drop to Attach" while something droppable is over it (none while sending). At regular width on iPad and the iPhone Duo inner display the form opens page-sized (`FestivalSheetSizing.regularPage`; a presented sheet keeps its opening size, so the room has to be there from the start) and Attach Media › Photo Library opens the system photo picker **inline** in a pane beside the form (title "Photo Library" and a "Hide" text button, never Done/Close). The form and the library are a two-up row of the canonical [hinge-columns](hinge-columns.md) `HingeRow` (`fillsHeight`), never a feature-local stack: on a partially folded Duo they end and start at the active fold's clearance (hinge-columns R1); flat, on iPad or on the flat Duo, they divide the sheet, the row's free space, at its midpoint (hinge-columns R7). Ticking a photo attaches it, unticking removes it, and removing its thumbnail unticks it. iPhone, compact windows and the Mac keep the form card and the presented picker; Choose File… always presents the system Files picker (no public inline form, on any platform). See the agent decision below. `FeedbackPhotoLibraryPlacement`, `FeedbackPickerLinks`, `FeedbackFormPanes` and (iOS drop, past the iOS 18+ `Form` drop interception) `FeedbackSheetDropInteraction` own it. Evidence: `FeedbackFormModelTests` (drop import, placement, links); `FeedbackFormPanesHostedTests` (book pose: form ends at the fold clearance, library starts after it, both full height; flat: halves of the sheet; hidden: form spans the sheet); `FeedbackMediaJourneyTests` (iPad and unfolded Duo: library beside the form, tick attaches, removing the thumbnail unticks, Hide keeps attachments, Cancel confirms; iPhone and the folded Duo: no pane, the picker is presented over the form; passing on iPad, iPhone 17 Pro and the folded Duo, while the unfolded Duo pose can't be set from this host's tooling, so `FeedbackFormPanesHostedTests` covers its geometry; iPad Split View drop from Photos onto the Description box shows the highlight, counted by the Debug marker `fst.settings.feedback.drop.shown`, and attaches).
- **R7. Serialize presentations.** Dismiss a sheet before opening another; a confirmation alert may sit above a modal, but never stack independent alerts. Apple HIG Sheets: “Display only one sheet at a time from the main interface.”
- **R8. Keep surfaces off a separating hinge with one side rule (Android).** Sheets, centred dialogs and the full-page service status ([empty-error-states](empty-error-states.md) R7) never straddle a **separating** fold or hinge. Material 3: “Never place interactive content or critical information across the hinge area.” A vertical hinge (book posture) keeps the wider side of the surface's page, the leading side on a tie; a horizontal hinge (tabletop) always keeps the part **below** it, whichever half is larger, and only a page that ends inside the hinge keeps the part above. Flat folds keep the ordinary placement. The rule lives once in `core/nav/HingeSide.kt` (`HingeSide.keep` / `HingeSide.padding`, page-rectangle aware); `SheetHinge`, `DialogHinge` and `serviceStatusHingeSide` only adapt its result to sheet padding, a centring area or page padding. Agent decision (#140, design review of #212): one shared helper after the three surfaces' copies drifted on tabletop; the owner may override. Evidence: `HingeSideTest`, `SheetHingeTest` and `DialogHingeTest` in `android-unit`; the connected `SongPathsDeviceTest#halfOpenSheetStaysOnOneSideAndReadsInOrderAtEveryTextSize` (`@HalfOpenFoldJourney`, #384: ATF, reading order, no straddle at 100% and 200% text) runs in CI `android-fold` on a half-open book-fold emulator.
- **R9. Size centred dialogs from the window (Android).** `FestivalModalDialog` always takes the window width less 16 dp margins, capped at 560 dp (Material 3: “Centered dialog (max 560dp wide)”), and never the platform's preferred dialog width (`usePlatformDefaultWidth`), which measured 320 dp in a 923 dp landscape phone window. First run (#139) fixed this for itself with a `compact` flag; #183 found What's New and Privacy Policy still 320 dp wide on landscape phones and moved the rule into the shell, removing the flag. Feature dialogs never set their own width.
- **R10. Hold the page's decorative motion while a modal covers it (Android).** Every Festival modal registers with `ModalCoverage` through `CoversBackdrop` (the shell does it; the feedback form, the R6 exception, wraps its own `Dialog` in it) and gives its window one more `LocalModalDepth`. Content behind the newest modal reads `coveredByModal()` and holds a still frame: the shared backdrop (#83), the `FestivalMarqueeText` scroll (held at its start, semantics `Held`), the Songs/Shop pulse and breathe (their reduced-motion frame), the first-run demo pulse and the service-status pulse. The newest modal's own content keeps animating (the first-run demos run inside the tour; a confirmation alert holds the sheet beneath it). Material 3 modal dialogs and sheets “block interaction” and sit over a scrim, so the page's loops are unseen work: a clipped leaderboard name kept the Leaderboards page drawing every vsync (837 frames in 15 s) behind the first-run tour on the FST_Phone emulator. Each consumer has a Robolectric regression that opens a real Festival modal over it and checks the held frame and the resume (`FestivalModalTest`, `MarqueeTextTest`, `ShopMotionHoldTest`; the first-run and service-status pulses sample their drawn alpha through the internal `LocalMotionProbe`, `null` in the app, in `FirstRunDemoPulseHoldTest` and `ServiceStatusUiTest`), so a new loop that reads `coveredByModal()` adds one too. Agent decision (#186): Android holds every covered page loop, not just the backdrop #83 asked for; Apple and Windows keep their own #28/#83 scope until checked. The owner may override.
- **R12. Owner-approved variant (#368, Apple Paths only): cover the window where the image and text fit side by side.** On the iPhone Duo inner display (unfolded or book pose at regular width), iPad in the sidebar shell and the Mac, Paths opens over the whole window instead of a sheet; on iPhone, the folded Duo and a compact iPad it stays the R1 sheet. Owner: "Duo unfolded/partial fold/MacOS: can we have a full-screen modal (align with platform design) that can show image and text side-by-side? If partial fold, enforce side by side; if full unfold (or iPad/MacOS), allow option to see full-screen image, text, or side-by-side." HIG Modality: "Full-screen modals suit temporary media and multistep work" (consider). `SongPathsPolicy.coverage` chooses; `festivalModalPresentation` presents, and it is the only way a Festival modal covers the whole window:
  - iOS/iPadOS: `fullScreenCover` with the opaque card colour, the same `FestivalModal` title and Close (R2, R4). A cover has no system swipe, so R3's vertical dismissal is `PullDownToDismiss` on the viewer's scroll views (iOS only; disabled in sheets, where the system swipe already works) — the What's New cover's existing gesture.
  - macOS: there is no cover, so it is a sheet sized to the presenting window's content area (`MacWindowSizedSheet`: the sheet window is matched to the parent's `contentLayoutRect` once attached, because SwiftUI adds the sheet's bar outside a fitted frame), Close-only (HIG Modality: "macOS/tvOS use a button in the main content view"), with `presentationSizing(.fitted)` instead of `.page`.
  - The coverage is **latched while open** (agent decision, #368): folding or unfolding a Duo, or resizing an iPad window, never swaps cover and sheet or loses the viewer's state (HIG Designing for iPhone Duo: "Preserve functionality, element state, hierarchy, and access across displays/poses" (must)). Its View menu still follows the live layout (Side by Side appears or falls back to the Settings default view).
  - Contrast: What's New covers the iPhone through the same `festivalModalPresentation` but stays a centred sheet on the Duo inner display (`WhatsNewPresentationStyle`: "a cover stretched the iPhone page"; [whats-new](../controls/whats-new/ios.md)); only Paths, which shows two panes, covers it. Do not spread the cover to other modals without an owner ask. Evidence: `SongPathsPolicyTests`, `SongPathsSheetRenderTests` (book pose and wide Side by Side), `DuoPathsSelectorJourneyTests.testUnfoldedOffersSideBySideBookPoseSplitsAtHingeAndFoldingFallsBack`.

## Agent decision (#373, 2026-10-08): inline photo library beside the form, Files presented, drop everywhere

Question: owner, "can file picker or photo library be opened on right side of screen instead of over the bug/feature modal? Can users drag photos or files to the modal?"

| Option | What you see | Guidance (strength) | Web / pattern precedent | Trade-offs |
|---|---|---|---|---|
| A | Photo Library and Choose File… stay system pickers presented over the form; photos and files can also be dropped onto the form. | HIG Entering data: "As much as possible, support drag and drop and paste" (should); Drag and drop: "Show whether a destination accepts the content, like an insertion point or highlight" (should). | Web `FeedbackModal.tsx`: a browser file input (presented file dialog, no drop or paste). modal-shell R6: the feedback form is the one Cancel/Submit sheet. | Least change, but the photo picker is a second sheet covering the form, which the owner asked to avoid. |
| **B (chosen)** | At regular width (iPad, unfolded Duo) Photo Library opens inline in a pane beside the form, laid out by `HingeRow`; Choose File… stays a presented system picker; drop works on every Apple surface, Mac included. | Same two clauses (should); Designing for iPadOS: "minimize modal interfaces and full-screen transitions, keeping controls reachable without obscuring content" (should); Sheets: "Display only one sheet at a time from the main interface" (should) and "Prefer page or form sheet styles in an iPadOS app" (should); Designing for iPhone Duo: "More space may expose another level if it makes sense for your content" (consider). | Web has no beside-the-form picker (browser dialog). hinge-columns R1/R7 give the two panes their fold-aware split; modal-shell R6 keeps Cancel/Submit and the discard confirmation. | Needs a page-sized sheet at regular width (a presented sheet cannot grow later). Files cannot follow: neither `fileImporter` nor `UIDocumentPickerViewController` has a public inline form on iOS, iPadOS or macOS. |

Chose **B**: no platform *must* or owner choice applies and the web has no equivalent, so the platform recommendations decide. B keeps the owner's intent (pick beside the form) with the public out-of-process `PhotosPicker` inline style (no photo permission) and native chrome, and removes the second sheet A keeps. The Mac keeps its default-size window sheet and the presented photo picker (HIG Sheets, macOS: "Present a sheet in a reasonable default size"); dropping from the Finder or Photos covers the ask there. Paste is deferred: SwiftUI's `pasteDestination` needs iOS 27. iPhone is unchanged apart from drop. Owner may override with `/choose A`.

## Agent decision (#400, 2026-10-08): 40 epx dialog commands on Windows

Question: design review of #468, "Every Close assertion explicitly accepts 40x32 … strategy.md requires a 40 epx Windows touch target."

| Option | What you see | Guidance (strength) | Web / pattern precedent | Trade-offs |
|---|---|---|---|---|
| A | Keep WinUI's default 32 epx `ContentDialog` command height; document an exception. | Microsoft Learn, Targeting: "Typically, WinUI controls align with 7.5mm touch target (this can vary based on the specific control …)" (consider). | WinUI `ContentDialog` default template. | Conflicts with the repo rule (strategy.md: 40 epx Windows touch target) and with the app's own `FSTMinTargetSize` buttons; needs a standing exception. |
| **B (chosen)** | Every dialog command (Primary, Secondary, Close) is at least 40 epx tall, set once in `DialogChrome.CommandTargets` from `FSTMinTargetSize`. | Targeting: "In general, set your touch target size to 7.5mm square range (40x40 pixels …)" (should); "targets that have severe consequences if touched in error should have greater padding" (consider; Reset/Remove are confirmations). | `FSTMinTargetSize` = 40 (#72) on the app's action buttons; #271 hit-target probes; web buttons ≥ 40 px. | Dialog buttons grow 8 epx; the dialog stays well under its max height at 225% text. |
| C | Invisible hit-area expansion around 32 epx buttons. | — | None in the app. | No public `ContentDialog` API; fragile template surgery. |

Chose **B**: the repo's accessibility rule is the strongest applicable requirement, the change lives in the canonical shell so all `FestivalDialog` callers inherit it, and it uses public API (`MinHeight` on the template's named command buttons). This supersedes the earlier #400 note that kept the 32 epx height. Owner may override with `/choose A`.
