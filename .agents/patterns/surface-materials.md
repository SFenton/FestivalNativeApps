# Surface materials

> **What:** shared policy for translucent content cards, rows and floating controls over artwork. **Read when:** adding or changing a card, row, capsule, sheet fallback or custom glass effect.

Status: **current**, 2026-10-14. Provenance: #291, #312 (R7), #319, #358 (R2 Duo variant), #381 (R8), #382 (R7 Apple in-card CTA), #499 (R8 Apple accessibility tests), #543 (R8 board page cards), #588 (R8 Android Score History card), #596 (R7 profile Bands group cards on Windows and Android; R8 Apple profile Bands group cards), #599 (R10), #603 (R8 Android Rivals cards), #609 (R4 Android reading panes), #632 (R2 iPhone floating page tools variant), #641 (R4 Windows flyout surface).

## Intent

Content must remain legible and cheap to scroll over animated artwork. Use one platform-native frosted surface per content role; reserve Liquid Glass and system equivalents for navigation and system chrome.

## Rules

- **R1. Content uses the canonical material surface.** Cards, content rows and non-system floating controls use the shared card/capsule primitive; no feature creates its own frosted, blur, glass or opaque plate stack. A floating control over rows (board pager, A–Z scrubber, switcher pill) wears the same surface as the rows, so it matches them in every accessibility mode.
  - Board pagers (arrow buttons and the page / total badge) float over rows and match them: the same fill, translucency, border and contrast fallback as the row cards, never a pager-only opaque plate or shadow (#319; web `Paginator` spreads `frostedCard`). The Windows board-footer **Your page** buttons, which shared the retired pager plate, moved to the same surface ([agent decision below](#agent-decision-windows-board-footer-your-page-button-319)); none remain since #307 and #318 made each pinned row its own jump. Apple: `RankingsPagerView` draws on `festivalCardCapsule`. Android: `RankingsPager` and `FrostedPagerButton` are `GlassCard`s, which also covers the Rank History and Song History chart pagers. Windows: `LeaderboardsPager` draws each arrow's 40 epx circle and the badge on `FSTCardSurfaceBrush` + `FSTCardStrokeBrush` (a surface `Border` behind a transparent `Button`, like `LeaderboardEntryRow`), so `MainWindow.ApplyTransparency`'s opaque fallback and the contrast-theme brushes reach it as they reach the rows; disabled arrows dim the whole host, surface included, except under a contrast theme, where the host stays fully opaque with its rim (R4) and only the glyph turns GrayText (`Festival.Core/Domain/PagerDimming.cs`, re-applied on a live contrast switch; tests `PagerDimmingTests`, UIA paint journey `tools/windows/journeys/a11y-pager-dim.json` per `--mode`). The bottom-edge fade, not an opaque plate, keeps the pager legible over rows ([scroll-edge](scroll-edge.md)).
  - **A card row that is a link stays pressable (#467, for #319).** A card row built as a `NavigationLink` or `Button` (`PlayerBandRow`, `BandMemberCard`, `BandSongRow`, `SongBandPreviewRow`) merges its content with `.accessibilityElement(children: .combine)` or labels the link itself, never `.ignore`, which drops the press on macOS (VoiceOver, Voice Control, Switch Control). Hosted: `RankingsPagerCardAccessibilityTests` (pager card frames and opaque-card contrast, band cards' AXPress); iPhone rendered contrast on the material: `PagerCardContrastJourneyTests` ([Apple accessibility](../testing/apple/accessibility.md)).
  - **A floating control on the capsule is one accessibility element (#454, for #291).** Apple's capsule controls (`RankingsPagerView`, `RankingsGlassPager`, the `RankingsSwitcherPillLabel` switcher pill, `PurpleActionLabel`) keep their spoken name, button role, edge-disabled state, adjustable page value ("Page, 1 of 3"), visual reading order and 44 pt target on the material card and on its opaque R4 card alike. Pager arrows keep a fixed 44 pt target at every text size (their symbols and the page label grow, the label shrinks to fit, `minimumScaleFactor`): `RankingsGlassPager` scaled its targets with `@ScaledMetric` to 124 pt at AX5, which pushed First Page and Last Page off an iPhone screen. A pill used as a `Menu` label is `.accessibilityElement(children: .ignore)` so the menu names it once: without it macOS split the icon and title into two 28 × 14 pt "Band size" menu buttons, read twice with a focus ring smaller than the pill. `RankingsFloatingBar` rebuilds the switcher menu whenever the pager's label changes (`placedMenu(showsTitle:)`, `.id(pager?.label)`): on iPad the iOS platform menu's element kept the whole bar's frame from before the pager arrived, a 560 × 124 pt "Band size" target over the pager at AX5, so touching the page badge found the menu (#462); a placeholder in the pager's slot, `fixedSize`, `compositingGroup`, a constant `id` or a `.contain` wrapper did not fix it. The bar is one `.accessibilityElement(children: .contain)` container with the pager at `accessibilitySortPriority(1)` (#620): the menu is the bar's only child until the first page loads, and iOS kept it ahead of the pager inserted later, so the tree (and VoiceOver) read "Band size" before the page controls drawn to its left, or above it at AX5, with or without #462's `.id`. Frame order alone does not fix it; the container's priority does. HIG Accessibility: "Label elements correctly for Voice Control and VoiceOver"; iOS default control size 44×44 pt. On macOS an adjustable element (role AXUnknown) reports its value as `accessibilityValueDescription`, not `accessibilityValue`; this is how SwiftUI exposes every adjustable element (A–Z scrubber, carousels), so tests read either. Tests: hosted `MaterialCardControlsAccessibilityTests` (every transparency and contrast setting), `BottomChromeFadeHostedTests.bandBoardFooterFadeKeepsRowsAndPagerAccessible` (the pill stays one 44 pt element below the fade), iPhone journey `MaterialCardAccessibilityJourneyTests` (default size and AX5, material and Reduce Transparency, scoped audit; in `apple-ci` `JOURNEYS`), iPhone and iPad journey `ScrollEdgeFadeAccessibilityJourneyTests.testBandRankingsFadeKeepsRowsAndPagerAccessible` (the pill's frame meets no pager control).
- **R2. Apple Liquid Glass is navigation-only.** Content cards and custom controls do not call `glassEffect`; only `Design/GlassSurface.swift` may implement the drawer and Debug A/B glass. HIG Materials: "Don't use Liquid Glass in the content layer."
  - **Owner-approved variant (#358, iPhone Duo bottom search field only):** the Duo `BottomSearchField` (Songs' Filter Songs and the Search tab's field on the inner display) wears regular, interactive Liquid Glass through `festivalGlassCapsule(.control, interactive: true)`, the `GlassSurface` modifier, with its opaque `cardBackground` + `borderSubtle` fallback (R4) under system Reduce Transparency, system Increase Contrast and the in-app Reduce Transparency and Increase Contrast toggles (hosted render test `bottomSearchFieldIsOpaqueAndBorderedUnderAccessibilitySettings`). Owner: "Filter Songs is not Liquid Glass like I expect". It floats beside the system's glass Search button in the vertical bar, as a search control over the content, not in it (HIG Materials, **should**: "Use Liquid Glass effects sparingly on custom controls"; "Use Liquid Glass for controls and navigation (such as tab bars and sidebars) floating above content"; regular variant for text-heavy controls). Every other custom floating control (A–Z scrubber, pagers, switcher pill, Paths pickers) keeps R1's material capsule; do not extend this variant. Guard `apple-glass-consumers`.
  - **Owner-approved variant (#632, iPhone floating page tools only):** each iPhone page tool (Songs' Sort, Filter and Quick Links; every page's tools) is an individual 44 pt Liquid Glass circle floating above the tab bar, drawn only by `FloatingPageToolsBar` (`App/Shell/FloatingPageTools.swift`) through `festivalGlassCapsule(.control, interactive: true)`, with R4's opaque `cardBackground` + `borderSubtle` circle under system or in-app Reduce Transparency and Increase Contrast. Owner: "Those buttons are now permanently floating individual glass chrome like the floating buttons on web." They are controls floating above content, not in it (HIG Materials, **should**: "Use Liquid Glass for controls and navigation … floating above content"; "Use Liquid Glass effects sparingly on custom controls"), replacing the system tab-bar accessory's glass ([page-tools-and-nav-chrome](page-tools-and-nav-chrome.md) R28). Pages never draw their own; the A–Z scrubber, pagers and switcher pill keep R1's capsule. Guard `apple-glass-consumers`.
  - **Agent decision (#559, 2026-10-09; owner may override with `/choose`): the system drawer search field is glass at every scroll position.** On iOS 26/27 UIKit draws a `.searchable` navigation-bar drawer field (iPhone and narrow-iPad Songs' Filter Songs) as a flat `tertiarySystemFill` while the list is at its top edge and turns it into Liquid Glass only once rows scroll under the bar. The field stays the system `.searchable` field. `SearchDrawerTransitionFill` installs `GlassSurface.swift`'s `SearchFieldBackingView` (public `UIGlassEffect(style: .regular)`, capsule) as the bottom subview of the field's `UISearchTextField` and clears its flat fill, also when UIKit restores it after a search ends (key-value observation of the field layer's background; it yields to the #544 transition fill), so it reads as the Duo field's regular glass (#358) at rest and scrolled. Under any R4 setting (system or in-app Reduce Transparency or Increase Contrast) the backing is the opaque `cardBackground` + 1 pt `borderSubtle` capsule. The policy is `SearchFieldBacking.resolve` (from `FestivalGlassSurface`); only a field whose `searchBarPlacement` is `.stacked` gets a backing, so wide iPad's toolbar field, the Mac toolbar field and pre-26 systems keep the system look. The backing takes no touches and is hidden from accessibility: focus, clear, keyboard and the VoiceOver search field are the system's. Tests `SearchFieldBackingTests`, journey `SongsChromeJourneyTests.testFilterFieldIsGlassAtTopAndScrolled`. [Decision record](#agent-decision-apple-drawer-search-field-always-glass-559).
- **R3. Raw standard material stays in the design layer.** Do not add `.ultraThinMaterial`, `.thinMaterial`, `.regularMaterial` or `.thickMaterial` backgrounds outside `Design/`; the explicit approved variants below retain their contrast and pre-26 behavior.
- **R4. Accessibility replaces translucency.** Reduce Transparency or increased contrast yields an opaque surface with a visible border; text and status information do not rely on the artwork behind them. HIG Accessibility: "If the default does not meet these minimums, provide a higher-contrast scheme when Increase Contrast is on."
  - Windows (#397): `MainWindow.ApplyTransparency` makes `FSTCardSurfaceBrush` opaque (and the overlay pane's acrylic solid) when Windows transparency effects are off **or** the in-app Less Transparency **or** Increase Contrast setting is on (`Festival.Core/Domain/CardSurfaceOpacity.cs`, the same switch as the scroll-edge hard edge; tests `CardSurfaceOpacityTests`). Increase Contrast alone used to leave cards translucent, unlike Apple's `FestivalCardModifier` and Android's `GlassCard`. Increase Contrast also strengthens `FSTCardStrokeBrush` to 50% white (`ApplyContrast`); contrast themes use system colours. The UIA paint pages `shop-row-surface-*` in `tools/windows/journeys/a11y-shop-list-row.json` pin it on the shared `SongRowCard`: an opaque `#121826` fill with a visible edge under `--mode no-transparency`, in-app Less Transparency, in-app Increase Contrast and `--mode app-contrast`, and a translucent fill otherwise. Song Detail's band preview rows (`Controls/SongBandPreviewRowView`, which draws `FSTCardSurfaceBrush` on its own surface `Border`) are held to the same rule by `bp-a11y-surface-*` in `a11y-song-band-preview.json` (#426, for #64): every consumer that paints the card brush outside `SongRowCard` needs its own paint page, since a shared-row page can't prove a separate surface stays wired to the fallback. The selected player's band keeps the leaderboard-row player purple (`FSTPlayerRowBrush`), as every board's player row on all three platforms; R4's Windows fallback covers the card surface only.
  - **Windows menus, flyouts and drop-downs share one surface (#641).** Owner: "Quick Links dropdown is transparent … Instrument dropdown has transparent background (check across app)". WinUI 2.x paints `MenuFlyoutPresenterBackground` and `CommandBarFlyoutBackground` transparent and relies on a desktop-acrylic `SystemBackdrop`, which only a windowed popup gets; every app popup opens in-window since #534 (`ShouldConstrainToRootBounds`), so menus showed the page through. `Themes/Styles.xaml` `FSTFlyoutSurfaceBrush` (Fluent's dark `AcrylicBackgroundFillColorDefault`: tint `#2C2C2C`, opaque `#2C2C2C` fallback) is the presenter background of every `MenuFlyout`, `CommandBarFlyout`, `Flyout` and `ComboBox` drop-down (`StaticResource` aliases in the Default theme dictionary), and `MainWindow.ApplyTransparency` switches it to its solid fallback under the same three settings as the cards. Contrast themes keep WinUI's system Window colour. Never give a menu presenter its own background or style a feature-only flyout plate. Fluent Acrylic: use acrylic for "transient, light-dismiss surfaces such as flyouts and context menus", with a solid fallback when transparency is off. Tests: `FlyoutSurfaceMarkupTests` (the aliases and the fallback switch) and UIA paint pages `tools/windows/journeys/a11y-menu-surface.json` (Quick Links and the Full Rankings Instrument menu: acrylic `#2C2C2C` in normal mode, exactly `#2C2C2C` under `--mode no-transparency`, `--mode app-contrast`, in-app Less Transparency and Increase Contrast, the system colour under contrast themes, 40 epx items at text 200%). Windowed `ComboBox` drop-downs (Paths pickers) can't be captured with `PrintWindow`; they use the same brush.
  - Apple glass: `FestivalGlassModifier` picks its surface through `FestivalGlassSurface.resolve` (`Design/GlassSurface.swift`), which treats system Increase Contrast (`colorSchemeContrast == .increased`) like system Reduce Transparency and the in-app toggles, so the drawer and the Duo bottom search field turn opaque and bordered under any of them (#358 review: system Increase Contrast had left the field on Liquid Glass). The boards' pinned selected row backing (`PinnedFooterBacking`, `Features/SongLeaderboard/SelectedScoreFooterRow.swift`) decides through the same resolver (#461: it had read only the system settings, so with the app's Increase Contrast it stayed translucent over the artwork while the pager beside it turned opaque); test `SongBandFooterAccessibilityTests.footerBackingTurnsOpaqueUnderTransparencyAndContrastSettings`. Tests `GlassSurfacePolicyTests` and the hosted render test above.
  - **Reading text in a list/detail pane sits in one card (#609).** Long-form text shown in a pane over the page artwork (the Privacy Policy, a package's license) reads inside one canonical card under the pane header, never on the bare pane, so the opaque fallback reaches it. Owner: "Privacy Policy should be in a card when it's open in landscape mode for easy readability regardless of background image". Modals keep their own opaque surface and get no inner card (R6). Android: `ui/settings/PrivacyPolicySheet.kt` `PrivacyPolicyPane` (`fst.privacy-policy.card`) in the shared Settings detail column (840 dp cap, header above the card like `PaneCard`), and the wide Licenses page's detail (`ui/settings/LicensesScreen.kt`, `fst.licenses.detail-card`); tests Robolectric `SettingsPaneCardSurfaceUiTest` (frosted by default, opaque under Reduce Transparency and Increase Contrast, text inside the card), `ExpandedSettingsUiTest.privacyPolicyOpensInThePane`, connected `journeys/PrivacyPolicyPaneAccessibilityJourneyTest`. Windows already did (`Pages/SettingsPage.xaml.cs`: the policy body in an `FSTCardStyle` border). Apple: [known debt](#known-debt).
- **R5. Preserve the native surface model.** Android `GlassCard` is an M3 `Surface` with a tonal card color and border; Windows cards use `FSTCardSurfaceBrush` rather than per-frame Acrylic. MD3: "Tonal surfaces replace elevation shadows as the primary depth cue."
- **R6. Avoid nesting surfaces.** A group owns one card; its rows, pills, badges and meters use flat fills. System sheets own their own material and must not contain a second glass card.
  - Example: the Apple Songs wide-row profile panel (#340, `Features/Songs/SongProfilePanel.swift`). Its instrument and band cards are flat `surfaceMuted` fills inside the one row card, with no material of their own ([songs-profile-panel](songs-profile-panel.md) R7).
  - Example: Windows Song Detail's Score History (#588) is one `FSTCardStyle` card like Apple's grouped section (R8): selector, chart, pager, the best scores, then View All Scores ([view-all-cta](view-all-cta.md) R1). The best scores are `GroupedRows.InCard` slices (`Controls/GroupedRows.cs`, geometry `Festival.Core/Domain/GroupedRowSlice.cs`): no fill, rim or outline of their own, hairlines between them and 4 epx corners, so the card is the only surface. The personal-best row keeps its flat purple fill and outline.
  - Example: Windows previews (#643) take the same in-card form: Song Detail's instrument and band previews and the Leaderboards overview boards are one `FSTCardStyle` card each, with in-card `GroupedRows` slices, the overview's spotlight as an in-card slice (`LeaderboardsSpotlight.InCard`) and View All inside, last ([leaderboard-row](leaderboard-row.md) R10). Their empty state stays card-less (#377).
- **R7. A "View all" call to action takes the web's surface.** Where the web frosts it (player page `BandViewAllCard`), it is a full-width frosted card on the canonical surface: 48 dp/pt/epx minimum height, centred Title Case label and the in-card chevron, one button named by its label. The purple filled leaderboard CTA is an **approved variant** only where the operator chose it over the web's frosted fill (6.29: leaderboard, song, ranking and rivals cards); do not extend it to new View-all rows. Owner #596 extends it to the profile Bands groups on Windows, Android and Apple, each group now one rows card ([view-all-cta](view-all-cta.md#owner-approved-variant-profile-bands-groups-596)).
  - Apple (#382): inside a `FestivalGlassSection` the purple CTA is the card's `action`, a **flat, opaque** `accentPurple` fill with no material or rim of its own (R6), 10 pt from the card's edges. It is never Liquid Glass (R2; HIG Materials: "Don't use Liquid Glass in the content layer"). Profile's Bands groups put theirs inside their group card too (owner #596, [variant](#owner-approved-variant-apple-profile-bands-group-cards-596)); no Apple CTA sits outside a card. [view-all-cta](view-all-cta.md#agent-decision-apple-view-all-inside-the-card-382).
  - Agent decision (#312, 2026-10-06), superseded on Android and Windows by the owner variant below (#596): Android's player-page "View All Bands (N)" was a clickable `GlassCard` (web frosted card), not `ViewFullLeaderboardButton`.
  - **Owner-approved variant (#596, Android profile Bands groups only).** Owner: "Band duos/trios/quads on profile page need to be single card with purple View All, as other cards … Band duos/trios/quads don't need "Trios" "Duos" etc. chips inside them since we're already looking at those sections". On the Android player profile each Duos/Trios/Quads group is one `GlassCard` (`fst.player.bands.card.<group>`) of bare `PlayerBandRow`s (no size pill) separated by the Song Detail hairline (`songdetail/RowSeparator`), ending in the purple `ViewFullLeaderboardButton` "View All Bands (N)", exactly like Song Detail's band cards (#543, R6: the group owns the one card). The Android Player Bands page and search keep a `PlayerBandCard` per band with its size pill (a list page keeps a card per row, R8; its "All" filter mixes sizes). Apple's form is the [Apple variant](#owner-approved-variant-apple-profile-bands-group-cards-596); Windows' form is the next bullet. Do not revert this to the frosted card on Android.
  - Windows (#312 review, superseded by owner #596): the profile Bands groups' "View All Bands (N)" was `Controls/ViewAllCard`, a frosted card on the card surface. Owner-approved variant (#596): each profile Duos/Trios/Quads group is one `FSTRowsCardStyle` card of `BandCardView` rows with `RowSeparators` hairlines and no size chip, ending in the purple `FSTViewAllButtonStyle` CTA ([view-all-cta](view-all-cta.md#owner-approved-variant-profile-bands-groups-596)). `ViewAllCard` was deleted, and the `windows-profile-band-group-card` guard keeps it out. The web keeps the frosted form.

- **R8. Apple groups a dashboard section's repeated rows in one card (#381).** On iPhone, iPad and Mac, a titled section on a dashboard page (Song Detail, Compete, Leaderboards overview, and their First Run demos, Leaderboards' your-rank and Song Info's top-scores demos included) puts its rows into one `FestivalGlassSection(rows: .flush(separatorInset:))` card, like the Rivals cards. Rows sit edge to edge with inset hairlines on every supported OS: iOS 17 and macOS 14, which can't enumerate subviews, draw each row's hairline above it (`FestivalLeadingHairline`) with the first one clipped by the card, so the layout matches iOS 18 (`GroupedRowsHostedTests` renders both). The selected-player row fills its full band in the player purple, and Mac hover and focus draw inside the band. The section's View All button ends the card inside it (`FestivalGlassSection` `action:`, R7, #382). A page that is itself one list keeps a card per row: Songs and Item Shop song rows, the Score History page, Player Bands and search results. The profile's Duos, Trios and Quads band previews are grouped like the dashboard sections (owner #596, [variant](#owner-approved-variant-apple-profile-bands-group-cards-596)). The full boards (solo, band, Full Rankings, Band Rankings) used to be in that list too; owner #543 groups each board page into one card on the native apps ([leaderboard-row](leaderboard-row.md) R10, [variant](leaderboard-row.md#owner-approved-variant-one-card-per-board-page-543)), and the pinned row and pager stay a floating bar. Apple draws a board's card as one segment per lazy row (`festivalGroupSegment`, the same fill, rim and hairlines as a flush `FestivalGlassSection`), so List virtualization, row ids and wide pairs keep working; Windows groups a board's rows through `GroupedRows`. Rows inside a flush group read `festivalGroupedRow` and drop their own card (`RankingRowSurface.treatment`, `ScoreHistoryListRow`, `CardMessageSurface`, `RankingsSkeletonRows`, `MacRowInteractionEffect`), so no new row surface exists. HIG Lists and tables: "iOS/iPadOS **grouped style** — headers, footers, extra spacing to separate groups." Android Song Detail follows the same grouping in its `GlassCard`s: instrument and band previews, and Score History (selector, chart, flush best-score rows with outline-variant hairlines, View All Scores; `SongHistoryCard`, #588) plus its First Run View All demo; the Score History page still keeps a card per row. Android Rivals groups the same way (#603, like Apple's Rivals cards): the hub's and Compete's rivals cards (`RivalPreviewRows`: hairline-separated `RivalRow`s, then View All Rivals inside), each Rival Detail category (`RivalSongRow`s in one `GlassCard`), and All Rivals and Rivalry, which can list hundreds of rows, as one card drawn as lazy segments (`RivalCardSegment` → `GlassCardSegment` with `CardSegment.of(index, count)`: the `GlassCard` fill and outline, rounded and outlined only at the card's two ends, zero item spacing, one column), like Apple's `festivalGroupSegment`. The First Run rivals demos group their rows the same way. Rows inside draw no surface of their own ([rival-rows](rival-rows.md) R6). Apple accessibility (#499): a grouped card reads its heading, then one element per row in visual order (the hairlines never reach the tree, and the selected-player row is spoken "Your rank, …" or "best score", not only purple), then its View All; each row is a full-width target at least 44 pt tall, the rows tile the card with only the 1 pt hairline between them, and AXPress opens a grouped row on both row layouts. `GroupedCardAccessibilityTests` (hosted: Leaderboards overview, Song Details top scores, Score History, the flush probe at Large and AX5) and the iPhone and iPad journey `GroupedCardAccessibilityJourneyTests` (AX5 growth, hit size, scoped audit) pin it. [Agent decision below](#agent-decision-apple-grouped-dashboard-rows-381).
- **R9. Apple card rims are drawn on the render server (#553).** The material card's 1 pt gradient rim is `CardRim` (`Design/RowCardSurface.swift`): a `RowCardStyle.rim` gradient view masked by a solid `strokeBorder`, not hit-testable and hidden from accessibility. `shape.strokeBorder(gradient)` draws the same pixels but CoreGraphics shades it on the CPU over the card's whole area every time a card draws, which made fast flicks hitch on every card page (Songs 702 and Song Details 1310 main-thread samples per 30 s pass, both now 0). Any surface sharing the rim (the tinted purple CTA) uses `CardRim` too. Accessibility evidence: hosted macOS `RowCardSurfaceTests.rimIsInvisibleToAccessibility`, and on iPhone the Songs row card in `SongsChromeJourneyTests/testRowUnderTheSectionBarFadeKeepsItsAccessibility` (no element inside the row but its own, same label and frame). Rule in [apple architecture § Performance](../platforms/apple/architecture.md#performance).
- **R10. A section that is one standalone control has no card (#599).** Where the web draws a section header and a single control outside any `FrostedCard` (Settings `resetRow`: header and red Reset All Settings button; the Licenses and Privacy Policy links), the native apps put the header and control straight on the page, never in a card. Cards hold groups of rows (R6, R8). Android: `ui/settings/SettingsScreen.kt` `ResetSection` (the shared section `Header`, then a full-width M3 `Button` in `colorScheme.error`, 40 dp drawn with its 48 dp touch target) and `NavigationRow` for Licenses and Privacy Policy, in one column and in the list/detail list pane. Apple: `Features/Settings/SettingsScreen.swift` `reset` (`FestivalSectionHeader` + full-width red button). Windows: `Pages/SettingsPage.xaml` reset `Grid` (header left, red button right). Tests: Android Robolectric `PhoneSettingsLayoutUiTest.resetSitsOnThePageWithoutACard`, `WideSettingsColumnUiTest.resetStaysInTheListWithoutACard`; connected `journeys/ResetSettingsAccessibilityJourneyTest`.
